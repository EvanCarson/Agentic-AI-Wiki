深入解析 · 多智能体系统

监督者/工作者编排：真正能上线的那个模式。

决定一套监督者/工作者系统能否胜过"一个带工具的智能体"的，是两个设置；而在大多数团队伸手去拿的那个库里，两者的默认值都是"全都抄过去"：一次 handoff 会把监督者的完整消息历史往下传给工作者，而 join 可以把每个工作者的完整对话记录往上传回来。两端的隔离正是这个拓扑全部的可靠性论据，所以默认配置买到的是"单个智能体的质量，星形结构的价格"——而你从没读过的那个 flag，会把你可用的扇出宽度挪动一个数量级以上。

STEP 1

控制流是 plan → dispatch → join → aggregate，而其中两条箭头就是全部的设计。

监督者攥着任务与计划；工作者只攥着自己那一片。循环是这样的：监督者把任务分解成子任务，把每一个带着受限指令派发给一个全新的工作者，在结果上汇合（等最慢的那个），再聚合成一个答案——如果结果太薄，可能重新规划。工作者彼此看不见；一切协调都由监督者居中完成。这种居中既是这个模式的长处（策略只有一处），也是它的天花板（过载只有一处）。

# supervisor/worker: scoped dispatch, central aggregate
def supervise(task, budget):
    plan = supervisor.decompose(task)
    jobs = [dispatch(w, sub, budget / len(plan)) for sub in plan]
    done = join(jobs)                         # waits on the slowest
    return supervisor.aggregate(task, done)   # may re-plan if thin

写成四个动词，它读起来像个调度问题；而正是这个取景框让团队去争论拓扑——星形、层级还是蜂群——而真正决定结果的那些决定根本不在 plan 或 join 里。它们在 dispatch 往工作者的上下文窗口里放了什么，以及 join 往监督者的窗口里放回了什么。这两份载荷都是配置，都有默认值，而默认值很大方。

STEP 2

派发载荷：可靠性论据，以及把它抵消掉的那个默认值。

支持这个拓扑的论据从来不是"智能体越多越聪明"。而是：一个只看到自己子任务与为之所需的最小上下文的工作者，更难被带偏、每次调用更便宜、提示注入面也更小。把完整任务与同僚的输出漏进每一个工作者，你就把它们重新耦合了起来，把每一个上下文窗口都灌胖了，还把你拆分正是为了避免的群体思维请了回来。

现在来读实现。langchain-ai/langgraph-supervisor-py——1,650 颗星、MIT，来自与这个模式关联最深的那个框架、专为它而写的库——用 create_handoff_tool 构造 handoff，而默认情况下，一次 handoff 会把监督者的完整消息历史传给接手的智能体，再加上一条确认 handoff 的工具消息。add_handoff_messages 同样默认为 True，于是 handoff 的调用本身也在状态里累积；README 指出把它设为 False 会得到更简洁的历史。

所以，最常被使用的那个监督者实现，开箱行为恰恰就是这个模式存在所要避免的那件事。这不是 bug——对一次handoff来说，传历史是正确的默认值：一个智能体接管了一段对话，它需要知道之前说了什么。只是对一个工作者来说这是错误的默认值，而这个库同时被用于两者。

该仓库已归档，最后一次提交在 2026 年 7 月 15 日，而它的 README 如今写着："对大多数用例，我们现在建议直接通过工具来实现 supervisor 模式，而不是使用这个库"，并指向 LangChain 的多智能体与 supervisor 指南。请仔细读这句话——它没有修掉那个默认值，它把这个决定搬进了你自己的代码里。手写派发意味着载荷由你显式选择，这更好；也意味着当你忘了选的时候，没有任何人替你选。

请把工作者边界当成一道硬接口：受限指令进去，结构化结果出来，别的都不许过。不管你用哪个框架，检验方式都是经验性的——把一个工作者收到的第一条消息打印出来，数一数它的 token。如果里面有监督者的规划推演，那你付的是扇出的钱、拿到的是广播。子智能体究竟继承了什么梳理了藏在这一条背后的另外四个继承决定，包括没有任何框架暴露出来的那一个：权限。

STEP 3

汇合载荷决定你的扇出宽度，而这个数你算得出来。

在这个拓扑里，稀缺资源是监督者的上下文窗口；而真正起约束作用的不是规划——写八个子任务很便宜——而是在一个窗口里调和八份结果。这让你可用的扇出成了一道有四个输入的算术题，其中三个由你掌握。

# the reconcilable width, in tokens
usable     = 120_000   # effective context, not the advertised number
prefix     = 8_000     # system prompt + tool definitions
plan       = 2_000     # the structured plan the supervisor wrote

per_report = 1_500     # compact structured artefact per worker
width      = (usable - prefix - plan) // per_report   # = 73

per_report = 40_000    # output_mode="full_history": whole transcript
width      = (usable - prefix - plan) // per_report   # = 2

这个 flag 是真实存在的：create_supervisor 接受 output_mode="full_history"，它会把每个工作者智能体的完整消息历史都包含进来；或者 output_mode="last_message"，只包含该工作者的最终回复。一个关键字参数，就把你扇出的上下文上限挪动了一个数量级以上，而它并不是那种会出现在架构评审里的设置。

关于这道算术，有两条该说实话的提醒。那个 73 不是建议——成本与延迟远在上下文之前就会咬人，扇出税说明延迟收益在大约三条分支之后就平掉了，而前缀项还在往上爬。另外 usable 这一项干的是安静的活：该填进去的是"你的模型仍能可靠调和的那个上下文长度"，而不是规格表上那个；有效上下文与标称上下文说明前者常常只是后者的一小部分。这道计算的意义不在答案；而在于答案会因为一个你花三十秒就能读到的默认值而相差 36 倍。

STEP 4

分解的质量，给下游的一切定了天花板。

糟糕的切分救不回来，再好的工作者也不行。监督者必须产出这样的子任务：彼此独立（没有哪一条分支需要另一条的中间状态——否则你造的是一条伪装成星形的流水线）、界定清楚（每条指令都具体到让一个上下文被隔离的工作者无从漂移）、带预算（每条都带着 token 与步数上限，这样扇出就不会失控）。生产中最常见的那一个缺陷，是含糊的子任务："研究一下市场"会派生出一个没有停止条件的工作者，把预算烧光，返回一团浆糊。

切分的形状还决定了扇出到底有没有帮助，而这件事是被量过的、不是被辩出来的。Google 对多智能体接线方式的对照研究发现，同样的拓扑在可并行的金融推理上最多提升 80.8%，在顺序规划上却下降 39–70%——同一张图、相反的符号，完全由任务是否可分解来选择。让读取扇出，把耦合的写入留在同一个智能体里。多智能体拓扑里有完整结果。

让监督者把子任务作为一个结构化的计划对象发出来——id、指令、成功判据、预算——而不是作为它随后还要再解析一遍的自由散文。成功判据正是让一个工作者知道自己做完了、而不是一路循环到预算耗尽的那样东西；它也是唯一能让一个工作者的报告压缩到足以被汇合的东西：回答一个具体问题的工作者返回一个答案，而被交了一个题目的工作者返回一份对话记录。

STEP 5

聚合是一次综合，而监督者是唯一一个没有自己成功判据的部件。

把结果汇合起来，是多智能体价值被实现或被丢掉的地方。幼稚的聚合器把工作者的输出粘在一起返回——于是工作者之间的每一处矛盾、每一个没被填上的缺口都浮到了表面，把真正的活推给了读者。一个真正的聚合器会调和：发现互相冲突的工作者主张、解决或标记它们、用一次重新派发去填缺口，并产出一份连贯的成品。关键在于，聚合器不应该还要把工作者做过的事重新推一遍。如果它必须这么做，那分解就失败了，而你为扇出付的钱什么也没买到。

把"聚合"实现成字符串拼接，是这个模式最常见的无声失效。它能过演示——在玩具输入上工作者很少冲突——然后在生产里第一次遇到两个工作者意见相左时失败：系统自信地把两个互相矛盾的答案缝在一起交了出来。

还有第二重不对称值得点名。每一个工作者都从监督者那里拿到一条成功判据；而监督者自己的停止条件是"聚合结果看起来完整了"，由写出那份计划的同一个模型实例来判定。这是一次由"最有动机宣布胜利"的那个部件做出的自我评估，也就是生成者—验证者落差出现在了树顶而不是树底。请让这次运行的完成判定交给"自称干完了的那个智能体"之外的东西，并用一本共享预算账代替会在扇出时相乘的按智能体上限——给一次多智能体运行收尾里有值得区分的那三个出口。

STEP 6

什么时候星形是错的形状。

上行空间没人否认：Anthropic 公开的多智能体研究系统报告里，多智能体配置在一项内部研究评测上比单个 Claude Opus 4 智能体高出 90.2%，而 token 用量约为一次对话交互的 15 倍，并且仅 token 用量一项就解释了约 80% 的性能方差。这两半都是这个模式的论据——它有效，而它靠花钱有效。

该跳过它的情形：子任务并不独立（你造了一条流水线却叫它星形）；不把工作者的推理重做一遍就没法完成聚合（拆分什么都没买到）；任务的价值撑不起一个 15 倍的乘数；或者扇面宽到没有任何单个监督者上下文能调和得过来，而层级结构多出来的那一跳摘要本身又会把答案弄坏。监督者/工作者恰好在这两件事成立时划算：分解干净、聚合是真正的综合——而这两件事都是那两份载荷的属性，不是那张图的属性。

在你去调提示词之前，先从正在运行的系统里读出四个数值：每个工作者收到的第一条消息有多少 token、每个工作者的报告有多少 token、这些报告在监督者汇合时的输入里占多大比例，以及你的模型实际能可靠调和的长度。把派发载荷设成"只有受限指令"，把汇合载荷设成"只有最终答案"，然后按那道算术给出的宽度给扇面封顶——或者按三，取其小者。这四个数能解决的架构争论，比任何拓扑图都多，而且它们一个都不需要换框架。

相关：何时（与何时不）采用多智能体是更前置的那个问题，子智能体模式对比讲 handoff 与"智能体即工具"的分野，并行写入与那次安静的合并讲工作者从"读"变成"写"时会发生什么。
