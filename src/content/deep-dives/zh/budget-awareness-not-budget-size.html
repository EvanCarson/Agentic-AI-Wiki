N13
深入解析 · 推理与测试时计算

把上限调高不是那根杠杆——告诉智能体还剩多少才是。

智能体做不出难题时，人人伸手去拧的那两个旋钮——想得更久、多调几次工具——都会停在一个平台上，而且是为同一个原因停住的：模型对自己剩下多少额度没有任何表征，于是多出来的预算全花在把它本来就在做的事情摊得更宽上。实测到的增益来自分配，不来自额度。2025 年的一项研究把一个预算计数器放进上下文，在工具调用次数大致不变的前提下，把解决率从 36.8% 抬到了 55.4%。

STEP 1

两个旋钮都会失手，而且失手的方式押着同一个韵。

扩展测试时计算有两种形态。你可以在单个轮次内多花 token——更长的思维链、更高的 effort 档位、更多次采样；也可以多花轮次，让智能体调用工具、读取结果、再试一次。前者是推理时扩展讨论的主题；后者才是大多数人说"给智能体更大的步数预算"时的意思。

这两者各有一篇已发表的失败记录。在"思考"这一侧，《Inverse Scaling in Test-Time Compute》（Gema 等，arXiv 2507.14417，2025 年 7 月；2025 年 12 月被 TMLR 接收）构造出了一批任务，在它们上面准确率随推理轨迹变长而下降。在受控设置里，Claude Opus 4 的准确率随轨迹变长而下滑，而 DeepSeek R1 未见显著变化；失败模式还因模型而异：Claude 系列推理得越久、就越容易被无关信息带跑，而 OpenAI o 系列顶得住干扰项、却过拟合到题目的表述框架上。在约束满足类任务上，受测的每一个模型都随推理延长而退化。该论文自己的结论是，天真地扩展测试时计算并不是答案，而真正敞着的问题是模型如何分配推理。我们在测试时计算中的逆向扩展里按它自身的脉络处理过这个结果。

在"行动"这一侧，《Budget-Aware Tool Use Enables Effective Agent Scaling》（arXiv 2511.17006）用另一种单位报告了同一种形状：单纯把工具调用预算加大并不能提升表现，因为智能体缺乏预算意识，很快就撞上一个性能天花板。两篇论文、两个旋钮、一个诊断——模型不知道自己处在预算的哪个位置，于是更大的预算买到的是更多同样的行为，而不是不同的行为。

如果你的修法是把某个上限调高，那你并没有定位到一个失败——你定位到的是"你不知道它是哪一种失败"。预算加大之后出现的平台期本身就有诊断价值：它在说，边际的那个 token 或那一步，被花在智能体早已做完的那部分任务上了。

STEP 2

增益在分配上，而且它可被测量。

那项预算感知结果里有用的部分，不是"更大的预算令人失望"，而是它的反事实对照。论文里的 Budget Tracker 让智能体对自己的剩余预算有一个实时的感觉——上下文里的一个数字，随运行推进而递减；而在其中一组对照里，仅这一项补充就把解决率抬高了 18.6 个百分点，在预算为 50 的条件下从 36.8% 升到 55.4%，而所用的工具调用次数相近。

最后那半句请读两遍。工具调用次数几乎没动。模型、工具、脚手架、额度，一样都没变。变的是智能体能分辨"第 50 步里的第 5 步"与"第 50 步里的第 45 步"，并在两种处境下行为不同。广度优先的探索在早期是对的、在晚期是毁灭性的；收敛到当前最优假设在晚期是对的、在早期则是过早下注。一个没有钟表的智能体没法挑，于是它挑定一种策略，然后在所有地方都跑那一种。

# what a budget-unaware agent sees on every step
[tool results]
# ...and that is all. Step 3 and step 47 are indistinguishable.

# what a budget-aware agent sees
[tool results]
budget: 12 of 50 tool calls remain; ~18k of 200k context tokens used
# the model can now trade breadth for commitment, and does.

这件事实现起来很便宜，却几乎没人实现。那个计数器住在你的 harness 里而不是模型里：你本来就在递减它以执行上限，所以唯一要做的事，是把它在每个轮次渲染进上下文，并写上一两行说明"余量很低意味着什么"。这段内容该放在轮次的哪个位置，见塑形工具结果。

STEP 3

模型看不见的预算，它会在结尾处花错。

截断是这个问题最锋利的版本。当一个硬上限触发时——最大步数、最大思考 token、来自超时与截止期预算的一个 deadline——智能体并不会把飞机落下来。它是在探索中途被切断的，而当时存在的任何局部状态都会被当成答案返回。那套取代了数值 token 旋钮的 effort 档位 API 修好了这件事里容易的那一半（模型现在会按查询自行定量），而把智能体那一半原封不动留着：没有任何厂商的 effort 档位知道你的 harness 还会再允许多少次工具调用。

修法是预留，而不只是设上限。把预算显式切开，并把两半都告诉模型：

  • 一份探索预算，允许智能体自由花在检索、读取和死胡同上。
  • 一份落地储备——通常是 10%–20%——它只为"用已经找到的东西产出一个答案"而存在，并且从第一个轮次起就告知智能体。

有了声明过的储备，那次转折就成了模型做出的一个决定，而不是它承受的一次中断。没有它，你那条失败长尾会被"用轨迹里错的那一半拼出来的答案"主宰。这与推理时扩展里那个计算最优策略的论证是同一个结构，只是从 token 搬到了步数上。

STEP 4

预算没对齐，正是拓扑结论复现不出来的原因。

一旦你接受"预算才是那个变量"，一整类已发表的对比就变得读不下去了。两种智能体设计在拓扑、提示词、工具集以及可花的额度上都不同，而头条却被归因给拓扑。把花费固定住，这个归因常常就塌了：2026 年的一项研究报告称，在推理 token 被固定的条件下，单智能体系统在多跳推理任务上一贯追平或胜过多智能体系统（arXiv 2604.02460）。

这个发现并不是说多智能体没用——何时以及为何走向多智能体列出了它真能创造价值的那些情形。它说的是，扇出最被引用的那项优势，有一部分是记账造成的假象，因为"一个主管带五个工人"悄悄就是五倍大的预算。扇出税把这笔账算了出来。

同样的纪律适用于安全与工具使用方面的声明。一项面向攻防安全智能体的成本感知评测（arXiv 2607.15263）主张，预算扩展类声明只有在对比是成对的时候才可信——同一个模型、同一个基准、同一条跑完的轨迹；而它在自己的实验里报告：追加的预算与工具用量并未买到有意义的防守端提升，并且高工具用量不是分数的代理指标。请把工具调用次数当成一项成本，永远不要当成努力程度的证据。预算对齐的评测是方法，而这就是它为何不是可选项的原因。

STEP 5

该给什么上仪表。

只有当预算进了轨迹，预算意识才是可审计的。三个信号，都很便宜，而且在多数智能体遥测里都缺席（它们该住在哪里，见智能体可观测性）：

  • 每一步的剩余预算，作为一个数字，与那一步并列记录。没有它，你分不清"在第 8 步解决了任务的运行"与"恰好在第 8 步停住的运行"。
  • 终止原因，拆成完成、放弃与被截断三种。把它们并成"失败"一项，会盖掉唯一那个能告诉你是否该调高上限的区分。被截断的占比在上升，是"更多预算确实就是答案"的那唯一一种情形。
  • 最后那一成预算的边际价值。取一个样本，分别用 70% 与 100% 的预算重跑，对比解决率。如果最后那 30% 买不到一个百分点，你的上限已经越过拐点了，这笔花费就是纯成本——杠杆于是移到环内成本控制上。

被报告出来的 token 计数本身就是个陷阱：思考 token 会计费，却常常不原样返回，所以从可见输出量出来的"预算"会低估实际花费。推理 token 记账讲这笔算术，智能体成本控制讲如何执行。

请按这个顺序做。第一，在每个轮次把剩余预算作为一个普通数字渲染进上下文——这是 harness 里几行代码的事，也是本文中唯一一项有已发表的两位数效应量的改动。第二，声明一份 10%–20% 的落地储备，并在系统提示词里写明，让截断成为一个决定而不是一次中断。第三，把终止原因拆成完成、放弃、被截断三类，并且只在被截断的占比上升时才调高上限。在把前三件做完之前，不要去调高任何上限：预算加大后的平台期不是一个资源问题，它是一个穿着资源问题外衣的分配问题。
