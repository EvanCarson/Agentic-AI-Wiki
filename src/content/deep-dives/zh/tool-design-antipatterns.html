K6
深入解析 · 工具与能力设计

反模式是相对某一套调用约定被定义出来的，而约定变了。

四个经典的工具设计缺陷仍然真实、仍然在消耗你的链路，但它们如今是这场审计里便宜的那一半——每一个都是花一分钟读一份 schema、再施以一个机械修法的事。贵的那一半，是 2024 年没人写下来的那个：目录本身。Anthropic 自己的工程博文报告，内部的工具定义在优化之前吃掉了 134K token，而一个按需搜索的工具大约只要 500。先审那四个，然后审这张清单的形状。

STEP 1

大杂烩工具：一次调用带一个模式开关，其实是五个工具。

它的特征：一个工具带着 action 或 operation 参数，而 schema 里大多数字段都只在特定条件下相关——一半只在 action="create" 时适用，一半只在 action="delete" 时适用。模型得先挑工具，再挑模式，再搞清楚这个模式需要哪些字段；而它会挑错模式、或填错那组字段。修法是 K2 那次拆分：一个动作一个工具，每个 schema 都收紧。链路上的迹象是同一个工具被以自相矛盾的参数调用。

# Anti-pattern: kitchen-sink, conditional fields
manage_user(action: str, id=None, name=None,
            email=None, role=None, hard=None)

# Fix: one tool per action, each schema tight
create_user(name, email, role)
delete_user(id, hard=False)

请注意这个修法的代价，因为它正是通往 STEP 5 的铰链：把一个大杂烩工具拆成五个收紧的工具，会让每次调用更可靠，同时让目录长出五条。在五个工具的规模上这是对的交易，在五百个的规模上就相当可疑——这恰恰是为什么这场审计的两半必须一起跑，而不是按先后顺序跑。

STEP 2

字符串化参数：本该是结构的地方放了一个自由字符串。

它的特征：一个被标为 string 的参数，实际上期待的是一个日期、一个枚举值、一段 JSON，或者一门要模型从零构造出来的查询 DSL。自由字符串正是模型塞进「看起来说得通的垃圾」的地方——把「下周二」塞进一个想要 2026-11-26 的字段，把「高优先级」塞进一个想要 P1 的字段。修法是 K3：把字符串换成一个枚举、一个带 format 的类型化字段，或者一个结构化对象，让坏值根本无法被表达出来。

把你的工具定义 grep 一遍，找出那些被标为纯 string、却没有 enum、format 或 pattern 的参数。每一个都是模型眼下可以自由幻觉的地方；它们中的大多数本来想要一个受约束的类型，只是没人去收紧它。

2026 年对这个修法有一条告诫：约束只有在厂商真的会执行你用的那个关键字时才有约束力。JSON Schema 的支持是一个按厂商而异的子集，不是一项标准——如果你的 pattern 在入口处被静默丢掉，你拿到的是一份文档，不是一份合同。在把某个字段记作「已修好」之前，先查一下你自家厂商接受的那个子集；并且无论如何都保留服务端校验，因为一份模型会在 97% 的时候遵守的 schema，仍然有 3% 的时候不遵守。

STEP 3

静默失败：什么都没发生，工具却返回成功。

它的特征：一个工具捕获自己的异常，然后返回一个空列表、一个默认对象，或者一个光秃秃的 200，而不是一个错误。这是最危险的一个反模式，因为它不产生任何局部症状——智能体在一个假前提上自信地往下走，而失败会在许多步之后，以任何链路都无法定位到病因的行为形式浮现出来。修法是 K4：大声失败，把部分成功报告为部分成功，永远不要让「什么都没发生」看起来像「它成功了」。

「出错就返回空，这样智能体不会崩」是智能体工程里最昂贵的一项便利。智能体不会崩——它会在一个假前提上自信地再做错十步，而事后复盘找不到它是在哪里跑偏的，因为那个工具把证据擦掉了。

把代价算出来，拿一支每天跑 10,000 次工具调用、底层错误率 2% 的编队：200 次失败。作为错误返回，智能体会重试或上报，损害被重试策略框住。被吞掉，这 200 次就变成 200 次各自在假前提上平均再往下走大约六步的运行——1,200 步错的、却看起来没问题的工作，以及一个按构造就看不见源头调用的分诊队列。这个反模式不会抬高你的错误率；它删掉的是你测量错误率的能力，而那更糟，因为仪表盘上的数字还变好看了。

一个不能可见地失败的工具，是不能被调试的工具。如果复核者没法从一个工具的返回值里看出世界是否被改变了，那这个返回值就不是一次观测——它是一个智能体会当成事实的猜测。

STEP 4

抽象泄漏，以及这四个为什么很少单独出现。

它的特征：一个工具的参数或输出是被后端而不是被任务塑形的——要模型自己串下去的分页游标、内部状态码、裸的连接键、一个逼模型自己写 SQL 的 db_query。模型被迫去推理你的存储层，而不是用户的目标，而且它推得很糟。修法是 K1：围绕任务设计工具，把机械部分藏起来。

然后去查另外三个，因为一个大杂烩工具通常同时也是字符串化的（那个 action 参数），而且往往是泄漏的（它照搬了一个 CRUD 端点）；它还倾向于静默失败，因为宽泛的工具有宽泛而含混的错误处理。修好粒度常常会同时溶解掉类型与抽象问题，因为一个按任务塑形的工具没有地方可泄漏、也没有东西可切模式。这种相关性正是「审计从粒度开始、而不从 schema 开始」的实务理由。

不过在 2026 年有一处泄漏值得重新审视，那就是分页游标。把一个游标穿过模型的上下文一向难看；而它现在还是错的那一层，因为一个结果多达数千行的工具，应当交给模型一个它可以在其上操作的引用，而不是一页要它一轮一轮拼回去的东西。反模式没有变。可用的修法变了。

STEP 5

第五个反模式，也是如今占主导的那个：把目录整份先发出去。

你工具清单里的每一条定义，在模型开始干任何活之前、每一轮都要付钱，无论这个任务有没有可能用到它。Anthropic 关于高级工具使用的工程博文给自家的情形标了一个数：工具定义在优化之前吃掉了 134K token，而只加载一个搜索工具、其余按需发现，大约是 500 token。两个数字就是这整个反模式。这不是关于超大型部署的假想；这是任何接了几台 MCP 服务器的智能体的默认状态，因为每台服务器都会把自己的整个表面贡献进来，不管你想不想要。

它的特征很容易看出来，而没人去看：数一数你的工具定义占了多少 token，再除以一个典型任务真正需要的 token。如果这个比例差过大约 1:10，那你跑的就不是一个带工具的智能体，而是一份挂了个智能体的目录。另有两个迹象与它同行——模型挑中正确工具的某个貌似相近的邻居，以及「删掉工具」比「改好工具」更能提升准确率。

修法全都是「不要把清单给模型看」的某种形式：

  • 用搜索，而不是枚举。加载一个发现工具，按需取回定义。这就是那次 134K 到 500 的动作，也是三者中最便宜的一个，因为它是一处配置改动，不是一次重新设计。
  • 把目录收到任务的作用域上。如果这次运行是「给这张工单分诊」，那么在这期间部署类工具根本不需要存在。逐任务定作用域恰好也是你本来就想要的那项安全控制，这种巧合少见到值得一提。
  • 让模型对着工具写代码，而不是一次一个地调用它们——见 STEP 6，因为这一条会连前四个反模式一起改变。

还要顶住那个看起来最便宜的修法：一路删工具，直到模型应付得过来。那是用能力去换选择准确率，这是一笔真实的交易，但是一个糟糕的默认选项，因为它在唯一要紧的那个方向上不可逆——你删掉的那个工具，正是下个季度的任务需要的那个。

STEP 6

拿你实际在用的那套约定去对每个反模式做核对——并在你自己的链路上验证修法。

STEP 1–STEP 4 里的四个特征，全都假设了同一套约定：模型每一轮吐出一个 JSON 对象，点名一个工具，从一张扁平清单里挑。这个假设已经不安全了。《The Bitter Lesson of Tool Calling》（arXiv 2608.06370）在 BFCL v4 的一个 309 条子集上评测了 14 个模型，报告称程序化工具调用——由模型写代码来调用你的工具——在其中 11 个上追平或超过了原生 JSON 工具调用，其中 GPT-5.6 系列相对 JSON 基线提升了 10.6%。

在那套约定下重读这四个，其中两个的权重会变。分页游标与内部连接键对代码的泄漏程度远低于对散文的泄漏，因为代码会循环、会过滤；而另一方面，一个带模式开关的大杂烩工具会更糟，因为模型现在得在缺少「直接工具调用所施加的那种按次 schema 压力」的情况下把模式挑对。这里的教训不是「程序化调用修好了工具设计」，而是：一个反模式是一项关于「某个特定读者会如何误读某个特定接口」的断言，所以换掉读者，就会给这张清单重新排序。先决定你的哪些工具是直接调用、哪些是代码调用，然后拿各自的约定分别去审这两组。

最后，当心你用什么来证明修法生效了。一项关于工具调用评测的效力审计（arXiv 2607.02577）请专家复核了取自 BFCL v4、τ²-Bench、LiveMCPBench 与 MCP-Atlas 的 496 个任务，发现 92 处评分器与人类的分歧——18.5% 的错配率。接近每五个任务就有一个，其评分方式会被一位人类专家质疑；而 BFCL v3 与 v4 本身也不是可相互比较的两套。所以排行榜上的差值，不构成「你那次 schema 改动生效了」的证据。你自己的录制链路、改动前后各回放一遍，才是证据——而你要清点的，正是上面点名的那些失败特征。

这一切都不会把那四个变成法律。一个一次性的内部工具，被一个固定外壳用一次，它可以是字符串化的、泄漏的，而这并不要紧。一个真正通用的逃生口——一个沙箱化的 run_code——是一次有意为之、被围住的抽象泄漏，它的威力正是重点所在。反模式在于，把这些东西不经意地发在一个面向模型、可被自由选择、且带副作用的工具上。

按这个顺序跑审计，因为它从最便宜的开始、而且每一步都会缩小下一步：（1）数一数你的工具定义占了多少 token，和一个典型任务的工作集相比——如果比例差过 1:10，先修目录，一份 schema 都别碰；（2）grep 出那些没有 enum、format 或 pattern 的纯 string 参数；（3）grep 你的工具实现里那些会返回「成功形状」值的 except 块；（4）列出每一个带 action 式模式开关的工具。然后在回放的链路上验证，而不是在一个基准上验证。
