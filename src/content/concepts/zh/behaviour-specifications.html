行为规范。

一次删掉某条规则的修订，不可能让你的测试套件变红——而这正是多数团队将来发现「模型的公开行为准则变了」的方式。如今有两家前沿实验室公开发布了带日期、可做 diff 的规范文档，写明它们的模型被训练去做什么：Anthropic 的宪章以 CC0 发布，OpenAI 的 Model Spec 挂在带版本号的网址上并附带变更日志。请钉住一个版本、在每次发布时做 diff，并且读那些被删掉的条目，而不是新增的条目。

STEP 1

行为规范写的是模型「应该」做什么，这和「它做了什么」是两份不同的文档。

有三类厂商文档经常被混为一谈，而其中只有一类是规范。

  • 行为规范写明模型被训练与评测所对照的规则：它听谁的指令、它拒答什么、当你的指令与用户的指令冲突时如何裁决。它是规范性的，针对的是一个模型家族，而不是某个检查点。
  • 系统卡是关于某一个检查点、在某一套能力激发方法下的实证安全测试记录。它是描述性的，而且会过期。
  • API 文档描述的是接口。它对「冲突之下的行为」什么也没说，而智能体一整天恰恰都泡在冲突里。

这个区分之所以要紧，是因为只有规范回答了智能体开发者真正的那个问题：当我的系统提示词让模型做某件事、而它的训练让它别做时，哪一边赢，以及这个答案稳不稳。Anthropic 在 2026 年 1 月全文发布了《Claude 的宪章》，以 CC0 1.0 发布——即公共领域贡献声明，所以你可以把它引进自己的政策文件里，不必纠结授权问题。OpenAI 的 Model Spec 自 2024 年起公开发布，现在挂在带日期的网址上（当前修订版是 model-spec.openai.com/2026-10-29.html），并在 openai/model_spec 仓库里附带变更日志。Google 发布安全框架与模型卡，但截至 2026 年 11 月，没有对应的规范性行为文档。

规范是实验室的一份意图声明，不是对你被服务到的那组权重的保证。它告诉你的是后训练瞄准的是什么。请把「规范与实际行为之间的落差」当成你自己的测量问题——验收评测就是干这个的。

STEP 2

真正约束你的是那个优先级顺序，而「有帮助」并不排第一。

两份已公开的规范都是「一小组价值 + 一条明确的冲突裁决规则」的结构，而那条规则，对任何在写系统提示词的人来说，都是整份文档里最承重的一句。

Anthropic 的宪章为 Claude 模型列出四项属性——广义安全、广义伦理、遵循 Anthropic 的指导方针、真诚的有帮助——并写明当它们冲突时，Claude 应当通常按此顺序排优先级。请把这个排序当作一项产品约束来读。「对运营方与用户有帮助」是四项里的第四项。一条在你的产品里拿指导方针去换更好结果的指令，是按公开设计输掉的，不是因为出了岔子；而且任何提示词工程都不该能把它扳回来。「通常」这个限定词也在做实功：它声明的是「此顺序是一个在判断之下的默认值，而不是一条字典序硬规则」，这也正是为什么两条看起来差不多的拒答，裁决结果可以不一样。

OpenAI 在 2026 年 10 月的修订把 Model Spec 围绕五项价值重新组织——忠于人的意图、最小化伤害、诚实与透明、人的自主性，以及体贴——并写明这五项价值用来引导两组核心张力：个体利益与集体利益之间，以及即时指令与长期目标之间。第二组张力正是智能体那一组。一个长时运行的智能体，按构造就是一台「被给了即时指令、又被期待去服务某个长期目标」的机器，而规范告诉你的是：这里的裁决是模型做出的一次判断，不是你能设的一个开关。

这两者底下坐着的是指令层级——平台高于运营方、运营方高于用户、用户高于工具输出。层级告诉你的是「谁的指令赢」；价值排序告诉你的是「当赢家的指令与模型的训练冲突时会发生什么」。开发者通常为前者做了准备，然后被后者打个正着。

STEP 3

它是一个带版本的依赖，而危险的那种修改是删除。

一份有带日期网址、也有变更日志的规范，是一个你钉得住的依赖；而这同时意味着，它是一个不随你的发布而变、却自己会变的依赖。OpenAI 在 2026 年至少发了两次修订——版本 2026.08.18，然后是 10 月 29 日那次重写，后者甚至把文档的主语从「助手」改成了「GPT」。二手报道还称那次重写砍掉了此前大量细节性的文风指引；我们没能把这条追溯到变更日志本身，所以请把改主语当成已核实的那个例子，而把「砍掉」当成你该自己在 diff 里核的事。

现在看每一类修改是怎么传到你这儿的：

# how a spec revision shows up in your test suite
edit type              example                         your evals
"added rule"           new teen-interaction guidance   may go red   ← you notice
"tightened rule"       narrower refusal boundary       may go red   ← you notice
"clarified wording"    same behaviour, new prose       stays green  ← harmless
"removed rule"         style guidance deleted          stays green  ← you never notice
# a deleted constraint widens the set of outputs that pass. nothing fails.

这种不对称就是整件事的要害。你的评测套件是一组针对你观察到的行为写下的断言，而那些行为是被你动笔时生效的那版规范塑造出来的。一次收紧会打断某条断言，并把你呼起来。一次删除不会：原本被要求的行为变成了仅仅被允许，旧的输出照样通过，而一个你从来没想到要禁的新输出也照样通过。如果你的产品靠的是实验室已经不再规定的某条文风规则——某种模糊措辞的惯例、你的解析器正盯着的某种拒答措辞、或是默认去提澄清问题——那你现在依赖的就是一个没人承诺的行为，而且它漂移时你的测试不会告诉你。

同一套逻辑贯穿拒答：一次放宽某条边界的规范修订，在一整套「假定该边界成立」的套件里，一条测试也打断不了。它只在生产环境的拒答率上可见——这正是为什么把拒答作为时间序列来监控，能抓到离线评测在结构上抓不到的规范漂移。

STEP 4

钉住它、diff 它，并为它没说的一切保留你自己的验收评测。

三个便宜的做法，按能换到多少价值排序：

  • 把规范版本记在模型版本旁边。你的部署元数据里已经写着某个模型快照了；再加上你验证时所对照的那个规范修订版。行为变了的时候，第一个问题是「这两者里哪一个动了」，而少了第二个字段，这个问题要查一周。这就是把钉住与校验那套纪律，从摘要值搬到一份文档上。
  • 每逢修订就 diff，并且先读删除的部分。对 OpenAI 来说这是对着一个公开仓库跑一次 git diff；对 Anthropic 那份 CC0 文档来说，这是一个你被明确许可留一份副本的文件。给它二十分钟预算。你要找的是被移除的约束、被放松的边界，以及冲突裁决措辞的变化——不是新增的行文。
  • 把你依赖的行为编码下来，而不是把别人承诺你的行为编码下来。凡是你的解析器、你的界面或你的护栏对模型输出所作的假定，都该落成一条由你自己持有的断言，无论当前的规范是否要求它。规范是「有理由预期某个行为」；而当这份预期不再成立时，唯一会注意到的东西是评测。这和「在系统卡旁边另备一套钉死版本的验收套件」是同一个论证。

规范真正给你的那样东西，换别的途径很难拿到：它可被引用。当审核者、客户或审计师问起智能体为什么拒答，「厂商公开发布的规范，2026-10-29 修订版，最小化伤害那一节」是一个带网址的答案。而诉诸「我们观察到的行为」不是。这使得规范既是你自己政策文件最好的输入，也是测试最差的替代品。

这一周就把这件事做一次：在你记录「部署了哪个模型」的地方加一个 spec_revision 字段，填上你最后读过的那份带日期的规范，再设一个日程提醒去 diff 它。全部价值都在后半截——这个字段把「动的是模型还是规则？」从一次调查变成一次查表，而 diff 是一条被删掉的约束唯一现形的地方。然后写下三条「少了它你的产品就会坏」的行为，并让每一条都变成一句由你自己持有的断言。
