服务端会话状态。

当厂商替你攥着会话、而你发过去的是一个指针而不是一份对话记录时，三件你以为属于自己的事会变成 API 调用：重放一个步骤、删除一位用户的数据、换一个模型。OpenAI 的 Responses API 默认就存——store"省略时默认为 true"，而被存下的响应数据会保留"至少 30 天"——所以这个托管权的决定，是你靠"不做决定"做出来的。请把服务端状态当成一份你租来的缓存，权威副本自己留着。

STEP 1

两种 API 形态，只有一种会忘。

一个无状态的对话 API 完全不记得你的会话。每一次请求都带着完整的消息列表；厂商处理完就丢掉。Anthropic 的 Messages API 就是这样工作的，这也是为什么一个智能体循环会在每一步重发整段对话记录，以及为什么智能体成本大致随步数的平方增长。

有状态的 API 把默认值反转了。在 OpenAI 的 Responses API 里，你传一个 previous_response_id，文档写的是"模型上一次响应的唯一 ID……用它来构造多轮会话"；或者你挂上一个 conversation，它的条目"会被前置到本次响应请求的 input_items 之前"，而本次请求的输入与输出"会在这次响应完成之后自动加入"该会话。两者互斥。你发出去的是一个句柄；模型看到的内容，是在线路另一端被组装出来的。

  • 存储是默认值，不是功能。即便你从不使用指针，store 仍然默认为 true，所以一次普通的单发调用也会保留响应，除非你显式退出。
  • 留存期是下限，不是上限。"至少 30 天"是文档里的承诺，并受数据留存例外条款约束——这与你自己数据库给出的承诺，是形状不同的两种承诺。
  • 无状态变成了一个你去选的模式。SDK 关于 include 的文档描述了推理条目被"无状态地（比如当 store 参数被设为 false 时……）"使用的情形，这句话本身就告诉你哪条路是例外。
STEP 2

你真正拿到了什么，老实说。

常见的卖点是请求更小，这是真的，但没听起来那么大——模型读到的 token 厂商照样计费，不管那些 token 是你发过去的还是它自己取过来的。其中有两项收益比带宽值钱得多。

  • 不透明的产物能活过这一轮。如今每一家主流推理 API 返回的内部推理都是你既读不了、也重建不了的形态，而把它带过工具调用，决定了模型是接着那条链往下走还是从头再来。服务端状态是这件事免费发生的那条路；无状态那条路意味着你得自己逐字节原样处理那团加密数据，推理摘要与加密轨迹把这件事讲得很细。
  • 前缀在缓存所在的那一侧被组装。你再也不会因为重排了自己的消息数组而不小心毁掉一条缓存条目，因为那个数组不是你在搭。相比手工做的提示词缓存，这是实打实的可靠性收益，也是支持有状态形态的唯一一条与"方便"无关的论据。

注意清单上没有什么：这不是记忆。一个会话句柄是厂商替你攥着的一份对话记录，不是一个会学习、会检索、会有意遗忘的存储。智能体记忆是你要建的东西；这个只是你不再需要搬的东西。

STEP 3

四项能力悄悄变成了别人的 API。

代价不是抽象意义上的隐私。代价是：四件你本来要在自己数据库上做的具体操作，如今需要向一个不由你运行的系统发请求。

  • 重放。你的 trace 记下的是你发出去的那个指针，不是模型拿到的那些消息。一次重放测试需要被解析后的输入，而"把这个句柄解析成模型当时看到的那个确切数组"这项能力，你只拥有厂商愿意提供的那么多——而且只在留存窗口还没过去的那段时间里拥有。一条无法被重新物化的轨迹是一条日志，不是一份评测夹具。
  • 删除。一次删除请求如今多了一个在作用域内的系统，而它有自己的时钟。对智能体记忆执行删除在你拥有每一份副本时就已经很难；当其中一份按一个不是你设的时间表过期时，就更难了。
  • 可迁移性。一个 response ID 是厂商形状的。把一段进行中的会话迁到另一家厂商，意味着从你自己的记录里重建消息数组——这意味着你本来就必须留着自己的记录，于是"我们不需要存对话记录"这笔省钱从来就不存在。参见提示词可移植性与模型下线与迁移。
  • 受监管的那条路。处在零数据留存安排下的组织根本不能用存储那条路，于是你最在意合规的那位客户，会把无状态形态强加给你。如果你只建了有状态那一套，那位客户就不是一个配置开关、而是一次重写——这正是零数据留存描述的那个陷阱。

失效模式很具体，也很常见：一个团队因为 previous_response_id 能让代码更短而采用了它，于是不再把完整对话记录写进自己的存储，然后在最糟的时刻发现这个缺口——在对一次运行做事故复盘时，而那些 response ID 如今已经比留存窗口更老了。那个指针上周还能解析。现在既没有东西可读，也没有东西可重跑。

STEP 4

缓存可以租，记录要自己拥有。

解法不是拒绝服务端状态，而是把"哪一份副本是权威的"说清楚，并且让答案在每一种情形下都是你自己那一份。

  • 记下被解析后的输入，而不是句柄。不管你的可观测性抓了什么，它必须在没有厂商的情况下也能重跑。如果你发的是指针，就把你认为它所代表的那个消息数组一并写在 span 旁边。
  • 按环境显式决定 store。它默认为 true。在你想要留存的地方把它写进代码，在你不想要的地方把它设为 false，这样"这段会话在不在别人的磁盘上"这个问题的答案，就在你的仓库里，而不在一个默认值里。
  • 让无状态那条路保持被跑过。至少让你产品的一个档位——或者一条 CI 流水线——在没有服务端状态的情况下跑。一条从未跑过的路，不是你拥有的路。
  • 只在句柄独有的事情上用句柄。把加密推理带过工具调用是强论据。省带宽是弱论据，而它正是那个悄悄挪走你托管权的论据。

把这一行规则写进你的客户端包装层：厂商那一份是缓存，你那一份是记录。具体做法是，每一个智能体步骤在返回之前，都把被解析后的完整输入与输出持久化到你控制的存储里，并且每一次调用都显式设置 store。你什么都没放弃——你照样可以为了只有它才能提供的推理连续性去用 previous_response_id——而重放、删除，以及某个星期二换掉厂商的能力，都还在你手上。
