Operation · Safety, Alignment & Agentic Security

Rotation is an enumeration problem: you cannot rotate a secret you cannot locate.

Every write-up of every 2026 agent credential incident ends with the same instruction — "rotate your keys" — and in an agent stack that instruction is incomplete in a way that leaves the attacker holding a working credential. A secret an agent has handled exists in eight or nine places, several of which have no delete API and at least one of which belongs to a company you have no relationship with. Issuing a new string does nothing to any of them. The act that actually closes an exposure is revoking the authority the credential carried, because revocation is the only step whose completion you can verify from your own systems.

STEP 1

Why the one-line remediation stopped being one line.

For a conventional service, "rotate the key" is sound advice because the premise behind it holds: the secret lived in a small, enumerable set of places you control — a secrets manager, a few pods' environment, maybe a CI variable — and replacing it everywhere makes the old value worthless. The advice is really a claim about completeness, and the completeness came from the architecture rather than from the rotation.

An agent voids the premise in three ways at once. It puts secrets into text, which is then copied by systems whose job is to copy text. It reads from and writes to stores that were never classified as secret-bearing, because nobody expected a credential to arrive there. And it operates across a trust boundary you cannot see past: the request leaves your process and what happens next is somebody else's logging policy.

Three disclosures in November 2026 each demonstrated a different half of the problem. Dragos found that secret URLs planted in prompts were being fetched two or three days later by systems belonging to the inference provider — so a copy existed, persisted, and was read on a schedule you do not control (the canary came back two days later). Together AI's notice describes automated secret scanning detecting a committed credential and the commit being reverted — after an unauthorised party had already taken it. And the compromised agent-framework PyPI releases included a stealer that could request fresh tokens from a cloud metadata endpoint, which means rotating the secrets it took would not have removed its access (the package ran without being imported).

Read together, they say: the copy that matters is not yours, the clock is shorter than your detection loop, and the string is not always the thing that grants access.

STEP 2

The copy list. Write it before the incident, because you will not write it during one.

Assume a credential has passed through an agent — as a tool argument, in a system prompt, inside a tool error, in a retrieved document, or typed by a user into a chat. These are the places it now is. The column that matters is not sensitivity, it is whether you have a delete path.

# Where a secret an agent handled actually lives
#                                   delete path?   who holds it
secrets manager / env                 yes            you
the transcript / conversation store   yes            you
the trace + tool-result store         yes, slow      you
agent long-term memory                partly         you
the eval set it got sampled into      partly         you
a fine-tune or distillation corpus    no             you
the provider's prompt cache           no             vendor
the provider's abuse-monitoring copy  no             vendor
a reseller / router's logs            no             vendor's vendor
# and, if it ever leaked:
the attacker's copy                   no             attacker

Four rows deserve a sentence each, because they are the ones teams discover late.

  • The trace store is the big one. It holds prompts, tool arguments and tool results, it is searched by more people than any vault, and it is usually retained longer than the provider's window. Redaction at write time is the control — redacting PII from agent traces — and redaction applied when somebody opens a trace is not redaction.
  • Memory has no schedule. Anything the agent persisted about a session is retention you did not declare, and deleting a fact is much harder than deleting a log line. Memory scopes and tenancy is where the reach is decided; migrating off a memory provider is what happens when the store is not yours.
  • A training corpus is permanent in the way that matters. Once a secret is in a fine-tuning set you cannot remove it from a model that was trained on it. This is the one row where the only possible remedy is on the authority side.
  • The vendor rows are where the November evidence landed. Prompt caches, abuse-monitoring windows and reseller logs are three separate copies with three separate schedules, and a zero-data-retention arrangement touches at most one of them — see zero data retention and abuse monitoring.
STEP 3

Revoke the authority, not the string.

Here is the distinction the whole page turns on. Rotating means issuing a new secret and updating your systems to use it. Revoking means telling the issuer that the old one no longer authorises anything. They are frequently confused because in a simple system the second follows automatically from the first — and in an agent system it very often does not.

Three cases where rotation alone leaves access intact:

  • Custody is split from revocation. Remove a provider API key from the tool that stored it and you have changed your own configuration, not the provider's view of the key. The key is still valid; only its owner's dashboard can end it. This exact gap was the finding in deleting the key did not revoke it, and bring-your-own-key integrations are structurally prone to it.
  • The credential mints other credentials. A role, a managed identity or a metadata endpoint does not hold a secret so much as a right to obtain one. Rotating what an attacker captured is irrelevant if they can ask for a new token; the only closure is removing the role binding or the trust relationship — the delivery channels are ranked in credential delivery to the sandbox.
  • The session outlives the secret. OAuth refresh tokens, long-lived sessions and cached authorisations commonly survive a password or key change by design. Ask the issuer, per integration, what a rotation actually invalidates, and write the answer down — because the answer differs per vendor and nobody will tell you unprompted.

So the correct order of operations in an incident is revoke, then rotate, then restore service. Teams reliably do it in the opposite order, because rotating is the step that gets production working again and revoking is the step that breaks whatever you forgot was using the credential. That discomfort is the control working.

Before you revoke, know what else was using the credential. A shared, long-lived key is exactly the kind you cannot revoke in an incident without taking down four unrelated systems — which is how exposures stay open for weeks. The pre-work is access reviews for agent credentials: one credential per consumer, so revocation is survivable.

STEP 4

The clock, and why detect-and-rotate is no longer a primary control.

Put the two measured intervals side by side. Microsoft Threat Intelligence reported in November 2026 watching an agent go from searching a public code host for secrets to exfiltrating data from a cloud vault in five minutes. Against that, the median enterprise detect-to-revoke path runs through an alert, a triage queue, a human deciding whether the finding is real, and a change that touches production.

# The race, in the units that actually get measured
attacker: find -> use                 ~5 min       # automated, no queue
you: scan -> alert                    1-10 min
you: alert -> triaged by a human      30 min - hours
you: decision -> revoked in prod      30 min - days

# You do not win this by shortening your side.
# You win it by making the credential worth less on arrival:
lifetime  = 15 min not 90 days
scope     = one tool, one tenant, one task
read_only(unless the task provably needs a write)

The conclusion generalises past this one statistic: detection is for knowing, and the controls that bound damage are the ones that were in place before the leak. Short-lived, narrowly scoped credentials turn a stolen secret into a stolen fifteen minutes of one capability — that is credential lifetime and scoped credentials for agents, and the reason they belong in this page rather than only in a prevention page is that they are what makes rotation tractable at all. You cannot enumerate copies of a credential that expired before you finished looking.

One addition that pays for itself in an incident: a canary credential alongside the real one, registered with the provider and alerting on first use. It converts "we think a key may have been in those prompts" into a timestamped event with a source address, and it is the only instrument that reports from the attacker's side of the boundary — honeytokens for agent systems has the placement rules.

STEP 5

The runbook, and the drill that keeps it honest.

Write this as a procedure with owners and expected durations, and run it once a quarter against a credential you deliberately expose. The drill is the point: an untested revocation path is a document, not a control.

  • Identify the authority, not the artefact. What could this credential do, to which systems, for which tenants? If you cannot answer in two minutes, your blast-radius work is the actual finding — blast radius.
  • Revoke at the issuer, and confirm from a second place. A call that returns success is not confirmation; a subsequent authenticated request that fails is. Capture that evidence, because it is the only part of the response that is verifiable.
  • Kill the sessions and the derived tokens. Refresh tokens, active sessions, cached authorisations and any role the credential could assume. Per integration, per issuer.
  • Hunt for use, do not assume none. Pull provider-side audit logs for the exposure window and look for your own credential being used from somewhere you are not. Detecting agent compromise is the signal side; note that if you bought zero data retention, the provider's independent record may not exist, which is a trade you made earlier.
  • Purge the copies you can, and record the ones you cannot. Transcripts, traces, memory, eval sets. The unreachable rows — caches, vendor logs, any training corpus — go into the incident record as residual exposure with the reason. This list is what justifies the authority-side remedy to an auditor.
  • Close the write path. If the secret reached a prompt, a tool argument or a tool error, fix that before restoring service, or you are scheduling the next incident. The broker pattern is in secrets management for agents, and egress control for agents bounds where a captured secret can be sent next.

The test that tells you the runbook is real: search your trace store, tool-result store and prompt cache for the first six characters of a live secret. If it is there, you have an exposure now, not a hypothetical one, and your first rotation is already overdue.

STEP 6

When NOT to rotate.

If you cannot enumerate the copies, do not let a rotation stand in for a revocation — a new string plus an un-revoked old one is a worse state than before, because the incident now reads as closed. Revoke first, verify from a second system, and record every copy you could not reach as residual exposure rather than resolving the ticket on the strength of the rotation.
