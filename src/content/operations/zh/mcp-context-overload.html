当 MCP 结果撑爆上下文时。

MCP 规范对工具目录做了分页，却对一次工具调用结果的大小只字未提。所以当某个服务器塞给你的智能体 100,000 个 token 时，会发生什么，取决于你跑的是哪个宿主、以及你留在默认值上的那些设置。那些服务器不归你管，而且会在你脚下悄悄变化。因此上限、溢出行为和驱逐策略都必须由你自己来定：按工具逐个设置，用你最大的客户而不是演示租户来测试，并在生产中持续度量。而且现有的每一种补救手段（落盘、代码执行、清除、压缩）都只是把成本挪到了别处，而不是把它消除。

STEP 1

在任何东西加工结果之前先度量它，按 token 也按字符。

大多数团队第一次见识到自己的结果大小，都是通过某个症状（一个 429、一轮卡住的对话、一个「忘了」任务的智能体），而到那时，日志里只剩下宿主截断或落盘之后的样子。在原始 MCP 响应到达、任何宿主或中间件碰它之前的那个位置埋点，每次调用记一行：

  • 服务器、工具，以及决定大小的那些参数：页大小、字段选择、日期范围。
  • 字符数和估算 token 数，两个都要。各个宿主用的单位并不一致。Claude Code 会把超过 50,000 字符的文本结果存到文件里，不管它的 token 设置写的是多少。claude-code issue #97622 的报告者测得：一个 50,000 字符的结果，拉丁字母文本约为 34k token，希腊文约为 48k token。一个按英文调好的阈值，对其他所有人都会在不同的位置触发。
  • 宿主对它做了什么：原样传递、截断、存成文件，还是报错。

然后按 p99 大小给工具排序，而不是按均值：过载是一个长尾问题，而长尾会随着账户一起长大。GitHub 的服务器为一份 30 个 pull request 的列表返回了 508KB（完整记录见那一页是按记录数计算的）。Figma 自己的客户端故障排查页面引用了一个 get_design_context 响应：351,378 个 token，而上限是 25,000 个 token。参考实现 Memory 服务器的 read_graph，据 issue #3953 报告，在使用六周之后会返回 50k–80k+ token。工具从未改变；是存储长大了。

这就是为什么测试数据比阈值更重要。一个只有 11 个项目的测试租户能通过每一项检查；而那个有 1,400 个项目的客户，才是半夜把你叫醒的人。在设定任何一个数字之前，先用你被允许复制的最大账户构建测试数据，或者按那个规模合成一份。

STEP 2

按工具设置上限，并弄清楚哪些旋钮归你。

单一的全局上限总会对某个人是错的：高到足以容纳日志搜索，就会让列表类工具淹没窗口；低到能管住列表类工具，日志搜索就没法用了。各种按工具的机制，在归谁所有、按什么单位计数上都各不相同。截至 2026 年 10 月：

  • Claude Code。它在 10,000 token 时发出警告，这是一个固定阈值。默认上限是 25,000 token，可以用 MAX_MCP_OUTPUT_TOKENS 调高。这个变量只管那些没有声明自身限制的工具。一个服务器可以在它的 tools/list 条目里声明 _meta["anthropic/maxResultSizeChars"]，把某个工具的阈值调高，最高到 500,000 字符的硬上限。那是服务器作者的旋钮，不是你的，所以要审计哪些已连接的工具声明了它：它们已经退出了你以为自己设下的那个上限。
  • Codex。tool_output_token_limit 设定存入历史的工具输出的预算。按工具的 mcp_servers.<id>.tools.<tool>.output_token_limit（于 2026-08-28 在 PR #41421 中合并）会针对单个 MCP 工具覆盖它，之后再加上标准的 20% 序列化余量。当插件策略与用户策略重叠时，最严格的限制胜出。默认值来自模型目录，且没有文档说明，所以要显式设置。
  • Gemini CLI。tools.truncateToolOutputThreshold 默认在 40,000 字符处截断；设为 0 或负值则关闭截断。
  • claude.ai 和 Claude Desktop。连接器的工具结果上限约为 150,000 字符。它不可配置，文档也没说超过之后会发生什么。
  • Cursor。没有文档记载的上限。较长的 MCP 输出会写入一个智能体可以读取的文件。
  • VS Code Copilot。没有文档记载的上限。过长的结果会被截断，并附上一个读取其余部分的提示，而这个提示照做会失败（案例见 Step 3）。
  • OpenAI Agents SDK。没有文档记载的上限。结果原样转发，resource 块会变成其 JSON 序列化后的文本。

速率限制也是一种上限，而且比窗口更早咬人：针对 GitHub 服务器的第一份溢出报告，是后续调用时的一个 429，而不是上下文溢出（具体数字见那一页是按记录数计算的）。像循环中的成本控制里那样的按任务 token 预算，应当把流入的工具结果也算进去，而不只是流出的模型输出。在服务器白名单里，把每个上限和它实测的 p99 放在一起；旁边没有度量数据的上限，只是一个猜测。

STEP 3

选定溢出行为，然后测试往返流程，而不是顺利路径。

当一个结果越过上限时，宿主会做三件事之一，而每一种都有自己的失败方式。

  • 落盘。Claude Code 会把超出上限的、成功的非图像结果存到会话的 tool-results 目录，并用一条写明路径的消息替换它。Cursor 会把较长的 MCP 输出写入一个智能体可以读取的文件。什么都没丢，但模型现在得通过一个指针来工作。
  • 截断。Gemini CLI 在它的字符阈值处切断。Claude Code 会截断错误结果：一个超过约 11,000 字符的 isError 文本只保留前 5,000 和后 5,000 个字符。对堆栈跟踪来说没问题；如果原因恰好在中间，就会误导人。
  • 报错。调用失败，智能体必须用更窄的参数重试。如果错误文本写明了补救方法，这是最诚实的选项。

落盘的失败案例早已公开。把它们当作你的测试套件：

  • 智能体能只读其中一部分吗？在 notion-mcp-server issue #206 中，一个 41,207 token 的页面以挤在大约五行里的 JSON 返回。这个落盘文件无法部分读取，因为读取工具按行偏移分页，而直接读取则以「exceeds maximum allowed tokens (25000)」失败。只有当文件是按行组织、可 grep 的，落盘才有用。
  • 它能编辑并写回吗？在 atlassian-mcp-server issue #106 中，一个 50–70KB 的 Confluence 页面正文被存到了磁盘上，于是模型从未看到它，也就无法重建它来调用更新工具。它本得内联输出约 15K token。任何「读取—修改—写回」的工作流，在读取落盘的那一刻就断了。
  • 补救提示真的管用吗？在 vscode issue #311068 中，VS Code 截断了一个 50KB–999KB 的文件结果，并让智能体去读一个 vscode-chat-response-resource:// URI 获取其余部分。读取以「outside the workspace」失败，智能体就此卡住。
  • 宿主告诉模型的话对吗？2.1.105 版本加入了按格式区分的处理方法（JSON 用 jq）。2.1.287 版本修复了 Claude 被告知用 Read 的 offset 和 limit 来分页读取大型 JSON 结果的问题。溢出提示文本是你系统的一部分，而宿主一升级它就会变。

为每个重型工具写一个测试：越过上限，然后让智能体去做下一件真实的事情：找到一个字段、修改一个值、把对象写回去。通过的标准是任务完成，而不是调用返回。服务端的那一半在 MCP 中的大型结果与分页；GitHub 的服务器是怎么学会这一课的，在那一页是按记录数计算的。

STEP 4

把大批量数据挡在循环之外，并为它的去处标好价格。

最便宜的 token 是从未进入主上下文的那个。有两种安排方式，各有各的账单。

  • 用子智能体做大型读取。Anthropic 的上下文工程指南描述了这样的子智能体：它们「可能会大量探索，使用数万甚至更多 token」，然后只返回「一份浓缩、提炼过的摘要」。成本转移到了子智能体的 token 和摘要的保真度上：编排者无从知道摘要漏掉了什么。记录子智能体的原始输入；当答案出错时，证据就在那里。
  • 程序化工具调用，或代码执行。模型写一个脚本，脚本在沙箱中调用工具并在那里过滤数据，只有结果才会到达模型。Anthropic 对这个问题举的例子是：一份两小时会议的转录从一个工具复制到另一个工具，会两次穿过模型，大约多出 50,000 token。被广泛引用的 150,000 → 2,000 token（98.7%）是 Anthropic 的示意性演算示例，不是基准测试。它在复杂研究任务上对程序化工具调用的实测数字，是平均从 43,588 降到 27,297 token，即 −37%。按实测数字做规划。

代码执行是真正的架构变更，不是一个设置项。在 Claude API 上，它需要代码执行工具（code_execution_20260120 或更新版本），Claude Haiku 4.5 不可用，也不符合零数据保留的条件。文档警告 allowed_callers 不是安全边界。Anthropic 列出的成本是沙箱、资源限制和监控，即「直接工具调用所没有的运维开销和安全考量」。你还会失去廉价的审计轨迹：原先的对话记录是一串工具调用，现在它是一个程序，其效果需要你去重建。代码即行动讲的是行动日志必须记录什么，才能让这一切保持可审查。

别让一个定义侧的数字为一个结果侧的项目背书。工具搜索的「超过 85%」削减、Cloudflare 的 1.17 million → 约 1,000 token，以及 Cursor 的 −46.9%，度量的都是预先加载的工具定义。它们对一次返回 100K token 的单次调用毫无作用。一份把两者混在一起的汇报材料，会让钱花在错误的修复上。

STEP 5

驱逐陈旧内容，并清楚驱逐做不到什么。

在一个长会话里，窗口的大部分是智能体早已据此行动过的旧工具结果，而清除它们，用 Anthropic 的话说，是「最安全、最轻量的压缩形式之一」。截至 2026 年 10 月：

  • Anthropic 上下文编辑（beta，header context-management-2025-06-27）。clear_tool_uses_20250919 策略会在输入越过触发点（默认 100,000 输入 token）后，从最旧的工具结果开始移除。默认保留最近 3 次工具使用。clear_at_least 会在无法至少释放这么多 token 时完全跳过这次编辑，这样微不足道的节省就不会让你付出一次重写提示的代价。exclude_tools 列出那些结果绝不能被清除的工具。
  • Anthropic 压缩（beta，header compact-2026-01-12，编辑类型 compact_20260112）。在触发点对历史做摘要：默认 150,000 输入 token，最低 50,000。
  • OpenAI Responses：context_management: [{ type: "compaction", compact_threshold: … }] 会在渲染后的 token 数越过你的阈值时运行服务端压缩。结果是一个加密条目，「不透明，且并非供人类解读」。另外，truncation: "auto" 会在输入超出窗口时，从对话开头丢弃条目。这是粗暴的从最旧开始丢弃；默认值 disabled 则会让请求以 400 失败。
# POST /v1/messages, with the header  anthropic-beta: context-management-2025-06-27
{
  "model": "<your-model>",
  "max_tokens": 4096,
  "tools": [ /* ...MCP-backed tools... */ ],
  "messages": [ /* ... */ ],
  "context_management": {
    "edits": [{
      "type": "clear_tool_uses_20250919",
      "trigger":        { "type": "input_tokens", "value": 60000 },
      "keep":           { "type": "tool_uses",    "value": 3 },
      "clear_at_least": { "type": "input_tokens", "value": 10000 },
      "exclude_tools":  ["getConfluencePage"]   // the read a later write depends on
    }]
  }
}

触发点故意设在默认值之下：根据你 Step 1 的数据来设定它，设在质量开始下降的地方，而不是窗口到头的地方。exclude_tools 运用的是 Step 3 的往返教训：绝不清除一个待执行写入所依赖的读取。

有两条限制让这一切保持诚实。第一，驱逐并不是白来的质量。arXiv 2606.00408 发现，在 4B–284B 的骨干模型上，屏蔽陈旧观察带来的收益呈倒 U 形，而当屏蔽移除了模型本会用到的证据时，它可能会起反作用。根据你的评测而不是 token 曲线来调 keep 和触发点。第二，无论清除还是压缩，对单个超大结果都无能为力。两者作用的都是历史，而一个 100K token 的负载在它到达的那一轮就已造成了破坏。那是 Step 2 的职责。摘要化的取舍在上下文压缩中。

STEP 6

对漂移报警，并对溢出路径做回归测试。

你的上限是对着今天的服务器设定的，而服务器会变。GitHub 的服务器展示了这种模式（那一页是按记录数计算的）：一个又一个端点家族撞上这个问题，然后得到了一个 minimal_* 响应类型。这样一个版本发布会让某个工具的 p99 一夜之间改变，而厂商加上的下一个字段又会把它推回去。这就是第三方工具漂移，而结果大小是它最容易度量的症状之一。

  • 对按工具的 p99 大小漂移报警，在服务器报告版本时以服务器版本为键。任一方向的阶跃都意味着契约变了；缩小可能意味着你依赖的字段现在需要显式开启。
  • 以比率的形式对溢出事件报警：每个工具每千次调用中的落盘、截断和大小错误次数。某个工具的比率上升，意味着某个客户的数据越过了你的测试数据从未达到的阈值。
  • 断言截断标记能到达模型。构建良好的服务器会在带内说明这一点，把截断标志紧挨着补救说明放置（这一模式见MCP 中的大型结果与分页的 Step 4）。中间件、宿主升级或你自己的摘要化都可能把它剥掉。测试模型的输入中是否仍然包含它；一个不知道自己数据不完整的智能体，会自信地报出一个错误的计数。
  • 锁定版本，并在宿主升级时重新测试。溢出行为是宿主代码，会在版本之间变化。每次宿主版本升级都运行 Step 3 的往返测试，就像你对待模型变更那样。
  • 保留一个金丝雀式的大账户评测。按计划对大账户测试数据运行一小组固定的真实任务，并按结果打分。这是唯一一个能同时抓住数据增长、服务器漂移和宿主变化的测试。

如果这些都还没有到位，这周先做两件事。第一，为每次工具调用记录原始结果大小和宿主采取的动作，这样你才有一个 p99 可以据理力争。第二，挑出你最重的三个工具，用大账户测试数据把每一个都推过它的上限，再让智能体完成一个真实任务的下一步。在那里失败的地方，才是你真正的上限和真正的溢出行为，不管设置文件里写的是什么。
