运维 · 安全、对齐与智能体安全

轮换是一个枚举问题：定位不到的秘密，你轮换不了。

2026 年每一起智能体凭据事件的复盘，结尾都是同一句指示——「轮换你的 key」——而在智能体技术栈里，这句指示的不完整之处，恰恰会让攻击者手里仍握着一把能用的凭据。一个被智能体处理过的秘密，存在于八九个地方，其中好几个没有删除接口，至少有一个属于一家你跟它毫无关系的公司。发一个新字符串，对它们一个都不起作用。真正能关闭一次泄露的动作，是吊销这把凭据所携带的权限——因为吊销是唯一一个你能从自己的系统里核实其完成状态的步骤。

STEP 1

那条一行搞定的补救，为什么不再是一行。

对一个常规服务来说，「轮换 key」是个靠得住的建议，因为它背后的前提成立：秘密只住在一小批你掌控、且可枚举的地方——一个密钥管理器、几个 pod 的环境变量、也许一个 CI 变量——把它到处替换掉，旧值就一文不值了。这条建议真正断言的是完整性，而完整性来自架构，不是来自轮换这个动作。

智能体同时从三个方向废掉了这个前提。它把秘密放进文本，而文本随后会被那些「以复制文本为职责」的系统复制。它读写那些从没被归类为「承载秘密」的存储，因为没人料到凭据会跑到那儿去。而它工作在一条你看不穿的信任边界上：请求离开你的进程之后发生的事，归别人的日志策略管。

2026 年 11 月的三起披露各自演示了这个问题的一半。Dragos 发现，埋进提示里的秘密 URL 在两三天后被属于推理提供方的系统抓取了——也就是说存在一份副本，它持久留存，并按你无法掌控的节奏被读取（两天之后，那只金丝雀回来了）。Together AI 的通告描述了自动化密钥扫描检测到一次凭据提交、该提交随后被回滚——而在那之前，未授权方已经把它拿走了。而被投毒的 agent-framework PyPI 版本里带的那个窃取器，能够向云元数据端点索取新的令牌，这意味着轮换它偷走的那些秘密，并不会移除它的访问权（那个包没被 import，却照样跑了）。

合在一起读，它们在说：要紧的那份副本不是你的，时钟比你的检测回路更短，而且那个字符串并不总是授予访问权的东西。

STEP 2

副本清单。请在事故之前写好，因为事故当中你写不出来。

假定一把凭据已经经过了某个智能体——作为工具参数、写在系统提示里、夹在一条工具报错里、藏在一篇被检索到的文档里，或者由用户敲进聊天框。下面这些就是它现在所在的地方。要紧的那一栏不是敏感度，而是「你有没有删除路径」。

# Where a secret an agent handled actually lives
#                                   delete path?   who holds it
secrets manager / env                 yes            you
the transcript / conversation store   yes            you
the trace + tool-result store         yes, slow      you
agent long-term memory                partly         you
the eval set it got sampled into      partly         you
a fine-tune or distillation corpus    no             you
the provider's prompt cache           no             vendor
the provider's abuse-monitoring copy  no             vendor
a reseller / router's logs            no             vendor's vendor
# and, if it ever leaked:
the attacker's copy                   no             attacker

有四行各值得一句话，因为它们是团队最晚才发现的那几行。

  • trace 存储是大头。它装着提示、工具参数和工具结果，被查看它的人数多于任何一个保险库，而且留存时间通常比提供方的窗口更长。控制手段是写入时脱敏——在智能体 trace 中脱敏 PII——而在有人打开一条 trace 时才做的脱敏，不叫脱敏。
  • 记忆没有时间表。智能体就某次会话所持久化下来的任何东西，都是你没有申报过的留存，而删掉一条事实远比删掉一行日志难。记忆作用域与多租户是决定它触及范围的地方；迁出一家记忆服务商则是当这个存储不属于你时会发生的事。
  • 训练语料在要紧的那个意义上是永久的。秘密一旦进了微调数据集，你就无法把它从一个已经基于此训练过的模型里拿掉。这是唯一一行里，唯一可能的补救只在权限那一侧。
  • 厂商那几行，正是 11 月那批证据落下的地方。提示缓存、滥用监控窗口与转售方日志是三份独立的副本，各有各的时间表，而一份零数据留存安排最多只碰到其中一份——见零数据留存与滥用监控。
STEP 3

吊销权限，而不是换掉字符串。

整页的要点都压在这个区分上。轮换是指签发一个新秘密，并把你的系统都改成用它。吊销是指告诉签发方：旧的那个不再授予任何东西。两者常被混为一谈，因为在一个简单系统里，第二件事会自动跟着第一件发生——而在智能体系统里，它经常不会。

有三种情形下，仅做轮换会把访问权原封不动地留着：

  • 保管与吊销被拆开了。把一把模型提供方的 API key 从存着它的那个工具里删掉，你改变的是你自己的配置，而不是提供方对这把 key 的看法。这把 key 依然有效；只有它所属方的控制台能终结它。这正是把 key 删掉并没有吊销它里的发现，而自带 key 的集成方式在结构上就易犯这个错。
  • 这把凭据能铸造别的凭据。一个角色、一个托管身份或一个元数据端点，与其说持有一个秘密，不如说持有「获取一个秘密的权利」。如果攻击者还能去要一个新令牌，那轮换他们截获的那份就没有意义；唯一的收口是移除那个角色绑定或信任关系——各条投递通道的排序见把凭据送进沙箱。
  • 会话活得比秘密更久。OAuth 刷新令牌、长寿会话与缓存下来的授权，按设计通常能在一次密码或 key 变更之后继续存活。请按每个集成逐一去问签发方：一次轮换到底作废了什么，并把答案写下来——因为答案逐厂商不同，而且没人会主动告诉你。

所以事故中正确的操作顺序是：先吊销，再轮换，然后恢复服务。团队几乎总是按相反的顺序来做，因为轮换是那个能让生产重新跑起来的步骤，而吊销是那个会弄坏「你早忘了还有谁在用这把凭据」的步骤。那份不适感，正是控制手段在起作用。

吊销之前，先知道还有谁在用这把凭据。一把共享的、长寿的 key，恰恰是那种你在事故中无法吊销、除非愿意顺手搞掉四个毫不相干的系统的凭据——而这就是泄露为何能开着好几周。前置功课是智能体凭据的访问复核：一个使用方一把凭据，这样吊销才扛得住。

STEP 4

那座时钟，以及「检测再轮换」为何不再是首要控制手段。

把两段被测量过的时间并排放。微软威胁情报在 2026 年 11 月报告说，他们看到一个智能体从在公共代码托管站搜索密钥，到把数据从云保险库里外带出去，只用了五分钟。与之相对，企业里那条「检测到吊销」的中位路径要穿过一次告警、一个分诊队列、一个人判断这条发现是否真实，以及一次会动到生产的变更。

# The race, in the units that actually get measured
attacker: find -> use                 ~5 min       # automated, no queue
you: scan -> alert                    1-10 min
you: alert -> triaged by a human      30 min - hours
you: decision -> revoked in prod      30 min - days

# You do not win this by shortening your side.
# You win it by making the credential worth less on arrival:
lifetime  = 15 min not 90 days
scope     = one tool, one tenant, one task
read_only(unless the task provably needs a write)

这个结论能推广到这一个数字之外：检测是为了知道，而真正限住损害的控制手段，是泄露发生之前就已经就位的那些。短寿、窄作用域的凭据，会把一把被偷的秘密变成「一项能力被偷走的十五分钟」——这就是凭据寿命与给智能体的受限凭据；而它们之所以该出现在本页、而不是只出现在某个预防页里，是因为正是它们让轮换这件事变得可行。一把在你还没找完副本就已过期的凭据，你根本不需要去枚举它的副本。

还有一项在事故中能把自己赚回来的补充：在真凭据旁边放一把金丝雀凭据，在提供方那里注册好，一经使用就告警。它能把「我们觉得那批提示里可能有一把 key」变成一个带时间戳、带源地址的事件，而且它是唯一一个从边界的攻击者那一侧回报情况的仪器——摆放规则见面向智能体系统的蜜标。

STEP 5

那份运行手册，以及让它保持诚实的那场演练。

把它写成一套带责任人和预期时长的流程，并且每季度拿一把你故意暴露出去的凭据跑一遍。演练才是重点：一条未经测试的吊销路径是一份文档，不是一个控制手段。

  • 识别权限，而不是识别那件物品。这把凭据能做什么、对哪些系统、为哪些租户？如果你两分钟内答不上来，那你的爆炸半径功课才是真正的发现——爆炸半径。
  • 在签发方处吊销，并从第二个地方确认。一次返回成功的调用不是确认；一次随后发出的、失败了的已认证请求才是。把这份证据留存下来，因为它是整个响应里唯一可核实的部分。
  • 杀掉会话和派生令牌。刷新令牌、活跃会话、缓存的授权，以及这把凭据能够假扮的任何角色。逐集成、逐签发方地做。
  • 去猎查使用痕迹，不要假定没有。把暴露窗口内提供方侧的审计日志拉出来，看看你自己的凭据有没有从你不在的地方被用过。检测智能体被攻陷是信号那一侧；注意：如果你买了零数据留存，提供方那份独立记录可能并不存在——而这是你早先做下的一项取舍。
  • 能清的副本就清掉，清不掉的就记录下来。会话记录、trace、记忆、评测集。那些触及不到的行——缓存、厂商日志、任何训练语料——要作为「残余暴露」连同原因一起写进事故记录。正是这份清单，才能向审计方解释为什么补救要落在权限一侧。
  • 把写入路径关掉。如果这个秘密曾进到一条提示、一个工具参数或一条工具报错里，就在恢复服务之前先修掉它，否则你是在给下一次事故排期。代理模式见给智能体做密钥管理，而智能体的出网管控则限定了一把被截获的秘密接下来能被送到哪里。

判断这份手册是不是真的那个测试：在你的 trace 存储、工具结果存储和提示缓存里，搜一把在用秘密的前六个字符。如果它在那儿，你现在就有一次暴露，而不是一个假设——而且你的第一次轮换早就该做了。

STEP 6

什么时候不要轮换。

如果你枚举不出那些副本，就不要让一次轮换冒充一次吊销——一个新字符串加上一个未被吊销的旧字符串，比之前的状态更糟，因为这次事故现在读起来像是已经关闭了。先吊销，从第二个系统核实，并把每一份你触及不到的副本作为残余暴露记录下来，而不是凭着「已经轮换过了」就把工单关掉。
