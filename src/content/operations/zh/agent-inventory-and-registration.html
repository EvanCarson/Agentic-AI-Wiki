C9
运维 · 治理与合规

智能体清单：其他每一项控制都默认你已经有的那项控制。

你搭起来的每一套治理机制，都在暗中假定一份智能体名单已经存在——一个瞄不准的熔断开关不是熔断开关，而一条只作用于你知道的那些智能体的策略，是一条例外清单无上界的策略。错误在于把清单当文档来做，那产出的是一张在调研截止前就已过期的电子表格。解法是结构性的：让"登记"成为智能体取得凭据的必经之路，于是清单成了部署的副产品而非某人维护的东西；再把它与轨迹对账，让"声明的"与"观测到的"之间那道缝隙变成你的发现，而不是你的盲区。

STEP 1

枚举是前提条件，不是文书工作。

监管者从他们自己的方向抵达了同一个要求。在欧盟《AI 法案》下，附件三所列高风险系统的提供方，必须在系统投放市场或投入使用之前，把自己与该系统登记进欧盟数据库（第 49 条，使用附件八规定的结构化信息，登记进第 71 条所设的数据库）；而属于公共机构、或代表公共机构行事的部署方，还必须额外登记自己对该系统的使用。ISO/IEC 42001 则把它当作管理体系卫生来处理：一套 AI 管理体系起步于一份清单，涵盖你开发、部署或消费的每一个 AI 系统——包括第三方模型与嵌在供应商工具里的 AI 功能。最后那半句，正是悄悄把名单变成三倍长的那一句。（这是一张地图，不是法律意见；见欧盟《AI 法案》——智能体视角与NIST AI RMF——智能体视角。）

但合规是做这件事最弱的理由，而如果它是你唯一的理由，你会造出错的东西。工程上的理由是：你已经在依赖的每一项运维控制，都把智能体名单当输入，而当名单不完整时它们会静默降级。你的急停开关只停得下它能寻址到的那些运行。策略执行只作用于经过执行点的那些调用路径。事故响应开局第一问是"哪些智能体碰了这个系统"，而这个问题你要么几分钟答出、要么好几天答出。这些控制在某个智能体缺席名单时都不会大声失败——它们只是安静地没覆盖它，而这道覆盖缺口从每项控制内部都看不见。

STEP 2

调研在截止之前就已经过期。

标准做法是给团队负责人发季度问卷，而它失败有一个具体原因：智能体不是由部署创造出来的。一个新智能体的诞生，可能只是有人给现有配置加了一个工具、把客户端指向了一个新的 MCP 服务器、在某个 SaaS 产品里启用了一个集成，或者把一段提示词复制进了一个定时任务。这些在当事人看来都不像"上线一个系统"，而其中大多数也不会经过一个新服务本该经过的评审。

所以调研确实测到了某样真实的东西，只不过不是你问的那样东西。它测到的是：哪些团队负责人回了信、关于他们个人还记得的那些智能体、在某一个瞬间、各自用自己临时发明的"智能体"定义。等汇总完成，配置早已挪动。典型结果是一份同时既不完整（没人上报的影子智能体）又虚胖（两个季度前就关掉、却仍持有着有效凭据的智能体还占着一行）的清单。

一份过期清单危险的那一半不是缺掉的行，而是那些活得比自己的智能体更久的行。一个已退役智能体的条目，若其令牌从未被吊销，读起来像是受治理的、在你的控制证据里被计为已覆盖，而实际上是一份无人认领、却握有工具权限的凭据。退役一个智能体是一次清单操作；如果它不是，你就在积累无主的权限。

STEP 3

把登记放到凭据的必经之路上。

靠尽责心维护的清单，会以尽责心衰减的速度衰减。而因为不登记就跑不起来而被维护的清单，根本不衰减。设计只需一句话：由登记表签发身份。没有登记记录，就没有客户端凭据；没有客户端凭据，就没有网关路由、没有工具作用域、没有模型访问权。登记不再是上线之后要填的表，而变成上线的第一步。

这不是一套新机制，所以它很便宜。你本来就被要求给每个智能体一个独立、受限的身份，而不是共用一把 API 密钥（智能体身份与权限、面向智能体的受限凭据）。把这些凭据从登记表里签发出去，清单就成了工程师本来就想要的那件事的副作用。登记表随之成为让其余一切变得可读的那个连接键：同一个标识符会出现在轨迹里、审计轨迹里（审计轨迹与溯源）、成本归因里，以及熔断开关的命名空间里。

# registry/agents/invoice-triage.yaml — the record that mints the credential
id: agent.finance.invoice-triage        # the join key: traces, ledger, kill switch
owner: "team-finance-ops"                  # a team, never a person who can leave
purpose: "Classify inbound invoices; route exceptions to a human."
autonomy: proposes                      # proposes | acts-with-approval | acts
model:
  platform: anthropic-api               # (platform, model_id) — see model-deprecation
  model_id: claude-opus-4-5-20251101
capabilities:                           # the authority, enumerated
  - tool: erp.invoices.read
    data: [vendor-name, amount, invoice-id]
  - tool: erp.invoices.flag              # write, reversible
personal_data: true                     # drives the DPIA / records question
review:
  human_gate: exceptions-over-10k
  eval_suite: evals/invoice-triage       # no suite ⇒ no production credential

把两个字段设为必填，缺一个就拒绝签发凭据：一个团队作为归属方，以及一个具名的评测套件。归属字段是防止孤儿的东西，而要求它是团队而非个人，是让它在一次组织调整之后仍然有效的东西。要求评测套件，则是你阻止登记表变成一份"谁都没法度量的智能体名单"的方式——它把评估驱动的开发放到了必经之路上，而不是许愿单上。

STEP 4

登记权限，而不是登记智能体。

大多数登记表就是在这里被建粗了一级。"智能体"是个稳定的对象：它有名字、有归属、有用途，而这些很少变。但任何人真正会去问清单的每一个问题，问的都是权限，而权限一直在变。值得做版本的单元是 (智能体, 能力, 数据范围) 这个三元组。

差别在第一次有人给现有智能体加一个写工具时就显现出来。在"智能体"粒度上，那是改动一行——没有新登记、没有评审、没有 diff。在三元组粒度上，那是一次带着新风险姿态的新能力授予，而它本来就是这个：昨天只能读你 ERP 的智能体，今天可以改它了。粗粒度登记的失败模式是：一个智能体的风险分级在出生时定下、此后再无复核，而它的实际权限却在年复一年地累积。

把粒度取对，治理需要的那些查询就从一个研究项目变成对登记表的一行语句：

  • 哪些智能体能在没有人工关卡的情况下做出不可逆动作？这是人在回路的问题，用数据而非记忆来回答。
  • 哪些智能体处理个人数据，其中又有哪些跨了境？直接喂给数据治理与数据驻留的工作。
  • 哪些智能体固定在了退役日期在 45 天之内的模型上？满足审计人员的那同一个登记字段，也驱动模型下线与迁移里的那个 CI 检查。
  • 哪些智能体没有归属团队、没有评测套件，或 90 天没跑过？三个问题，一个答案：吊销凭据。
STEP 5

把声明的与观测到的对账，否则你手上只是一份文档。

只靠申报填出来的登记表，是一份意图的记录。控制是在你把它与现实做差异时才诞生的，而第二个数据源你已经有了：轨迹（智能体可观测性）会在每一步上打上智能体 ID、模型与工具的戳。两个方向，两种不同的发现：

-- observed but not declared: shadow agents and un-reviewed capability creep
SELECT agent_id, tool, count(*), min(ts) AS first_seen
FROM spans WHERE ts > now() - '7 days'
  AND (agent_id, tool) NOT IN (SELECT agent_id, tool FROM registry_capabilities)
GROUP BY 1, 2 ORDER BY first_seen DESC;

-- declared but not observed: dead rows still holding live credentials
SELECT r.agent_id, r.owner, r.last_seen
FROM registry r WHERE r.credential_active
  AND (r.last_seen IS NULL OR r.last_seen < now() - '90 days');

第一条查询是你的影子智能体探测器，而你第一次跑它时它会让你难堪，通常是因为某个六个月前在一次配置改动里被加上去的能力。第二条是你的吊销队列。让两条都按计划跑，把输出路由给归属团队，清单就不再是一张快照，而变成一个正在收敛的过程——那是唯一能在一个快速变动的代码库里存活下来的形态。

有一个前提值得明说：对账只看得见你的遥测所覆盖的那些调用路径。一个绕开你的网关、直接触达厂商 API 的智能体，对两条查询都是不可见的——而这正是"把模型与工具流量都路由过一个你自己掌控的收窄点"的真正理由。那个收窄点不是为指标而设的；它是为了让"轨迹里没有"能被读成"没有发生"，而不是"没有被埋点"。

STEP 6

先造小的那一版，今天就把它放进路上。

这件事不需要一个平台。它需要的是版本控制里的一个 YAML 目录、一个在记录缺归属或缺评测套件时拒绝签发凭据的 CI 任务、两条每周定时跑的对账查询，以及一条"网关拒绝未登记的客户端 ID"的规则。版本控制会免费给你变更历史与评审流程——一次能力授予变成一个 pull request，而那恰恰是你本来想创造出来的那道评审。

要避免的失败模式是先去设计那份大而全的 schema。一份只有六个精挑字段、但把住凭据签发的登记表，价值高于四十个没人填的字段，因为那六个是真的。只在"某个你确实有过的问题答不出来"时才加字段——并且删掉任何你从未查询过的字段，因为一个没被查询过的字段不是治理，是一张表格。

从凭据出发，而不是从问卷出发。把今天智能体能取得权限的每一个地方都列出来——API 密钥、服务账号、OAuth 客户端、网关路由、MCP 服务器配置——然后让它们每一个都要求一个登记表 ID。仅这一处改动，就把清单从一项你用问卷回复来支付的经常性成本，变成了系统的一个属性；而这正是"一份你向审计人员辩护的名单"与"一份你真能靠它按下熔断开关的名单"之间的差别。
