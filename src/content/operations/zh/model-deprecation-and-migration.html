运维 · 智能体运维：部署与运营

模型下线：在别人的日历上做迁移。

你的智能体是针对某个模型验收的，而那个模型有一个不由你选择的退役日期，且通知窗口比重新验收一个智能体所需的时间更短——Anthropic 承诺对公开发布的模型至少提前 60 天通知，OpenAI 对正式可用模型承诺六个月，对 preview 模型则可能只有两周。把行为固定到带日期的快照仍然是对的，但要清楚它买到了什么：当下的确定性，以及日后一次由别人定日子的强制迁移。所以真正的交付物是一套常设的"候选对基线"评估差异，而不是一次匆忙之中改动的配置。

STEP 1

截止日期是提前公布的，只是没人去读。

厂商下线不是突袭，而是一套有文档的生命周期。Anthropic 把模型标为活跃 → 遗留 → 已弃用 → 已退役，会通知仍有活跃部署的客户，并承诺对公开发布的模型至少提前 60 天通知退役。对已退役模型的请求不会降级——它们直接失败。OpenAI 公布的政策分三档：正式可用模型至少六个月，专门变体至少三个月，而名字里带 preview 的可能只有两周。

60 天窗口的具体形状：claude-opus-4-1-20250805 于 2026 年 6 月 5 日被弃用，退役日期为 2026 年 8 月 5 日。两个月，你要在其中意识到自己受影响、拿到候选模型、重新验收智能体、修好回归掉的部分，并让它走完你平常的晋级关卡。如果你的晋级路径是两周灰度，那你只有六周工程时间，且没有余量。

这件事里被浪费掉的另一半，是预报早于弃用就存在。Anthropic 为每个活跃模型公布一个"不早于"退役日期——它剩余寿命的下限——所以一个下限在十一个月之后的模型，和一个下限在两个月之后的模型，是完全不同的规划对象。选模型时不看它公布的下限，就是在盲选自己的迁移日期。

STEP 2

固定版本是对的，而固定版本正是那个截止日期的来源。

灰度发布、版本化与固定主张把行为固定到带日期的 (模型, 提示, 工具) 三元组，这个主张依然成立。但要诚实地接受它的推论：一个被固定的快照是一份有到期日的带日期资产，而你已经承担了续期的义务。浮动别名不是出路——它并不消除迁移，它消除的是你对迁移何时发生的控制权，以及行为在你脚下改变时你能指着一个 diff 说话的能力。

所以两种失败形态并不是"固定"对"安全"，而是：

  • 固定了然后忘了。一切正常，预发正常、生产正常，一路正常到退役日——然后所有请求同时 404，包括那个没人认领的季度 cron 任务里的请求。这个失败是全面的、同时发生的，而且有确定日期。
  • 浮动而无法归因。别名在某个平常的周里把你挪到了新模型上。质量挪动了几个点、拒答率变了、某个工具开始被调用两次——而你的变更日志里没有任何一次部署可以与之关联。那次事故的第一天，你会花在盯自己的代码上。

"固定了然后忘了"是更好的失败，因为它可以被提前检测——但前提是退役日期是一个被追踪的字段，而不是一条活在厂商更新日志里的事实。这要求你知道自己实际调用了什么，而那是一个轨迹问题，不是代码搜索问题：智能体会在运行时通过路由器、兜底路径和按租户覆盖来挑模型，所以 grep 会漏掉那条真正要紧的路径。如果每次运行都打上模型 ID 的戳（正如 rollout-and-versioning 要求的），你的暴露面只需一次查询，而把它变成截止日期的那个 CI 检查只有十五行：

# models.yaml — the registry, keyed by (platform, model_id), with an owner
- platform: anthropic-api
  model_id: claude-opus-4-5-20251101
  retire_not_sooner_than: "2026-11-24"
  owner: agents-platform

# ci/check_model_horizon.py — fails the build at T-45 days
for m in registry:
    days = (date.fromisoformat(m["retire_not_sooner_than"]) - today).days
    if days < 45 and seen_in_traces(m, window="30d"):
        raise SystemExit(f"{m['model_id']} retires in {days}d and is still live")

把 CI 阈值设在 45 天，而不是 7 天。60 天通知配一个 7 天的警报，等于 7 天通知——窗口里有用的那部分你都花在毫不知情上了。警报应该在"迁移还是一件排得进计划的工作"时就响，而不是在它已经成了一桩事故时。

STEP 3

迁移是一次行为移植，不是换个字符串。

模型 ID 是最便宜的那个会坏掉的东西。按代价从低到高：

  • 标识符本身。一次硬的、立即的、显眼的失败。这是人人都会为之做准备、也从来不会真伤到人的那个。
  • 请求参数。Anthropic 在 Claude Opus 4.7 及之后弃用了 temperature、top_p 与 top_k：现在给它们设非默认值会返回 400。一个你的客户端从 2024 年就一直在传的参数，在替代模型上变成了硬错误。这恰恰是击溃"就换个字符串"的那一类情况，也是为什么迁移需要一次真实的试运行，而不是一次查找替换。
  • 工具调用的形状。并行调用行为、严格程度，以及 JSON Schema 中真正被遵守的那一部分，都会在模型代际之间挪动——见各厂商的 JSON Schema 子集。旧模型容忍的 schema 可能变成一个校验错误，或者更糟：悄悄地不再被强制执行。
  • 拒答边界与语域。拒答、啰嗦程度、排版习惯与人格都是在后训练里装上去的，而那一层每发布一版就重做一次。为把某个模型劝出无益拒答而调过的提示词，在下一个模型上会变成拒答过多或过少。
  • 令牌经济学。不同的分词器、价格点或思考预算默认值，会同时改变你的账单与上下文预算，而这可能把一个塞得进去的提示词变成塞不进去。从智能体成本控制重新推一遍数字，而不要假设它们照搬过来了。

代价最高的那一类是你自己的绕行办法。你为对付某个模型的怪癖而加进去的每一句话——那句"不要道歉"、那个三重强调的输出格式、那个只为阻止一个反复出现的错误而存在的示例——现在要么是烧令牌的死重量，要么是一个正在误导某个从来没有那个怪癖的模型的 bug。迁移是删掉提示词疤痕组织的唯一好时机，而 STEP 5 里的评估差异就是你弄清哪些疤是承重的方式。

STEP 4

定你日期的是平台，不是模型。

这是那个会绊倒"其他每件事都做对了"的团队的陷阱。退役日期是平台的属性，不是模型的属性。Anthropic 公布的日期适用于由 Anthropic 运营的平台；由合作方运营的平台（如 Amazon Bedrock 与 Google Cloud）自行设定退役排期，所以同一个模型 ID 可以在一个平台上活跃、在另一个平台上已退役。你的清单主键是 (平台, 模型 ID)——一个只按模型字符串建索引的登记表，追踪的是错误的对象，而且会在日期上自信地答错。

这一点与故障转移叠加。一个在压力下跨厂商改道的网关（见速率限制与厂商容量）可能把你放到一个你从未追踪过日历的平台上——而第一个证据将是来自某条你都不知道还活着的路由的退役错误。从轨迹去枚举，而不是从你以为生效的那份配置。

不要让跨厂商兜底成为你的迁移方案。兜底路径是一个你没有验收过的模型、在一次事故里被第一次触及、且位于一个退役日期不同的平台上。那是一次同时发生的两个未经验收的变更。故障转移买的是可用性，它买不到一次迁移。

这本账的另一面值得诚实定价：权重在你自己手里的模型，根本没有退役日期。这不是"什么都自己托管"的论据——前沿差距是真实的。它是"注意哪些步骤是大宗商品活儿"的论据。嵌入、重排序、路由与抽取是高频步骤，也是一个小的本地模型就够用的地方，而把它们从跑步机上拿下来，就等于把它们从今后每一次迁移里移除。嵌入是两个方向上都最锋利的例子：更换嵌入模型会强制对整个语料重嵌一遍，所以一个托管嵌入端点的退役不是一次配置改动，而是把你手上的一切重新索引一遍（本地知识库）。

STEP 5

把验收机器常设起来，迁移才会变无聊。

把 60 天的救火演习变成两天的改动，靠的是验收机器已经存在、并且已经在跑。这就是评估驱动的智能体开发的回报：把评测套件指向候选模型，然后做差异。

输出必须是一份差异，不是一个分数。一个从 0.83 挪到 0.85 的总分，会把十一个从通过变失败的用例藏在十四个反向变化的用例背后——而在智能体上，通过→失败那一组才是你的用户会来报的。逐用例地，你需要变化方向，并在旁边配上成本、步数与拒答的增减，因为一个准确率打平却多花 40% 步数的候选，在你实际运营的每一个维度上都是回归：

$ evaldiff --baseline claude-opus-4-1-20250805 --candidate claude-opus-4-8

  cases           412     pass 0.83 → 0.86   (+0.03)
  pass  → fail     11     # the only column that matters on day one
  fail  → pass     23
  refuse → answer   4     # check each: newly helpful, or newly unsafe?
  answer → refuse   2
  median steps    6.0 → 8.5   (+42%)         # cost + latency regression
  median $/task   0.11 → 0.14  (+27%)

  pass → fail, grouped by tag:
    tool-schema-strict   7    # candidate rejects a schema the baseline accepted
    long-context         3
    formatting           1    # a prompt workaround that is now the bug

评测集给不了你两样东西，而一个习惯能覆盖它们。你的套件里装的是你想到过的输入分布；生产里是你没想到的那个。让候选模型在真实流量上做影子运行，丢弃其输出、离线比对（rollout-and-versioning）——那个古怪的租户、那个病态的附件、那段八轮的对话，都住在那里。而由于一次运行的输出即使在固定模型上也不可复现，判读差异时要有足够多的用例，确保你读的是一次位移而不是采样噪声；在一个 40 个用例的套件上翻了几个用例，那是一次配了电子表格的抛硬币。

STEP 6

在窗口之内，按你自己的日子迁移。

让这件事变成例行的顺序是：给每次运行打上 (平台, 模型 ID) 的戳，使暴露面成为一次查询；维护一份你所调用之物的登记表，带上退役下限与一位具名负责人；对任何仍在线的项目在 T-45 天让 CI 失败；把候选对基线的评估差异跑成持续的而非收到通知才跑的，这样一次新的前沿发布就是一个你去评估的机会，而不是一桩你去承受的紧急事件；按模型给提示词做版本，而不是让一个字符串跨越代际边界共用；并且用你对任何行为变更都会用的那套"先影子再灰度"的关卡去晋级它，因为它本来就是一次行为变更。

在窗口早期做迁移，你就能从容地只做一次，而且旧模型还活着、还能调用，可以当比对基线。在最后一周做，你就是在没有参考实现的情况下调试一次行为移植——因为你本来要拿来做差异的那个东西，已经被关掉了。

对每一次前沿发布都跑一遍候选差异，而不只在退役通知到达时跑。工作是同一份，而持续地做会把强制迁移变成一个你早就做完的决定——你通常会发现自己可以提前好几个月就搬到替代模型上，到那时退役日期就完全不再是一桩运维事件了。把下线当危机的团队，正是那些只在旧模型快死时才去看新模型的团队。
