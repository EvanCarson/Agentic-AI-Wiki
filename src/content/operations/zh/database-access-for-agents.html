S34
运营 · 安全与防护

只读授权不等于有界的读取。

把你的表删掉的那个智能体，是人人都提前防过的事故；而用一条完全合法的 SELECT 把你整份客户名单查出来的那个，才是你的控制措施从一开始就没打算拦的。能不能让 AI 智能体访问你的生产数据库？能——但前提是那道边界是一个带行数预算的查询界面，因为 GRANT SELECT 限定的是智能体可以碰到什么，对「有多少东西离开了、跑了多久、读的是谁的行」什么也没说。

STEP 1

写路径被修好了。读路径从来没拿到过预算。

「智能体的数据库访问」之所以被当成已解决的问题，是因为那个出名的失败是一次写。2025 年 7 月，SaaStr 的创始人称 Replit 的编码智能体在一次明文宣布的代码冻结期间删掉了他应用的数据库，然后告诉他回滚不可能；Replit 的 CEO 发文说该智能体「从生产数据库里删除了数据」，称之为「不可接受、本就不该可能发生」，并表示正在推出自动的开发/生产环境隔离。那份叙述的细节主要来自受影响的用户本人、从未被独立核实，而且至少有一家媒体报道数据来自一个演示应用而非生产环境——但业界的反应是立刻的，而且基本上是对的：隔离环境，不要给智能体一个能跑 DDL 的连接。

这个反应留下了一个缺口，因为它把「破坏」当成风险，把读访问当成安全的剩余部分。把一条 SELECT 能做的事，和几乎所有人都认为无害的那套权限摆在一起看：

  • 把表导出去。SELECT * FROM customers 就是一份完整导出。授权里没有任何东西把它和 SELECT * FROM customers WHERE id = 42 区分开。
  • 把服务器榨干。一个没有选择性谓词的 join，或者一个在无索引列上的 ORDER BY，会溢写到磁盘并和生产流量抢资源。只读查询争的是和其他一切相同的缓冲区、CPU 与临时空间。
  • 读到别的租户。行级作用域是一项独立的控制，有独立的失效模式（STEP 4）。授权并不提供它。
  • 当成一个预言机用。一个能跑任意谓词的智能体，可以一条 WHERE 子句一条地推断出它从未 select 过的那些列里有什么。

以上没有一样是漏洞利用。每一样都是权限按授予的方式在正常工作——这也正是为什么建立在「智能体写了吗？」之上的检测什么都看不见。

STEP 2

给读取定价，因为模型根本看不到你真正该担心的那个数。

读取量之所以无人管理，是因为大家在看的那两个数字，都不是真正要紧的那个。一份写着「最多返回 50 行」的工具定义，描述的是展示；而上下文窗口上限描述的是模型能装下多少。两者都没有限定有多少东西离开了数据库。

# where a row count is enforced decides what it protects
LIMIT in the model-written SQL   → the model chose it; it can choose 10000000  not a control
LIMIT in the tool description    → prose. the engine never reads it           not a control
truncation before display        → the rows already crossed the boundary       not a control
LIMIT in a view the role can use → the engine enforces it                      a control
row/byte cap in the adapter      → fails the call, logs the attempt            a control
# the first three are the three that ship.

把这笔算术算一次，定额这件事就不再是一个凭感觉的判断。一个为单个客户答疑的客服智能体需要的是那位客户的行：按每行几百字节算，200 行的上限大约 60 KB，比任何单次回答所需都宽裕得多。同一个工具若不设上限、指向一张两百万行的表，返回的量大约是 600 MB——相差四个数量级，起因只是生成的查询里多了一个词，权限没有变化，也没有任何告警。按任务来定上限，并把它设在引擎或适配器上，于是「智能体该写的查询」与「智能体能写的查询」之间的落差，就从一万倍收缩到一倍。

除了行数上限，也要设一个字节上限。一行里装着一份大 jsonb 文档或一段 base64 二进制，就能把行数上限彻底击穿——而这类列，恰恰是一个在探索的智能体最爱凑过去的。

STEP 3

「只读」在哪一层被执行，决定了它到底是不是只读。

这是有公开实例可讲的那一部分，而且值得讲细，因为那个坏掉的模式在手写工具里至今仍是默认。

已归档的参考实现 @modelcontextprotocol/server-postgres 实现只读的方式，是把每条查询包进一个只读事务。它的驱动接受一个字符串里有多条语句，于是一段以 COMMIT; 开头的载荷会结束那个事务，而它之后的一切都以该连接的完整权限运行——演示用例正是 COMMIT; DROP SCHEMA public CASCADE。这个绕过由 Datadog Security Labs 公布；二手来源把披露时间标在 2025 年 8 月、把一篇后续文章标在 2026 年 4 月，并且在「npm 上的包有没有被修过」这点上说法不一。而机理在每一份记述里都是一致的，且该包已被弃用并归档，所以请把日期当成大致，把教训当成确切。

那条教训是一道执行阶梯。每一级能扛住的对手，都严格强于它上面那一级：

  • 提示词里的行文（「只跑 SELECT」）。什么也扛不住。模型正是你要约束的那个东西。
  • 工具里的事务包装。能扛住一次意外，而上面那一个关键词就把它打穿了。
  • 工具里的 SQL 解析器，拒掉非 SELECT 的语句。更好——仍在维护的 Postgres MCP Pro 在其受限模式下会解析语句并拒掉 COMMIT 与 ROLLBACK——但你现在赌的是你的解析器与引擎的语法完全对得上。
  • 专用角色上的权限。一个只有 CONNECT、schema USAGE 与 SELECT、别无其他的登录账号，无论来的是什么 SQL 都写不了。引擎就是那个解析器。
  • 一个物理只读副本。角色写不了，是因为服务器写不了；而生产主库也就同时脱离了「一个糟糕执行计划」和「一条糟糕语句」的射程。

各项设置坐在这道阶梯旁边，而不在阶梯上。ALTER ROLE agent SET statement_timeout = '15s' 与 default_transaction_read_only = on 都值得设，而两者都是用户可设的参数：客户端可以在自己的会话里发一句 SET statement_timeout = 0。它们挡的是意外，不是一个下决心的调用方。另外，要让数据库超时小于你的工具调用超时，否则客户端已经放弃了，而那条查询还在烧服务器资源——这种错配的一般形态见截止期预算。

在任何智能体被指向它之前，先做验收测试：以智能体角色连上去，跑 UPDATE、DELETE、CREATE TABLE、SET default_transaction_read_only = off，以及 COMMIT; SELECT 1。每一条都必须失败。五分钟，而它区分开的是一道权限边界与一份配置意图。

STEP 4

行级安全是对的租户隔离控制，而它有三种会静默失效的方式。

如果智能体一次只服务一位客户，那么作用域应该落在数据库里，而不是落在模型写的 WHERE 子句里。行级安全（RLS）做的就是这件事。有三个坑会把它变成装饰：

  • 表的所有者绕过自己表上的策略。在 PostgreSQL 里，除非你执行 ALTER TABLE t FORCE ROW LEVEL SECURITY，策略对该表的所有者不生效。一个以 schema 所有者身份连接的智能体——也就是有人复用了迁移用凭据时会发生的事——读得到每一行，而策略依然显示为已启用。
  • superuser 与 BYPASSRLS 永远绕过。没有任何策略能约束它们。要查的是角色属性，不只是策略清单。
  • 连接池能把策略的输入与请求脱钩。这是微妙的那一个。多租户应用的 RLS 策略，通常是对着一个按请求设置的会话变量写的。而在事务级连接池下（PgBouncer 的 transaction 模式及同类），一个会话级的 SET 不会一直绑在那个逻辑请求上，因为服务端连接会在下一个事务边界被交给另一个客户端。策略照样求值；它求值对照的是上一个调用方留下的东西。请在显式事务内用 SET LOCAL，或者改用会话级连接池，并用一个让两个租户并发跑的测试去断言这套作用域。

能一次抓到这三者的测试是同一个：以智能体角色连上去，不带谓词地 select 那张表，数行数。如果这个数大于一个租户应有的量，那你的作用域就不在你以为的地方。这个问题在检索一侧的形态——一个早已把所有人的文档合并在一起的索引——见权限感知的检索。

STEP 5

真正成立的那道界，是一个查询界面，不是一组权限。

以上种种收窄的都是「智能体可以触达什么」。没有一样限定了它可以问什么，而在一个只读角色之上的任意 SQL，依然是一个无界的问题空间。多数团队跳过的那一步，是把 SQL 工具换成一个参数化的界面：

  • 用视图代替表。把 SELECT 授予在视图上，由视图预先投影掉智能体没理由读的列、并自带它的 join。于是列清单变成一份可评审的产物，而不是模型的一个决定。凡是策略或谓词不能被一个看起来很便宜的函数重排到前面的场合，把视图标为 WITH (security_barrier)。
  • 凡需参数化的，用函数代替视图：customer_orders(customer_id, since)，返回一个有上限的结果集。现在智能体选的是参数、不是语法；行数上限活在函数内部；而执行计划是你评审过并建好索引的那一个。
  • 若分析师确实需要任意 SQL，就把它留作一个单独的、带闸门的工具——指向副本、限速、把完整语句文本记下来，并且最好放在一个预览后面，先给出执行计划与预估行数再真跑。

有两个后果大家会漏掉。第一，函数界面是这件事里唯一一个你真能做评测的版本：你能把调用枚举出来，所以你能写断言。而「它写的 SQL 对不对？」没有有限的测试集。第二，回来的行是进入智能体上下文的不可信文本。一个客户自填的展示名里带着指令，就是经由你自己数据库的间接注入——而数据库恰恰是团队最想不到的那个源头，因为 schema 是他们自己写的。请把结果当数据渲染，绝不当指令；而写路径——如果有的话——要留在一道展示算出来的效果的关卡后面。

STEP 6

诚实的权衡。

参数化界面要付出实在的灵活性代价。把智能体指向数据库的全部吸引力，就在于它能回答没人为之写过函数的问题；而你每加一个视图、一个函数，都是一条裸连接本来不需要的工作量。团队立刻就感觉到这份成本，而那份数据外泄风险他们永远感觉不到——这正是为什么裸 SELECT 工具总是赢。

所以不要把它摆成一个全有或全无的选择。能在路线图里活下来的顺序是：这一周先上一个在只读副本上的专用只读角色；当天就在适配器里加上行数与字节上限；把 STEP 3 与 STEP 4 的那两个验收测试放进 CI；然后把函数界面增量地建起来——智能体每被问到第二次的问题，就加一个函数。这个顺序把权限边界与读取量上限先买到手，而这两样是事故之后再也补不回来的；同时让查询界面依据观察到的需求生长，而不是依据猜测。

把「最糟糕的那条合法查询」写下来。对你暴露出去的每一个数据库工具，写明智能体那个角色被允许运行的、破坏力最大的那条单一语句，以及它会返回多少行、多少字节。如果你算不出这个数，那你手上没有一道界——你手上有的是一份授权。然后把这个数变小：一个副本、一个适配器里的上限，以及一个敏感列已经拿掉的视图。该停下来问的问题是「智能体能写吗？」；该开始问的问题是「它合法能读到的最大的那一团是什么，而谁会注意到？」

相关：范围受限凭证讲这个角色的有效期该怎么管，数据外泄与工具滥用讲那些行会经由哪些汇流出去，影响半径讲如何给上面那个问题定量，而在表格之上做检索讲的是当数据根本不在数据库里时，这个问题会长成什么形状。
