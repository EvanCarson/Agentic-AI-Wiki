运营 · 智能体运维：部署与运营

把界面交付进你无法掌控的宿主。

当你的工具服务端返回的不再是文本而是一个界面，你就接下了一份自己无法部署的部署：宿主想什么时候取就什么时候取你的标记，还可能把它缓存起来，用你几周前写下的那份声明去构造安全策略，然后把它渲染进一个你的错误上报器连网络都摸不到的沙箱里。运营层面的后果由规范钉死，而多数团队读过去了——文本结果才是契约，界面只是增强；所以你要监控、告警和回滚的对象是工具，而那个控件只是工具里的一个版本号。

STEP 1

你不是在部署一个页面，你是在发布一件别人来取的产物。

在 MCP Apps 扩展里，工具用 _meta.ui.resourceUri 指向一份界面资源；该资源 MUST 使用 ui:// 方案与 text/html;profile=mcp-app 这一 MIME 类型，而宿主 MUST 用 resources/read 去读取它。规范同时写明：宿主 MAY 预取并缓存该内容，还可以在工具真正运行之前就预加载模板。

把这两句话合起来读，运营的形状就显出来了。这里没有任何缓存失效原语。没有清除调用，没有一份规范强制宿主遵守的 ETag 纪律，也没有办法告诉宿主它手里那份标记现在是错的。这意味着「你能改的东西」与「用户看到的东西」之间隔着一层缓存，而这层缓存的策略是逐宿主的实现细节——而你对它唯一的把手，就是 URI。

# fragile: the host may be holding last week's markup
ui://acme/invoice-table

# operable: the URI is the version, so a rollout is a pointer change
ui://acme/invoice-table@2026-11-02.3
  # old URIs stay resolvable; a stale cache serves a
  # consistent old view instead of a broken new one
  • 把构建标识放进资源 URI，每次标记变更都换它。变动的是工具的 _meta；资源本身一经发布即不可变。
  • 让前两三个 URI 继续可解析。手里握着缓存模板的宿主，会去取它记得的那份资源，而你希望那次取回是成功的。
  • 让回滚只是一次指针变更，而不是一次重新部署——与灰度与版本化是同一套纪律，只是多了一条约束：你没法把旧版本排空。
  • 绝不要把密钥或租户数据放进标记里。它是一件存在别人仓里的、可缓存的静态产物。数据要单独走，走工具结果。
STEP 2

文本结果才是契约。监控它。

这句话该写进你的运行手册：即使界面可用，工具 MUST 仍然返回有意义的 content 数组；并且对每一个启用了界面的工具，服务端 SHOULD 提供纯文本回退行为。扩展本身是可选的，在 io.modelcontextprotocol/ui 下协商，客户端声明自己支持的 mimeTypes；服务端 SHOULD 在注册启用界面的工具之前检查客户端能力。尚未采用该扩展的宿主会把你的工具当作普通工具，什么都不会坏。

所以界面并不是你的产品界面。它是一层表现层，盖在一个「契约是文本」的工具之上；而这件事把你正打算搭的监控整个倒了过来。你的可用性目标该挂在工具调用上。你的正确性评测该跑在 content 数组上。那个控件只能拿到一个弱得多的保证——渲染出来，或者没有——因为在相当一部分会话里它根本不会渲染，而任务仍然必须完成。

这能防住的失效很具体也很常见：团队先做控件，让文本结果退化成 "See the table above."，于是交付出一个在所有没有该扩展的宿主里都没用的工具——而且即便在有扩展的宿主里对模型也没用，因为模型读的是 content 数组，不是你的像素。一个只有配着界面才讲得通的文本结果，就是一个配了漂亮截图的坏工具。

STEP 3

你的遥测默认是被拦住的，而这个默认值是对的。

宿主在一个默认拒绝一切的内容策略下，于沙箱 iframe 中渲染 MCP App。如果你完全省略 ui.csp，宿主会套用 default-src 'none' 外加 connect-src 'none'。connectDomains 为空或缺失即表示没有任何对外连接；frameDomains 为空即表示不允许嵌套 iframe；baseUriDomains 默认为 base-uri 'self'。宿主 MUST 依据你声明的内容构造策略，MAY 进一步收紧，MUST NOT 放行你未声明的域。对于 Web 宿主，你的视图还要经由一个与宿主不同源的沙箱代理来运行。

对运营有三个后果，按它们会耗掉你多少时间排序：

  • 把产物内联进去。每一个源都要算，包括你的 JavaScript 与 CSS 的来源。一个你忘了声明的远程 <script src>，在一个什么都不会回报给你的宿主里，就是一个空白控件。
  • 通过工具上报，而不是通过信标。视图可以调用 tools/call，由宿主代理到你的服务端。这条路径本来就存在、在默认策略下本来就能用，而且本来就带着你的鉴权。而把一个分析域写进 connectDomains，会变成别人宿主安全评审上的一条条目，并且是他们第一个要求你删掉的那条。
  • 假定你永远看不到客户端异常。没有任何错误上报 SDK 能把数据送回家。你的可观测性就是工具调用流：发出一条带 STEP 1 里那个构建标识的结构化 view_error 工具调用，并把「错误调用数飙升的那个构建」当作回滚候选。追踪与可观测性里的一切依然成立；只是那个 span 必须从代理的你这一侧开始。
STEP 4

能力是逐宿主的事实，所以你的发布单位是「宿主 × 版本」。

在该扩展于 2026 年 1 月发布时，支持它的宿主是 Web 与桌面版 Claude、Goose、VS Code Insiders，以及当周正在逐步放量的 ChatGPT。ext-apps 仓库很坦白：除一个基础示例外，它不提供任何生产级宿主实现，而若干宿主是经由 MCP-UI 客户端 SDK 来实现该扩展的。在线上协议层面，SDK 的版本兼容被刻意放宽——ext-apps 1.x 与 2.x 之间的协议未变，2.x 的视图能在 1.x 宿主里工作，2.x 宿主也能渲染 1.x 视图——这是一份礼物，同时也正是「某个宿主特有的 bug 不会以版本不匹配的形式自报家门」的原因。

请像 2010 年对待浏览器那样对待它，因为从运营角度看，它就是那回事。

  • 维护一份显式的宿主矩阵——宿主、能拿到的版本、渲染正常／渲染有缺陷／回退为文本——并给每一行标日期。它和第三方工具漂移里的厂商矩阵是同一件产物，而且腐坏得一样快。
  • 靠协商，不要靠嗅探。在注册启用界面的工具之前检查已声明的能力与 mimeTypes；按声明分支，而不是按宿主名字符串分支。能力发现就是这个模式，而本扩展是它的一个实例。
  • 预期无声的不对称。规范里沙箱握手的那几条通知，在 2026-01-26 版中是 MUST，在 draft 中是 SHOULD。一个对着 draft 实现的宿主，行为可以与对着稳定版实现的宿主不同，而两者都没错——这恰恰是协议修订与弃用窗口存在的意义所在。
  • 某个宿主的故障不是你的故障。如果一个宿主不再渲染，你的工具照样返回文本，你的任务照样完成——前提是你做了 STEP 2。那就是做它的全部价值。
STEP 5

把生命周期通知当成你手上唯一的那只钟。

握手顺序是 ui/initialize 再到 ui/notifications/initialized，而在后一条通知到达之前，宿主 MUST NOT 向视图发送任何请求或通知。随后 ui/notifications/tool-input 最多到达一次，且必须在 ui/notifications/tool-result 之前到达；tool-input-partial MAY 在流式过程中到达零次或多次，而视图 MUST NOT 依赖部分参数去做关键操作；若执行被取消则 tool-cancelled 到达；而在拆除资源之前，宿主 MUST 发送 ui/resource-teardown，并 SHOULD 等待响应。

这些就是你的生命周期钩子，每一个都对应一条运营规则。

  • 在 teardown 时落盘。这是你被明确告知「视图即将结束」、且宿主被要求等你的唯一时刻。任何你想留痕的东西——一份草稿、一段时长、一条还没发出的错误——都在那里送出去，以工具调用的形式。
  • 绝不要依据部分参数行动。规范禁止依赖部分参数去做关键操作，实践中就是：不要在一个流式参数上做写入、扣款或跳转。这与语音栈里「把副作用卡在最终转写之后」是同一条规则。
  • 把取消当作一条正常路径来处理。一次被取消的工具，会留下一个握着输入却没有结果的视图。请决定那个视图显示什么，否则你的用户会替你找出答案。
  • 上报尺寸，不要假定尺寸。内容尺寸变化时视图 SHOULD 发送 ui/notifications/size-changed，而当尺寸可变时宿主 MUST 监听它。一个从不上报自身尺寸的控件，就是一个在每个宿主里都被裁得不一样的控件。
STEP 6

把模型的上下文当作一次要做版本管理的写入，因为它是覆盖式的。

视图可以通过 ui/update-model-context 告诉模型里面发生了什么。它的语义是「后写覆盖」：每一次请求都覆盖该视图先前送出的上下文；若在下一条用户消息之前到达多次，宿主 SHOULD 只发送最后一次。宿主同时代理来自视图的 tools/call，并且对可见性不含 "app" 的工具 MUST 拒绝这类调用；而可见性不含 "model" 的工具，MUST NOT 出现在智能体的工具列表里。

由此引出两件事，而第一件是一场正在候场的生产事故。因为上下文更新是覆盖而不是追加，一个在每次按键都写入部分状态、然后停下的视图，会让模型手里只剩它最后一次恰好写进去的东西。随后模型会自信而错误地描述这张表单。请让每一次更新都是视图状态的一份完整、自描述的快照，绝不要做增量；并且在真正重要的时刻写它——提交时、teardown 时——而不是持续地写。

第二件是一个值得用起来的设计余量。「仅应用」工具，正是安放「界面需要、而模型不该自行触发」之物的合适位置：一次分页取数、一次预览渲染、一次校验调用。把它们挡在模型的工具列表之外，既降低了你工具目录的 token 成本，也减少了智能体能给你的惊喜花样——这与MCP 工具设计里「不要因为一个工具存在就把它暴露出去」是同一个论点。

上线之前跑一遍「陌生宿主」演练。在你自己的客户端里关掉界面扩展，只用文本结果把这个工具用上一天——如果任务变难了，说明 STEP 2 没做完。然后把 ui.csp 清空、加载这个控件，确认它仍然渲染、仍然上报错误；如果它一片空白，那你有一个没声明的远程依赖。两件事各花一个下午，而这两种失效否则就只会由某个用户、在一个你从未跑过的宿主里替你发现。
