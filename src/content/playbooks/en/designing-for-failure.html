H6
Playbook · Agent UX & Human Interaction

The quality of an agent product is decided by what happens after it is wrong.

The failure screen you are able to show is already determined by a decision you made in the write path, hours earlier, because "the invoice was not sent" and "undo" are claims about state that only exist if something recorded them before the effect landed. Teams try to fix failure UX by rewriting copy, and copy is the one part that cannot be fixed, since an error message can only report what the system knows. Decide at each write which of three tiers the effect is on — cancellable, compensable, or merely disclosable — store the handle that tier needs, and your failure screens write themselves; skip it and no amount of careful wording saves you from "something went wrong".

STEP 1

You cannot author a failure message retroactively.

Most agent UX effort goes into the happy path, and the failure path gets whatever the exception handler happened to do. The usual diagnosis of that is a priorities problem, which makes it sound fixable later. It is not. Users form their durable judgment of an agent during failures, and by the time a failure is being rendered the useful information either exists or does not.

Work backwards from the three sentences a user actually needs — what state am I in, what can I do about it, what should I not assume — and each one resolves to a record somebody had to write earlier. "Nothing was applied" requires that effects were ordered and journaled, not fired concurrently. "The email was not sent, but the ticket was created" requires per-effect outcomes, not a single try/except around a five-step plan. "Undo" requires a stored inverse. A handler that holds only an exception object can tell the user that it is sorry, which is the one thing nobody needs.

The dangerous failure is not the visible crash — it is the agent that quietly produces a plausible-but-wrong result and continues. Bias detection toward surfacing uncertainty and stopping rather than pushing through, and treat a half-applied plan as a failure even when every individual call returned 200.

STEP 2

Three tiers of reversal, and the handle each one demands.

"Can we undo it?" is not one question. Real systems answer it in three distinct ways, each requiring a different thing to have been stored, and the tier is a property of the effect rather than of your product's ambition.

Cancellable — the effect has not landed yet, and withdrawing the authorisation leaves no trace. Stripe is the cleanest illustration: a payment that has been authorised but not captured cannot be refunded at all, it must be cancelled, which releases the hold without creating a Refund object and costs nothing. Gmail's Undo Send is the same shape in consumer clothing — a send-cancellation period of 5, 10, 20 or 30 seconds, chosen in web settings and defaulting to 5, during which the message has not actually gone anywhere. The handle this tier needs is the pending operation's id plus the deadline.

Compensable — the effect landed and an inverse exists, but running it is a second visible event. The same Stripe payment, once captured, must be refunded through the refunds API; you may refund partially and more than once, up to the original amount. The money comes back and the statement line does not disappear. The handle is the stored inverse operation, with the identifiers it needs, written down before the forward action ran.

Disclosable only — no inverse exists at any price. Mail accepted by a receiving server has no protocol-level recall; a notified counterparty cannot be un-notified; a consumed quota is gone. The handle here is the full description of what happened, because disclosure is the entire remedy.

# Classify at the write, not at the error. Three fields, forever.
effect = plan.next()
journal.record(
    tier   = effect.tier,            # cancel | compensate | disclose
    handle = effect.reversal_handle(),  # op id, or the inverse call
    until  = effect.cancel_deadline, # None for the other two tiers
)
op = effect.apply()                   # journal BEFORE, always

if user.undo(op) or monitor.regressed(op):
    journal.reverse(op)              # picks cancel or compensate by tier
# and if the tier is 'disclose', the UI says so instead of offering a button
  • Where true reversal is impossible, buy yourself a cancellable window: a short delay before the effect lands converts tier three into tier one for the price of some latency, which is what Gmail's five seconds are for.
  • Never show an Undo control for a disclosable effect. A button that does not work is worse than an explanation, and users generalise from one lying affordance to all of them.
  • Invest in reversibility before investing in better confirmations. Strong undo lets you safely lower approval friction, which reduces fatigue, which improves the oversight that catches the failures undo then cleans up — the lever in full is undo and reversibility, and the server-side machinery is repairing agent side effects.
STEP 3

An error message is a UI for the user's next action.

"Something went wrong" tells the user nothing they can use, and the fix is not better prose — it is reporting the applied/not-applied boundary. A failure in a five-step plan has at least four distinct meanings: nothing ran; some steps ran and were reversed; some steps ran and could not be reversed; everything ran but the result is wrong. Those four have four different recovery actions, and a UI that renders them identically has thrown away the only information the user needed.

So the shape of a good failure screen is a short ledger, not a sentence. Name each effect, its outcome, and whether it is reversible; put the single most likely recovery action as the primary control next to it; and state the negative facts explicitly, because a user cannot infer "the email was not sent" from the absence of a line. Then give the run's identifier — the failure the user reports and the trace you investigate have to be joinable, and retrofitting that join is far harder than emitting it now.

Write the ledger for the worst case first: the agent died mid-plan, with two effects applied and one unknown. If your data model cannot render that screen, the gap is in the write path and no copy edit will reach it. Durable state and resumability is the substrate; dry run and preview is how you let the user see the plan before any of it is a question.

STEP 4

Fail closed on consequence, fail open on capability.

The direction of failure is a deliberate choice, and the two axes pull opposite ways. On the consequence axis — money, data, external communication — fail closed: when uncertain or erroring, do less rather than more, because an action not taken is recoverable and an erroneous irreversible one frequently is not. On the capability axis — a tool is down, a source is unreachable — fail open toward honest degradation: return partial results clearly labelled, or hand back to the human with state intact, rather than fabricating to appear functional.

The worst failure mode combines them: a confident, complete-looking, wrong, irreversible result. That is the one that destroys trust in capabilities which never failed, and the structural defence is to keep the irreversible step behind a check that is code rather than a model — the argument is in fail closed and fail open, and the worked version for money is the deterministic boundary for finance agents.

STEP 5

Trust repair is scoped, explicit work — not the passage of time.

A visible error does not just cost that task; it resets the user's calibration for the whole agent, usually globally even though the failure was narrow. Trust does not recover by waiting. It recovers through three deliberate moves, in this order.

  • Acknowledge the specific error plainly. No minimising, no anthropomorphic apology theatre. "The refund was calculated against the wrong invoice" lands; "I apologise for any inconvenience" does not, and over-apologising reads as a system that expects to be wrong again.
  • Scope the damage out loud. "This affected refund handling; ticket labelling is unchanged." Unscoped failures silently poison trust in capabilities that never failed, and the user has no way to draw the boundary themselves — which is the calibration argument in designing for trust.
  • Propose a demotion the agent asks for itself. Offer a temporarily lower autonomy rung in exactly the scope that failed — approval required on refunds, nothing else changed — and let the user accept or decline. A self-proposed demotion reads as accountability and rebuilds calibrated trust faster than any wording, and it gives you a measurable ladder back up: progressive autonomy.

Two failure modes of repair itself are worth naming. Repairing silently — shipping the fix with no message — leaves the user's calibration where the failure left it, so the engineering cost buys no trust. And repairing too broadly, by dropping the whole agent to manual approval, teaches the user that one mistake costs them the product; the demotion has to be as narrow as the failure.

STEP 6

When NOT to auto-retry.

If the failure may have partially applied a non-idempotent effect, do not auto-retry — silently retrying over uncertain state turns one recoverable failure into a duplicated, irreversible one, and the user now has two of something with no record of which attempt created which. Park the task, show the ledger, and make the human choose; the keys that would have made the retry safe are in idempotency, retries and side-effect safety.
