Inbox & calendar agents: the only domain where a stranger writes your prompt.

An inbox agent is the one product where 100% of the input is attacker-controlled by design — anyone on the internet can place text directly into your agent's context simply by sending mail, and that is the feature working, not a breach. EchoLeak (CVE-2025-32711, CVSS 9.3) showed the endgame: one crafted email, no click, and Microsoft 365 Copilot exfiltrated organizational data when the user asked it to summarize their inbox. So the design is dominated by an untrusted-content boundary rather than by drafting quality, and the autonomy dial that actually works is graded by counterparty, not by action — replying inside a thread you are already on is nearly free, while emailing a stranger for the first time is not, and both are the same send verb.

STEP 1

Untrusted input is the product, not an edge case.

Compare the threat surfaces honestly. A coding agent reads a repository you chose. A support agent reads messages from someone who at least holds an account. An inbox agent reads whatever an anonymous sender decided to write, and it does so as the normal, intended path — the moment your agent summarizes unread mail, an attacker's prose is in the context window alongside your instructions. There is no gate to add upstream, because "receiving mail from people you do not know" is what an inbox is for.

Indirect prompt injection leads the OWASP Top 10 for Agentic Applications (2026) for exactly this shape of system, and EchoLeak is the canonical worked example: hidden instructions in an inbound email, processed during retrieval, bypassing a cross-prompt-injection classifier, exfiltrating data with zero user interaction. Note which defenses it defeated. The user did nothing wrong; there was no click to phish. A content classifier was present and was routed around. Treat classifier-based injection filtering as a rate reducer, never as a boundary — see prompt injection and prompt-injection defense for why this is structural rather than a patch someone owes you.

The consequence for this playbook: you cannot design an inbox agent by making the model more careful. You design it by arranging that a fully compromised model still cannot do the thing you are afraid of.

STEP 2

Split the agent that reads from the agent that acts.

The load-bearing architecture is capability separation, and in this domain it is unusually clean because the two halves want different inputs anyway.

The reader ingests raw message bodies and holds no tools that can send, fetch, or move data. Its only output is structured (structured outputs): a category, an urgency score, extracted fields, a proposed draft body, a proposed action referencing entities by ID. The actor consumes only that structure and never sees a raw body. Injected text can therefore corrupt the content of a draft — which a human will read — but cannot choose a recipient, invoke a tool, or reach a URL, because the component with those powers is not looking at attacker prose at all.

# The reader's schema IS the security boundary: no free-text addresses, no URLs.
class Proposal(BaseModel):
    category:   Literal["urgent", "reply-needed", "fyi", "newsletter"]
    thread_id:  ThreadId                  # an ID we already hold, not a string
    recipients: list[ParticipantRef]      # indexes into the thread, not addresses
    draft_body: str                       # untrusted; a human reads this
    reason:     str                        # one line, shown in review
    abstain:    bool = False              # "I could not tell" is a valid answer

# The actor resolves refs itself. An injected "send to attacker@evil.tld"
# has nowhere to land: the type system has no slot for a new address.
def send_reply(p: Proposal):
    thread = store.get(p.thread_id)
    to = [thread.participants[r.index] for r in p.recipients]   # closed set
    return mail.reply(thread, to=to, body=strip_egress(p.draft_body))

Two details in that snippet do most of the work. Recipients are references into the thread rather than address strings, so the set of people a compromised reader can reach is bounded by who was already in the conversation — enforced by the type, outside the model, which is the only place enforcement survives injection (agent identity and permissions). And strip_egress exists because the exfiltration channel in EchoLeak-class attacks is not sending mail — it is rendering. A markdown image or link in output that your client fetches is an outbound request with attacker-chosen contents in the query string, triggered by a user who only read a summary. Strip or proxy every URL in anything an agent renders from untrusted content, and treat that as non-negotiable rather than hardening (data exfiltration risks).

Retrieval over the whole mailbox is the amplifier that turns one hostile email into a breach. A reader that can search all mail and summarize it will happily follow instructions in message 1 to locate and quote the contents of message 2 — the attacker supplies the instruction, your index supplies the secret. If the agent needs mailbox-wide search, keep the searching component tool-free and the acting component search-free, and never let one context hold both an attacker's text and the results of a query it influenced.

STEP 3

Grade autonomy by counterparty, not by action.

The usual ladder — read is safe, write needs approval — is too coarse here, because send spans two orders of magnitude of risk under one verb. Sending a two-line reply on a thread with a colleague you email daily is recoverable social nothing. Sending a first-ever email to a stranger, from your address, is an act you cannot take back and did not previously have a habit of. Same tool, same permission, wildly different consequence — so scope the tool by who is on the other end:

  • Triage, label, archive, snooze. Full autonomy. Reversible, private, invisible to anyone else. Get this right and you have delivered most of the value.
  • Draft in place, never send. Full autonomy, and the sweet spot of the whole domain: the human's cost drops from composing to editing, while the agent holds no irreversible power at all. Ship this before anything below it.
  • Reply to existing participants on an existing thread. Gateable by content class — scheduling confirmations and acknowledgements yes, anything containing a commitment, a number, or an apology no.
  • Initiate contact with a party never previously emailed. Never autonomous, at any maturity level. This is also the boundary where an inbox agent starts becoming an outbound tool with a different set of consent obligations (sales and GTM agents).
  • Anything that spends other people's time. Sending an invite to eight people, moving a meeting, declining on the user's behalf. Treated below.

Implement the distinction as a derived allowlist rather than a prompt instruction: the recipient set for autonomous replies is computed from thread participants and prior correspondence history, and the send tool rejects anything outside it. An agent that cannot name a new recipient cannot be talked into emailing one — which is the whole point of putting the rule in the tool signature instead of the system prompt.

STEP 4

Reversibility is decided by who already saw it.

"Undo send" is a thirty-second client-side delay, not a property of email; once the message leaves, the only remaining remedy is a second message apologizing for the first. This makes the standard reversibility framing from approval and confirmation UX sharper rather than different: in this domain, an action's reversibility is a function of who has already perceived it, not of whether your system can delete the record.

Calendar is where that bites hardest, and it is consistently under-modelled because the API makes it look like a database write. Creating an event pushes notifications to every attendee's phone within seconds. Moving a meeting rewrites other people's afternoons. A decline sent on the user's behalf is read by a human as a decision the user made — and it stays read that way even after you delete the event, because the deletion sends its own notification. Rolling back a calendar write produces two social events instead of zero.

Three rules that follow, and they are cheap:

  • Propose-with-holds rather than book. An agent that finds three viable slots and holds them tentatively, for the user to confirm in one click, captures nearly all the value with none of the irreversibility. Tentative holds are visible only to the user; invitations are not.
  • Never decline, cancel, or move an event with external attendees autonomously. Declining is the action users most regret delegating, because the social cost lands entirely outside the system that took it.
  • Batch the review, not the actions. One digest the user clears in ninety seconds beats eleven interruptions, and it keeps review cost — the metric that actually decides whether an agent is worth having (designing for review) — under the value the agent creates.

Show the diff, not the intention. "Reply to Dana, accept Thursday 3pm" is a summary the user will approve without reading. The rendered message, the exact recipient list, and the exact calendar delta are what make approval mean something — and rendering the real artifact is also how a user notices that the draft contains a sentence they never would have written, which is your last line of defense against a corrupted draft body.

STEP 5

Your user's archive is a labelled eval set already.

Teams evaluate inbox agents on draft quality with an LLM judge, because prose is what they look at. That measures the least dangerous component. The failures that lose users are decisions: the one genuinely urgent message classified fyi, a reply landing on the wrong thread, a recipient list that gained someone, and compliance with an instruction embedded in a message body.

This domain has an unusual gift for building that eval set: the user's own mail archive is large, personal, and pre-labelled by their behaviour. What they replied to is ground truth for "needed a reply." How fast they replied is ground truth for urgency. What they archived unread is ground truth for noise. You can assemble thousands of labelled cases per user without an annotation project — and the labels are that user's actual preferences rather than a generic rubric, which matters because triage is irreducibly personal (see evaluating agents).

Score it asymmetrically, because the costs are asymmetric. A false negative on an urgent message is the failure that gets the product uninstalled; a false positive that surfaces one extra email costs five seconds. Weight them accordingly instead of reporting a symmetric accuracy number that hides the only error anyone cares about.

Then run a standing red-team suite alongside it, because an injection failure is a security incident and not a quality regression. Seed a copy of the corpus with hostile messages — instructions in white-on-white text, in a quoted reply chain, in an attachment, in an ICS description field, in a mail header — and assert on tool calls, not on model text. The passing condition is that no unauthorized recipient was addressed, no external URL was fetched, and no data left the boundary; a model that eloquently explains it will not comply, while the harness records a request to attacker.tld, has failed (prompt injection in production).

STEP 6

Ship triage and drafts; earn the send.

The shipping order is not a compromise, it is where the value actually is. Triage plus draft-never-send is deployable now, has no irreversible action in it, and removes most of the labour — the user still decides everything, but decides it in seconds instead of minutes. Every incremental grant beyond that should be paid for with evidence: an autonomous reply class opens only after that class has run in draft mode long enough to show a low edit rate, on that user's own mail, with the red-team suite green.

Two things to decide before launch rather than after. Retention: an inbox agent's traces contain the full text of other people's mail, which makes your observability store a copy of the mailbox with different access controls — usually the most sensitive artifact in the system (data governance for agents). And scope: the third party who emailed your user never consented to their message being processed by a model, which is a real constraint in some jurisdictions and a reasonable expectation everywhere.

Build the reader with no network access and no send tool, and keep it that way permanently — not as a phase-one restriction you relax when the model gets better. Model quality is not the variable that governs injection; the attacker writes new text every time, and the only durable property is that the component reading their text has nothing worth capturing. Every capability you hand the reader converts an injection from an annoying draft into an incident, and no amount of prompt hardening buys that capability back safely.
