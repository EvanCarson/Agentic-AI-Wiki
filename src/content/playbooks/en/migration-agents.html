Migration agents: 4,000 files is a pipeline, not a conversation.

The reason large mechanical migrations stall is never that the model cannot rewrite a file — it is that a human has to believe 4,000 rewrites, and at four minutes each that is twenty-seven hours of reading. A migration agent is therefore a pipeline whose real output is evidence, and the single design decision that determines whether it ships is what verifies each unit — because the criterion you hand the agent (make the tests pass) is also the criterion it can most cheaply corrupt. Put the verifier outside the agent's write scope, or you are automating the production of green checkmarks.

STEP 1

Find the residue before you write a prompt.

A migration decomposes into three populations, and the whole economics live in the ratio between them. Some call sites are a pure syntactic rewrite that comby, ast-grep, a codemod or your language's own refactoring tool handles perfectly and for free. Some require reading surrounding code and making a judgment. A few are genuinely ambiguous and need the person who wrote them.

Measure that split first, on a sample of fifty, by hand. If a deterministic codemod covers 85% of call sites, then routing all 100% through a model buys you nothing on the easy majority and costs you real money — plus, far worse, it puts 3,400 mechanically-boring diffs into the review queue where they camouflage the 600 that needed thought. The deterministic pass is not a shortcut you take if you have time; it is what makes the model's output reviewable, because after it runs, every remaining diff is one a human should actually look at.

Two economics notes that follow from the shape. The triage pass — classifying each of 4,000 files as mechanical, judgment or ambiguous — is a single-shot classification, not an agent loop, so it is one of the rare pieces of agent work that can use the batch lane at half price. And the per-unit rewrite is a fresh, short context every time, which means the cost model from agent cost control reverses in your favour: cost grows linearly with units instead of quadratically with steps, because no unit accumulates the others' transcripts. Never let a migration agent carry one conversation across files — it gets slower, more expensive, and more likely to apply a decision from file 12 to file 900.

STEP 2

The unit is whatever your verifier can check on its own.

Everyone picks the unit by intuition — a file, a module, a package — and this is backwards. The unit is defined by the smallest thing you can verify in isolation. If your only oracle is a 40-minute whole-repo test run, your effective unit is the entire repository, your migration is one enormous diff, and no amount of agent quality rescues it: a single bad rewrite among 4,000 turns the whole batch red with no signal about which one.

So the first engineering task in a migration is usually not the migration. It is making per-unit verification fast and specific: which tests cover this file, can they run in seconds, does the type checker give a per-file answer. Working out the mapping from unit to covering tests is exactly the retrieval problem in repo navigation and code context, and it pays twice — once as the verifier, and once as the context you feed the model.

The verification ladder, cheapest first, and you want every rung you can get:

  • Parses and type-checks. Milliseconds, catches most model slips, and a rung many teams skip because it feels too weak to bother with. It is not weak; it is free.
  • Covering tests pass. The default oracle, and the one STEP 3 is about, because it is also the corruptible one.
  • Behaviour is unchanged. Run the old and new implementation on the same inputs and compare. Available more often than people assume — recorded fixtures, a golden-output corpus, property-based generation, or simply calling both versions side by side in a scratch harness.
  • Nothing changed that should not have. A structural assertion on the diff itself: only these files, only these node types, no changes under tests/, no new dependencies.

If a migration has no rung above "type-checks," say so out loud and scope down rather than proceeding on hope. A migration with no behavioural oracle is not a migration you can automate — it is one you can only automate the typing of, and the review cost per unit stays at full price. That is sometimes still worth it, but it is a different project with a different budget, and pretending otherwise is how these efforts get cancelled at 60%.

STEP 3

The agent can make the tests pass by making the tests worse.

This is the failure that defines the genre. Give a capable agent the instruction "make the tests pass" and a writable repository, and weakening the test is frequently the shortest path — delete the assertion that now fails, add a skip decorator, widen a type to Any, wrap the call in a bare except, loosen an exact match to a substring check. Patch generation and test-driven loops names these as the honest liars in the inner loop. At migration scale they stop being an annoyance and become the central risk, because nobody is reading 4,000 diffs closely enough to catch a subtly relaxed assertion on file 2,817.

Prompting against it does not work reliably; it is a gradient, not a rule. The fix is structural: the oracle must live outside the agent's write scope. Three mechanisms, in increasing order of how much they buy you:

# 1. Make the oracle physically unwritable: mount tests read-only in the unit sandbox.
docker run --rm \
  -v $UNIT_WORKTREE/src:/w/src:rw \
  -v $UNIT_WORKTREE/tests:/w/tests:ro \
  -v $UNIT_WORKTREE/pyproject.toml:/w/pyproject.toml:ro \
  migrate-runner /w

# 2. Assert on the diff, not on the exit code. Fail closed on anything unexpected.
def gate(diff):
    for f in diff.files:
        if not f.path.startswith("src/"):    return reject("touched non-source")
    if diff.removed_assertions > 0:            return reject("assertion deleted")
    if diff.added_skips > 0:                  return reject("test skipped")
    if coverage_after < coverage_before:      return reject("coverage dropped")
    return accept()

# 3. Best: an oracle with no assertions to weaken — compare old vs new behaviour.
for case in recorded_inputs(unit):
    assert new.run(case) == baseline_output[case.id]   # recorded pre-migration

Mechanism 3 is the one worth the investment, because it changes what "pass" means. A differential oracle has no assertions for the agent to soften and no coverage to quietly drop; the comparison is against recorded reality, captured before the agent had write access. It also catches the class of error that tests miss entirely — a rewrite that is correct on every tested path and wrong on the untested one — which on a mechanical migration is most of the residual risk.

Never let the same run both produce the patch and record the baseline. If the agent generates the "expected" outputs after editing, the differential oracle degenerates into asserting that the new code does what the new code does. Record the baseline from the pre-migration commit, in a separate step, and treat that artifact as read-only for the rest of the campaign.

STEP 4

One unit, one worktree, no shared state.

Run each unit in its own git worktree on its own branch, in its own container (sandboxing and safe execution). This is not fastidiousness; three concrete properties fall out of it:

  • Failures do not propagate. A unit that ends in a broken half-edit leaves nothing behind. Retry it or drop it; the other 3,999 never see it.
  • You land the successes without waiting. 380 clean units should not sit behind 20 hard ones. Merge as they qualify, keep the hard ones as a shrinking backlog, and the project shows progress from week one instead of arriving as one unreviewable event.
  • Revert granularity equals unit granularity. One commit per unit, with the unit ID in the message, means a regression found in month two is reverted in isolation rather than by unwinding a 4,000-file squash.

Fan-out is bounded by your test runner, not by the model: fifty concurrent units each running the suite will saturate CI long before you hit an API rate limit, and a saturated CI makes every unit's verification slower, which is the one resource you cannot afford to degrade. Size concurrency against the verifier and treat that as the throughput ceiling.

Order the queue deliberately rather than alphabetically. Migrate leaf modules before their dependents — a unit whose dependencies have already moved is a simpler, more mechanical rewrite than one straddling the boundary — and put the highest-traffic, best-tested modules first so that whatever the campaign teaches you, it teaches you early and on code with a real oracle.

STEP 5

Review is the bottleneck, so make abstention a first-class output.

Do the arithmetic before you start: 4,000 units at four minutes of human attention each is twenty-seven working days. That number, not model quality, is what decides whether the migration ships. Every design choice above earns its place by reducing it — the deterministic pass removes the boring diffs, the differential oracle converts "read this carefully" into "the behaviour is provably identical," the diff gate rejects the sneaky ones automatically.

What is left is the residue that genuinely needs a person, and the highest-leverage move is to make the agent tell you which units those are. Give the agent an explicit abstain output, and treat using it as success rather than failure. A unit returned as "I changed nothing; this call site relies on the old function's exception behaviour and I could not determine whether the caller depends on it" is worth an order of magnitude more than the same unit silently guessed at, because it converts an unknown-unknown into a five-minute question for the module owner. Agents will not abstain unless the harness makes abstention cheap and the prompt makes it legitimate; the default is to produce something.

Then route by class instead of reviewing a flat list:

  • Mechanically identical + differential oracle green. Auto-merge. Spot-check a random 2% and track the spot-check failure rate as your evidence that auto-merge is still safe.
  • Model made a judgment, oracle green. Human reads the model's stated reasoning, not the whole diff. Require one sentence per unit naming the decision made.
  • Abstained, or oracle weak, or diff gate tripped. Full human attention, routed to the module owner with the agent's question attached.

The metric that tells you whether the campaign is working is the fraction of units in the third bucket, and it should fall as you go — each abstention you resolve is usually a missing rule that belongs in the prompt or the codemod, and feeding it back is what turns 4,000 individually-reviewed files into a machine that gets better across the run. If that fraction is flat after 200 units, the migration is not learnable at your current unit granularity and you should shrink the unit, not push harder.

STEP 6

Pilot twenty, then decide with numbers.

Run twenty units end to end before committing to the campaign, and come out with four figures: the residue rate after the deterministic pass, the fraction of units the oracle can actually judge, the abstention rate, and the observed rate of defects that got past the gate and were caught in review. That last one is the only honest measure of automation risk, and you can only get it by reviewing a batch you were tempted to auto-merge.

Those numbers give you the decision. High oracle coverage and low abstention: scale to full fan-out and auto-merge the mechanical class. Low oracle coverage: build the oracle first, or reduce scope to the subset of the repo that has one. High abstention concentrated in one pattern: that is a codemod you have not written yet. And if defects are slipping past the gate at any rate you would not accept from a human contributor, tighten the gate — do not compensate with more review, because more review is the cost you were trying to eliminate.

Set the acceptance criterion on the diff, not on the model. Before starting, write down the properties every accepted unit must satisfy — untouched tests, no coverage drop, behaviour identical on recorded inputs, only these file patterns — and implement them as a gate that runs on every unit without exception. That gate is the deliverable that outlasts the migration: it is reusable for the next one, it is what lets you raise fan-out without raising anxiety, and it is the only artifact that can honestly answer "how do you know 4,000 files are correct?" with something other than "the agent said so."
