H28
Playbook · Agent UX & Human Interaction

A fleet's output is not code, it is interrupts — and the agent count is the dial that sets the arrival rate.

Run eight agents instead of one and you have not multiplied your throughput by eight; you have multiplied the rate at which something demands your attention, and review capacity did not move. The design that scales is the one where agents queue for attention instead of competing for it: output lands in a queue the human drains on their own schedule, triage is deliberately cheaper than attaching, and the fleet size is capped at a number you derived rather than one your plan allows.

STEP 1

Work out the review ceiling before you raise the agent count.

This is already happening at scale, so the arithmetic is not hypothetical. GitHub's Octoverse 2026 report, covering the year to 30 September 2026, found that more than 40% of pull requests on GitHub started with an agent's first draft by September 2026, up from 17% in March — 110 million in that month alone, roughly six times March's volume. GitHub notes the figure is a floor, since not all agent use is detected. On GitHub's own account, more than one in five code reviews now involve an agent, and agent pull requests are already saturating review bandwidth.

Now do it for one reviewer and one fleet. The honest decision cost is the part people skip, so pick it deliberately: reading a diff, checking the tests it touched, and deciding takes four minutes for a change you did not write.

# what a fleet actually delivers into one reviewer's hour
attention_per_hour   = 2400 s          # 40 of 60 minutes, being generous
seconds_per_review   =  240 s          # diff + tests + decide, not yours to begin with
review_ceiling       = 2400 / 240      # = 10 completed units per reviewer-hour

agents               =    8
task_minutes         =   25            # per agent, per completed task
arrival_rate         = 8 * 60 / 25     # = 19.2 units per hour

# arrival is ~2x the ceiling, so the queue grows 9.2/hour
# after one 8-hour day: 74 units deep, and nothing alarmed
# the reviewer does not stall — they reprice:
actual_seconds_each  = 2400 / 19.2     # = 125 s, half of what the decision costs

Read the last line, because it is the failure mode. An approval queue has no backpressure: when arrivals exceed capacity nothing blocks and nothing warns, the reviewer silently halves the time they spend per item, and your review quality becomes a function of your agent count. That is the oversight capacity argument, and what a fleet adds is new and worse — the arrival rate used to be set by your users and is now set by a number you typed.

Three things are genuinely unmeasured as of November 2026, and you should not let a vendor imply otherwise: there is no published study of how many minutes a human spends reviewing an agent-produced change, none of how review time scales with the number of concurrent agents, and nothing on merge-queue behaviour under many-agent load. Pick your own seconds_per_review by timing ten of them. It will be the most useful number on your dashboard.

STEP 2

Put the output in a queue, and separate "ready" from "blocked".

The single highest-leverage choice is that a finished agent should not ask for anything. It should leave its work somewhere a human will find it. Claude Code's background sessions do exactly this: a session that isolated its work in a worktree commits, pushes its own branch — never main — and opens a draft pull request when it finishes rather than asking first. GitHub's cloud coding agent reaches the same shape by constraint, with one branch and one pull request per task.

Then split the queue by what it demands of you, because "finished" and "stuck" need different responses. Claude Code's Projects overview is the most developed published taxonomy: six groups — Ready for review, Waiting on you, Working, Landing, Idle, Resolved — where Ready for review is a queue you drain and Waiting on you is a blocker you must clear. Threads auto-resolve after a week with no activity, which is the right default for a surface that would otherwise accumulate forever.

Notification defaults carry the same logic and are worth copying literally. In Claude Code Projects a notification fires when a thread needs input, errors, or Claude posts — and per-turn completion notifications are off by default and must be opted into. In the terminal, scheduled sessions such as /loop runs notify only when they need input, never on completion. A fleet that pings on every finish trains you to ignore pings; one that pings only on blockers keeps the channel meaningful. Notifications and digests has the message design; async agent UX has the re-entry problem this creates.

STEP 3

Make triage structurally cheaper than attaching.

With one agent you read the transcript. With twelve you cannot, so the fleet needs a surface whose whole purpose is to be cheaper than the real thing. Claude Code's agent view is a worked example of all three parts.

  • A summary line, written on a throttle. While a session works, its row text updates at most once every fifteen seconds from the session's own recent output without sending a model request, and a model writes a fresh summary when each turn ends. Legibility at fleet scale cannot cost a model call per row per second, and this is how you get it for nearly nothing.
  • Peek before you attach. Pressing Space opens a panel showing the session's most recent output, or the question it is waiting on, rather than the full transcript — and you can reply from there without leaving. Arrow keys peek at adjacent sessions. This is the primitive that keeps triage O(1) per agent instead of O(transcript).
  • Deliberately coarse counters. The footer shows how many sessions wait on you and how many are done, refreshing about every ten seconds, and above ninety-nine it just shows 99+. A precise count of an unmanageable number is not information; the ceiling is an honest design decision.

And know what cannot be batched. In Claude Code, a permission prompt or dialog cannot be answered from the peek panel — you have to attach. In Projects, an approval lives inside its thread and telling Claude in the project conversation does not reach it. Resist building the approve-all button for this class: Antigravity's Shift+A batch-approve works because it approves artifacts — plans, walkthroughs, screenshots — not privilege grants, and its comments are absorbed mid-run without stopping the agent. Batch the review; never batch the permission. Approval and confirmation UX is why.

STEP 4

Isolate per agent, then find out what isolation does not cover.

Worktree-per-agent is the settled answer and appears in every serious implementation. In Claude Code a dispatched background session moves into its own worktree under .claude/worktrees/<name>/ on branch worktree-<name>, so parallel sessions read the same checkout and each writes to its own. It is enforced rather than conventional: edits targeting the main checkout are blocked, commands whose working directory resolves into it are blocked, git redirected via git -C, --git-dir or GIT_DIR is blocked, and a last check you cannot turn off refuses commands it cannot verify.

The documented hole is the instructive part: none of those checks tracks which files a shell command writes, so a cp or a shell redirect into the main checkout is not refused. That is the general lesson — isolation covers the tool surface, and your agents have a shell.

Two consequences for fleet design. First, there is a real operational tax: each worktree is a fresh checkout needing its own dependency install, gitignored files like .env must be carried in deliberately, a running agent holds a lock so cleanup cannot remove its tree, and a sweep that removes old worktrees must refuse any holding uncommitted or unpushed work. Budget the disk and the install time before you raise the agent count.

Second, and less obvious, isolation does not prevent integration failure. A 2026 study of agent pull requests (arXiv:2607.04697) replayed three-way merges over co-active pull-request pairs and found textual conflicts in 41.7% of cross-agent pairs, markedly more than within a single agent. Co-activity is the norm — 40.2% of repositories had co-active agent pull-request pairs, accounting for 79.4% of all agent-generated pull requests — while cross-agent pairs were only 0.5% of them. So the expensive configuration is the rare one, and it is the one a growing fleet drifts into: mixing agent brands on one repository roughly doubles your conflict rate. Beyond conflicts, each agent can succeed in isolation and still break the whole — one renames a function while another calls the old name — which no worktree catches. Parallel writes and silent merges covers that class; merge queues is the control.

STEP 5

Both of you pay a switching tax, so run tasks to completion.

The reason to prefer a deep queue of finished work over a wide spread of half-finished work is that interleaving is charged twice.

On the human side, Gloria Mark's shadowing study — 36 managers, analysts, developers and engineers observed over three days — found that 81.9% of interrupted work was resumed the same day, on average after 23 minutes and 15 seconds. That figure is widely misquoted as "time to regain focus"; it is the time to return to the task at all, which for fleet design is the more useful quantity, because every attach-and-detach cycle pays it.

On the agent side there is now a measurement too. Switch-SWE (arXiv:2611.02017, November 2026) evaluated seven agent configurations across nineteen Python repositories and found an average 11.5-percentage-point drop in resolution rate under within-repository task switching, with a per-agent range of 6.0 to 15.0 points, concluding that code persistence alone does not ensure reliable resumption. So "just let the agent remember" does not rescue interleaving; the agent is worse at coming back too.

The design conclusions follow directly. Size the fan-out to the review ceiling from STEP 1, not to your plan's concurrency cap. Approve the fan-out plan before it runs rather than after — Devin proposes its child sessions for human approval before launching a batch, which is a cheap way to catch the twelve-agent impulse while it is still one decision. And bound it, because unbounded fan-out is a documented failure mode: Anthropic's own multi-agent research system used roughly fifteen times the tokens of chat, and early versions sometimes spawned fifty subagents for simple queries. Claude Code's own guidance is to have the agent propose threads before starting them and run a few at a time, dropping the limit once threads come back the way you wanted — which is progressive autonomy applied to a count rather than a capability. The fan-out tax has the cost model.

STEP 6

Cap the fleet in code, and measure the three numbers nobody publishes.

A cap is the one control that cannot be eroded by enthusiasm, and the vendors with the clearest position publish theirs. GitHub's Copilot CLI caps concurrent subagents by plan — 2 on Free, 4 on Pro, 8 on Max, 16 on Business, 32 on Enterprise — and rejects new subagent requests outright when the limit is reached rather than queueing them invisibly. Its cloud coding agent adds structural bounds: one branch, one pull request per task, and a 59-minute maximum execution time that cannot be extended or bypassed. Cursor's cloud agents cap simultaneous runs by plan, and shipped a bug worth learning from, where completed agents still counted against the cap — a limit that leaks is worse than no limit, because you cannot reason about it.

Then instrument the three things the literature does not give you:

  • Seconds per review, measured not assumed. Time ten agent-authored changes end to end. This sets your ceiling and every other decision on this page.
  • Queue depth and its slope. Depth alone arrives late; the slope tells you the fleet is outrunning review while you can still turn agents off. Alert on the derivative, exactly as you would for spend.
  • Accepted-and-wrong rate. The share of merged agent changes later reverted, hotfixed or implicated in an incident. Acceptance rate alone rewards a persuasive agent; this is the number that prices the review you are buying. Octoverse's finding that agent-involved pull requests merged within two weeks rose from 83% in February to 90% by September 2026 — against about 86% for pull requests without detected agent involvement — says agent work merges faster, which is only good news if you are tracking this.

One closing note on tooling, because it affects what you should build on. The standalone fleet-dashboard category is churning hard: Conductor, the best-known "run several coding agents side by side" app, was reported acquired by Meta on 4 November 2026, with Conductor Cloud going read-only on 13 November and shutting down on 20 November; Vibe Kanban announced it was sunsetting; Crystal was deprecated in February 2026. Meanwhile the first-party surfaces are in a hardening phase rather than a feature phase — Claude Code's thirteen releases in the three weeks to 23 November 2026 added no new multi-agent supervision features and instead stopped sessions from deleting a worktree another session was working in, and made worktree exit refuse while a background subagent might still be running. Build your fleet process on the queue, the cap and the three numbers, all of which you own; treat any particular dashboard as rented.

Do it in this order. Time ten reviews to get your real cost per unit, divide your available attention by it, and set the agent count from that quotient — not from your plan's cap. Make every finished agent open a draft pull request and ask for nothing. Split the queue into ready-to-review and blocked-on-you, and notify only on the second. Give yourself a peek surface cheaper than the transcript, batch artifact review, and never batch a permission. One worktree per agent, same agent brand per repository where you can, and a merge queue because isolation does not prevent integration failure. Run each task to completion rather than interleaving, since the human pays 23 minutes to come back and the agent pays about 11 points of resolution rate. Then watch queue slope and accepted-and-wrong. If you keep one sentence: adding an agent does not add throughput, it adds arrivals — and you are the server.
