中断是一个请求，恢复是一次重新执行，所以真正的活儿是「最后一次持久写入」到「叫停落点」之间的幂等性——不是那个停止按钮。

停止按钮是容易的那一半，而把它做出来，正是大多数团队宣布这项功能完工的地方。在它底下，一个 2026 年的智能体最可能依赖的那两套协议，都明白告诉你：取消可以被忽略，而恢复会重跑已经跑过的代码。这意味着一个实现正确的停止控制，仍然能把同一封邮件发两遍，而这个 bug 浮出水面的样子是：一个用户叫停了一次明显走错的运行，却照样被扣了钱。

STEP 1

取消是劝告性的，而规范就是这么一字一句写的。

MCP 的取消工具是一个通知——notifications/cancelled 点名一个请求 ID——而通知是「发出去就不管」的。规范明确写着接收方可以忽略它：如果请求 ID 未知、如果处理已经完成，或者如果这个请求根本无法被取消。它还直接写明了那个竞态：由于网络延迟，取消通知可能在处理结束之后、甚至在响应已经发出之后才抵达，而双方都必须优雅地处理这种情况。

所以一次叫停请求有三种可能的结局，而你的界面大概只在展示其中一种。工作停了。工作照样跑完，于是你丢掉一个「其效果早已发生」的结果。又或者工作正处在一个不提供停止的位置上，而那个通知就掉在地上了。2026-07-28 修订版把服务端这一侧收得更紧——服务端可以发 notifications/cancelled 来拆掉一条 subscriptions/listen 流，且不得为任何其他目的发送它——这值得当作一个行进方向来读：取消正在被收窄为一个传输层信号，而不是被拓宽成一条控制通道。

设计上的指令是：别再把取消呈现为一个「会完成」的动词。一个停止控制应当把运行推入一个正在停止的状态，它可见、且与已停止有区别；而通往已停止的那次跃迁，应当由运行本身确认来驱动，并配一个会升级处理、而不是撒谎的超时。一个因为「通知已发出」就把转圈变成对勾的加载动画，是一个用户界面在断言协议并不保证的事。

这块地方有一个仍然存在的正确性 bug，如果你跑的是 Python SDK 就值得知道：issue #3807，截至 2026 年 11 月仍未关闭，报告称在途请求是以一个被强制转换过的请求 ID 为键的，于是一个点名请求 7 的取消，可能取消掉并发的请求 "7"。报告者的要点是一个普遍结论——任何比「ID 完全相等」更松的匹配规则，都能取消错的那份工作——而以带类型的 ID 为键的 TypeScript SDK 没有这个问题。

STEP 2

恢复会把那一步从头重跑，这是写在文档里的，而且照样让每个人意外。

LangGraph 的人在回路原语是 interrupt()，用 Command(resume=...) 恢复，而它自己的文档把语义写得很清楚：恢复时，运行时会把那个节点从头重启，而不是从调用 interrupt() 的那一行继续。文档自己的建议正是由此而来——让中断之前的任何操作保持幂等，或者把副作用挪到它之后，或者把它们放进单独的节点。

这句话请读两遍，因为它把「恢复」这个词装进你脑子里的心智模型给掀翻了。中断不是一次保留了调用栈的让出。它是一次「检查点加重放」，而你那个节点在抵达中断点之前做过的一切，都落在被重放的区间里。一个先写一条记录、再调一个 API、然后才请求审批的节点，会在人类点下批准时把那次写和那次 API 调用再做一遍。

这不是对文档的一种理论性读法。截至 2026 年 11 月，这个行为的边缘地带有一串未关闭的 issue：从一次工具错误恢复后副作用重复发生（#9185）；在子图里恢复两个并行中断中的一个，会重跑一个已经完成的兄弟节点（#9106）；子图里一个已完成的节点在恢复时重跑，其模型调用也重复了一次（#9276）；以及在 durability="exit" 之下，一个在兄弟节点失败时仍在运行的节点会把活儿干完、但它的写入不会被保存，于是恢复时又跑一遍（#9397）。另有一个文档 issue（#7074）主张文档把另一侧也说得太好了，因为放在中断之后的效果，若该节点随后失败并被重试，同样会重复。

可迁移的教训与框架无关。任何以「从检查点重放」来实现暂停的持久执行引擎都有这个性质，因为重放的含义就是如此——也就是持久状态与可恢复性里的那套纪律。中断不是你搭在一个循环之上的交互功能。它是一条关于「这个循环的每一步可以怎么写」的约束。

STEP 3

设计的单位是「最后一次持久写入」到「叫停落点」之间那一段。

把前两步并起来，你真正必须动手工程化的东西就具体了。对你的智能体可能被中断在其中的每一步，算出哪些副作用坐落在「它最后一次持久检查点」与「一次叫停能够落下的那个位置」之间。那一段里的一切都会跑两遍。

一个算过的例子。一个六步的客服智能体：取工单、查账户、起草回复、发出回复、更新 CRM 字段、关闭工单。用户在第 4 步在途时按下停止。如果第 1–3 步都已落检查点，而第 4 步是一个「先发出回复、再等审批」的节点，那么重放会把回复再发一遍——客户收到两条消息，而第二条抵达的时间，是在人类出手正是为了阻止这件事之后。解法不是一个更快的中断。解法是 post_reply 带上一个由工单与草稿摘要推导出来的幂等键，于是第二次执行是一次空操作，并返回第一次的结果。

# the replayed region is the design surface
def post_reply_node(state):
    # everything above interrupt() runs again on resume
    key = idem_key(state.ticket_id, digest(state.draft))
    sent = mail.send(state.draft, idempotency_key=key)   # safe to repeat

    approval = interrupt({"sent": sent.id, "ask": "close ticket?"})

    # and everything below can repeat too, if this node is retried
    return {"approved": approval}

由此掉出三条规则，而它们比看上去便宜，因为它们只作用于你刚刚圈出的那几段，而不是整个智能体：

  • 给每一次对外写入都配上一个由你生成的幂等键，从内容推导、而不是从一个计数器推导——幂等性与重试讲了具体形状。这是让重放语义变安全的那一项改动。
  • 把不可逆的动作单独放进它自己的一步里。一个只含一次不安全调用的步骤，其被重放的区间里只有一次不安全调用，而这已经是这个问题能缩到的最小尺寸。
  • 对那些无法做成幂等的动作设闸，而不是试图去中断它们——一笔退款、一次实物派送、一条发给没有去重机制的第三方的消息。闸门归属于那次调用之前，也就是审批与确认交互设计；而对这些动作而言，「可中断」的诚实版本是：叫停的窗口在调用之前就关上了，而不是在调用当中。
STEP 4

暂停、引导与中止是三个意图，而只有其中一个能普遍地安全实现。

把它们塌缩成一个停止按钮，会逼着用户要么做得过多、要么做得过少。暂停是冻结并保全，打算原样恢复。引导是停下、接受一处纠正，然后带着新约束与此前的进度一起恢复。中止是停下并丢弃。

中止是你能普遍实现的那一个，因为丢弃状态把对账问题整个拿掉了——你欠用户的只是一份关于「哪些副作用已经落地」的准确交代。暂停比看上去难：一次暂停住的运行握着租约、令牌与打开的事务，而它们各按自己的时刻表过期，所以一次没有最长时限的暂停，会在一个无法预测的时刻变成一次中止。给暂停设一个明确的上限，并告诉用户它是多少。

引导是价值最高、也最常缺失的那一个，因为用户通常并不想杀掉这次运行——他想推它一把。它同时也是与重放相处得最糟的那一个，因为一处纠正改变了被重放区间的输入：用户改过的那份草稿，不是当初那份用摘要充当幂等键的草稿。要刻意决定一次引导是让先前的副作用失效、还是在它们之上继续，并把这是哪一种展示给用户。能绕开这一切的廉价版本是：让引导无需停下就能触达，做成一个在下一个步骤边界上生效的「另外，做 X／别做 Y」输入框。大多数纠正并不需要一次停顿，而一处从未触发重放的纠正，也就无从重复任何东西。

STEP 5

交还才是智能体把人的修复撤销掉的地方，而状态是唯一的解药。

团队会设计智能体把一个难办的案子交给人，然后忘掉回程。一次干净的接管会把目标、已走过的步骤、当前状态——以及关键的——它为什么停下一并交出去，好让人不必把智能体早已知道的东西重新推一遍。一次干净的交还更难：智能体必须从人编辑过的状态恢复，而不是从它自己交接之前的记忆恢复。

这个 bug 有一个具体形状，而且是这整片地方最毁信任的那一个。人手工把记录修好；智能体从一个在修复之前拿的检查点恢复；它的计划里仍然有那次产出错值的写入；它执行了那次写入；修复消失了。用户亲眼看着系统撤销了自己的纠正，而他再也不会交还了。

这三种交互——中断、引导、交接——归结到同一个原语：一个能在控制权易手之后存活、并且能被当前持有者读写的任务状态对象。如果智能体的工作状态只住在一个不透明的上下文窗口里，这三者一个都不可能正确，因为人看不见自己要接管的是什么，而智能体看不见人改了什么。把目标、计划、进度、产物与未定决策外化到一个双方都读写的结构里，把当前由谁持有控制权做成对双方都显式可见的东西，并让智能体在每次恢复时的第一个动作是重读那份状态、并把它与自己的计划做差分，而不是接着往下跑。在人的编辑与一次被重放的写入确实撞车的地方，人的编辑胜出、那一步重新规划——而如果你的副作用已经落在了真实世界里、而不是落在你自己的存储里，那你就身处修补智能体的副作用，而那是一个比合并冲突糟糕得多的处境。

STEP 6

什么时候不该提供自由形式的任务中引导。

如果某一步正处在一次不可逆的对外动作的中途，正确的控制是「干净地完成或回滚这一步」，而不是「现在接受一处任意的纠正」。把一次未提交的对外动作引导走，对状态的破坏比根本不中断更严重。同理适用于这样一步：它被重放的区间里含有一次你没能做成幂等的写入——在那里提供一个叫停，就是在提供一次重复。

还有一条关于这整项功能的诚实限制。一个响应及时的中断要求智能体很快抵达一个安全的停靠点，这意味着步骤要短——但步骤短就意味着更多检查点、更多重放边界、更多次往返。可中断性是用延迟与令牌买来的，所以请把它买在用户真能看见一次运行走偏的地方：长的、可见的、多步的工作。对一次四秒的调用，诚实的控制是撤销，不是中断。

动界面之前先做这件事。列出你的智能体可能被中断在其中的每一步；对每一步，列出「它最后一次持久检查点」与「一次叫停最早能落下的位置」之间的每一次对外写入；然后给这些写入每一个都配上幂等键，并把你配不上键的那些挪进它们各自带闸的步骤里。那张清单才是你那个停止按钮的真正规格说明，而它同时也是一个你写得出来的测试：从同一个检查点恢复一次运行两遍，然后断言对外副作用只发生了一次。接着让界面说实话——正在停止是一个状态、已停止是一次确认，而停止时的那份状态快照应当说清哪些已经落地，好让用户从事实而不是从一片空白的暂停里，去选择引导、接管还是放弃。
