H28
实战手册 · 智能体体验与人机交互

一支智能体编队的产出不是代码，是打断——而智能体数量就是设定到达率的那个旋钮。

把一个智能体换成八个，你并没有把吞吐乘以八；你乘的是「有东西来要你注意」的那个频率，而审阅容量一点没动。真正能扩展的设计，是让智能体排队等你的注意力、而不是互相抢它：产出落进一条人按自己节奏去清的队列，分诊要刻意做得比真正进去看更便宜，而编队规模要卡在一个你算出来的数上，而不是你的套餐允许的那个数上。

STEP 1

在提高智能体数量之前，先把审阅上限算出来。

这件事已经在大规模发生了，所以这笔算术不是假想。GitHub 的 Octoverse 2026 报告（覆盖至 2026 年 9 月 30 日的一年）发现：到 2026 年 9 月，GitHub 上超过 40% 的 pull request 是以智能体的初稿开头的，而 3 月还是 17%——仅 9 月一个月就有 1.1 亿个，约为 3 月的六倍。GitHub 指出这个数字是个下限，因为并非所有智能体使用都被识别出来。按 GitHub 自己的说法，现在超过五分之一的代码审阅有智能体参与，而智能体的 pull request 已经在把审阅带宽占满。

现在把它算到一位审阅者和一支编队上。那个诚实的决策成本正是人们会跳过的部分，所以请刻意把它定下来：读一份 diff、检查它碰到的测试、再做决定，对一份不是你写的改动来说要四分钟。

# what a fleet actually delivers into one reviewer's hour
attention_per_hour   = 2400 s          # 40 of 60 minutes, being generous
seconds_per_review   =  240 s          # diff + tests + decide, not yours to begin with
review_ceiling       = 2400 / 240      # = 10 completed units per reviewer-hour

agents               =    8
task_minutes         =   25            # per agent, per completed task
arrival_rate         = 8 * 60 / 25     # = 19.2 units per hour

# arrival is ~2x the ceiling, so the queue grows 9.2/hour
# after one 8-hour day: 74 units deep, and nothing alarmed
# the reviewer does not stall — they reprice:
actual_seconds_each  = 2400 / 19.2     # = 125 s, half of what the decision costs

请读最后那一行，因为那就是失效模式。审批队列没有背压：当到达量超过容量时，什么都不会堵住、什么都不会报警，审阅者会悄悄把每一条上花的时间砍半，于是你的审阅质量变成了你智能体数量的函数。这就是监督容量那套论证；而编队新添的那部分既是新的、也是更糟的——到达率过去是由你的用户决定的，现在是由你敲进去的一个数决定的。

截至 2026 年 11 月，有三件事确实没有被测量过，你不该让任何厂商暗示相反：没有已发表研究测过人类审阅一份智能体产出的改动要花多少分钟，没有测过审阅时间如何随并发智能体数量变化，也没有关于多智能体负载下合并队列行为的研究。自己计时十份，定出你自己的 seconds_per_review。它会是你看板上最有用的那个数字。

STEP 2

把产出放进队列，并把「做好了」和「卡住了」分开。

杠杆最大的那一个选择是：一个干完活的智能体不该要求任何东西。它该把自己的成果留在一个人类会找到的地方。Claude Code 的后台会话正是这么做的：一个把工作隔离在 worktree 里的会话会提交、推送自己的分支——永远不是 main——并在完成时开一个草稿 pull request，而不是先来问你。GitHub 的云端 coding agent 用约束达到了同一个形状：每个任务一个分支、一个 pull request。

然后按「它要你做什么」把队列拆开，因为「做好了」和「卡住了」需要不同的反应。Claude Code 的 Projects 概览是目前已公开的最完整分类：六个分组——Ready for review（待审阅）、Waiting on you（等你）、Working（在做）、Landing（正在落地）、Idle（空闲）、Resolved（已了结）——其中「待审阅」是一条你去清的队列，而「等你」是一个你必须解掉的阻塞。线程在一周无活动后会自动了结，对一个否则会无限堆积的界面来说，这是对的默认值。

通知默认值体现了同一套逻辑，值得照字面搬。在 Claude Code Projects 里，通知会在线程需要输入、报错，或 Claude 在对话里发言时触发——而「每一轮完成」的通知默认是关的，必须主动打开。在终端里，像 /loop 这类按计划运行的会话只在需要输入时通知，完成时从不通知。一支每次干完都要戳你一下的编队，会训练你学会无视这些提示；一支只在阻塞时戳你的编队，能让这个通道保持有意义。通知与摘要讲消息怎么写；异步智能体体验讲这样做之后带来的「重新进入」问题。

STEP 3

从结构上让分诊比「进去看」更便宜。

只有一个智能体时，你会读完整的对话记录。有十二个时你读不完，所以编队需要一个「存在意义就是比真东西更便宜」的界面。Claude Code 的 agent view 把这三件事都做了一遍。

  • 一行摘要，带节流。会话工作期间，它那一行的文字最多每十五秒从该会话自己最近的输出更新一次，不发出任何模型请求；而每一轮结束时由模型写一条新摘要。编队规模下的可读性不能是「每行每秒一次模型调用」的代价，而这就是你几乎免费拿到它的办法。
  • 先窥视，再进去。按 Space 会打开一个面板，显示该会话最近的输出、或者它正在等的那个问题，而不是完整记录——而且你可以就在那里回复、不用离开。方向键可以窥视相邻会话。这就是让分诊对每个智能体保持 O(1)、而不是 O(对话长度) 的那个原语。
  • 刻意做粗的计数器。底部会显示有多少会话在等你、有多少已完成，约每十秒刷新一次，而超过九十九就只显示 99+。给一个已经管不过来的数字一个精确计数并不是信息；这个上限是一个诚实的设计决定。

也要知道什么是不能批量的。在 Claude Code 里，权限提示或对话框无法从窥视面板回答——你必须进去。在 Projects 里，一次审批住在它自己的线程里，在项目对话里跟 Claude 说「去吧」是传不到的。请抵住为这一类做「全部批准」按钮的冲动：Antigravity 的 Shift+A 批量批准之所以成立，是因为它批准的是产物——计划、走查、截图——而不是权限授予；而它的评论是在运行中被吸收的，不会让智能体停下。批量审阅，永不批量权限。审批与确认体验讲为什么。

STEP 4

按智能体隔离，然后去弄清隔离覆盖不到什么。

「一个智能体一个 worktree」是已经定下来的答案，并且出现在每一个认真的实现里。在 Claude Code 里，一个被派发的后台会话会移入自己的 worktree，位于 .claude/worktrees/<name>/、分支为 worktree-<name>，于是并行会话读同一个检出，各自写进自己那个。这是被强制执行的，而不是靠约定：指向主检出的编辑会被拦，工作目录解析进主检出的命令会被拦，通过 git -C、--git-dir 或 GIT_DIR 重定向的 git 会被拦，而最后一道你关不掉的检查会拒绝它无法核实的命令。

被写进文档的那个漏洞才是最有教益的部分：这些检查没有一个会追踪某条 shell 命令写了哪些文件，所以一个 cp 或一次重定向写进主检出，是不会被拒的。这就是那条通用的教训——隔离覆盖的是工具面，而你的智能体手里有一个 shell。

对编队设计有两个后果。第一，有一笔实实在在的运维开销：每个 worktree 都是一个全新检出，需要自己装一遍依赖；像 .env 这类被 gitignore 的文件必须刻意带进去；一个正在运行的智能体会持有锁，于是清理动作移不掉它那棵树；而一个清扫旧 worktree 的作业必须拒绝移除任何还留着未提交或未推送内容的那棵。在提高智能体数量之前，先把磁盘和装依赖的时间预算出来。

第二，也更不显然：隔离并不能防止集成失败。2026 年一项关于智能体 pull request 的研究（arXiv:2607.04697）对共同活跃的 PR 配对重放了三方合并，发现跨智能体配对中有 41.7% 出现文本冲突，明显高于同一个智能体内部。共同活跃是常态——40.2% 的仓库存在共同活跃的智能体 PR 配对，占到全部智能体生成 PR 的 79.4%——而跨智能体配对只占其中 0.5%。所以最贵的那种配置恰恰是罕见的那种，也正是一支不断变大的编队会漂移进去的那一种：在同一个仓库上混用不同品牌的智能体，大约会把你的冲突率翻一倍。除了冲突之外，每个智能体都可能各自在隔离中成功、而整体照样坏掉——一个把函数改了名，另一个还在调旧名字——这是任何 worktree 都抓不到的。并行写入与静默合并讲这一类；合并队列是对应的控制手段。

STEP 5

切换这笔税你们两边都要交，所以把任务一次做完。

宁要一条「已完成工作」的深队列、也不要一片「做了一半」的宽铺开，理由是：交错是要收两次费的。

在人这一侧，Gloria Mark 的跟班观察研究——36 位管理者、分析师、开发者与工程师，观察三天——发现81.9% 被打断的工作在当天被恢复，平均要过 23 分 15 秒。这个数字被广泛误引为「重新进入专注状态所需的时间」；它其实是重新回到那件事上所需的时间，而对编队设计来说这是更有用的那个量，因为每一次「进去再出来」的循环都要付它。

在智能体这一侧，现在也有测量了。Switch-SWE（arXiv:2611.02017，2026 年 11 月）在十九个 Python 仓库上评测了七种智能体配置，发现在同仓库内任务切换的情况下解决率平均下降 11.5 个百分点，各智能体的区间为 6.0 到 15.0 个百分点，并得出结论：仅靠代码留存并不能保证可靠的恢复。所以「让智能体自己记着就行」救不了交错；智能体在「回来」这件事上也更差。

设计结论直接就出来了。按 STEP 1 的审阅上限来定扇出规模，而不是按你套餐的并发上限。在扇出跑起来之前批准那个计划、而不是之后——Devin 会在启动一批之前把它的子会话提交给人类批准，这是一种便宜的办法，能在「十二个智能体一起上」的冲动还只是一个决定的时候就把它拦住。并且要设界，因为无约束扇出是一个有记录的失效模式：Anthropic 自己的多智能体研究系统用掉了大约聊天场景十五倍的 token，而早期版本有时会为一个简单查询生出五十个子智能体。Claude Code 自己的建议是：让智能体先提出线程再开始，一次只跑几个，等几个线程按你想要的样子回来之后再把限制放开——这就是把渐进式自主用在了一个数量上、而不是一项能力上。扇出税有对应的成本模型。

STEP 6

把编队上限写进代码，并去测那三个没人公布的数字。

上限是唯一一个不会被热情侵蚀的控制，而立场最清楚的那些厂商都把自己的公布了出来。GitHub 的 Copilot CLI 按套餐限制并发子智能体——Free 2 个、Pro 4 个、Max 8 个、Business 16 个、Enterprise 32 个——并且在到达上限时直接拒绝新的子智能体请求，而不是悄悄排队。它的云端 coding agent 还加了结构性边界：每个任务一个分支、一个 pull request，以及一个不可延长、不可绕过的 59 分钟执行上限。Cursor 的云端智能体按套餐限制同时运行数，并且曾出过一个值得学习的 bug——已完成的智能体仍然占着名额；一个会漏的上限比没有上限更糟，因为你没法对它做推理。

然后去把文献不会给你的那三件事装上仪表：

  • 每次审阅的秒数，要测出来而不是假设出来。给十份智能体撰写的改动完整计时。它定下你的上限，以及本页其余的每一个决定。
  • 队列深度，以及它的斜率。只看深度来得太晚；斜率会在你还能把智能体关掉的时候，告诉你编队已经跑在审阅前面了。请对导数报警，就像你对花费那样做。
  • 「采纳了但是错的」比率。已合并的智能体改动中，后来被回滚、被热修，或在某次事故中被牵连的占比。只看采纳率是在奖励一个有说服力的智能体；而这个数字才给你买到的那份审阅定价。Octoverse 发现有智能体参与的 pull request 在两周内合并的比例，从 2 月的 83% 升到了 2026 年 9 月的 90%——而未检出智能体参与的 PR 约为 86%——这说明智能体的工作合并得更快，而这只有在你盯着上面这个数字时才算好消息。

最后关于工具的一句话，因为它影响你该把东西建在什么之上。独立的「编队看板」这个品类正在剧烈洗牌：Conductor，也就是最知名的那个「把几个编码智能体并排跑起来」的应用，据报道于 2026 年 11 月 4 日被 Meta 收购，Conductor Cloud 在 11 月 13 日转为只读、11 月 20 日关停；Vibe Kanban 宣布正在日落；Crystal 已于 2026 年 2 月弃用。与此同时，第一方界面处在加固期而不是功能期——Claude Code 在至 2026 年 11 月 23 日的三周里发了十三个版本，没有新增任何多智能体监督功能，而是去阻止一个会话删掉另一个会话正在用的 worktree，并让退出 worktree 在某个后台子智能体可能仍在运行时拒绝执行。请把你的编队流程建在队列、上限和那三个数字上——这些都归你所有；而把任何一块具体的看板当成租来的。

按这个顺序做。给十份审阅计时，拿到你真实的单位成本，用你可用的注意力除以它，并按这个商去定智能体数量——不是按你套餐的上限。让每个干完活的智能体都开一个草稿 pull request，并且什么都不要求。把队列拆成「待审阅」和「卡在你这里」，只对后者发通知。给自己一个比完整记录更便宜的窥视界面，批量做产物审阅，永不批量批准权限。一个智能体一个 worktree，能做到的话一个仓库只用同一个品牌的智能体，并且要有合并队列，因为隔离防不住集成失败。把每个任务一次做完、不要交错，因为人回来一次要 23 分钟，而智能体要付出大约 11 个百分点的解决率。然后盯住队列斜率和「采纳了但是错的」。如果只留一句话：多加一个智能体不会多出吞吐，只会多出到达量——而你就是那台服务器。
