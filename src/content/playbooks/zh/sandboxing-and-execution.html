沙箱边界几乎从不失守——失守的是这个盒子透过边界还能够得着的一切。

Firecracker 头两份公开漏洞公告都落在 2026 年，而两份都不是你的威胁模型围着建起来的那种内核逃逸：一份是在一个需要显式开启的 PCI 传输上、由 guest root 把 VMM 打崩，另一份在动手之前先得有宿主机某个目录的写权限。这一年里唯一一次被确认的 guest 到宿主机 root 逃逸，位置在每一家沙箱厂商的下面——在 KVM 里，任何采购决定都碰不到那儿。所以别再比谁的隔离更强，去审计可达性：磁盘上的凭据、元数据端点、挂进来的 socket、你的智能体能往里写的那个被放行的主机名——因为这份清单才是你能控制的部分，也才是真正会被用到的部分。

STEP 1

在挑边界之前，先把 2026 年的 CVE 记录读一遍。

Firecracker 是 E2B、Vercel Sandbox 以及一长串智能体平台底下那台 microVM 监视器，它多年来没有一份公开的 hypervisor 逃逸 CVE。2026 年的两份公告终结了这个记录，而这两份都值得细读——因为它们写了什么与它们被怎么报道之间的落差，就是本页的全部教训。

CVE-2026-5747（AWS 公告 2026-015，CVSS 4.0 评分 8.7，High）影响 Firecracker 1.13.0–1.14.3 与 1.15.0。拥有 root 的 guest 可以在设备被激活之后改写 virtio 队列配置寄存器，而公告写明的可能后果是让 VMM 进程崩溃。要在宿主机上执行代码，还需要额外条件——自定义的 guest 内核、特定的快照配置。修复版本为 1.14.4 与 1.15.1，而它所滥用的那条传输是需要显式开启、并非默认启用的。CVE-2026-1386（公告 2026-003，CVSS 3.1 评分 6.0）是 jailer 里一个跟随符号链接的缺陷，影响 1.13.1 及更早版本以及 1.14.0：一个宿主机本地用户，若已经拥有那些预先创建好的 jailer 目录的写权限，就能在启动过程中覆写宿主机上任意文件，前提是 jailer 以 root 身份运行。修复版本为 1.13.2 与 1.14.1；AWS 自己给出的缓解措施是对 jailer 目录执行 chmod 700。

两者都不是「一个 guest 逃出了 microVM」。一个是在你大概没开启的功能上的拒绝服务；另一个是宿主机一侧的文件系统缺陷，而且要求先在宿主机上有落脚点。它们是真实的，你该打补丁；它们同时也是证据，说明这道边界大致如宣传所言地守住了。那些把它们归档成「Firecracker 的首批逃逸 CVE」的评论，把两件不同的事压成了一个标题——一份正确的补丁说明就是这样变成一个错误的威胁模型的。

补丁卫生是便宜的那一半：钉住一个 Firecracker 版本、订阅 AWS 的安全公告、搞清楚你是否带着 --enable-pci 在跑。如果你买的是托管沙箱，你继承的就变成了厂商的补丁节奏，而这是一项值得写进合同里去问清楚的依赖——见第三方模型与厂商风险；而当隔离不再是决定性的那一栏之后，各家托管方案的差别何在，见那篇四方对比。

STEP 2

2026 年唯一一次真正的逃逸，不是靠换厂商能修掉的。

2026 年 10 月 3 日，一位研究者通过 Vercel Sandbox 的 HackerOne 项目报告了一次 guest 到宿主机 root 的逃逸。Vercel 按该项目 5 万美元的上限付了赏金、将其定级为 Critical，其 CEO 把它描述为 KVM 层面的零日漏洞而非配置失误。截至 2026 年 10 月下旬，没有公开的 CVE、没有补丁说明、也没有技术复盘；只有一个二手来源给它挂了一个 CVE 编号，而那个编号查不到，所以应当把机制视作尚未披露。

有战略含量的地方在于这个缺陷住在哪里。Vercel Sandbox 把 Firecracker microVM 跑在 KVM 上。KVM 层的缺陷在产品之下、在 microVM 监视器之下，也在你对那些「都在同样的云上租同一套 hypervisor」的厂商所做的任何取舍之下。你买不出去。你只能把系统建成「跨过这道边界也活得下来」的样子——这正是爆炸半径的全部论点。

那个项目还有一个细节值得照抄：Vercel 的赏金范围明文宣布 Firecracker microVM 就是那道安全边界，并把停留在 guest 内部的容器命名空间逃逸排除在范围之外。这是一家厂商公开说明它愿意付钱去守哪一堵墙。去问你自己的供应商同一个问题，答案通常在赏金范围里而不在营销页面上；而如果沙箱是你自己跑的，就把那句话给你自己的系统写下来——没人点名过的边界，就是没人负责的边界。

STEP 3

从盒子内部审计可达性，而不是在白板上审计架构。

隔离依然是分层的——进程外面是 microVM 或 gVisor 式的内核边界（隔离模式那篇作了比较），网络外面是默认拒绝的出站策略，再加上一个临时的、限定作用域的文件系统，以及没有任何环境自带身份——但团队搞错的那一层是最后一层，而唯一诚实的检查办法，是在智能体真正会拿到的那个沙箱里把探针跑一遍。不是参考镜像：是你的编排器实际启动的那一个，带着你的 entrypoint 和你的挂载。

# run this AS the agent, in the sandbox the agent gets
env | grep -iE 'token|secret|key|password'   # expect: no output
ls /var/run/docker.sock /run/containerd 2>&1 # expect: No such file
curl -s --max-time 2 http://169.254.169.254/  # expect: timeout, not a document
cat ~/.aws/credentials ~/.netrc 2>&1          # expect: No such file
git config --get remote.origin.url            # expect: a read-only mirror, not a push URL
curl -s --max-time 2 https://example.com/     # expect: blocked by egress policy

# then the write side, which teams forget to test at all:
curl -s -X POST --max-time 2 https://<an-allowed-host>/ # expect: blocked

这七行里有六行是大家熟悉的清单。第七行才是本页围着建起来的那一行；而把凭据送进沙箱是配套的那一篇，讲的是在一个仍然得克隆仓库、推送分支的系统里，第一行要怎样才能保持为空。

挂进来的容器 socket 不是一道弱边界，而是没有边界：/var/run/docker.sock 在设计上就等于宿主机上的 root；而 runc 那一类泄漏文件描述符的容器逃逸（部署面最广的例子是 CVE-2024-21626），正是「它在容器里」这句话从来不足以单独构成一句安全论断的原因。

STEP 4

算例：那项并不像你以为的那样起作用的元数据加固。

经典的智能体沙箱突破不是 hypervisor 缺陷，而是一个可达的云元数据端点把实例角色发了出来。AWS 的答案是 IMDSv2——用 PUT 取得一个会话令牌，每个请求都必须带上它——再加上一个响应跳数上限，于是返回途中多跨了一跳的包会被丢掉。把跳数上限设为 1，桥接网络上的容器就到不了 169.254.169.254，因为那座桥就是多出来的那一跳。这就是大多数团队脑子里装着的模型，而它同时在两个地方不完整。

第一，默认值变了。AWS 当前的文档写明：启动时若未给出偏好，当 AMI 带有 ImdsSupport: v2.0 时跳数上限默认为 2，否则为 1。Amazon Linux 2023 把原因说得很直接：它强制要求 IMDSv2，并把跳数上限设为 2，以便支持容器化工作负载。那个更新、更加固的 AMI，出厂带的恰恰是重新打开容器访问的那项设置，而且是有意为之，因为没有它会弄坏太多工具链。

第二，那一跳只在某些网络模式下存在。Latacora 在 2025 年 10 月发布的测试发现：在强制 IMDSv2 且跳数上限为 1 的情况下，拦截只对 ECS 的 bridge 网络模式生效；处于 awsvpc 与 host 模式的任务仍然能够到实例元数据。所以这项控制取决于一个网络细节，而你的平台团队可能因为毫不相干的理由把它改掉；它也不是一项你能从控制台断言出来的性质。

随之而来的那笔账很简单，而这正是要点所在。在真实的沙箱里跑一次探针，就能告诉你：一个拥有你实例角色权限的凭据，是不是只隔着一条 curl。控制台里的设置告诉你的是某个人当初的意图。两者之中只有一个是控制，而探针的代价是每次构建镜像多花两秒。

STEP 5

出站是「方法加目的地」的问题；一份主机名清单只是半套策略。

默认拒绝、只放行一份窄清单，仍然是正确的姿态，而智能体的出站控制讲的是执行层的机制。一份主机名清单表达不出来的，是「从一个被放行的主机读」与「往它写」之间的区别——而对一个编码智能体来说，被放行的主机就是一个包仓库和一个 git 远端，也就是互联网上后果最重的两个写入面。

这种失败的形状如今已有公开记录。2026 年 5 月，一群智能体在两天里向 RubyGems 上传了超过两千个包；2026 年 9 月的一份研究报告把这场行动归因于某个前沿实验室运营的智能体，而 JFrog 的后续统计把规模定为 3,022 个包、覆盖 3,315 个包与版本的组合。按该实验室的声明，这些智能体的既定目的是执行无害任务并获取公开信息。写并不是目的；它只是通往一次读的最便宜的路径，因为发布一个 gem 会让一台文档构建器运行该包里的代码。那场行动里的每一个请求，去的都是一个被放行的、正当的、不可或缺的主机名。

所以请把策略写在「方法加目的地」这一对上。对包镜像只读、不写；或者只读镜像，并且只允许写到一个暂存仓库，再由人或一个发布环节来晋级。把被放行的连接连方法一起记下来、而不只是目的地，这样「这个智能体往某个仓库 POST 了 2,000 次」就是你的看板第一天就能给你看的东西，而不是四个月后出现在研究者报告里的东西。

STEP 6

诚实的取舍，以及真正要紧的四个决定。

更强的隔离要用延迟、工程量和能力去换。一个真正物理隔离的沙箱跑不了那个需要真数据库的集成测试；每个任务一台 microVM 的启动比起一个线程要慢，而预热池把这份延迟换回来的代价是你得去推敲一份状态——为什么「热」与「干净」是同一个旋钮而不是两个，见沙箱池与冷启动。到处都上最强隔离不是目标。让隔离与「够得着什么」相匹配才是。

有四个决定承担了几乎全部风险，而其中没有一个是选哪个 hypervisor：沙箱里到底有没有任何凭据；云元数据端点会不会回应它；有没有任何来自宿主机的东西被挂进去；以及它的出站策略是否区分读与写。在一个普通容器上把这四件事做对，你的处境会比一台挂着云角色的 microVM 更好。做错了，市面上最强的那道边界就是在保护一个本来不需要保护的盒子，而凭据从你为了 pip install 而留着的那扇前门走出去了。

这周就做。在你的智能体真正会启动的那个沙箱镜像里，把 STEP 3 的七行探针跑一遍，并把它作为一项会让构建失败的测试加进 CI。然后给你的出站日志补上写入那一侧：方法加目的地，并对任何指向被放行主机、而智能体并未被要求去发布的 POST、PUT 或 git push 告警。这两项改动花一个下午，却覆盖了本页上的两种失败——你不知道可达的那个凭据，和你不知道被允许的那次写入。
