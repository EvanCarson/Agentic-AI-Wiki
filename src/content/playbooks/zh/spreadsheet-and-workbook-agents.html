电子表格与工作簿智能体。

一个读取单元格值的工作簿智能体，读的是一份缓存，而它缓存的是一张没人画过的依赖图。这正是这类智能体演示起来漂亮、审计起来糟糕的原因：显示 48,210 的那个单元格，是一条公式的输出，而它的输入散落在另外三张工作表上——所以一处看起来局部的编辑并不局部，一份只显示一个单元格变化的 diff，可能已经挪动了四十个数字。请构建在公式图之上而不是渲染出来的网格之上，把你的写入原语做成「公式补丁 + 重算 diff」，并用那唯一要紧的基准差距来设定自主度——单条指令的编辑约 57% 分，而多表工作流落在 35% 以下。

STEP 1

两个文件，两种不同的对象：读图，不是读网格。

一个 .xlsx 文件为每个单元格存了一条公式以及那条公式上一次求出的值。两者都在文件里。你的库交给你的是哪一个，是一个大多数团队无意中做下的配置决定，而它决定了你造出来的是哪一类智能体：

# openpyxl: the same cell, two different objects

wb = load_workbook("plan.xlsx")                 # formulas
wb["Rev"]["E12"].value   -> '=SUM(Q1:Q4)*FX!B3'

wb = load_workbook("plan.xlsx", data_only=True)  # cached values
wb["Rev"]["E12"].value   -> 48210

# and the trap: data_only reads the value EXCEL last wrote.
# a workbook generated by a script and never opened in Excel has
# no cached values at all — every formula cell reads as None.

所以，读值的智能体读到的是「最后一个按下保存的人当时屏幕上恰好显示的东西」，而读公式的智能体读到的是真正的模型。只有后者能回答任何编辑都绕不开的那个问题：有什么依赖它？在摄入时把公式解析成一张依赖图，只做一次，你就拿到了安全写入的前提——每个单元格的可达集合。没有它，每一次编辑都是盲写。

这个问题的读取侧另一半——先从一张人类格式化过的工作表里拿到可查询的模式，以及为什么「表头在哪一行」就是整个模式决定——在对表格与电子表格的检索里。本手册讲的是写入侧。

STEP 2

让基准差距替你设定自主度，因为它异常清楚。

电子表格工作的公开度量比大多数智能体领域都好，而这些数字对「把人放在哪里」说了一些很具体的话。把厂商自报的数字当成厂商自报、把预印本当成预印本，这个形状依然成立：

  • 单条指令的编辑：约一半正确，而且在快速改善。SpreadsheetBench（NeurIPS 2024）是取自线上 Excel 论坛的 912 个问题。其作者报告 GPT-4o 以及包括 Copilot in Excel 在内的商业产品为 17–20%，而人类高于 70%。微软此后报告 Excel 的 Agent Mode 在同一套 912 条指令上达到 57.2%，评分使用的是基准作者自己那套基于 openpyxl 的脚本。大约两年里约 3 倍的提升，是在一个真实任务分布上的真实进展。
  • 多表工作流：差得远。SpreadsheetBench 2 预印本在跨多表工作簿的 321 个专家标注任务上做评测——是端到端的业务工作，而不是一条指令。整体准确率停留在 35% 以下，而在电子表格产品之中，所报告的最高者是 Claude for Excel 的 15.4%。
  • 调试别人的工作簿：地板。在同一份预印本里，调试是最弱的类别，为 12.00%。

这三行是一份自主度政策，不是一张排行榜。「加一列算毛利」属于第一条，可以在轻度审阅下运行。「把这六张表之间的季度合并重建一遍」属于第二条，应当在计划层设闸，而不是在输出层。「查出为什么这个模型的合计是错的」属于第三条，是一项研究任务，智能体的职责是产出证据交由人类判断——一道渐进式自主的阶梯，每一条占一级。

第一条与第二条之间的差距，不是一个你靠等待就该指望被填平的能力差距。单条指令的任务自带裁判——指令本身说了要做什么。多表工作流没有；它只有一个意图，而满足该意图的结构是欠定的。这与评测多轮智能体比评测单轮更难是同一个理由，只是出现在一个你真能从数字里看见它的领域。

STEP 3

写入原语：一份公式补丁，然后一份重算 diff。

不要让智能体交给你一个新工作簿。重新生成的文件与旧文件之间没有可审阅的关系——格式会移位、列宽会变，而你真正在意的那一处编辑，会隐没在上千处无关差异之中。把工作的单位做成「针对公式图的补丁」，把审阅的单位做成「应用它所产生的效果」：

# what the agent proposes
patch:
  - cell: Rev!F12
    before: '=SUM(B12:E12)'
    after:  '=SUM(B12:E12)*FX!$B$3'
    reason: convert local-currency total to USD

# what the harness computes BEFORE anything is saved
recalc diff (LibreOffice --headless / formulas / Excel COM):
  Rev!F12         48,210  ->  44,433   (intended)
  Rev!F13..F28    unchanged
  Summary!C4   1,284,900  ->  1,281,123  (expected: rolls up F12)
  Board!B7        12.4%   ->   11.9%   (NOT in the plan)
  Covenants!D2      PASS   ->     FAIL   (NOT in the plan)

# 2 cells edited. 5 outputs moved. the last two are the review.

重算 diff 就是整个控制点。它很便宜——对一份副本做一次无头重算——而它把一处无法审阅的改动，转换成一张简短的「被挪动的数字」清单，而那是一位财务负责人真能批准的东西。关键在于，智能体必须在 diff 运行之前声明它预期的影响范围，这样框架才能标出「动了但没被预测到」的输出。未被预测的变动不一定是错的，但它永远是该去看的那一处，也正是通用影响半径纪律在表格场景下的形态。

有两处机制值得做对。请把绝对引用原样保留——$B$3 与 B3 在任何东西被复制的那一刻就行为不同，而一个把它们归一化掉的智能体，等于埋了一个将来才会出现、出现在别的单元格、发生在别的用户身上的 bug。另外，绝不要原地写入：在副本上操作、保留原件，并让恢复路径就是一次文件移动。撤销与可逆性在这里异常便宜，也异常值钱，因为另一种结局是一个财务团队无路可退。

STEP 4

能活过审阅的那种失败：构想对，结构错。

工作簿智能体的典型错误不是一个错的答案。它是一条「用错误的区域实现了正确想法」的公式，产出的数字数量级正确、格式正确、落在正确的单元格里。SpreadsheetBench 2 预印本记录了它的极端形态：它形容为「构想上合理但结构上错误」的公式，产出了约 4% 的单元格准确率。输出里没有任何地方看起来是坏的。

它到来的方式是一张简短且反复出现的清单，而每一条都有一个机械化的检查：

  • 差一位的区域，把表头或合计行包了进来。SUM(B1:B50)，而表头是第 1 行、Total 是第 50 行。检查：断言任何聚合区域都不与表卡标记为表头或合计的行相交。
  • 区域没够到数据末尾。在一张现在有 412 行的表上硬写 B2:B400，会悄悄丢掉十二行。检查：把每个区域的范围与工作表的已用区域比对，标出任何在最后一行数据之前就结束的聚合。
  • 经由小计造成的重复计算。对一列已经含有小计的列求和。检查：标出任何「区域内含有某个单元格、而该单元格本身就是对同一区域内若干单元格的 SUM」的情形——这是一个纯粹的图属性，计算便宜，而且它抓住的正是这类错误里代价最高的那一种。
  • 单位与货币被悄悄混用。把一列以千为单位的加到一列以个为单位的上。检查：为每列携带一个声明过的单位，并拒绝跨两个不同单位的相加。
  • 本该是引用的地方写了硬编码数字。=48210*1.085 今天给出正确答案，然后永远冻在那里。检查：标出任何「所含数字字面量等于工作簿别处某个当前单元格值」的待提交公式。

请把这些作为针对补丁的确定性断言来跑，而不是作为一个请求交给模型。它们是答案清脆的图谓词，这让它们恰恰是裁判模型最不该干的活、也恰恰是代码最该干的活——这个区分在用代码写出确定性的财务工作流里论证过。

STEP 5

智能体绝不能做什么，以及什么必须在编辑后依然存在。

工作簿常常是某种受监管事物的记录系统，而且它是唯一没有事务日志的记录系统。由此跟出几条约束，而在财务或报表语境下它们没得商量：

  • 绝不要悄悄把一条公式替换成它的值。这是唯一一种在值 diff 里看不见、却摧毁模型的编辑。如果智能体必须冻结某个数字，补丁必须用文字说出来，而原公式必须被保留在批注或相邻的审计列里。
  • 为每个被改动的单元格留下归属。追加一张工作表，记单元格地址、原公式、新公式、运行 id、提示词与模型版本。这就是审计轨迹，而在工作簿里它必须住在工作簿内部，因为这个文件在一小时之内就会被邮件发出你的基础设施之外。
  • 把工作簿自身的内容当作不可信输入。单元格文本、批注与工作表名来自这个文件来自的任何地方，而一份由交易对手转发来的工作簿就是一个提示词注入面——参见提示词注入。绝不要执行宏，也绝不要让 WEBSERVICE 或外部链接公式在重算期间运行；在摄入时就把它们剥掉。
  • 在那份署名的产物前停下。如果一个工作簿喂给一份对外报送的报表，那智能体的输出是一份提案，不是一次提交。落进监管报送里的那个数字需要一个具名的人，这就是问责与角色规则，施加在一个没人把它当成系统的文件上。

还有一条，很容易被漏掉：保护假设输入页。大多数真实模型都有一小组「其他一切都读它」的假设单元格。把它们标出来，默认对智能体设为只读，并要求一份显式、单独批准的补丁才能动其中任何一个。一个通过改假设来达成预期输出的智能体并没有做那件工作——它挪动了球门，而重算 diff 会看起来完美无缺。

STEP 6

工作簿智能体清单。

  • 摄入：解析公式而非值；构建依赖图；记录表头行、合计行与每列单位；剥掉宏与外部链接公式。
  • 提案：一份公式补丁，每个单元格附一条理由，并声明预期影响范围。
  • 验证：在副本上做无头重算；对计算出的输出做 diff；标出每一个未被预测到却动了的输出。
  • 断言：STEP 4 的五项结构检查，以代码形式，失败即关闭。
  • 设闸：单单元格编辑用轻度审阅；多表工作用计划层批准；调试只交证据。假设单元格永远需要它自己的批准。
  • 留痕：文件内部一张审计表；原件完好保留；恢复就是一次文件移动。
  • 度量：用真实请求攒出你自己的任务库，按重算后的输出而不是按动过的单元格来评分——再加上「智能体预测的影响范围与实际 diff 相符」的比率，那是它是否读懂了这个模型的最佳领先指标。

如果你只先建一样东西，就建重算 diff——在智能体之前，在提示词之前。它只是对一份副本做一次无头重算、再比较两张值网格；它是让之后每一个决定都可被审阅的那个控制点；而它也是唯一能把「智能体改了这个模型」变成一位财务负责人三十秒内能批准或驳回的东西的产物。然后再加上依赖图，这样智能体就能预测那份 diff，而不是发现它。
