实战手册 · 智能体 UX 与人机交互

在终端里，批准提示既是安全控制，又是挡住全部工作的那堵墙。这是少了一条通道。

Anthropic 自己给出的 Claude Code 数字是：用户批准了约 93% 的权限提示——这个数字描述的是介质，不是用户，因为在一个 TTY 里，提示占据的正是智能体与人类共用的那唯一一条输入流。别再写更吓人的文案了，把提示混为一谈的两个问题拆开：智能体能够做什么，以及它什么时候必须来问。

STEP 1

图形化智能体有三块界面。终端智能体只有一块。

在一个网页或桌面产品里，需要征得同意的智能体有地方放这个问题，而那地方不是干活的地方：一层盖在仍然可见的 diff 之上的模态框、一个侧栏、一个浮层提示、一条在用户走神时仍然留存的通知。工作与问题占据不同的像素，所以用户可以读其中一个，让另一个等着。

一个终端智能体有 stdin、stdout，以及 TUI 在它们之上重绘的那些东西。它一开口问，就停住；它一停住，提示上方的回滚缓冲就是用户拥有的全部上下文，而提示本身是他们唯一能交互的东西。三个后果是机械地推导出来的，而其中没有一个是你能在提示文案里修掉的 bug：

  • 每个问题都是阻塞式的。不存在「稍后再问」这条车道，所以一个问题的代价是整场会话的延迟，而不是瞥一眼的工夫。
  • 问题会和它自己的证据争地方。一段长 diff 会把提示顶出屏幕，或者提示把 diff 挤出屏幕；用户批准的是他们还能看见的那部分。
  • 答案空间是一个选择器。做集成的人报告，Claude Code 的工具权限对话框是「是 / 是且以后不要再问 / 否」，没有自由输入框——对一个 TTY 来说这是对的决定，而它意味着「去做，但换个做法」没有可表达的形式。

这三条就是这一页的全部命题。下面的一切，都是在想办法少花一点你只有一条的那种通道。

STEP 2

93% 是对介质的一次测量。请照这样对待它。

2026 年一项关于 Claude Code 设计空间的研究引用了 Anthropic 自己的数字：用户批准了大约 93% 的权限提示。诱人的读法是「用户不小心」。而结构性的读法证据更足：一项在常见情形上触发、在等待期间阻断全部进展、且有一个压倒性正确答案的控制，会被任何人在约一天之后条件反射地用那个答案回答掉。

佐证的细节是 Anthropic 为此做了什么。它的回应不是重新设计警告语——而是沙箱化与自动模式分类器，也就是划出一个边界，在那个边界内智能体不必再问。这是在给「缺陷在提示的数量、不在提示的措辞」投票。

所以该摆上仪表盘的指标不是批准率，而是每个完成任务所用的提示数，而方向是向下。当提示数随任务上升、批准率随之爬向 100% 时，那不是一个信任信号；那是同一件事被看了两遍。

如果你产品的安全叙事是「破坏性动作由用户确认」，而你的「每任务提示数」是两位数，那你没有一个确认步骤——你有的是一个被用户练成肌肉记忆的按键。你所产出的那份批准制品，会忠实地记录下一个当时并没有在读的人类。

STEP 3

把两个问题拆开：先是能力，然后才是打断。

当前这批 CLI 智能体里结构上最有用的那个想法，正是 Codex CLI 明确拆成两项独立设置的那个：sandbox_mode 决定智能体究竟能够做什么，approval_policy 决定它什么时候必须来问。一个「因为外壳没有办法让这个动作变安全」而存在的提示，和一个「因为用户希望被告知」而存在的提示，是两种不同的东西。

一旦这两个轴分开，大多数提示就消失进第一个轴里了。工作树内的读取、目录列举、以及只往沙箱已允许写入处写的构建与测试，都不需要问。网络出口、工作树之外的写入、以及任何会离开这台机器的东西，才是剩下的残余——而它们之所以是残余，恰恰因为沙箱没法在不把它们一并变得无用的前提下让它们变安全。

# The shape to aim for: the sandbox is the policy,
# the prompt is the exception.
sandbox:
  write:  ["./", "$TMPDIR"]        # no prompt, ever
  read:   ["./", "~/.config/app"]
  egress: ["registry.npmjs.org"]    # allowlist, not a question

ask_when:
  - write_outside_sandbox            # cannot be made safe
  - egress_to_unlisted_host          # cannot be made safe
  - git_push | publish | deploy      # reversibility is the reason

第三组才是有意思的那组。git push 原则上是可以沙箱化的；你之所以为它设问，是因为它难以撤销，而不是因为你关不住它。把这一组明确标注为可逆性而不是安全性，正是阻止它膨胀的办法：复核者可以就「某个动作是否可逆」展开争论，而把它做成可逆的，是一种删掉提示而非重写提示的办法。

STEP 4

像给延迟做预算那样，给打断做预算。

给提问次数定一个数，设计上的决定就会自己做出来。取一场 200 步的会话——对一次重构来说很普通——每六步一个提示，每个提示花掉人类十二秒注意力：

prompts      = 200 / 6            # 33
attention    = 33 * 12            # 396s ~ 6.6 min of pure waiting
rubber_stamp = 33 * 0.93          # 31 approvals that carried no decision
# decisions actually made: ~2 out of 33 interruptions

六分半钟的人类注意力，买到了两个决定。更糟的是，那 31 次条件反射式批准，正是训练出「会把第 32 次也批掉」的那个反射的东西。一个说得过去的预算大致是每场会话五个提示，每一个都是你在事后复盘里敢于辩护的决定；其余的一切，要么挪进沙箱，要么挪进可逆动作。如果你压不到这个数以下，那是你的沙箱太窄，不是你的用户太没耐心。

同一道算术也给「是，且以后不要再问」这个选项定了价。那个选项不是一项便利——它是用户在时间压力下永久地改写了你的策略，而且恰好发生在他们最无力评估它的那一刻。把它的作用域收到「能让当前这场会话跑完」的最小那一点上（这个命令形状、这个路径、这场会话），绝不要收到整个工具上；并把由此产生的规则用一行显示出来，这样这份授权日后是可复核的。

STEP 5

把问题设计成一个选择器答得了的样子。

既然答案空间是一个选择器，问题就必须是选择器能了结的那种。常见的失败是问了一个是非题，而它诚实的答案是「做点别的」——要执行 rm -rf build/ dist/ .cache/ 吗？会诱使一个只想删掉 build/ 的用户回答「否」、丢掉这一轮，然后用散文重新引导。有两种修法，按偏好排序。

把提案收窄到「是」就是全部答案为止。问 rm -rf build/，做掉，如果下一个确实需要再问一次。三个用户答对了的窄问题，胜过一个他们答错了的宽问题，哪怕这是三次打断——而这正是第 4 步那份预算唯一应该输掉争论的地方。

让第三个选项成为一个真选项。如果「否」之后反正会跟着一段散文，那就把这件事写进选项里：否——告诉我该怎么做，这把这一轮交还给用户，而不必让他们去猜智能体是否还在运行。在一个 TTY 里，无声的「否」落进一个被阻塞的循环，是能出现的最坏结局，因为用户分不清这是拒绝还是卡死。

还有，把被批准的那个东西显示在和问题同一帧里。一个把自己的 diff 滚出屏幕的提示，是一台多绕了几步的自动批准机器：把预览截断到提示上方装得下的篇幅，把「已截断」这件事说出来，并把完整视图作为一个选项提供，而不是把它设成默认。

STEP 6

回滚缓冲不是记录。请另外产出一份。

各个团队之所以倾向终端，部分原因是它感觉上可审计——一切都明明白白在缓冲区里。它不是。TUI 会重绘，转圈动画会覆写，长输出在抵达缓冲区之前就被渲染器截断，缓冲区本身有有限的回滚上限，而关掉窗口会把这一切销毁。那块唯一看起来像日志的界面，恰恰是你在一次事故里拿不出来的那块。

所以请把记录写到带外去，而且和功能本身在同一次提交里：对每一个被设了闸的动作，记下确切的命令或载荷、它的摘要、要求发出提示的那条规则、用户选择的那个选项，以及由此产生的授权作用域。那个文件是让事后回溯成为可能的东西，同时也是那份告诉你「每任务提示数」的数据集。建它的两个理由，指向同一件制品。

还有一个终端特有的陷阱：恢复会话。--resume 会从一份用户看不到的记录里重建一场会话，所以在先前那场会话里给出的授权，可能仍然静默地生效。请在恢复时把继承来的授权打印出来，每条一行。一项用户看不见的权限，就是一项他们没有给出的权限——而在一个单通道的介质里，打印出来是唯一能把它展示出来的办法。

先做这件事：把「每个完成任务所用的提示数」埋点测一周，然后按频次给提示排序。排在前三的几乎总是本该属于沙箱、而不是本该成为问题的读取或树内写入——删掉它们，你就能收回你的产品目前花在空处的大部分人类注意力。只有到那时，才去争论剩下那些的措辞；并把余量压在每场会话五个以内，每一个都写明理由：关不住，或者撤不回。任何理由不属于这两者的提示，都是你出于习惯留着的提示。
