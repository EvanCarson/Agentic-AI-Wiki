H5
实战手册 · 智能体体验与人机交互

你设计的梯级是按作用域的，而每个已发货的 harness 的旋钮都是按会话的——所以梯级必须住在权限规则里，模式选择器只负责决定"该问谁"。

截至 2026 年 10 月，Claude Code 提供六种权限模式，Codex CLI 则把三种沙箱模式与一条独立的审批策略交叉组合，而这些设置里没有任何一个能在同一时刻表达"给工单打标签时可以不打招呼、发起退款时每次都要问"——因为它们全都是会话级全局的。把自主性梯级做成一个模式选择器，你造出的就是这样一个产品：用户必须为两种风险截然不同的任务挑同一个信任档位，于是他们要么把安全的任务管得过死，要么对危险的任务给得过宽。梯级属于允许/拒绝规则与沙箱边界，晋级属于某一个作用域内看得见的履历，而降级的代价必须低于晋级的代价——否则没人会理性地往上爬。

STEP 1

梯级是一串人的角色，不是智能体的功率档。

请用人在做什么来描述每一级，因为那才是用户真正经历的东西，也是他们在移动档位时真正同意的东西：

  • 操作员（Operator）——人来驾驶；智能体只执行明确指令。
  • 协作者（Collaborator）——智能体提出并执行小步骤；人在旁边一起干。
  • 顾问（Consultant）——智能体给建议；人来决定并执行。
  • 审批人（Approver）——智能体干活；人在效果落地之前审批。
  • 观察者（Observer）——智能体直接行动；人事后监控与审计。

更高并不等于更好。一个梯级对某个给定作用域、某份给定履历来说，要么合适要么不合适；产品的职责是让当前梯级清晰可读、让下一级的前置条件明确写出来。这套词汇出自 2025 年关于自主性层级的文献，它作为"和用户对话的方式"一直成立——"每一笔退款发出前你会审批"是一位客服主管能够评估的句子，而"自主性等级 3"不是。

没有成立的，是"这套梯级能映射到软件里某个控件"这个假设。它映射不了，下一步就是证据。

STEP 2

各家 harness 实际发出来的东西，是一个会话级全局旋钮。

看一下截至 2026 年 10 月部署最广的两个智能体 harness，模式完全一致：一个作用于整个会话的设置，与手头这次任务的任何属性都正交。

Shipping autonomy controls, October 2026. Scope of each: THE SESSION.

Claude Code — six permission modes
  default           reads auto-approved; edits and commands asked
  acceptEdits       reads + file edits auto-approved; commands asked
  plan              read-only; produces a plan for approval
  auto              a separate classifier model reviews each action
  dontAsk           auto-denies anything not pre-approved (CI shape)
  bypassPermissions no prompts; documented for containers and VMs

Codex CLI — two orthogonal dials
  sandbox    read-only | workspace-write (default) | danger-full-access
  approvals  when the agent asks, set independently of the sandbox
  note       network off by default under workspace-write

Neither can say: Observer for "label ticket", Operator for "issue refund".

这张表里有两个细节干的活比看上去多。第一，Codex 把沙箱与审批拆开是正确的分解方式，值得照抄：审批策略决定该问谁，沙箱决定什么事情在物理上可能，而把审批设为"从不询问"本身并不授予无限制执行权。第二，Claude Code 的 auto 模式与其余五个在种类上不同——按其描述，它把"每一次动作该不该放行"的决定交给一个分类器而不是静态规则，这正是 STEP 4 的主题。

这两个产品还都提供了组织级的覆盖设置，而作用域恰恰在那里才真正出现：Codex 的受管配置可以直接封掉 --sandbox danger-full-access；Claude Code 的云端会话会忽略来自签入仓库的设置文件中 bypassPermissions 或 dontAsk 这类 defaultMode 值，于是一个仓库无法让云端会话以绕过权限的模式启动。那是一个天花板，不是一道梯子——但它是天花板该有的正确形状，而且它告诉你强制层住在哪里。生命周期钩子与 harness 配置详细讲了这个面。

STEP 3

把梯级绑到（能力，作用域）这一对上，并在 harness 之下强制执行。

一个智能体完全可以在同一瞬间：在"给来件工单打标签"上值得观察者级自主性，在"发起退款"上只配操作员级。一个全局旋钮逼用户二选一，而无论选哪个，对两项任务中的一项都是错的。所以梯级不能是那个旋钮。它必须是"智能体即将采取的那个动作"的函数。

# The rung is a function of (capability, scope) — never a global flag.
level = policy.autonomy_for(
    capability="refund",
    scope={"max_amount": 50, "region": "EU"},
)
if level >= APPROVER and request.amount <= 50:
    await act_then_review(request)
else:
    await recommend_only(request)

# Three layers, and only the first two are yours to design:
#   1. sandbox / credential scope  -> what is POSSIBLE at all
#   2. allow-deny policy per call  -> what runs without asking
#   3. harness mode (session-wide) -> WHO gets asked when 2 says ask
# A ladder implemented at layer 3 is a ladder with one rung.

实践中第 1、2 层才是梯级真正住的地方，而这两层你本来就有可用的原语。智能体持有的凭据决定上限——一个在计费 API 上只读的令牌，在任何权限模式下都发不出退款，这正是影响半径由凭据而不是由提示词决定的原因。按次调用的允许/拒绝规则决定什么可以静默通过，而它们能指名能力及其参数——这恰恰是会话模式做不到的事。策略即代码是长篇版本；任务作用域提供了书写那一对里"作用域"那半边的词汇。

对界面的设计后果很小也很具体：模式选择器留下，但它不再是自主性控件，而成了路由控件。"该问谁、怎么问"——当下这位用户内联询问、队列里的某位审核员、第二个模型、还是谁都不问——确实是一个会话级问题，也正是一个会话级控件该回答的问题。而"要不要问"留在策略里。

STEP 4

晋级要以看得见的履历为闸门——而一个分类器梯级，是一个它的错误率从此归你所有的梯级。

不要让用户第一天就跳到高自主性，也不要悄悄晋级。每一步上升都要以该作用域内展示出的可靠性为闸门：最低执行次数、可接受的修正率、零次被回滚的高后果动作。把这个提议做成显式的、带证据的——"在审批人档位上处理了 80 笔退款，你调整了 2 笔、回滚了 0 笔。要把 50 以下的欧盟退款移到观察者档吗？"——这样用户同意的是一次经过校准的变更，而不是凭信念拨了个开关。为信任而设计里那份履历，就是在这里买梯级用的货币。

2026 年 10 月有两个已发货的产品用另一条路走到了同一处，两者都值得理解，因为它们会变成默认范式。Notion 10 月 19 日的智能体发布引入了"Review for me"模式：由一个独立的模型检查智能体的动作，并只就它标记为可能不安全的那些请用户审批。微软在同一天宣布了一组控制措施：随着智能体被评估出的风险上升而收紧它可以做的事。Claude Code 的 auto 模式是同一想法在编码 harness 里的版本。

这是真正的进步——一个分类器能表达会话模式表达不出的"逐动作判断"，而那正是 STEP 3 指出的缺口。但要把你买到的东西说清楚。一个分类器梯级把一项显式的策略决定换成了一个带假阴性率的预测，而那个比率从此就是你产品的安全余量。这意味着它需要任何其他检测器都要接受的那套待遇：在你自己的动作分布上测出混淆矩阵；按"错批一笔退款"与"错拦一次工单打标"之间的不对称去选阈值；并随着你的动作构成变化而监控漂移。按风险打分的权限讲运维那一侧，而决策模型讲为什么一个不是你校准出来的置信度数字，不是一个你能拿来设阈值的数字。

在证据最新鲜的那一刻提出晋级——在该作用域刚走完一串干净记录之后——而不是埋在一个用户只访问过一次的设置页里。而且要把证据写进提议本身。一条不含任何数字的晋级提示是在索取信念，而凭信念给出授权的用户，就是在第一次意外时收回授权的那个用户。

STEP 5

降级必须是自动的、可逆的，而且比晋级更便宜。

一道没有下行档的梯子，就是一次慢放的不可撤销授权。一起实质事故、一次错误率回退、一次作用域变更、一次语境迁移，都必须能自动把智能体降一级——持续校验，而不是一次性毕业。要把它表述成正常的安全响应而不是失败判决：它应当在预期之内、被记录、被解释，并且可以凭一份新的履历重新爬上来。一个用户知道可以被安全降级的智能体，才是他们能够理性晋级的智能体。

这份不对称是承重部分，而已发货的 harness 其实已经演示了它。Claude Code 不允许一个会话中途切进 bypassPermissions，除非启动时就已启用；而 dontAsk 被刻意排除在键盘循环之外，必须用显式参数设定。相反，降到更严格的模式是立即生效的。照抄这条规则：下降是一个无需确认的动作，上升需要证据加一次刻意的手势。当这个机制需要持久化时，请把降级写进策略层而不是会话里，否则智能体下一次启动它就蒸发了。

有两件事能让降级变得可承受、而不是令人恼火。它在发生的那一刻就需要一个明示的重入条件——"再有 20 笔干净退款就回到审批人档"——否则用户会把它体验成一次无处申诉的惩罚。还有，在途的工作需要有地方去：智能体本来要无人监督执行的那个动作，应当变成一个等待审批的动作，而不是一个错误。撤销与可逆性管已经落地的那些效果，而权限授予与撤销的体验管这次降级实际上在编辑的那个授权面。

STEP 6

让当前梯级与它的边界无法被误读，然后在往上爬之前先算一遍期望值。

现场最大的自主性失效，是"智能体当下被允许自行做什么"这件事含混不清。用户必须能够不翻找就回答：这个智能体在这个作用域上处于哪一级，以及它会在哪条确切边界上停下来问。请把梯级与它的作用域渲染在动作发生之处，而不只放在设置里——用户已经失去跟踪的自主性，会同时产生过度信任（以为它会问）和信任不足（以为它不会问）。这也是唯一一处会话模式确实该出现在屏幕上的地方，因为当策略说"要问"时，是模式决定了究竟有没有人会看到这个问题。审批与确认体验讲提示本身的机制；计划评审与编辑专门讲 plan 模式这一级。

然后是"是否要爬"这个决定。它是一次期望值比较，而人们通常不做这次比较就决定了，所以请把它写下来：

Should "EU refunds under 50" move from Approver to Observer?

  volume            400 refunds / month
  approval time     45 seconds each
  time saved        400 x 45s = 5.0 hours / month

  observed error rate at Approver   2 adjusted in 80 = 2.5%
  errors that reach the customer    400 x 2.5% = 10 / month
  cost of one escaped bad refund    50 refund + 25 handling + goodwill

  10 x 75 = 750 / month of error cost against 5 hours saved.
  Climb only if 5 hours is worth more than 750 — and note the
  error rate was measured WITH a human catching them.

最后那一行是陷阱。在审批人档位上观察到的修正率，是"审核员抓到了某件事"的比率；它告诉你智能体多久错一次，却没告诉你在无人观察时它会多久错一次。请把实测比率当成下界，把第一个观察者档窗口开得小一点，并在晋级之后让审核员继续抽样一部分动作，使这个数字持续被测量。决策回执与审计才是让事后复盘根本成为可能的那样东西。

如果在更高梯级上一次罕见失手的代价，超过了所有成功累加省下的时间，那就停在低一级——期望值为负的自主性不是成熟度里程碑，而是一起被推迟的事故。按顺序要造三样东西：把凭据的作用域收窄，使上限在 harness 之下就被强制；把梯级放进按次调用、以（能力，作用域）为键的允许/拒绝策略里，把会话模式留给"该问谁"；并让降级自动、立即，且自带重入条件。如果你采用了分类器梯级——Notion 的审核模型、Claude Code 的 auto、一个风险分数——请在让它替代人的审批之前，先在你自己的动作上测出它的假阴性率，因为从那一刻起那个比率就是你的自主性策略。至于哪些能力组合无论履历多好都不该高于审批人档，见致命三要素。
