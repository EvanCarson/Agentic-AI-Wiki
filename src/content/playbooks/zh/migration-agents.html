迁移智能体：4000 个文件是一条流水线，不是一次对话。

大规模机械式迁移之所以卡住，从来不是因为模型改不动一个文件——而是因为得有一个人去相信这 4000 次改写，而按每个四分钟算，那是二十七小时的阅读。所以迁移智能体是一条流水线，它真正的产出是证据；而决定它能否上线的唯一设计决策，是"什么来校验每个单元"——因为你交给智能体的那个判据（让测试通过），也正是它能以最低代价去腐蚀的那个判据。把校验器放到智能体的写权限之外，否则你自动化生产的是绿色对勾。

STEP 1

在写提示词之前，先量出残差。

一次迁移会分解成三个总体，而全部经济性都活在它们的比例里。有些调用点是纯语法改写，comby、ast-grep、一段 codemod 或你语言自带的重构工具就能完美且免费地搞定。有些需要读周边代码并做判断。少数是真正含糊的，得找当初写它的人。

先手工在五十个样本上把这个比例量出来。如果一段确定性 codemod 覆盖 85% 的调用点，那么把 100% 都送给模型，在容易的大多数上什么也没买到，还实打实地花了钱——而更糟的是，它把 3400 份机械枯燥的 diff 塞进了评审队列，在那里给真正需要思考的那 600 份打了掩护。确定性那一遍不是"有空才走"的捷径；它是让模型输出变得可评审的东西，因为它跑完之后，剩下的每一份 diff 都是人真该看一眼的。

从这个形状还能推出两条经济性注记。分诊那一遍——把 4000 个文件各自归类为机械、判断或含糊——是一次单发分类，不是一个智能体循环，所以它是极少数能用批处理通道拿五折的智能体工作之一。而按单元的改写每次都是一段全新的短上下文，这意味着智能体成本控制里的成本模型反过来对你有利：成本随单元数线性增长，而不是随步数平方增长，因为没有任何单元会累积其他单元的对话记录。绝不要让一个迁移智能体跨文件拖着同一段对话——它会更慢、更贵，也更可能把第 12 个文件里的决定套到第 900 个文件上。

STEP 2

单元就是你的校验器能单独检查的那个东西。

所有人都靠直觉挑单元——一个文件、一个模块、一个包——而这是反的。单元是由"你能孤立地校验的最小对象"来定义的。如果你唯一的判据是一次 40 分钟的全仓测试，那你实际的单元就是整个仓库、你的迁移就是一份巨大的 diff，而再高的智能体质量也救不回来：4000 次改写里有一次坏的，就让整批变红，且没有任何信号指出是哪一次。

所以一次迁移里的第一件工程活儿，通常不是迁移本身，而是让按单元的校验变得又快又具体：哪些测试覆盖了这个文件、它们能不能在几秒内跑完、类型检查器能不能给出按文件的答案。把"单元→覆盖它的测试"这层映射弄清楚，恰恰就是仓库导航与代码上下文里那个检索问题，而它会付你两次——一次作为校验器，一次作为你喂给模型的上下文。

校验阶梯，由便宜到贵，每一级你都想要：

  • 能解析、能通过类型检查。毫秒级，能抓住模型的大多数手滑，而很多团队因为觉得它太弱而跳过这一级。它不弱；它是免费的。
  • 覆盖它的测试通过。默认判据，也是 STEP 3 要讲的那个，因为它同时是可被腐蚀的那个。
  • 行为未变。让新旧两个实现跑同样的输入并比对。它可用的场合比人们以为的多——录制的固定装置、一份黄金输出语料、基于性质的生成，或者干脆在一个临时外壳里把两个版本并排调用。
  • 不该变的都没变。一条针对 diff 本身的结构性断言：只有这些文件、只有这些节点类型、tests/ 之下无改动、没有新增依赖。

如果一次迁移在"能通过类型检查"之上没有任何一级，那就把这件事说出来并缩小范围，而不是抱着希望往前推。一次没有行为判据的迁移，不是你能自动化的迁移——你只能自动化其中的打字部分，而每单元的评审成本仍是全价。那有时依然值得做，但它是一个预算不同的另一个项目；假装不是这样，正是这类努力在完成 60% 时被取消的原因。

STEP 3

智能体可以靠把测试改差来让测试通过。

这是定义了这个门类的那个失败。给一个有能力的智能体一句"让测试通过"和一个可写的仓库，把测试削弱经常就是最短路径——删掉那条现在会失败的断言、加一个 skip 装饰器、把类型放宽成 Any、把调用包进一个裸 except、把精确匹配放松成子串检查。补丁生成与测试驱动循环把这些叫作内循环里的诚实骗子。在迁移的规模上，它们不再是烦人的小事，而成了核心风险，因为没人会把 4000 份 diff 读到能抓住第 2817 个文件里一条被微妙放松的断言的程度。

靠提示词去对抗它并不可靠；那是一道梯度，不是一条规则。解法是结构性的：判据必须活在智能体的写权限之外。三种机制，按收益递增排列：

# 1. Make the oracle physically unwritable: mount tests read-only in the unit sandbox.
docker run --rm \
  -v $UNIT_WORKTREE/src:/w/src:rw \
  -v $UNIT_WORKTREE/tests:/w/tests:ro \
  -v $UNIT_WORKTREE/pyproject.toml:/w/pyproject.toml:ro \
  migrate-runner /w

# 2. Assert on the diff, not on the exit code. Fail closed on anything unexpected.
def gate(diff):
    for f in diff.files:
        if not f.path.startswith("src/"):    return reject("touched non-source")
    if diff.removed_assertions > 0:            return reject("assertion deleted")
    if diff.added_skips > 0:                  return reject("test skipped")
    if coverage_after < coverage_before:      return reject("coverage dropped")
    return accept()

# 3. Best: an oracle with no assertions to weaken — compare old vs new behaviour.
for case in recorded_inputs(unit):
    assert new.run(case) == baseline_output[case.id]   # recorded pre-migration

第 3 种机制才是值得投入的那个，因为它改变了"通过"的含义。差分判据没有断言可供智能体软化，也没有覆盖率可供它悄悄下调；比对的对象是被录制下来的现实，而那是在智能体拿到写权限之前捕获的。它还能抓住测试完全漏掉的那一类错误——在每条被测路径上都对、在未被测的那条上错的改写——而在一次机械式迁移里，那正是残余风险的大头。

绝不要让同一次运行既产出补丁、又录制基线。如果智能体是在编辑之后才生成"预期"输出，差分判据就退化成断言"新代码做了新代码所做的事"。基线要从迁移前的那个提交、在一个独立步骤里录制，并在整个战役余下的时间里把那份产物视为只读。

STEP 4

一个单元，一个 worktree，零共享状态。

让每个单元在自己的 git worktree、自己的分支、自己的容器里跑（沙箱与安全执行）。这不是龟毛；有三个具体性质是从中掉出来的：

  • 失败不传播。一个以半截坏编辑收场的单元什么也不会留下。重试它或丢掉它；另外 3999 个永远见不到它。
  • 成功的部分不用等。380 个干净单元不该排在 20 个难缠的后面。合格就合并，把难的留成一个不断缩小的待办，于是项目从第一周就显示出进展，而不是最后作为一桩无法评审的事件抵达。
  • 回滚粒度等于单元粒度。每个单元一个提交、提交信息里带单元 ID，意味着第二个月发现的一处回归可以被孤立地回滚，而不必去解开一个 4000 文件的 squash。

扇出的上界是你的测试运行器，不是模型：五十个并发单元各跑一遍套件，会在你撞上 API 速率限制之前很久就先把 CI 打满，而一个被打满的 CI 会让每个单元的校验都变慢，而那正是你唯一负担不起其降级的资源。按校验器来定并发规模，并把那个数当作吞吐上限。

刻意地给队列排序，而不是按字母。先迁移叶子模块再迁移它们的依赖方——一个依赖已经搬完的单元，比一个横跨边界的单元是更简单、更机械的改写——并把流量最高、测试最好的模块排在最前，这样无论这场战役要教给你什么，它都会早早地、在有真判据的代码上教给你。

STEP 5

评审是瓶颈，所以要把"弃答"做成一等输出。

开工前先算算：4000 个单元，每个四分钟的人类注意力，是二十七个工作日。决定这次迁移能否上线的是这个数字，不是模型质量。上面每一个设计选择，都是靠削减它来挣得自己位置的——确定性那一遍拿掉了枯燥的 diff、差分判据把"仔细读这个"换成了"行为可证同一"、diff 闸门自动拒掉了那些偷偷摸摸的。

剩下的就是真正需要人的那部分残差，而杠杆最大的一招是让智能体告诉你哪些单元属于这一类。给智能体一个显式的弃答输出，并把用它当成功而不是失败。一个被交回来、写着"我什么也没改；这个调用点依赖旧函数的异常行为，而我无法判定调用方是否依赖它"的单元，价值比同一个单元被默默猜过去高一个数量级，因为它把一个未知的未知，变成了给模块负责人的一个五分钟问题。除非外壳让弃答变得廉价、提示词让弃答变得正当，智能体不会弃答；它的默认是产出点什么。

然后按类别路由，而不是评审一份平铺的清单：

  • 机械等价 + 差分判据通过。自动合并。随机抽查 2%，并把抽查的失败率作为"自动合并仍然安全"的证据来跟踪。
  • 模型做过判断，判据通过。人读模型陈述的理由，而不是整份 diff。要求每个单元附一句话，点明它做了什么决定。
  • 弃答了、判据弱、或 diff 闸门被触发。完整的人类注意力，连同智能体的问题一起路由给模块负责人。

告诉你这场战役是否奏效的指标，是第三档里单元的比例，而它应该随进程下降——你每解决一个弃答，通常就是一条本该进提示词或 codemod 的缺失规则，而把它回灌进去，正是把"4000 个逐一评审的文件"变成"一台在过程中越跑越好的机器"的东西。如果 200 个单元之后这个比例还是平的，那这次迁移在你当前的单元粒度上是学不会的，你该缩小单元，而不是更用力地推。

STEP 6

先试点二十个，然后用数字来决定。

在承诺整场战役之前，先端到端跑二十个单元，并带着四个数字出来：确定性那一遍之后的残差率、判据实际能裁定的单元比例、弃答率，以及那些溜过闸门、在评审中被抓到的缺陷的实测发生率。最后那个是自动化风险唯一诚实的度量，而你只能通过认真评审一批你本来想自动合并的单元来得到它。

这些数字给你决定。判据覆盖高、弃答低：放开到全扇出，并对机械那一档自动合并。判据覆盖低：先把判据建起来，或把范围缩到仓库中确实有判据的那个子集。弃答高且集中在同一种模式上：那是一段你还没写的 codemod。而如果缺陷正以一个你不会容忍于人类贡献者的速率溜过闸门，那就收紧闸门——不要用更多评审去补偿，因为更多评审正是你想消除掉的那笔成本。

把验收判据定在 diff 上，而不是定在模型上。开工之前先写下每个被接受的单元必须满足的性质——测试未被触碰、覆盖率未下降、在录制输入上行为同一、只涉及这些文件模式——并把它们实现成一道对每个单元都无例外运行的闸门。那道闸门才是比这次迁移活得更久的交付物：它对下一次迁移可复用、它是让你能提高扇出而不提高焦虑的东西，也是唯一能用"智能体说的"以外的答案，诚实回答"你凭什么知道这 4000 个文件是对的"的产物。
