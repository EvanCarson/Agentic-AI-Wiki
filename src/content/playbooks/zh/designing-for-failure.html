你的失败路径需要三个终态，而所有人都漏掉的那个叫「未知」。

2026 年 11 月在跑的每一种恢复原语——检查点、回退、重试、审批闸——作用范围都只到「它能快照或能重跑的东西」，而没有任何一种声称自己能撤销一次网络调用。所以一次「写入过程中崩掉」的诚实结果既不是成功、也不是失败，而是我不知道那件事到底有没有发生；而一个只有两个终态的产品会悄悄替你挑一个。它挑的是失败，于是触发重试，于是一次可恢复的事故变成了两次不可逆的。

STEP 1

可逆边界是你工具面的属性，不是你那句承诺的属性。

「我们有撤销」从来不是某个 harness 真正做出的声明。去读文档，那句声明总是更窄、更具体；而目前已发货的四种答案彼此差别大到你不能把它们当成可互换的东西来推理。

  • Claude Code 的 /rewind 追踪的是它自己的文件编辑工具所做的改动。每一条开启一轮的提示都会创建一个检查点；它为一次会话中最近的 100 个检查点保留快照，并在该会话最后一次保存快照之后约 30 天的清理扫描中删除它们。一条 shell 命令的写入，只有在它的工具此前已经碰过的文件里才可恢复。子智能体的编辑通常不被捕获。目录的创建、移动或删除不会被撤销。远程与网络文件不被追踪。符号链接与硬链接路径会被跳过，并给出一条写明跳过了多少个的警告。
  • GitHub Copilot CLI 的 /undo 在三条轴上都是相反的边界：文件改动按轮次追踪，覆盖编辑工具、shell 命令以及子智能体，而且不需要 Git。它为此付出的代价是一组硬性数字上限——超过 10 MB 的文件不被捕获，单一轮次若改动超过 500 个文件则该轮完全不被捕获，而一个内容已不再与 Copilot 最后写入的相符的文件会被原样留下。回退本身无法再被撤销。
  • Codex CLI 没有发货任何 undo、rewind、checkpoint 或 revert 命令。Git 就是全部答案。
  • Copilot 的云端 coding agent 也没有回退，而是用架构把它替掉了——见 STEP 5。

有两点是通用的。第一，它们每一个都把版本控制点名为「自己覆盖不到的那部分」的补救手段——这是厂商在告诉你：这条边界比你的用户会假定的更窄。第二，没有任何 harness 声称自己能撤销一次对外生效的动作。撤销是一个披着产品词汇的文件系统功能。

STEP 2

按「每次运行」而不是「每个工具」去算撤销覆盖率。

团队会引用的那个数字，是他们工具里可逆的那部分占比。而能预测事故的那个数字，是「每一处副作用都可逆」的那部分运行占比；两者相差甚远，因为不可逆的那些工具恰恰是有用的那些。

# a support agent's tool surface, and what undo really covers
tools_total          = 14
file_edits           =  9      # reversible by checkpoint
shell_commands       =  3      # reversible only where a file tool touched it first
outbound             =  2      # send_email, issue_refund
tool_coverage        = 9 / 14  # = 64% — the number that gets quoted

# now sample 200 real runs and ask what each one touched
runs                        = 200
runs_only_reversible_tools  =  56   # = 28% — the number that matters
runs_touching_outbound      =  31   # = 16% where "undo" is a word, not a feature

工具里的六成四，运行里的两成八。在你对用户许下任何承诺之前先算这一笔，而且每加一个工具就再算一遍：一个落在常用路径上的新对外工具，就能把「按运行算」的覆盖率砍掉一半，而被引用的那个数字一动不动。

然后把剩下的工作按「撤销代价」而不是「这个动作听起来多吓人」来排序，这正是撤销与可逆性所建立的那根杠杆。真正的可逆胜过一个只会警告的确认，因为确认要求人去预测一个坏结果，而撤销只要求他认出一个。在真正回滚不可能的地方，一个带取消的延迟窗口能更便宜地买到同一样东西。

STEP 3

把第三个终态加上，因为现在有四家厂商在叫你这么做。

这正是本页上一版、以及多数已上线产品弄错的地方。各家文档已经独立地收敛到同一句承认：

  • LangGraph：一次重试会从头重跑整个节点，这给出的是「节点执行至少一次」的语义——而它明确表示这并不能让外部副作用恰好发生一次。检查点是在超步边界写入的，不是在函数中途，所以节点内部的支付与邮件落在那条边界之外。
  • Temporal：Temporal 不会让副作用只跑一次。它自己举的例子就是：一个 worker 成功执行完某个 activity，却在通知服务之前崩掉，于是事件历史里没有记录、该 activity 被重试，而支付处理方看到的是一笔重复扣款。
  • OpenAI 的 Agents SDK 说得最直白：批准允许一次工具调用被执行，它并不保证恰好执行一次——一笔支付可能已经完成，而被保存的快照里完全没有这个结果的记录。紧接着那条指引才是真正该去实现的：在一次普通查询里没查到结果，并不证明重试是安全的，因为读取会滞后、而更早的那次请求仍可能落地；所以如果结果仍然不确定，就把它记为未知，并避免自动重放。
  • Claude Code 把这件事的界面做出来了。2.1.326 版修掉了这个问题：当一条 shell 命令改动了 /rewind 无法恢复的文件时，它原本会报「无代码改动」；现在一个改动未被追踪的轮次会显示「代码改动未知」。

最后这一条才是该整套搬走的范式。那个 bug 不在于这个 harness 没能恢复文件——按设计它就是不能。那个 bug 在于它把「我无从得知」渲染成了「什么都没发生」，而这是一个恢复界面能印出的最昂贵的句子。请让 unknown 成为你的状态机能持有、你的 API 能返回、你的界面能画出来的一个取值，并且在视觉上让它既区别于成功、也区别于失败。一个被告知「这笔退款可能已发出、也可能没有——重试前请先核对」的用户能做出正确动作；一个被告知「退款失败」的用户会再按一次那个按钮。

危险的失败从来不是那次可见的崩溃。而是那个安静地给出「看着合理但其实是错」的结果、然后继续往下走的智能体；以及它的近亲——那个在毫无证据的情况下报出「干净失败」的恢复界面。请把你的检测偏向「把不确定性摆出来并停下」。关于这件事在模型那一侧的样子，见失败隐瞒。

STEP 4

恢复就是一次重新执行，所以幂等键必须在副作用之前就已持久化。

LangGraph 的文档对机制讲得毫不含糊：中断之后恢复执行时，运行时会从节点的开头重新开始整个节点，而不是从调用 interrupt 的那一行继续，所以在它之前跑过的任何代码都会再跑一遍。子图的重放方式也一样。中断、引导与交接算的是这件事在运行中途要让用户付出什么；而对失败路径真正要紧的，是它埋下的那个具体陷阱。

在它所保护的那一步内部生成幂等键是不行的，而且这个失败是静默的：

# the key must already be durable BEFORE the side effect runs
attempt 1:  node starts -> generate key K1 -> charge succeeds -> process dies
attempt 2:  node starts -> state has no key -> generate key K2 -> charge AGAIN

# K1 was never checkpointed, because the node never returned.
# Fix: derive the key from state that is already durable, or persist
# it in a step that completes before the effect.

三条推论，都来自厂商文档。把副作用放在暂停之后，或者放进它自己单独的一步，这样重放窗口里就不包含任何会向谁扣钱的东西。在一次长暂停之后，重新读取外部状态——价格、库存、政策——因为暂停之前那个世界已经过期了。并且记住：幂等是由你调用的那个服务强制执行的，不是由你的 activity 执行的；你的键只是一个请求，而目标方的保留期决定它还能被认账多久。请让「工作单元」成为恢复边界，因为那是唯一能阻止已完成工作重复发生的杠杆。幂等与重试有具体实现。

STEP 5

撤销不了的地方，就去设界——并且选定失败的方向。

对「万一智能体干了坏事怎么办」最强的答案，有时根本不是撤销。GitHub 的云端 coding agent 没有发货任何回退，取而代之的是把影响半径压到小得让普通 Git 就够用：它只能推送到唯一一个分支、别的都不行；它的凭据只允许简单的推送操作，所以它无法直接运行 git push 或别的 Git 命令；它的草稿 pull request 必须由人类审阅并合并——它不能把它们标为可供审阅、不能批准、也不能合并；而默认情况下，在有写权限的人批准之前工作流不会运行。没有什么需要可逆，因为什么都还没落地。这是一条比回滚更好的保证，而且任何「产出可以先暂存」的智能体都能用上。

在副作用必须落地的地方，失败的方向是一个刻意的选择，而且因轴而异。在后果这条轴上——钱、数据、对外通讯——向关闭失败：不确定时就少做，因为一个没做的动作是可恢复的，而一个做错了的不可逆动作往往不是。在能力这条轴上——某个工具挂了、某个来源连不上——向开放失败、走诚实降级：返回标注清楚的部分结果，或者在状态完好的情况下交回给人，而不是编造出来好让自己看着还在工作。最糟的结果是两者的组合：一个自信、看着完整、错误、而且不可逆的结果。向关闭失败与向开放失败是一般性的论述；影响半径才是你实际在度量的那个东西。

有一处细节值得照搬，因为它太常被弄错：取消不是回滚。Copilot CLI 的文档写明，一次已经在进行中的文件写入会完成，所以文件不会在写到一半时损坏，但剩下那些计划中的改动会被放弃。这是正确的行为，而它意味着一次被取消的运行结束在一个部分已应用的状态里——这正好就是 STEP 3 那第三个终态，也正是你的停止按钮该明说出来的东西。

STEP 6

把提示写好，再去修复信任——并且不要在不确定之上自动重试。

一条错误提示是「用户下一步动作」的界面，它要回答三个问题：我现在处在什么状态（什么已应用、什么已回滚、什么是未知的）、我能做什么（重试、撤销、接手、上报），以及我不该假定什么——「这封邮件并没有发出」，或者在很多情况下更诚实的说法是「我们无法确认这封邮件是否已发出」。把用户最可能想要的那个恢复动作做成主控件、就放在那儿，并把那些确定的事实摆出来，而不是摆一段堆栈。「出了点问题」不是一个句子，它是一次推卸。

永远不要对一个「可能已部分应用了非幂等副作用」的失败自动重试。这是本页唯一一条「会把一次可恢复事故变成一次重复且不可逆的事故」的规则；而 Agents SDK 的指引正是该套用的那个判据：只有在权威性的核对确立了「此前没有任何一次尝试执行过该动作、且没有任何一次仍可能执行它」之后，才去重试。查不到记录不等于核对完成。在无法核对的地方，这次运行就以 unknown 结束，由人来决定。重试放大讲的是一整支编队同时犯这个错会发生什么。

然后去做信任那部分的工作，因为一次可见的错误不只花掉了那个任务——它会重置用户对整个智能体的校准，而且通常是全局性的，哪怕那次失败本身是有范围的。信任不会靠等待恢复。它靠具体的修复恢复：平实地承认那个确切的错误，不轻描淡写、不演道歉戏；说出那个让它更不容易再发生的具体改动；并明确划出损害范围——「这影响的是退款处理；工单打标签没有受影响」——因为不划范围的失败会毒化那些从未失败过的能力上的信任。可用的最强一招，是让智能体主动在「恰好出事的那个作用域」里提出暂时降一级自主性，这读起来像是担责，而不像一句措辞过的道歉（渐进式自主）。

按顺序来：去读你那个 harness 的文档，把真实的可逆边界写下来，然后按「每次运行」而不是「每个工具」算撤销覆盖率。把 unknown 作为一等终态加进你的状态机、你的 API 和你的界面，并且永远不要把它渲染成失败。让每一个幂等键都从「已经持久化的状态」推导出来，并把副作用放在暂停之后。对任何你撤销不了的东西，改成把它暂存在一道闸后面——一个分支加一次审阅胜过一次回滚。在后果上向关闭失败，在能力上向开放失败。如果只留一句话：一个会说「我不知道那件事有没有发生」的智能体是在正确工作，而那条消息旁边的一个重试按钮是一个 bug。
