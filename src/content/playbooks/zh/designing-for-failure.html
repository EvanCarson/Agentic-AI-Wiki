实战手册 · 智能体体验与人机交互

一个智能体产品的质量，由它出错之后发生的事决定。

你能摆出来的那张失败界面，其实早在几个小时前、在写入路径上的某个决定里就已经定下了——因为「发票没有寄出」和「撤销」都是关于状态的断言，而只有在副作用落地之前有东西把它们记下来，它们才存在。团队总想靠重写文案来修好失败体验，而文案恰恰是唯一修不好的部分，因为一条报错只能报告系统已知的事。请在每一次写入时就判定这个副作用属于三层里的哪一层——可取消、可补偿，还是只能告知——并把那一层所需要的句柄存下来，你的失败界面就会自己写好；跳过这一步，再怎么字斟句酌也躲不过「出了点问题」。

STEP 1

失败提示没法事后补写。

智能体体验的功夫大多花在顺利路径上，失败路径则拿到异常处理器碰巧做了的那点东西。对此惯常的诊断是「优先级问题」，听起来像以后还能补。补不了。用户对一个智能体的长期判断正是在失败时形成的，而当一次失败正被渲染出来时，有用的信息要么已经存在，要么不存在。

从用户真正需要的那三句话倒着推——我现在处于什么状态、我能做什么、我不该假定什么——每一句都落到某条必须更早写下的记录上。「什么都没有生效」要求副作用是被排序并记入日志的，而不是并发打出去的。「邮件没发，但工单建了」要求的是逐项副作用的结果，而不是把一个五步计划整个套进一个 try/except。「撤销」要求存有一个逆操作。一个手里只有异常对象的处理器，能告诉用户的就只有「它很抱歉」——而这恰恰是谁都不需要的那一件事。

危险的失败不是那种看得见的崩溃，而是智能体悄悄产出一个看似合理却错误的结果，然后继续往下走。请把检测偏向于「暴露不确定并停下」，而不是硬推过去；并且即使每一次调用都返回了 200，也要把一个做了一半的计划当作失败。

STEP 2

三层回退，以及每一层各自要求的句柄。

「我们能撤销吗？」不是一个问题。真实系统用三种截然不同的方式回答它，每一种都要求事先存下不同的东西，而层级是副作用本身的属性，不是你的产品志向的属性。

可取消——副作用还没有落地，撤回授权不留任何痕迹。Stripe 是最干净的例子：一笔已授权但未扣款（uncaptured）的支付根本无法退款，只能取消，取消会释放这笔冻结、不产生 Refund 对象，而且不收费。Gmail 的 Undo Send 是同一形状的消费级版本——发送撤销期可在网页端设置里选 5、10、20 或 30 秒，默认 5 秒，在这段时间里邮件其实还没去过任何地方。这一层需要的句柄，是这笔待定操作的 id 加上它的截止时刻。

可补偿——副作用已经落地，存在一个逆操作，但执行它本身是第二件看得见的事。同一笔 Stripe 支付一旦扣款完成，就必须走退款 API 退回；你可以部分退款，也可以多次退款，总额不超过原始金额。钱回来了，而对账单上那一行不会消失。这一层的句柄，是在正向动作执行之前就写下来的那个逆操作，连同它所需的各个标识符。

只能告知——在任何代价下都不存在逆操作。被接收服务器收下的邮件在协议层没有撤回；已被通知的交易对手无法「取消通知」；用掉的配额就是没了。这一层的句柄是「到底发生了什么」的完整描述，因为告知本身就是全部的补救。

# Classify at the write, not at the error. Three fields, forever.
effect = plan.next()
journal.record(
    tier   = effect.tier,            # cancel | compensate | disclose
    handle = effect.reversal_handle(),  # op id, or the inverse call
    until  = effect.cancel_deadline, # None for the other two tiers
)
op = effect.apply()                   # journal BEFORE, always

if user.undo(op) or monitor.regressed(op):
    journal.reverse(op)              # picks cancel or compensate by tier
# and if the tier is 'disclose', the UI says so instead of offering a button
  • 在真正的回退不可能时，为自己买下一个可取消的窗口：让副作用落地之前先延迟一小段时间，就能以一点延迟为代价把第三层变成第一层——这正是 Gmail 那五秒的用途。
  • 绝不要为「只能告知」的副作用显示撤销控件。一个按不动的按钮比一句解释更糟，而用户会从一个说谎的控件推而广之，怀疑全部控件。
  • 先投资可回退性，再投资更好的确认弹窗。强有力的撤销让你可以安全地降低审批摩擦，摩擦降低则疲劳减少，疲劳减少则监督变好，而正是监督抓住了那些随后由撤销来收拾的失败——完整的论证见撤销与可回退性，服务端的那套机制见修补智能体的副作用。
STEP 3

一条报错，就是用户下一步动作的界面。

「出了点问题」没给用户任何能用的东西，而解法不是更好的文笔——而是把「已生效／未生效」的那条边界报出来。一个五步计划里的失败至少有四种不同含义：什么都没跑；有几步跑了并已回退；有几步跑了且无法回退；全都跑完了但结果是错的。这四种对应四种不同的恢复动作，而把它们渲染成同一个样子的界面，正好扔掉了用户唯一需要的信息。

所以一张好的失败界面的形状是一份简短的台账，而不是一句话。列出每一项副作用、它的结果、以及它是否可回退；把最可能用到的那一个恢复动作作为主控件摆在旁边；并且把否定性的事实明确写出来，因为用户没法从「少了一行」推断出「邮件没有发送」。然后给出这次运行的标识符——用户报告的那次失败和你要去排查的那条 trace 必须能对上，而事后补这条关联远比现在就发出它要难得多。

先为最坏情况写这份台账：智能体在计划中途死了，两项副作用已生效，第三项状态未知。如果你的数据模型渲染不出这张界面，缺口就在写入路径上，任何文案润色都碰不到它。持久状态与可恢复性是它的底座；试运行与预览则是让用户在这一切还只是个问题之前先看到计划的办法。

STEP 4

在后果上失败关闭，在能力上失败打开。

失败的方向是一个有意的选择，而这两条轴的拉力正好相反。在后果轴上——钱、数据、对外沟通——要失败关闭：不确定或出错时，做得更少而不是更多，因为一个没做的动作可以挽回，而一个错误的不可逆动作往往挽回不了。在能力轴上——某个工具挂了、某个数据源不可达——要朝着诚实降级的方向失败打开：清楚标注地返回部分结果，或者在状态完好的情况下交还给人，而不是为了显得还能用而编造。

最糟的失败模式是两者的合体：一个自信、看起来完整、错误而且不可逆的结果。正是它摧毁了用户对那些从未失败过的能力的信任，而结构性的防线是把不可逆的那一步放在一个由代码而非模型做出的检查之后——论证见失败关闭与失败打开，针对钱的完整版本见金融智能体的确定性边界。

STEP 5

信任修复是有范围、要明说的工作，不是时间的流逝。

一次看得见的错误的代价不止于那一个任务；它会重置用户对整个智能体的校准，而且往往是全局性的，哪怕那次失败范围很窄。信任不会靠等来恢复。它靠三个有意的动作恢复，顺序如下。

  • 平实地承认那个具体的错误。不要轻描淡写，也不要拟人化的道歉表演。「退款金额是按错误的那张发票算的」能落地；「为带来的不便深表歉意」落不了地，而过度道歉读起来像一个预期自己还会再错的系统。
  • 把损害范围明确说出来。「这影响了退款处理；工单打标未受影响。」范围不明的失败会悄悄毒化用户对那些从未失败过的能力的信任，而用户自己没有办法划出这条边界——这正是为信任而设计里的校准论证。
  • 提出一次由智能体自己请求的降级。在恰好出问题的那个范围内，提议暂时下调一个自主档位——退款需要审批，其他一切不变——并让用户选择接受或拒绝。一次自我提出的降级读起来像在担责，比任何措辞都更快地重建有校准的信任，而且它给了你一条可度量的回升阶梯：渐进式自主。

修复本身有两种失败模式值得点名。悄悄修复——把修补发上去却不说一声——会把用户的校准留在失败当时的位置，于是这份工程投入买不到任何信任。而修复得过宽——把整个智能体降到全部人工审批——则是在教用户「一次失误要用整个产品来付账」；降级必须和失败一样窄。

STEP 6

什么时候不要自动重试。

如果这次失败可能已经部分施加了一个非幂等的副作用，就不要自动重试——在状态不确定的情况下静默重试，会把一次可挽回的失败变成一次重复且不可逆的失败，而用户现在手上有了两份东西，却没有任何记录能说明哪一次尝试造出了哪一份。把任务挂起、把台账摆出来、让人来选；那些本可以让重试变安全的键，在幂等、重试与副作用安全里。
