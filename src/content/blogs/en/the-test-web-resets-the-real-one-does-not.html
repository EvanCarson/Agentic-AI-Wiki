Google published a throughput number and no pass rate, and that pairing is the most honest thing in the announcement. Chrome's new synthetic web can tell you whether this build of an agent got worse than the last one; it cannot tell you how often the agent resists injection on the real internet, and the reason is the same property that makes it work — every run starts from an identical clean state, and the page that attacks you in production is the page that just changed.

The agent acts through Chrome DevTools for Agents — screenshots, clicks, typing, navigation — and each trajectory begins from an identical clean start, so side effects from one run cannot leak into the next. The system is internal; nothing in the post offers it as a public harness.

The loop that builds the world

Four engineering decisions are doing the work here, and three of them are portable to a team with a thousandth of the budget.

Real URLs through a proxy. The generated pages are served under the hostnames an agent would actually request, so nothing in the agent, the prompt or the page has to be rewritten for the test. This is the difference between an eval environment and a mock: a mock changes the thing under test, a proxy does not. If you have ever watched an agent behave differently because your fixture URLs looked like fixtures, this is the fix.

The payload as a header toggle. This is the cleverest part and the easiest to steal. Because the injection is switched on by an HTTP header rather than by serving a different page, the attack run and the control run are byte-identical apart from the header. A failure is therefore attributable to the payload and not to some incidental difference in the markup — a paired comparison, which is also the trick that rescues small eval sets from their own noise (eval variance and statistical power).

The identical clean start. Every trajectory begins from the same state and leaves nothing behind. On the live web this is impossible: a cart has items in it from the last run, a rate limiter remembers you, an account is now in a state no test set up. That irreducible statefulness is the whole reason evaluating against live systems is hard, and it is what the sandbox buys.

And the one to be nervous about: a custom root CA trusted inside the sandbox. In a sealed box this is correct and necessary — without it the browser's own security machinery would flag every page and you would be measuring certificate errors. But it means the test profile has deliberately disabled the browser's strongest signal about who a page really is. That is fine until the profile, the image or the automation that configures it is reused for something that can reach the real internet, at which point you have shipped a browser that trusts a certificate authority you generated. Keep the CA lifetime short, keep it out of any shared base image, and treat "which profile has our test CA installed" as an inventory question.

Determinism is the feature and the ceiling

Here is the trade that a reset buys, stated as plainly as it deserves. A clean, identical start makes a run comparable. Comparability is what a regression harness runs on: you change the agent, hold the world fixed, and the difference is attributable to the change. Without it you cannot tell a worse model from a redesigned checkout page, which is why almost nobody successfully runs a browser-agent regression suite against production sites.

But the thing held fixed is the thing that attacks you. In production, the injection arrives on a page you have never seen, phrased by someone who has read your previous defence, inside markup that changed this morning. A pass rate measured against a fixed payload library on a fixed corpus answers the question "does this build still resist the attacks we already know about" — which is genuinely valuable and is not a safety property. It is the browser-agent instance of the result in The Attacker Moves Second (Nasr, Carlini and colleagues, October 2025), where twelve published defences that had reported near-zero attack success rates were pushed past 90% by attackers allowed to adapt to each defence's design. A fixed corpus is, by construction, the non-adaptive case.

Which is why the absence of a published pass rate reads as discipline rather than evasion. Google published the number its environment can honestly produce — generated test candidates per engineer per day — and declined to publish the number it cannot. The claim "the agent cannot tell it is being tested" is also a measurement Google made about its own system, and worth treating as a hypothesis rather than a property: evaluation awareness is measured by looking for the cues you thought of, and a header toggle removes the cue a human would think of first.

The generator is now inside the measured system

This is the part the coverage has skipped, and it is the most interesting thing about the design. The websites are written by agents. The user journeys are charted by an agent. The code is reviewed by an agent. The attack payloads are placed in a corpus built by that pipeline. And the thing under test is an agent.

Two consequences follow, and neither is a criticism of Chrome specifically — they apply to anyone building this, which increasingly means everyone:

  • Coverage is bounded by the generator's imagination, and throughput does not measure coverage. A thousand candidates a day is a statement about how fast you can produce variations, not about how much of the attack space they span. If the builder agent writes shopping carts because the research agent charted shopping, the corpus is dense where you already looked. The analogous failure in benchmark construction is well documented — see benchmark contamination for the version where the overlap is with training data rather than with imagination.
  • Shared weights mean shared blind spots. If the generator and the target come from the same model family, the attacks you can produce are drawn from roughly the distribution the target was trained to handle. You cannot write a payload your generator cannot conceive of, and a generator built from the same weights conceives of the same things. The cheap mitigation is to generate the adversarial half with a different model family than the one you are testing, and to keep a human-written payload set as a control group — if the human set finds things the generated set does not, your generator is the bottleneck, and that ratio is a metric worth tracking release over release.

None of which makes the environment less useful. It makes the throughput number the wrong headline, and makes "what fraction of our payload library was written by a model from the same family as the agent" a question any team doing this should be able to answer.

What to copy if you are not Google

A thousand generated sites is out of reach for most teams; the architecture is not. In descending order of return:

  • Serve your fixtures through a proxy at real hostnames. Cheap, and it removes a whole class of "it behaves differently in the test harness" confounds. Record once, replay forever — the pattern in replay testing with recorded traces.
  • Make every adversarial case a header-toggled variant of a benign case. You get the paired comparison for free, and your eval set halves in size without losing power.
  • Reset state per trajectory, and make it cheap enough that you actually do. If resetting takes a human, nobody resets, and your suite starts measuring run order. This is most of the content of staging environments for agents.
  • Capture the artefacts you will need to diagnose a failure — screenshots and DOM snapshots at each step, not just the final verdict (screenshot and DOM artefacts). A browser-agent failure you cannot see is a bug report nobody will act on.
  • Keep a live-web canary. A small, continuously-run set against real sites you control, accepted as noisy, is the only thing that tells you the synthetic corpus has drifted away from the web. It is the one row the matrix above says you cannot fill any other way.

And keep the claim proportionate to the instrument. "Our injection defence did not regress against our payload library this release" is a real, useful, defensible sentence. "Our agent resists prompt injection" is not one that any sealed environment can earn — the state of the art on what can be earned is in prompt-injection defence in 2026.

FAQ

Is Mirror Dimension available to use?

No. As described on 19 November 2026 it is internal to Chrome's AI Security work, and the post does not offer it as a public harness or an open-source release. The reusable part is the architecture, not the corpus.

How is this different from WebArena, BrowserGym or OSWorld?

Those are public benchmark environments with fixed task sets, designed so results are comparable between labs. This is an internal generation pipeline designed for throughput against one product, with payload injection as a first-class feature. Different jobs — see OSWorld vs WindowsAgentArena vs AndroidWorld vs BrowserGym for the public-benchmark landscape.

Why does serving fake pages under real hostnames matter?

Because an agent that can tell it is in a test harness is no longer the agent you are testing. Real hostnames plus a trusted certificate remove the two most obvious cues without touching the agent's code.

Does a synthetic web help with non-security evaluation too?

Yes, and that is arguably its larger value: task-completion rates on carts and forms are very hard to measure against live sites that change under you. The security framing dominated the coverage, but the reproducibility problem it solves is general.

What is the risk of the custom root CA?

Inside a sealed sandbox, close to none — it exists so the browser does not reject the proxy's pages. The risk is reuse: a browser profile or container image carrying a test CA, used somewhere that can reach the public internet, trusts a certificate authority under your control. Treat it as an inventory item with a short lifetime.
