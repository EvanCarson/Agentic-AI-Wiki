Read the headline and you would move your Workspace integration in a panic: "REST API access for AI agents ends 1 February 2027." It does not end. The REST APIs keep answering — they just stop being eligible for quota you can buy, which means Google's new control over agent traffic is not an access check at all. It is a price list, and a price list needs to know who you are.

What was actually announced

On 24 November 2026 Google made two things generally available: a set of Google-hosted Workspace MCP servers covering Gmail, Drive, Docs, Sheets, Slides, Calendar, Chat and Tasks, with Keep still to come; and an official Workspace CLI (gwscli) aimed at agents that live in a terminal, a VM or a sandbox rather than inside an app. Rollout across Rapid Release and Scheduled Release domains runs over roughly two weeks, so the admin controls do not all appear the same day.

Alongside them came a Workspace AI Tools Addendum and a standardised two-tier usage model. The dates that matter:

DateWhat changesWho it binds
24 Nov 2026MCP servers and gwscli GA; Standard and Scaled tiers published; addendum in forceEveryone with a Workspace API project
1 Feb 2027Agents calling Workspace REST APIs directly are limited to Standard tier quotas regardless of the tier selectedAnything Google classifies as an AI agent or similar access tool
1 Apr 2027Billing begins for usage above the daily free allowance; projects over Standard limits that have not moved to Scaled revert to StandardScaled-tier projects, and anyone currently exceeding Standard

The Standard tier is free and, as reported at GA, caps each generally available MCP server at 5,000 requests per day. Note the one detail the coverage does not agree on: whether that cap is per project or per project per product. Google's own quota documentation is the place to settle it before you size anything, and the difference is a factor of eight across the eight GA servers. A per-request rate card for Scaled was not confirmed at GA; a figure circulated from a single outlet, and a number that appears in exactly one place is not a number you plan a budget on.

"Ends" is the wrong verb, and the right verb changes your plan

A shutdown and a quota ceiling fail in different ways, on different timelines, with different fixes, so the distinction is not pedantry. If REST access ended, your agent would break on 1 February and you would schedule a migration as a hard deadline. It does not break. It carries on, at Standard-tier quotas, until the day your traffic grows past 5,000 requests — and then it fails with the most ordinary error in the catalogue, a rate-limit response, which your retry logic will absorb and your dashboards will read as latency.

That is a worse failure shape than an outage, because it is the one your monitoring is built to hide. An outage pages someone. A quota ceiling you cannot lift by paying produces a slow, uneven degradation whose cause is a contract term from four months earlier. The teams that get hurt here are not the ones who missed the announcement; they are the ones who read "ends" and concluded that whatever still worked in February must be compliant.

The enforcement mechanism is billing eligibility, so the real requirement is identification

Look at what the 1 February rule has to do in order to work. It applies to "AI agents or similar access tools" — not to a protocol, not to an IP range, not to a scope. Somebody has to decide that a given stream of REST calls belongs to an agent, and the mechanism Google reaches for is the one it already owns: the project, its OAuth client, and the tier that project is allowed to hold.

That inverts the usual migration question. You are not primarily being asked to adopt a protocol; you are being asked to declare which of your traffic is agentic, because that declaration is what makes the traffic eligible for paid quota. Agents need dedicated OAuth client IDs and least-privilege scopes under the new model, which is exactly the registration step that makes the meter possible. An unlabelled agent is not a loophole — it is a project that cannot buy headroom.

This is why MCP won the slot, and it is not mainly a story about protocol quality. A REST API is a surface a vendor can rate-limit but cannot easily characterise: a GET is a GET whether a human clicked it or a planner emitted it. A hosted MCP server is a chokepoint the vendor operates, where every call arrives already attributed to a named client, a declared tool and a session. The protocol that wins an enterprise is the one that lets the data owner count. We have argued the mirror image of this for identity — bot verification and agent access is the same problem viewed from the other side of the request — and the commercial version arrived first.

The second-order effect is worth naming now, because it will shape procurement for a year: once the data owner can count agents, pricing stops tracking seats and starts tracking metered agent calls. A seat licence does not care how many tool calls your planner makes. A per-request allowance cares enormously, and it makes the granularity of your tools a line item: five tight tools that each make one call cost five times what one well-designed call costs, and nothing in your agent framework will tell you that.

The clause that will cost more than the quota

Quotas are arithmetic and you will solve them. The addendum is the part that touches architecture. Two of its terms stand out from the GA coverage: a limit on how long you may retain data derived from Workspace API use — reported as 30 days for material such as embeddings — and a prohibition on using AI agents to scrape the Workspace APIs.

If that retention limit reads the way it is reported, it lands directly on the most common Workspace agent design in production: index the user's mail and drive into a vector store, keep the index warm, answer from it. A 30-day ceiling on derived data makes that index a cache with a mandatory expiry rather than a durable asset, and the operational consequence is a recurring reindex you now have to budget for — both in cost and in the quota you just started paying for, because rebuilding the index is itself API traffic. Verify the exact wording against the addendum before you redesign; but if you are running a long-lived Workspace index, this clause is the one to read first, not the price list.

The scraping prohibition is the quieter one. "Scraping" is not defined by request volume alone, and a research agent that walks a Drive tree breadth-first to build a corpus looks, from the server side, exactly like the thing being prohibited. The defensible posture is the one that was always good engineering: fetch on demand for a task, keep a task scope you can point to, and do not build a mirror of someone else's corpus because it was convenient.

What to do before February, and before April

Four things, in order of how much they shrink the others.

Attribute your Workspace traffic. Before anything else, find out which of your projects and OAuth clients are emitting agent calls today, and separate them from human-driven calls. You cannot evaluate a tier you cannot measure, and every later decision depends on this split. If one client ID serves both your product's UI and its background agent, that is the first thing to fix — it is also the thing that will make the 1 February rule ambiguous for you in a way it is not for teams who split cleanly.

Count requests per task, not per user. Take your ten most common agent tasks and count the Workspace calls each one actually makes end to end, including retries and re-reads. That number against 5,000 a day is your headroom, and it is usually much worse than teams expect, because an agent loop re-reads context the way a human never does. If a single ticket-triage run touches the mailbox eleven times, your free tier is 454 runs a day, not 5,000.

Move the hot paths to the MCP servers or gwscli, and leave the rest. This is a migration you can do by traffic share rather than wholesale. The paths that will hit the ceiling are the agent paths; a nightly batch job that is not an agent is not what the February rule is about. Treat the hosted servers as the metered lane and keep REST for what genuinely is not agent traffic — but write down which is which, because that written classification is the thing you will be asked for.

Read the addendum before you price the tiers. A retention clause can invalidate a design; a quota only makes it more expensive. Teams reliably do these in the wrong order because the price list is shorter.

And the thing not to do: treat 1 February as the deadline. The deadline that bites is 1 April, when projects that have not moved to Scaled revert to Standard limits, and the two-week rollout means your admin controls may not even have appeared yet. February changes what you are allowed to buy. April is when not having bought it shows up.

FAQ

Will my existing Workspace REST integration stop working on 1 February 2027?

No. Direct REST calls keep working. What changes is that traffic Google classifies as coming from an AI agent is limited to Standard tier quotas regardless of the tier your project has selected, so you can no longer buy headroom for that path.

Is Google charging for the Workspace MCP servers now?

No. The Standard tier is free and, as reported at GA, caps each GA MCP server at 5,000 requests per day. Billing for usage above the daily free allowance begins 1 April 2027 for Scaled-tier projects. A per-request rate card was not confirmed at GA.

Does the 5,000-a-day cap apply per project or per product?

The GA coverage disagrees on this, and across eight GA servers the difference is a factor of eight. Check Google's own usage-tiers and quotas documentation for Workspace APIs and MCP servers before sizing anything on it.

Which is better for a terminal or sandbox agent, the MCP servers or the CLI?

The CLI exists for exactly that case — agents in a terminal, VM or sandbox — and avoids running an MCP client in an environment that may not have one. Agents embedded in an application are the MCP servers' case. Both are inside the allowed path, so this is an ergonomics choice, not a compliance one.

Does this mean MCP has won as the enterprise agent protocol?

It means a major data owner has made MCP the only lane where agent traffic can buy capacity, which is a stronger form of adoption than a technical preference. The mechanism is commercial rather than architectural: a hosted MCP server is where a vendor can attribute and meter calls, and a REST endpoint is not.
