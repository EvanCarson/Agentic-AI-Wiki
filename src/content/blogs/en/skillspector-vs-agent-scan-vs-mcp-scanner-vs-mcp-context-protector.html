Three of the four best-known security tools for agent skills and MCP servers answer the same question — is this dangerous right now? — and all three had a commit yesterday. The fourth answers the question that actually matters once something is installed: is this still the thing you approved? It pins the configuration, blocks tool calls until you re-approve a change, and was archived in April 2026 with 228 stars against SkillSpector's 27,593. The market bought the dashboard and let the gate rot.

At a glance

All four are Apache-2.0 and all four take an MCP server or a skill directory as input. Star counts and the last push are as recorded by the GitHub API on 25 November 2026.

NVIDIA SkillSpector — the one with the dataset

What it does

SkillSpector scans git repos, URLs, zip files, directories and single SKILL.md files, and in skillspector mcp mode it will walk servers from the official MCP registry. Detection is 71 vulnerability patterns across 17 categories — prompt injection, data exfiltration, supply chain, MCP least-privilege and tool-poisoning checks among them — plus AST-based behavioural analysis, taint tracking and YARA signatures. It never executes the skill's code. The output is a 0–100 risk score mapped to LOW/MEDIUM/HIGH/CRITICAL and then to one of three verdicts: SAFE, CAUTION, or DO_NOT_INSTALL.

The CI story is the most complete of the four: SARIF 2.1.0 and JSON output, exit codes 0 for SAFE or CAUTION, 1 for a gated failure and 2 for an error, and gates for --fail-on-findings, --fail-on-incomplete and --min-coverage. An optional LLM stage can confirm, dispute or explain a finding, and the deterministic findings stay in the report either way — a design decision worth copying, because it means the semantic layer can only add context, never silently delete a hit.

The number that should change how you think about skills

SkillSpector's own README carries a figure it attributes to Liu et al. (2026): across a 31,132-skill analysed subset, 26.1% of skills contained vulnerabilities and 5.2% showed likely malicious intent, and skills carrying executable scripts were 2.12× more likely to be vulnerable. Take the second number at its own framing — "likely malicious intent" is a classifier's judgement, not a court's — and it still says that roughly one skill in twenty in a public corpus is trying something. That is the base rate your review process has to beat, and it is the strongest argument on this page for scanning at all.

What leaves your machine

Static scanning is local and the skill's code is never run, but "local" needs a footnote. With LLM analysis enabled, analyzer-eligible file contents go to the configured provider. Its dependency check queries OSV.dev for dependency names and versions even under --no-llm, falling back to an offline list when it cannot reach the service. --no-llm keeps file contents on your machine; it does not make the scan airtight.

One thing to configure before you ship it: SkillSpector exposes its own MCP server with a scan_skill tool so an agent can scan on its own behalf, and its HTTP transport has no authentication and is restricted to loopback. That is the correct default, and it is also a reminder that a scanner you expose to an agent is one more server in the catalogue someone has to vet.

Snyk Agent Scan — the one that changed hands

From mcp-scan to a vendor product

The repository created on 7 April 2025 as Invariant Labs' mcp-scan — for most of 2025 the default answer to "how do I check an MCP server?" — now resolves to snyk/agent-scan and the tool is Snyk Agent Scan. The scope grew with the rebrand: it auto-discovers Claude, Cursor, VS Code, Windsurf, Gemini CLI and other agents on the machine, and from v0.6 it reports scored risks for MCP servers (prompt injection, untrusted content, private data, destructive capabilities) and for skills (suspicious downloads, malicious code, credential handling, secret detection). Skill scanning can be turned off with --no-skills.

The trade you are making

Analysis is a service. You export a SNYK_TOKEN, and the tool sends agent application details, MCP server configurations and signatures, tool names and descriptions, and skill content for analysis, with secrets in configuration values and text redacted first. It states that it does not store or log usage data, meaning the contents and results of MCP tool calls. The README names no licence in its text and links to a TERMS.md, and says the project does not accept external contributions — although the repository's own licence field still reads Apache-2.0, which is the kind of mismatch worth resolving with your own counsel rather than with a blog post.

If your agent's tool descriptions are themselves confidential — internal service names, undocumented endpoints, the shape of a private schema — that is the part to weigh. Every scanner that reasons semantically has to read the text; this one reads it somewhere else. And note what the scan itself does to check tools: it starts stdio MCP servers and connects to configured remote URLs, so running it executes commands and makes outbound requests. Consent prompts are on by default in interactive runs, and the CI path is explicitly spelled --ci --dangerously-run-mcp-servers. The flag name is doing honest work.

Cisco MCP Scanner — the one with the most dials

Nine analyzers, three of them free

Cisco's scanner is the broadest of the three in what it will look at: tools, prompts, resources and server instructions on live servers; MCP server source code behaviourally; PyPI and npm packages, Docker-sandboxed by default; Python dependencies via pip-audit; and binaries by VirusTotal hash lookup. The analyzers are YARA (with custom rules), an LLM analyzer, the Cisco AI Defense inspect API, a readiness analyzer with 20 heuristic rules, a prompt_defense analyzer that checks for missing defences against 12 attack vectors, plus vulnerable-package, virustotal, behavioral and an opt-in schema analyzer. Readiness and prompt_defense need no API keys.

It is the one that fits an air-gapped pipeline most honestly. The static subcommand scans pre-generated JSON without a live server connection, which is the shape you want in CI; combine it with YARA and readiness and the scan needs nothing outside your network. The LLM and API analyzers do call out — the README notes the LLM path was tested with GPT-4o, GPT-4.1 and Claude 4.5 Sonnet on AWS Bedrock — so the offline configuration is a choice you make per analyzer, not a mode you switch on.

Where it will surprise you

Two defaults to know before a big run. VirusTotal's free tier allows 4 requests a minute and 500 a day, and the scanner caps itself at 10 files per directory by default, so a binary-heavy scan is rate-limited long before it is complete. And the default stdio startup timeout is 60 seconds — generous for a healthy server, and long enough that a hanging one quietly dominates your pipeline's wall clock.

Trail of Bits mcp-context-protector — the one that asks the second question

Trust on first use, enforced in the path

mcp-context-protector is not a scanner. It is a wrapper you put between the host application and the server — stdio via --command, streamable HTTP via --url, legacy SSE via --sse-url — so it works with any MCP client rather than requiring support inside the host. On connection, and again on every notifications/tools/list_changed, it compares the server's configuration against an approved copy. The comparison is semantic and covers server instructions, tool descriptions and tool input schemas, ignoring tool and parameter order, so a cosmetic reshuffle does not cry wolf. Approvals live in ~/.mcp-context-protector/servers.json; you grant one with --review-server, which connects, shows you the configuration, and stores it if you accept.

The important sentence: any deviation from an approved configuration blocks downstream tool calls until you explicitly approve the new one. That is a gate, not an alert. And servers are identified by transport plus URL or exact launch command — renaming the server in your client's config does not matter, but changing the command string makes it a new server needing fresh approval, which is the right side to err on.

It also reads what comes back

With --guardrail-provider set — LlamaFirewall, for instance — every tool response is scanned for prompt injection. A detection does not get rewritten or dropped: the response is written to ~/.mcp-context-protector/quarantine.json, the host app receives the provider's output in its place, and you review with --review-quarantine; if you approve, the model can retrieve the original through a quarantine_release tool. It also sanitises ANSI control characters, with --visualize-ansi-codes to make escapes readable during an investigation. Of the four tools on this page, this is the only one that sees a tool result at all.

And it is archived

228 stars, last push 14 April 2026, repository archived. Nothing is wrong with the code — the pinning database format is boring and the comparison logic is the kind of thing that ages well — but an archived security wrapper in the call path of every tool call is a decision, not a default. It will not track protocol revisions, and the 2026-07-28 MCP revision changed enough (no handshake, no session id, per-request metadata) that "will it still work against my server" is now an empirical question you have to answer yourself.

The two questions, and why only one of them is maintained

A verdict is a fact about a moment

Comparing these four on detection quality misses the structural difference. SkillSpector, Snyk Agent Scan and Cisco MCP Scanner all read declared text — instructions, tool descriptions, schemas, source, dependencies — reason about it, and emit a judgement. That judgement is true of the bytes they read, on the day they read them. None of the three sits in the call path, so none of them can notice that the bytes changed afterwards. mcp-context-protector reads less and remembers more: it has no opinion about whether a tool description is dangerous, only about whether it is the same description you accepted.

Which question matters depends on the threat. For a one-off install from a public registry, the risk is concentrated in the initial content and a scanner is the right tool — that 5.2% figure is the argument. For a server you have been calling for six months, the initial content was reviewed by someone and the risk has moved: it is now the update you did not review. A tool-poisoning change ships in a description, takes effect on the next call, and shows up in no diff you were watching. SkillSpector's skillspector baseline plus --baseline is the nearest a scanner here gets to catching that, and it is a diff of findings on a run you have to remember to trigger, not a pin that blocks.

Three places the data goes

Write the architectures as data flows and they separate cleanly. SkillSpector keeps file contents local unless you enable its LLM stage, and contacts OSV.dev with dependency names regardless. Snyk Agent Scan sends configurations, tool names and descriptions and skill content to Snyk for analysis, with secrets redacted. Cisco MCP Scanner can be run with only key-free analyzers and never leave your network, or with the LLM and AI Defense analyzers and leave it on every scan. mcp-context-protector sends nothing anywhere by default; with a guardrail provider configured, the provider sees tool responses.

What none of them does

None of the four decides whether a tool should have been callable in the first place. A clean verdict on a tool that can read your repository and post to the internet is a true statement about a capability combination that will hurt you anyway. Scanning is a supply-chain control; it is not a substitute for scoped credentials or egress control, and reading these tools as prompt-injection defences is the most common way to buy the wrong one.

The practical recommendation is unglamorous: run a scanner at install time and own the pin yourself. Hash the configuration you approved — server instructions, every tool name, description and input schema, with order normalised — store it next to your deployment config, and compare on every start and on every tools/list_changed. That is a hundred lines, it never gets archived, and it is the part of this stack that keeps working when the vendor landscape moves again.

FAQ

Is a scanner enough to stop MCP tool poisoning?

No. A scanner judges the text it read on the day it ran, and tool poisoning that arrives as a post-approval description change is invisible to it unless you re-run the scan and diff the result. The control that stops it is a pinned configuration with a re-approval gate.

What happened to mcp-scan?

The repository created in April 2025 as Invariant Labs' mcp-scan is now snyk/agent-scan and the tool is Snyk Agent Scan. It needs a SNYK_TOKEN and sends configurations, tool descriptions and skill content to Snyk for analysis, with secrets redacted first.

Can I run any of these with no network access?

Cisco MCP Scanner comes closest: its static subcommand scans pre-generated JSON with no live server, and the YARA and readiness analyzers need no API keys. SkillSpector keeps file contents local under --no-llm but still queries OSV.dev for dependency names, with an offline fallback list. Snyk Agent Scan's analysis is a hosted service.

Should I use an archived security tool in my call path?

Only with eyes open. mcp-context-protector's design is sound and its approval database is a plain JSON file, but it stopped tracking the protocol in April 2026 and the 2026-07-28 MCP revision was large. Either verify it against your own servers and pin the version, or implement the same trust-on-first-use comparison in your own gateway.

How many public skills actually contain something malicious?

SkillSpector's README cites Liu et al. (2026) for 26.1% of a 31,132-skill subset containing vulnerabilities and 5.2% showing likely malicious intent, with script-carrying skills 2.12× more likely to be vulnerable. Treat the second figure as a classifier's judgement on a public corpus rather than a measurement of your own registry.
