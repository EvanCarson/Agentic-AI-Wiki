GitHub's official MCP server paginated from the start — perPage up to 100, after cursors on the newer tools — and its issue tracker still filled with single calls that broke the context window: 30 commits at more than 64k tokens, 30 pull requests at 508KB, 50 project items at about 100K tokens. Pagination bounds how many records come back. The context window is a budget of tokens, and a record can weigh anything. Count your pages in tokens, cut fields before you page, and assume the host your users run will handle the overflow differently from the one you tested.

A paper trail from one server

Most MCP servers that overflow a context window leave no record. GitHub's left eighteen months of one, because its users file issues and its maintainers answer them in public. Read in order, the issues tell the same story every time.

The first, #142 in April 2025, was a list_commits call on zalando/skipper. Thirty commits produced more than 64k tokens on the next model call, about 5–6KB per commit. The reporter was a tier-1 OpenAI user and got a 429: the request needed 68,490 tokens against a limit of 30,000 tokens per minute. That is the one hard cost number in this story. The call was well within its page size and still could not be sent.

The pattern held. In May 2025 get_pull_request_comments returned 26,688 tokens to a Claude Code user whose cap was 25,000 (#425). In June, a report that complete job logs "can easily exceed LLM context limits" led to a tail_lines parameter (#608). In February 2026, list_pull_requests returned 508KB for 30 PRs — about 17KB each, 36KB each on another query — and the reporter asked for the minimal_output option that search_repositories already had (#1934, still open). In April, 50 project items came to about 400KB, roughly 100K tokens, which the reporter called "roughly half of a typical LLM context window"; two pages of 50 fill one (#2383).

The cause was the record, not the count

GitHub's REST objects are built for programs that ignore what they don't need: user objects carry more than fifteen URL templates, plus reactions and metadata a model will never use. Passed through unchanged, five to seventeen kilobytes per record times a perPage limit of 100 is a page no model can hold. The server's page sizes were reasonable for an HTTP client and far too large for a context window.

The fix that worked, each time, was projection. PR #2563, merged on 28 May 2026, added minimal types for project items. The maintainers measured five live items at about 12,875 tokens before and 901 after — a 93.0% cut, from roughly 2,575 tokens per item to 180. Scaled to a page of 50, that is 128,750 tokens down to 9,010. The page size stayed the same, and every record got smaller. The same fix is now spreading endpoint by endpoint: a fields parameter on the issue and pull-request list and search tools, whose README notes that "omitting body drops the largest per-result data"; PR #2675 making search_pull_requests compact by default with minimal_output: false to get the raw objects back; and the minimal types collected in pkg/github/minimal_types.go. As of October 2026, pull_request_read is next in line, still returning full patches from get_files (#3236).

Pagination you cannot reach is not pagination

Issue #2122, from March 2026, shows the other way record pagination fails. pull_request_read's get_review_comments method advertised cursor pagination, but the after argument was missing from the tool's schema, and page and perPage were silently ignored by three methods. The model could not ask for a second page because nothing in the schema let it. The results, above about 50–100KB, pushed Cursor and VS Code to 100% CPU and needed a hard restart. PR #2489 exposed after and the issue closed in May. A cursor only works if the model can see it in the schema, and only helps if every page fits.

Why a record count cannot bound a window

Datadog reached the same conclusion from the opposite kind of data. Its engineers found their agents running out of context because "a few of the logs were huge" — "a Datadog log message might be only 100 characters or it might be 1 MB". No record count bounds that. So they changed what a page means: "The server cuts off its response after a certain number of tokens and returns a cursor for more." The page is defined by tokens, and the cursor carries the rest.

They then worked on the cost of each record. CSV used "about half as many tokens" as JSON per record; YAML saved "around 20%" on nested data; the format change plus dropping rarely used fields fit "about 5x more records in the same number of tokens" for some tools. The biggest win was letting agents aggregate instead of page. With SQL, agents could SELECT fields, LIMIT rows or COUNT, and evals ran "about 40% cheaper".

Two other servers show what a size-aware page looks like in code. MotherDuck's DuckDB server caps rows at 1,024 and characters at 50,000 by default. It fetches one row more than the cap to find out whether more exists, sets truncated: true with a warning ("Results limited to N rows. Query returned more data."), and if the JSON is still over the character cap it drops about 10% of the rows at a time until it fits. Grafana's query_loki_logs defaults to 10 lines with a maximum of 100 and returns resultsTruncated and maxLinesAllowed alongside the data, and the server has a response-body byte limit that rejects an oversized response with an error rather than passing it on.

The servers that take neither precaution show the default. ClickHouse's server documents a query timeout but no row cap; crystaldba/postgres-mcp calls fetchall() with no limit. A SELECT * on a large table through either is bounded only by whatever the host decides to do with it — which is the subject of the next section.

The protocol pages the catalog, not the call

MCP has pagination. It covers exactly four methods — tools/list, resources/list, resources/templates/list and prompts/list — in both the 2025-11-25 and 2026-07-28 revisions. The spec's own wording is "list operations". tools/call has no cursor, no size limit and no chunking in either revision. Every server that pages a tool result invents its own page, perPage, after or cursor argument, as GitHub did.

This is not for lack of asking. Issue #229, "Pagination for tool/call", has been open since 26 March 2025. Issue #798 proposed a paginationHint annotation and a pagination: {hasMore, nextCursor} block in tool results and was closed the day it was filed. Two proposals for streaming partial results were closed this year: SEP-2664 on 2 July and SEP-2998 on 22 September, with a maintainer noting that "every new SEP should be developed with the help of a Working Group". The roadmap, last updated 22 August 2026, lists a redesign of the tools/call result shape, "progressive discovery" and ETags for tool-call results. All three are planned. None has shipped or been given a date.

Two bloats, one of them addressed

The well-known context savings of the past year are mostly on the other side of this line. Anthropic's Tool Search cuts tool-definition tokens by about 85%; Cloudflare's Code Mode server describes 2,500-plus endpoints in about 1,000 tokens of definitions instead of 1.17 million; Cursor's folder of synced tool descriptions cut total agent tokens by 46.9% in runs that called an MCP tool. All three shrink the catalog the model reads before it calls anything. None of them makes a single list_pull_requests response smaller. The protocol pages the catalog, and so does most of the industry's optimisation work.

The file spill is not a page

Spilling to a file looks like the host solving the problem. The result is kept, the window is spared, and the model can read what it needs. Datadog's write-up notes that Cursor and Claude Code now do this and that it may make format efficiency matter less — and that it "is not in the MCP spec yet". In practice the file only helps if the model can read part of it and act on what it reads. Three reports show where that breaks.

  • Notion, #206 (February 2026). notion-fetch returned a 2,376-line, 41,207-token page as JSON compressed onto about 5 lines. Claude Code saved it to a file, but its Read tool pages by line offset, so five enormous lines could not be read in part, and reading the whole file failed with "exceeds maximum allowed tokens (25000)". The data was on disk and unreachable.
  • Atlassian, #106 (March 2026). A Confluence page's ADF body runs 50–70KB. The reporter says Claude Code persists outputs over about 20KB to disk, so the model never saw the body — and to call updateConfluencePage it would have had to emit about 15K tokens of it inline. Reading worked; editing what was read did not. The spill broke the round trip.
  • VS Code, #311068. A get_file_contents result of 50KB to 999KB is truncated before it reaches the model, with a hint to read the rest through a vscode-chat-response-resource:// URI. Reading that URI fails as "outside the workspace". Tested with 120KB and 233KB files on VS Code 1.116.0, the agent is simply stuck.

The hosts are adjusting. Claude Code 2.1.105 began giving the model format-specific recipes for oversized output — jq for JSON, chunk sizes for text — and 2.1.287 stopped telling Claude to page large JSON with Read's offset and limit. That second fix addresses the same trap the Notion report fell into. But each host fixes its own spill, on its own schedule. A server cannot rely on any of them.

What to do on the server side

The server is the one place that knows what a record contains and which fields matter. The four practices below come from the servers that stopped overflowing.

Count the page in tokens

Take a budget, not just a count: add records until the next would cross it, then return a cursor. Keep a record cap as well — it stops a page of tiny records from becoming a very long list — but let the budget decide where the page ends. Measure the budget the way the host will, and since hosts count both tokens and characters, cap both. The Block team's playbook for MCP servers puts the first step plainly: measure output before returning it.

Project before you page

Return the fields an agent will act on by default and make the full object something it asks for. GitHub's −93% came entirely from this, with no change to page size. Keep the identifiers, though. Anthropic's Slack example cut a response from 206 tokens to 72 with a concise format, and the concise form dropped the IDs that later calls need — so "minimal" has to mean minimal for the next call, not for display. Where the agent wants a number rather than rows, give it a way to aggregate, as Datadog's SQL tool does.

Put the truncation flag and the remedy in the result

The model should never have to guess whether it got everything. Fetch one more than the limit to know, say so in a field, and add a sentence on what to do next. Anthropic's tool-writing guidance asks for truncation text that steers the agent toward "many small and targeted searches". A sketch of the envelope, with field names of your choosing:

{
  "items": [ { "number": 4182, "title": "Fix cursor reset", "state": "open" } ],
  "returned": 40,
  "truncated": true,
  "reason": "token_budget",
  "nextCursor": "eyJvIjo0MH0",
  "hint": "More PRs match. Pass nextCursor for the next page, or narrow with state or author."
}

Design for the smallest host

Size your default page for the strictest host your users run, not for the one on your desk. That means under Claude Code's 25,000-token default — preferably under its 10,000-token warning — and under Gemini CLI's 40,000 characters. Claude Code lets a server raise a single tool's limit through _meta["anthropic/maxResultSizeChars"], up to 500,000 characters. That is one host's escape hatch, not a fix. If a result must go to a file, make the file line-structured so a reader that pages by line can use it, and don't build an edit flow that needs the model to re-emit a body it could not read.

FAQ

Does MCP support pagination for tool results?

No. As of the 2026-07-28 revision, MCP pagination covers only tools/list, resources/list, resources/templates/list and prompts/list. A tools/call result has no cursor, no size limit and no chunking, so a server that pages tool results has to define its own cursor argument.

Why did GitHub's MCP server overflow context windows if it paginated?

Its pages were counted in records, and its records were large — 5–6KB per commit and 17–36KB per pull request in the reported cases. A page of 30 could exceed 64k tokens. Minimal response types, not smaller pages, fixed it: PR #2563 cut project items by 93%.

What happens when an MCP tool result is too large in Claude Code?

Claude Code warns at 10,000 tokens and has a 25,000-token default cap, set with MAX_MCP_OUTPUT_TOKENS. A successful text result over the cap, or over 50,000 characters, is saved to a file, and the model gets a message with the file path. Error results over about 11,000 characters keep only the first and last 5,000.

How big should an MCP tool's page be?

Set it in tokens or characters, not records, and size it for the strictest host your users run — under Claude Code's 25,000-token default and Gemini CLI's 40,000-character truncation. Return a truncated flag, a cursor and a sentence on how to narrow the query.

Is the MCP spec going to add tool-result pagination?

Not soon. The roadmap updated in August 2026 plans a redesign of the tools/call result shape and ETags for tool-call results, with no date. Proposals for streaming and partial tool results were closed in July and September 2026, and maintainers now want new proposals developed through working groups.
