Pick one of these four because it "gets you reliable JSON" and you will discover the expensive truth on a Tuesday: every one of them guarantees parseable, none of them guarantees correct, and a required field the model has no answer for is a field it will fill in anyway. The real axis separating them is where the schema is enforced — after generation by retrying, during generation by masking tokens, around generation by a compiler, or upstream inside the vendor's API — and that single choice sets your retry bill, your provider portability, and whether the model can still tell you it does not know.

The question before the question

Constrained decoding guarantees syntactic validity. That is a real and useful guarantee, and it is smaller than the one people believe they bought. The values inside a perfectly-shaped object can be wrong, invented, or subtly worse than what the model would have written in prose — and because the object parses, every downstream system treats it as clean data. A schema is a type check, not a fact check.

The sharpest version of this is the required field. A schema that marks every field required is instructing the model to produce a value whether or not the input contains one, and the model complies: when a required field has no good answer, you get a confident invention wrapped in valid syntax rather than an admission of uncertainty. A schema with no slot for "I don't know" converts abstention into fabrication, and it does so invisibly, since the failure arrives as a well-typed string. The fix is not a better library — it is Optional, a confidence field, or an explicit not_found variant, so that not knowing is a representable state (see hallucination and grounding).

The second thing worth knowing before you choose: constraining generation is not free in quality terms. Masking the tokens a model wants to emit renormalizes the distribution over what is left, and can push generation down a non-canonical tokenization path it rarely saw in training. Published evaluations report performance degradation on the order of 10–15% on complex tasks under constrained generation compared with free-form, with schema field ordering a significant driver of the gap. That last detail is actionable in a way most quality findings are not: put reasoning fields before conclusion fields in the schema, because a model that must emit answer before rationale has committed before it has thought.

Instructor — deep dive

What it owns

Being unremarkable, in the best sense. You define a Pydantic model, you wrap your existing client, and it works — across 15+ providers, with a native TypeScript implementation alongside the Python one, at roughly three million monthly downloads. There is almost no new vocabulary to learn, which is why it remains the right default for most teams starting today.

What you get back

A typed object, or an exception once max_retries is exhausted. The interesting part is what happens in between: the validation error is fed back to the model as context for the next attempt, which is a genuinely good use of an LLM's strength — it is much better at fixing a named error than at avoiding an unnamed one.

What it makes hard

Knowing what you are spending. Each retry is another complete billed call, and the chart above is just arithmetic: at a 95% first-pass rate you pay 1.05 calls per object and will never notice, at 60% you pay 1.67, and at 40% you pay two and a half calls plus two extra round trips of latency for every object you produce. In an agent loop that re-sends its transcript each step, that multiplier lands on an already-superlinear bill (agent cost control). Instrument the retry rate per schema and treat a rising number as a schema design problem, not a budget problem — the schemas that retry are usually the over-constrained ones.

Outlines — deep dive

What it owns

The strongest guarantee available. Outlines compiles your schema — or regex, or grammar — into a state machine over the token vocabulary, and at each step masks every token that would make the output unparseable. There is no retry logic because there is no failure mode to retry: the sampler cannot emit invalid output. For a high-throughput extraction pipeline where every retry is real money, this is the structurally correct answer rather than the convenient one.

What you get back

Output that matches the grammar, first time, every time. It also handles constraints a JSON Schema cannot express at all — a regex, a fixed choice set, a domain-specific grammar — which is a capability the hosted options simply do not have.

What it makes hard

It needs the logits, which means it needs the sampler, which means local weights or a server you control such as vLLM. That single requirement excludes it from any stack built on a hosted frontier API, and it is not a limitation anyone can patch — masking logits you never receive is not possible. Worth knowing about the neighbourhood: xgrammar has become the default structured-output backend in vLLM, with JIT-compiled grammars that are faster for most schemas, while Outlines stays competitive when a complex schema is reused across thousands of requests and its compile cost amortises. Overhead itself has largely stopped being the objection — vLLM's V1 engine reports time-per-output-token only marginally above unconstrained decoding, where V0 could let a single constrained request degrade the whole server.

BAML — deep dive

What it owns

The claim that a purpose-built language is the right abstraction — the same argument that made SQL beat string-concatenated queries. A .baml file holds the function, the schema and the prompt together; a Rust compiler generates native typed clients for Python, TypeScript, Go, Ruby and others. At around 8,400 GitHub stars it is smaller than Instructor's community, and it ships updates weekly.

What you get back

A typed function call in each language, generated from one definition. If you have a Python service and a TypeScript front end both calling the same extraction, this is the only option here that keeps their types provably identical rather than conventionally identical — which is precisely the drift that produces a production bug six months in. BAML also brings its own parser, which repairs some malformed output that would fail a strict JSON load, so its practical failure rate sits below what the "enforced after" column suggests.

What it makes hard

A DSL and a build step. That is a real cost: a new file type in the repo, a code-generation stage in CI, a thing every new engineer has to learn, and errors surfaced at compile time rather than where the model call lives. The trade is earlier error detection and better autocomplete against slower iteration — worth it when the schema is shared across services and long-lived, hard to justify for one extraction in one script.

Provider structured outputs — deep dive

What it owns

Being already there. Send a JSON Schema with the request and the provider runs constrained decoding server-side — no dependency, no retry loop, no compile step. For the plain case of "give me this object," the vendors commoditized the problem, and that reframes what the libraries are for: everything around the schema, not the schema itself.

What you get back

Valid JSON matching your schema, guaranteed inside the subset the vendor supports — and that qualifier is the whole story.

What it makes hard

Portability, in a way that bites quietly. Each vendor honours a different slice of JSON Schema, and the parts that get dropped are the expressive ones — recursion, unions, conditional subschemas, certain string formats (JSON Schema subsets per vendor). A schema that works on one provider can be rejected by the next, or worse, silently accepted with a constraint ignored, so the model is free to violate exactly the rule you were relying on. If you have a gateway that fails over across providers, this is a behaviour change hiding inside an availability feature.

Cross-cutting comparison

The enforcement point is the whole taxonomy

Every difference that matters is downstream of the enforcement point. Enforcing after works everywhere and pays per failure, which makes Instructor maximally portable and maximally exposed to a bad first-pass rate. Enforcing during makes failure impossible and requires the sampler, which is why Outlines is the right answer on your own hardware and unavailable on a hosted frontier model. Enforcing around buys cross-language type identity and costs a toolchain. Enforcing upstream costs nothing to adopt and buys you one vendor's dialect. Ask where the constraint runs and the shortlist writes itself.

What is left to choose, now that JSON is solved

The libraries no longer compete on "can I get JSON out." They compete on the surrounding engineering: retries with the error fed back as context, streaming a partial object so a UI can render before generation finishes (streaming and partial output), one schema across several languages, a test runner for prompts, and portability across providers whose schema dialects disagree. Pick on which of those you actually need, and notice that for a single Python service calling one vendor, the honest answer is often none of them.

The schema is a prompt, so write it like one

The finding that field ordering measurably moves output quality is the tell: the schema is not a passive contract, it is part of the instruction. Three consequences worth acting on. Order fields so reasoning precedes conclusions, because generation is left to right and a model cannot revise a field it has already emitted. Make every field optional that could legitimately be absent, so the model has a way to be honest. And keep the schema shallow — deeply nested required structures are where both the retry rate and the quality degradation concentrate. Then validate semantics separately from shape, because no tool on this page will do it for you: a parseable object with a hallucinated invoice number passes every check described here.

FAQ

If the provider supports structured outputs, do I need a library at all?

For one service calling one vendor with simple objects, no — and saying so is the honest answer. Libraries earn their place when you need multi-provider portability, retries with error feedback, streaming partial objects, cross-language types, or constraints outside the vendor's supported subset.

Does constrained decoding make the model less accurate?

Sometimes, and it is measurable: published evaluations report roughly 10–15% degradation on complex tasks versus free-form generation, driven partly by non-canonical tokenization and partly by schema field ordering. The mitigation is schema design — reasoning fields first, shallow structures, optional where absence is legitimate — not abandoning structure.

What is the difference between structured outputs and tool calling?

Mechanically they are close cousins; both constrain the model to a schema. The difference is intent: a tool call is a request for your code to do something, a structured output is the answer itself. Some vendors implement one in terms of the other, which is why their reliability characteristics often match.

Is xgrammar a replacement for Outlines?

They occupy the same slot and you generally pick one. xgrammar has become the default backend in vLLM and is faster for most schemas thanks to JIT-compiled grammars; Outlines stays competitive when one complex schema is reused across thousands of requests so its compile cost amortises. Benchmark both on your schema rather than trusting either default.

Why does my extraction return plausible but wrong values instead of nulls?

Almost always because the field is required. A required field with no answer in the input is an instruction to invent one, and constrained decoding guarantees the invention will be well-typed. Make it optional, or add an explicit not-found variant.

Can I combine these?

Yes, and one combination is common: provider-native constraints for shape plus your own validation layer for semantics — units, ranges, referential integrity, cross-field consistency. That second layer is the one that catches real errors, and none of these four provide it.
