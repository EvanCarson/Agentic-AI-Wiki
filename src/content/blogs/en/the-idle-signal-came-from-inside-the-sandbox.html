For thirty years a platform decided your workload was idle by watching it from outside — CPU below a threshold, no requests for N seconds, a scheduler's timeout. Google's Agent Compute Engine, announced on 22 October 2026, inverts that: "when an agent finishes executing a tool call and enters the 'thinking' phase of the agentic loop, the microVM signals that it's idle, and the host moves it from an active to an idle state." That is the correct design, and it quietly makes your idle bill a property of your agent's code — which means the suspend boundary is now something you have to choose, evaluate and defend, not something the platform gets right on your behalf.

What was actually announced

Agent Compute Engine is described as "a purpose-built compute service that already powers Gemini as an agent for work tasks," giving "every Gemini agent its own high-performance, secure computer to act upon." It is not generally available: "it will be available in preview in the coming months," and "you will soon be able to use this service to power your own custom agents." So the thing to read it as is a published design from a platform already running it at scale internally, not a product you can buy this quarter.

Three mechanisms carry the whole post. Isolation is "a hardware-isolated Cloud Hypervisor boundary with its own guest kernel and root access," run on Titanium, Google's offload IPU, for what the post calls "silicon-rooted defense-in-depth built for untrusted AI agents." Density comes from "copy-on-write memory sharing to run multiple agents on a single operating system template." And the lifecycle is "pausing idle microVMs via fast checkpoint and restore," which the post says can also "pause a running microVM while an agent waits on a human or an external system, and quickly resume it from snapshots."

The numbers belong to the sibling, not to this

Agent Compute Engine's own section carries no performance figures — microVMs "boot rapidly" and that is all. The quantities in the announcement attach to Agent Substrate, the open-source GKE runtime launched alongside it: "as much as 10x higher compute density compared to traditional compute," and "in benchmark validation running 200,000 agents, Agent Substrate sustained 500 activations per second at less than 500 ms suspend and resume latency," with a Filestore integration quoted at "sub-second resume latency."

Those are the numbers worth planning against, and they are vendor benchmark numbers for a different product in the same family, so treat them as an order of magnitude rather than an SLO. The order of magnitude is the point: suspend and resume is a sub-second operation, not a free one.

Why moving the decision inside the box is right

An agent is the worst possible workload for utilisation-based idle detection. A long-horizon run alternates between bursts of real work — a tool call compiling something, a browser rendering a page — and stretches where the sandbox holds a checked-out repository, a warm interpreter and an open session while literally nothing executes, because the model is generating tokens somewhere else entirely. From outside, those stretches look exactly like a process that might resume at any millisecond, which is why the safe scheduler choice has always been to keep it warm. That is how a sandbox ends up billing about 66 cents of pure nothing through a four-hour approval wait.

Software inside the box knows the answer exactly. The harness just posted a tool result and is waiting for the next model response; there is nothing to schedule and nothing to lose. No amount of outside-in heuristics recovers that fact, and no timeout tuned to be safe can be aggressive. Giving the guest a way to say so is the first real improvement to this problem, and the design to copy whether or not you ever touch Google Cloud: the runtime that knows the loop's phase is the only thing that can declare the phase.

What you have just taken on

The flip side is that an idle signal is code, and code is a thing that can be absent, wrong, or late. Three consequences follow, and none of them is on the announcement.

  • An agent that never signals is billed as active forever. Your most expensive run becomes the one whose harness crashed in an unusual place, or whose custom tool wrapper swallowed the post-call hook. That failure is silent in every dashboard you own, because the sandbox looks healthy — it is healthy, it is just awake.
  • An agent that signals at the wrong boundary pays a resume on every step. Suspend at the end of each tool call and a twenty-step task eats twenty suspend-and-resume cycles. At the Agent Substrate order of magnitude that is a few seconds of added wall clock on a task where the thinking phases might have totalled less than that.
  • The signal is now part of your evaluation surface. "Did the run emit an idle signal at each quiescent point?" is a trajectory property, measurable the same way you measure whether a run called the right tool — and if you do not measure it, the regression that stops emitting it shows up first as a cloud invoice.

The suspend boundary is a latency decision wearing a cost costume

Work the arithmetic rather than the architecture. Suspending between steps saves you the held-resource cost of the thinking phase and charges you a suspend plus a resume. Whether that trade is positive is decided entirely by how long your thinking phase is, which is a property of your model and your effort budget, not of the platform.

A fast tool-calling loop with a small thinking budget sits in the top row: the wait is short, the saving is a fraction of a vCPU-second, and the cost is user-visible latency added to every single step. A reasoning model with a large effort budget can sit in the middle: tens of seconds of thinking is long enough that a sub-second resume disappears into it. And the bottom row — waiting on a human, waiting on a batch job, waiting on a webhook that may not arrive for hours — is the case where this is not an optimisation but a different cost structure, and it is the one the announcement names explicitly.

So the rule that falls out is narrower than "suspend when idle": suspend on the waits you can name, not on the gaps you can detect. A wait on a human or an external system is a semantic event your harness already knows about and can safely declare. The inter-step gap is a mechanical one, and tying a checkpoint to it converts a cost win into a latency tax that your p95 will find before your finance team does.

Two design details worth stealing immediately

The credential never enters the box

"Each microVM runs its agent's own identity, using short-lived credentials. Every microVM also gets its own cryptographically verified ID, and service credentials are injected in egress outside the microVM." Read that last clause slowly, because it is the strongest sentence in the post. The usual question about a sandbox is whether code can get out; the question that actually sets your blast radius is what the platform put inside before the agent started, and the answer here is: nothing worth stealing. Egress goes through Agent Gateway, the post's "air traffic controller for client-to-agent and agents-to-anywhere traffic," and the gateway attaches the credential.

Be precise about what that buys. A prompt-injected agent inside the box still gets to make requests, and the gateway will still attach the credential to them — this is confused deputy, unchanged. What it removes is exfiltration of the secret itself: the token cannot be read, logged, copied into a file or carried into the next session, because it was never resident. That is a genuine reduction in the worst case and it is independent of the hypervisor, which is why it is worth implementing on any sandbox you run.

The snapshot is state with no retention policy

Fast checkpoint and restore means guest memory is now a durable artifact, and guest memory mid-task is the agent's working set: the tool results it just read, the document it just fetched, the customer record it was reasoning over. Transcripts have retention rules and redaction pipelines because somebody classified them as conversation data. Snapshots get lifecycle rules written by infrastructure teams who classified them as machine images.

The credential design above partly saves you here — a snapshot that never contained a token is a much less interesting object — but it does not save you from the content. If your answer to "where is this user's data" has to be complete, add "and in any checkpoint of the sandbox that was processing it" to the list, before someone else does. This is the same obligation that durable state created for every other resumable system, arriving in a form that does not look like a database.

What to do about it this quarter

Agent Compute Engine is in preview "in the coming months," so nothing here is a migration plan. It is a specification of a design that two Google runtimes now implement, and most of it is portable to whatever you are running today.

  • Find your longest wait and instrument it. Not average sandbox lifetime — the specific named waits: human approval, external job, scheduled retry. Multiply held-resource cost by that duration by run volume. If the number is small, none of this matters to you yet.
  • Make the harness declare quiescence explicitly. Even without checkpointing, an explicit "this run is parked on X" event is what lets you release a sandbox, drop a pool slot, or hand the warm sandbox to someone else. The signal is useful before the suspend mechanism exists.
  • Do not checkpoint between steps because a vendor can. Measure your thinking-phase distribution first. If the median gap is shorter than a resume, per-step suspension is a latency regression you will ship as a cost optimisation.
  • Move credentials out of the sandbox regardless. This one needs no new platform: a proxy that attaches the token on egress is an afternoon's work and it changes what a compromise is worth.
  • Classify your snapshots as content. Whoever owns transcript retention should own checkpoint retention, and should know they own it.

FAQ

Can I use Agent Compute Engine today?

No. The announcement of 22 October 2026 says it already powers Gemini as an agent for work tasks and that it "will be available in preview in the coming months," with support for custom agents coming after that. Treat it as a published design rather than an available product.

How fast is suspend and resume?

Google published no figures for Agent Compute Engine itself. The numbers in the same announcement belong to Agent Substrate, its open-source GKE sibling: 500 activations per second at under 500 ms suspend and resume latency in a 200,000-agent benchmark, and sub-second resume via Filestore. Those are vendor benchmarks for a different runtime, so plan to the order of magnitude, not the digit.

Does checkpointing a microVM between tool calls save money?

Only when the gap it covers is long. The saving is held-resource cost for the duration of the thinking phase; the charge is one suspend plus one resume, on the critical path. For a fast tool-calling loop the gap is often shorter than the resume, which makes per-step suspension a latency cost dressed as a cost saving. For a wait on a human or an external job it is clearly positive.

If credentials are injected at egress, is prompt injection solved?

No. An injected agent can still make requests, and the gateway still attaches the credential to those requests — the deputy is still confused. What the design removes is theft of the secret itself, because it was never inside the sandbox to read.

What does an idle signal mean for my evals?

It becomes a trajectory property. Whether a run emitted an idle signal at each quiescent point is measurable in a trace the same way tool choice is, and it is worth asserting, because a regression that stops emitting it does not fail any test — it raises an invoice.
