Somebody will tell you this quarter that agent prompt injection has a 27% success rate, or an 84% one, and both will be citing a real paper correctly. The spread is not disagreement and it is not model variance — it is four benchmarks measuring four different attack surfaces with four different success conditions. An attack success rate quoted without its benchmark is not a weak number; it is not a number at all.

Putting the headline numbers on one axis, so you can see why you should not

Read the chart as a diagnostic of the benchmarks rather than a ranking of risk. The 100% at the top and the 24% at the bottom are not measuring the same event. VPI-Bench's browser-use figure counts an agent that executed an instruction rendered into a page it was told to read, in an architecture that hands it the attacker's text as an addressable node. InjecAgent's 24% counts a specific model, under a specific prompting strategy, completing a specific attacker goal in a single step. Agent Security Bench's 27.55% for indirect injection and 84.30% for mixed attacks come from the same paper and differ by a factor of three, which is the cleanest possible demonstration that the attack composition sets the number.

The practical consequence: when a vendor tells you their guard reduces attack success from X to Y, the first question is not "by how much" but "on which benchmark, against which channel, and what happened to the task". We have made that argument from the defence side in evaluating guardrails and detectors; this post is the same argument read off the benchmarks themselves.

What each one is actually for

AgentDojo — the one that measures the cost of the defence

AgentDojo puts 97 user tasks and 629 security test cases across four simulated suites — a workspace, Slack, travel booking and banking — and reports three numbers: benign utility (user tasks solved with no attack present), utility under attack (security cases where the user's task was solved and no adversarial side effect occurred), and targeted attack success rate. It checks the resulting environment state with formal assertions rather than asking a model to judge, which matters more than it sounds: a model judge is itself injectable, so a benchmark that uses one has a defect in the same class as the one it is measuring.

That three-metric shape is why AgentDojo is the one to run first if you are shipping a defence rather than writing a paper. A filter that drives targeted ASR to zero by refusing everything scores perfectly on any benchmark that only reports ASR. AgentDojo is the one that makes you publish what the refusal cost.

InjecAgent — the cheap, narrow regression test

InjecAgent is single-step: one tool response carries the injection, one attacker goal, two harm categories (direct harm and data stealing), and an enhanced setting that prepends a hacking prompt to the injected instruction. Its 1,054 cases over 17 user tools and 62 attacker tools make it fast and completely deterministic in shape, and its headline result — ReAct-prompted GPT-4 attacked 24% of the time, with some open-weight models reported well above 80% — is now mostly of historical interest as a model comparison.

It is still the right first thing to wire into CI, precisely because it is narrow. A single-step benchmark gives you a signal that moves when your sanitisation changes and does not move when your orchestration does, which is what a regression test is supposed to do. Treat it as a unit test and AgentDojo as the integration test.

Agent Security Bench — the attack/defence matrix

ASB is the broadest of the four: 10 scenarios (e-commerce, autonomous driving, finance and others), 10 agents, over 400 tools, 27 attack and defence methods and 7 evaluation metrics, run across 13 LLM backbones. Its per-attack averages are the most useful thing in the paper: direct prompt injection 72.68%, indirect prompt injection 27.55%, memory poisoning 7.92%, with mixed attacks highest at 84.30%. The paper's own conclusion about the defence side is that current defences show limited effectiveness.

Note what the ranking tells you. Direct injection — where the attacker controls the user turn — succeeds nearly three times as often as indirect, and memory poisoning succeeds least often per attempt. That last number is the one most often misread: a 7.92% per-attempt rate on a channel that persists is not reassuring, because the attacker gets to try repeatedly and a success survives the session.

VPI-Bench — the channel the other three cannot see

VPI-Bench carries the attack in rendered pixels: a webpage or application displays a malicious instruction and the benchmark records both whether the agent attempted the attacker's action and whether it completed it, over 306 cases across five platforms. The split that matters is architectural rather than about model quality — up to 51% against computer-use agents working from screenshots, up to 100% against browser-use agents handed an extracted page description in which the attacker's text is already a first-class node. The paper also reports that system-prompt defences produce only limited improvement.

If your agent takes screenshots or consumes an accessibility tree, the other three benchmarks tell you nothing about your main attack surface, because all of their controls and all of their attacks are strings. We work that through in visual prompt injection, including why a screenshot classifier cannot be a gate.

The axis almost nobody reports, and the one almost everybody games

Three of the four report attack success as the headline. One of them makes you report what the user's task did while the attack was running. That asymmetry is the single most useful thing in this comparison, because the cheapest way to improve an ASR number is to make the agent worse.

Work it on a support agent handling 2,000 tickets a day with a baseline 70% automated resolution. A filter that cuts targeted ASR from 8% to 1% looks excellent. If it also drops resolution to 58%, you have traded 240 resolved tickets a day — about 9,000 a quarter, each landing in a human queue — for 140 prevented attacks a day. That may still be the right trade in banking and clearly the wrong one in a help desk, but you cannot even have the argument unless somebody measured the second number. A benchmark that reports only ASR structurally hides the side of the trade that costs money.

The same asymmetry explains a result worth keeping in view: a validity audit of tool-calling evaluation (arXiv 2607.02577) had experts review 496 tasks from four tool-calling benchmarks and found 92 evaluator–human disagreements, an 18.5% misalignment rate. Security benchmarks are not exempt from that class of problem. Which is the argument for AgentDojo's design choice — formal state assertions over a model judge — and the argument for not treating any single published delta as proof your defence works.

And the composite rule that is worth more than any single choice: run the benchmark whose channel matches your architecture, then re-run your own recorded traces. Public benchmarks tell you whether a defence class works; only your own replayed traces tell you whether it works on your tools, with your scopes, against the content your agent actually reads.

FAQ

Why do reported attack success rates range from 24% to 100%?

Because the four benchmarks define the attack channel and the success condition differently. VPI-Bench's 100% is a browser-use agent executing an instruction rendered into a page; InjecAgent's 24% is one model under one prompting strategy completing one attacker goal in a single step. The spread is a property of the harnesses, not of the models.

Which prompt-injection benchmark should I run first?

Match the channel to your architecture. Tool outputs: AgentDojo. Persistent memory: Agent Security Bench. Screenshots or an accessibility tree: VPI-Bench. If you are shipping a defence rather than comparing models, start with AgentDojo, because it reports utility under attack as well as attack success.

What is "utility under attack" and why does it matter?

It is the fraction of security cases in which the user's task was completed and no adversarial side effect occurred. It matters because the cheapest way to reduce attack success is to make the agent refuse more, and a benchmark that reports only attack success rate cannot distinguish a good defence from a broken agent.

Is memory poisoning less dangerous than prompt injection?

Not in the way the per-attempt figures suggest. Agent Security Bench reports 7.92% for memory poisoning against 72.68% for direct injection, but memory persists: the attacker can retry, and one success outlives the session rather than ending with it.

Can I compare scores across these four benchmarks?

No, and not across versions of one benchmark either — BFCL v3 and v4 are documented as non-cross-comparable suites, and the same caution applies here. Compare a defence against itself on one benchmark, before and after.
