所有人都读成「智能体现在能付钱了」的那份公告里，真正要紧的是一句话，而它讲的是强制执行、不是付款：AWS 说，对智能体采购的花费限额，是在基础设施层以确定性方式强制执行的。没有人要求模型对钱小心。这就是整套设计，它与动作护栏是同一个结构性动作，也正是智能体采购在云控制台这边比在消费端店面早好几年可用的原因。

速览

三个日期——因为这件事的形状，排成序列看比当成一次发布看要清楚得多。

时间发生了什么为什么重要
1997 年 1 月 HTTP 402 Payment Required 被写入规范，并标注为「保留供将来使用」 这条通道存在了 28 年，却没有东西要它载
2026 年 4 月 Amazon Bedrock AgentCore 的 Payments 能力进入预览，由 AWS 与 Coinbase、Stripe 共同构建 智能体有了结清一份报价的办法——偏加密、仅面向开发者
2026 年 11 月 19 日 AWS 把它延伸到 AWS Marketplace：按请求以美元付费，记入买方的 AWS 账单 付款不再是钱包问题，而成了计费与策略问题

机制如下，取自 AWS 自己的公告与文档：智能体通过 AgentCore Gateway 的 Marketplace 连接器发现一条商品列表；卖方端点对一个未付费的请求返回 402 与一份报价；智能体请求支付服务去结清它；费用落在买方的 AWS 账单上，并出现在 CloudTrail 与 Cost Explorer 中。买方配置一个 Payment Manager、在支付会话上设定花费限额，并维护一份被批准的卖方名单。卖方必须在 AWS Marketplace 注册，并集成其 x402 SDK。

付款这一步从来不是难处

把这份公告剥到只剩协议，你得到的是：一个请求、一个 402、一份报价、一次结清调用。这不是难题，从来也不是。HTTP 为这件事准备的状态码自 1997 年 1 月就在那儿了——那时 402 Payment Required 被写进规范，随即被标注为「保留供将来使用」，而它在网络的大半生里就一直待在那里。Coinbase 在 2025 年以 x402 之名把它复活，用于稳定币支付；AWS 如今把它指向了一张发票。

真正难的那一半——也是过去十八个月里每一个智能体商务协议都在绕着转的那一半——是授权问题。不是钱怎么动，而是：凭谁的授权、付给谁、为什么、最多多少、多久一次，以及谁有权撤回。AP2 的 mandate、Agentic Commerce Protocol 的受托支付令牌、卡组织的智能体交易标记，全都是对这个问题的尝试；这也正是为什么一篇关于这些通道的对比（Poppy vs UCP vs ACP vs AP2）读起来像是在比较同意模型，而不是在比较支付格式。

照这个角度读这次 AWS 的发布，那个 402 就是个脚注。产品是它外面那层信封。

「在基础设施层以确定性方式强制执行」

这句话出自 AWS 自己对 AgentCore Payments 的描述，是这次发布里最重要的一句话，而值得把「它排除掉了什么」说清楚。它并不承诺那些限额选得好、给得大，或者不容易配错。它陈述的是这个决定住在哪里：住在模型之外，住在一个被模型调用、而不是能被模型说服的组件里。

把一个团队本可以采用的三种做法摆在一起比较：

  • 把预算告诉模型。在系统提示里写「你今天最多可以花 50 美元」，然后指望它。这是模型属性，不是控制；它的有效期恰好等于「上下文里没有别的东西说反话」的时长，而在一个会读网页和 API 响应的智能体里，那不会很长。
  • 让一个模型来检查。让第二个模型逐笔裁定被提议的采购。好一些，但仍然是一个带假阴率的分类器——这条论证在用大白话讲护栏里走了一遍：最好的提示词注入检测器所公布的召回率，在一个读过这个检测器的攻击者面前会塌掉。
  • 让一个整数来检查。把一个数字和一个数字比，把一个卖方字符串和一份名单比，而且是在智能体碰不到的代码里。误报率在构造上就是零，而一个被检索到的网页里再有说服力的文字，也改不了这个答案。

AWS 上的是第三种。这与「动作护栏区别于输入过滤器」是同一件事；而这个区分在这里比在几乎任何别处都更要紧，原因是：采购是不可逆步骤的典型样本——退款退回的是钱，但它没法把一托盘货退回去、没法把一条已发布的商品撤下来、也没法把已消耗的 API 额度退回来。它所例示的那条架构规则，适用范围远超支付：如果一个智能体的动作不可逆，那么约束它的东西应当是结构性的，而模型应当只是那个提议的东西，永远不是那个许可的东西。

这件事对提示词注入意味着什么也值得直说，因为「智能体现在能花钱了」听起来像是会让注入变得更糟。它并没有把攻击者的能力提升多少，而这恰恰是把限额放到外面的意义：一次成功的注入能让智能体想买点什么，然后也仍然只能从你名单上的卖方那里买，且不超过你的上限。它真正改变的，是一次配置错误的价值。一个按账户而不是按会话设定的上限，配上四十个并行子智能体，就是一个被乘了四十倍的上限——所以面对控制台时，第一个该问的问题不是「有没有限额」，而是「限额是按什么范围计的」。

为什么它落在控制台、而不是店面

同一家公司，其零售一侧在 2026 年整年都在拦截第三方购物智能体——九月以「使用条件」为由切断 Meta 的 Muse，以及更早与 Perplexity 浏览器智能体的那场交锋——如今却把智能体采购做成了自家云上一项有文档的功能。当成企业行为来读，它看起来前后不一。当成基础设施来读，它一点也不矛盾，而差别就在一个前提条件上。

AWS Marketplace 的买方本来就有一个账户、一段计费关系、一个为 API 调用签名的身份、一份审计日志，以及一条商业争议路径。授权的那四个维度，每一个都有地方可以挂。而站在消费端店面前的智能体什么都没有：它以一个身份不明的第三方到场，可能还拿着某个人的凭据，店面与它的运营方之间没有任何合同，商家也没有办法把一个被授权的购物者、一个爬虫和一个攻击者区分开。这就是机器人验证与智能体访问里那个结构性问题，也正是为什么店面理性的做法是先拦、而控制台理性的做法是上线。

所以结论不是「智能体商务来了」。结论是：智能体商务会落在那些买方本来就有一张账单的地方——而这能预测它接下来的顺序。下一步要在采购系统、企业卡平台，以及双方本来就是合约对手方的垂类市场里看到它；而开放的消费互联网会继续慢下去，直到某种类似「可验证的智能体身份」的东西到位。通道从来不是瓶颈，计费关系才是。

买方仍然得自己建的那一半

平台覆盖了采购授权四个维度中的两个——比此前任何通道都多，但仍然不是一套完整的控制。剩下的是：

  • 速率，而不只是金额。日上限和每分钟限额是两种不同的控制，而其中只有一种能把正常负载和重试循环区分开。一个设在「预期的五倍」上的上限，会被一个不到一分钟就把它抽干的循环满足——每天如此，而且全在策略之内。这段账在当智能体可以买东西里算过。
  • 比商品更窄的范围。「这个卖方被批准了」不等于「这个任务可以买这个」。把采购授权绑到任务上、而不是绑到智能体上，就是「有界授权」和「长期授权」的区别。
  • 与运行的那一连。一笔你的财务没法归因到某条 trace 的费用，就是一条审计发现；而事后重建这份归因，比现在就把 trace id 放进幂等键里要难得多。请在结清之前记录下被提议的采购，这样一笔没有对应提议的费用才能作为一类独立的失效被检测出来。
  • 怎么解开。这条通道里没有任何东西规定：谁来取消智能体创建的那项订阅、总闸拉下时在途采购怎么办、谁去发起争议。一份 9 美元、自动续期的年度许可，是比一笔 900 美元一次性支出更糟的授权，而没有任何花费限额能表达这个差别。

以上都不是对这次发布的批评。这是平台与使用者之间正常的分工，而这次发布特别有用的一点恰恰是：它把这条分界画清楚了——你现在能准确指出哪一半归你。

常见问题

x402 是一个加密货币协议吗？

它起步时是——Coinbase 在 2025 年把 HTTP 402 复活用于稳定币结算——但这个状态码本身与支付方式无关，而且早在 1997 年 1 月的 HTTP/1.1 规范里就有了。AWS Marketplace 这条路以美元对买方的 AWS 账单结清，不涉及钱包，也不涉及稳定币。

这是不是意味着智能体可以买 AWS Marketplace 上的任何东西？

不是。按公告所述，它覆盖的是那些卖方已注册智能体商务、并集成了 AWS Marketplace x402 SDK 的商品；此外买方还要维护一份被批准的卖方名单与花费限额。范围按设计就是窄的，而对一个第一版来说，这个形状是对的。

一个花费限额能保护我免受提示词注入吗？

部分能，而这就是诚实的答案。它约束金额与对手方，所以一次成功的注入不能从任意卖方那里买、也不能超过你的上限。它挡不住智能体买错了一个「被允许的东西」，而且如果限额是按账户计、你的智能体却并行跑四十个会话，它也帮不上忙。

在控制台里我该先检查什么？

限额是按什么范围计的——会话、payment manager，还是账户——因为这一个事实就决定了一次并行扇出能把上限花掉一遍还是很多遍。然后是：到底有没有速率限制，而不只是一个总额。

为什么退款解决不了不可逆性问题？

因为钱是退款唯一能逆转的部分。发出去的货、已发布的商品、被消耗的额度、已被通知的对手方、已创建的订阅，全都留了下来；而在一笔采购里，它们往往比金额更要紧。
