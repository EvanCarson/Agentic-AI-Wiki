四家厂商在六个月里先后交付了「智能体身份」，而真正要紧的对比不是谁给智能体的目录条目更好看——而是在你吊销它之后五分钟，这个智能体手上还握着什么。在这条轴上，四款产品差得不是一点；其中两款的差别要花钱买，另外两款厂商压根没说。

一眼概览

下表的日期与价格来自各厂商自己的公布；而「未作说明」正是对一个它们谁都没发布过答案的问题的如实回答。

产品上线时间智能体拿到什么吊销能停掉什么
Okta Agent SSO 2026-08-24 正式可用 Universal Directory 身份，外加按连接签发的短命令牌 下一次令牌交换
Microsoft Entra Agent ID 2026 年 4 月正式可用（据 Entra 发布说明） 每个智能体一个目录对象，所有 Entra 客户可用 那个对象——强制执行需要 Agent 365
Gemini Enterprise 智能体 2026-10-08 公布，私有预览 一个带自有地址与审计轨迹的 Workspace 账号 那个账号；子智能体未作说明
1Password for Agents 2026 年 10 月公布 不给身份——给一次智能体读不到的代填 下一次请求

两种不同的形态，卖在同一个词下面

这四款里有三款是签发方。它们为智能体造出一个主体，并交给它一样东西拿着。第四款是代理方：它什么都不造，自己拿着秘密，只把它释放进一张登录表单——智能体能用，但读不到。两种形态都站得住。它们回答的是不同的问题；而一场把「智能体身份」当成单一品类来谈的采购会议，会买下其中一个、却以为自己拿到了另一个。

签发方回答的是是谁在调用。代理方回答的是什么会泄漏。一个被提示词注入攻陷的智能体并没有冒充任何人——它就是那个合法主体，正拿着自己的凭证做错事——所以签发方那个答案买到的是归因与一条吊销通路，不是预防。代理方那个答案买到的恰好相反：没有可供外带的东西，但也没有「哪个智能体做了什么」的记录。

Okta Agent SSO——吊销之所以快，是因为授权本来就短

Okta 随着 Agent SSO 于 2026 年 8 月 24 日正式可用，把开放的 Cross-App Access 标准并入了自家核心 SSO 产品，在核心 SSO 方案内不额外收费。当一个智能体连上某个企业应用时，它会被登记进 Universal Directory、与人类员工并列；Okta 则签发短命的、受身份治理的令牌，以取代存起来的凭证。Cross-App Access 去掉了运行时那块用户同意页面；这条连接改由 Okta 管理员来管。

为什么这是架构上最有意思的一款

机制是一枚 ID-JAG——Identity Assertion JWT Authorization Grant（身份断言 JWT 授权许可）——由 RFC 8693 的令牌交换与 RFC 7523 的 JWT bearer 许可组合而成。客户端握着它在 IdP 的登录，去申请一枚以某一台具体服务器为受众的 ID-JAG，再拿它到那台服务器换取访问令牌。这份许可本身并不是 bearer 凭证，而且明说了：交换响应里的 token_type 是 N_A。

由于 ID-JAG 是按受众、按有效期签发的，策略在每一次签发时都会被评估一遍——组成员关系、条件访问、设备姿态；而在 IdP 里的一次吊销，意味着下一次交换直接失败。这同时也是协议的答案，不只是 Okta 的答案：Cross-App Access 是企业托管授权（EMA）的底座，而 MCP 2026-07-28 规范把 EMA 与 Tasks、MCP Apps 并列列为正式扩展。我们在《企业托管授权》里把它的机制拆开讲过。

要留的那个保留意见，和 EMA 自带的那个一样：它授权的是连接，不是那一次工具调用。这里没有任何东西能决定 transfer_funds 能否在那个时辰、带着那些参数跑起来。

Entra Agent ID——身份是免费的，牵绳是要付钱的那部分

微软的 Entra 发布说明把 Agent ID 平台列为自 2026 年 4 月起正式可用，创建智能体身份对所有 Entra 客户开放，不过管理中心里的部分向导仍标着预览。每个智能体都成为一个一等的目录对象——这是正确的原语，也是最有可能熬过企业 IAM 未来十年的那一个。

把授权许可当成安全模型的一部分来读

微软的文档把面向智能体的那些安全控制——把条件访问与 ID Protection 延伸到智能体——圈在 Microsoft Agent 365 后面；后者于 2026 年 5 月 1 日正式可用，含在 Microsoft 365 E7 内，或单独购买每用户每月 15 美元。于是：目录条目一分钱不花，而让这个条目真正有意义的强制执行，是另一笔采购。各方资料对所需的底层订阅说法也不一致——这是一个「去查你自己的合约、而不是查某篇博文的摘要」的理由。

这个切分不是在抱怨定价；它是一个需要被规划进去的架构事实。一套只创建 Entra 智能体身份、却没买那个附加项的部署，拥有一份清册、一条审计轨迹和每个智能体一个名字——这些确有用处，也是智能体清册的基础——但它没有的那样东西，是一条在每次连接时都被评估的策略。另外也请注意：这个许可的报价单位是每用户、而不是每智能体——在一个人跑十一个智能体的世界里，这是对的形状。

Gemini Enterprise——邮箱是一种人真的看得见的身份

在 2026 年 10 月 8 日的 Gemini at Work 上，谷歌描述了会长期存在的「同事型」智能体：它们拿到自己的 Workspace 账号，审计日志归因到这个智能体而不是某个人类用户；而为较长的任务服务的临时子智能体，各自带着自己的身份。有报道把地址格式说成 @agents.company.com，谷歌并未在自家材料中确认过。它目前处于私有预览，未公布价格。

真正新的那个想法，和真正缺失的那个答案

给智能体一个邮箱不是花招。它让这个智能体在人们本来就在用的系统里变得「可寻址」，把它放进组织架构图，并让它产出的每一件制品都有一个作者——而这个作者不是某个被搞混的人类账号。在共享频道里，委托代理关系的混乱会制造归因问题，而这是对那个问题的一个真实回答。

未作说明的，恰是这场对比里最要紧的那部分。子智能体的身份是否会在任务结束时被吊销，以及子智能体的权限能否超出其父级——这两点都没有被发布过，而这两个问题就是一个会向下委派的智能体的全部影响半径。我们那一页《子智能体继承了什么》之所以存在，正因为答案几乎从来不是「什么都没继承」。

1Password for Agents——唯一回答了「什么会泄漏」的那一款

2026 年 10 月公布的 1Password for Agents，让智能体在全程都拿不到凭证的情况下完成登录。智能体用一枚唯一的数字密钥向 1Password 证明自己，用户批准或拒绝这一次具体的请求，然后 1Password 把秘密直接填进登录表单，而不是交到智能体手上。该公司把它描述为一个凭证代理（Credential Broker）：只在需要时释放秘密，且不把它暴露给智能体或底层模型。它对 1Password.com 上的个人与家庭账户免费。

在架构上，这是这一组里对「真正会制造事故的那个问题」最强的回答——智能体无法外带它从未持有过的密码，模型也无法记住它从未见过的密码。而它也是这里唯一一款没有定位在企业客户的产品。1Password 与 Okta 都表示在支持共用的身份标准，以便智能体经过核验的身份与授权上下文能在双方系统之间流转；但在那件事落地之前，你是在「归因」与「不暴露」之间做选择，而不是两样都拿到。

三款产品告诉你是哪个智能体打来的。一款确保它从未拿到过那个秘密。至今没有人把两者卖在同一张发票上。

常见问题

给智能体一个自己的身份，能挡住提示词注入吗？

不能。一个被攻陷的智能体就是那个合法主体，正拿着自己的凭证做错事；所以身份买到的是归因与一条吊销通路，而不是预防。真正限制损害的控制手段是逐工具策略、受限范围的凭证，以及短命的令牌。

什么是 ID-JAG？

Identity Assertion JWT Authorization Grant（身份断言 JWT 授权许可）：由企业 IdP 为某一个指名受众签发的短命断言，由 RFC 8693 的令牌交换与 RFC 7523 的 JWT bearer 许可组合而成。它不是 bearer 凭证——交换响应里报出的 token_type 是 N_A——它要被拿到目标服务器去换取访问令牌。

Entra Agent ID 单独用够了吗？

就清册、命名与审计而言，够了。就强制执行而言，微软的文档把面向智能体的条件访问与 ID Protection 都导向 Microsoft Agent 365，而那是一份单独的许可：每用户每月 15 美元，或者含在 Microsoft 365 E7 里。

我能把凭证代理和企业身份签发方组合起来用吗？

今天还没有这样一款已上市的产品。1Password 与 Okta 各自表示在支持共用标准，以便经核验的智能体身份与授权上下文能跨系统流转；但在那件事存在之前，你是在挑选「先解决问题的哪一半」。

MCP 实际用的是其中哪一个？

Okta Agent SSO 背后的 Cross-App Access 流程，正是 MCP 的企业托管授权扩展所建立于其上的东西；而该扩展在 2026-07-28 规范里与 Tasks、MCP Apps 并列列出。另外三款是平台身份产品，而不是 MCP 的机制。
