面向 agent skill 与 MCP 服务器的四个知名安全工具里，有三个回答的是同一个问题——这东西现在危险吗？——而且三者昨天都还有提交。第四个回答的，才是装完之后真正要紧的那个问题：这还是你批准过的那一份吗？它把配置钉住，一旦有变更就拦住工具调用直到你重新批准；它在 2026 年 4 月归档，228 颗星，而对面 SkillSpector 有 27,593 颗。市场买走了仪表盘，让闸门烂在了那里。

先看全景

四者都是 Apache-2.0，都接受一台 MCP 服务器或一个 skill 目录作为输入。星数与最后一次提交时间为 GitHub API 在 2026 年 11 月 25 日的记录。

项目星数它读什么最后提交
NVIDIA SkillSpector 27,593 skill 包、仓库、zip、MCP 注册表条目 2026-11-24
Snyk Agent Scan 3,277 整机上已安装的 harness、MCP 配置与 skill 2026-11-24

NVIDIA SkillSpector——手里有数据的那个

它做什么

SkillSpector 能扫 git 仓库、URL、zip 文件、目录，以及单个 SKILL.md；在 skillspector mcp 模式下，它会遍历官方 MCP 注册表里的服务器。检测手段是横跨 17 个类别的 71 条漏洞模式——其中包括提示注入、数据外泄、供应链、MCP 最小权限与工具投毒检查——再加上基于 AST 的行为分析、污点追踪与 YARA 特征。它从不执行 skill 的代码。输出是 0–100 的风险分，映射到 LOW/MEDIUM/HIGH/CRITICAL，再映射到三种结论之一：SAFE、CAUTION、DO_NOT_INSTALL。

四者里它的 CI 故事讲得最完整：SARIF 2.1.0 与 JSON 输出，退出码 0 表示 SAFE 或 CAUTION、1 表示被闸门拦下、2 表示出错，并提供 --fail-on-findings、--fail-on-incomplete 与 --min-coverage 三道闸。可选的 LLM 阶段可以确认、反驳或补充解释一条发现，而确定性的发现无论如何都留在报告里——这个设计值得照抄，因为它意味着语义层只能增添上下文，不能悄悄删掉一次命中。

一个该改变你对 skill 看法的数字

SkillSpector 自己的 README 里有一组它归到 Liu et al.（2026）名下的数字：在一个被分析的 31,132 个 skill 的子集中，26.1% 含有漏洞，5.2% 表现出可能的恶意意图，而带可执行脚本的 skill 出现漏洞的可能性高 2.12 倍。就按它自己的措辞来理解第二个数字——"可能的恶意意图"是分类器的判断，不是法庭的判决——它说的仍然是：一个公开语料里大约每二十个 skill 就有一个在动手脚。这就是你的评审流程必须跑赢的基线，也是本文里支持"该扫"最有力的论据。

什么会离开你的机器

静态扫描在本地跑，skill 的代码也从不执行，但"本地"需要一条脚注。启用 LLM 分析时，符合分析条件的文件内容会被发到你配置的那家提供商。它的依赖检查即便在 --no-llm 之下也会把依赖名与版本查询 OSV.dev，连不上时退回到一份离线清单。--no-llm 把文件内容留在你机器上，但它并不让整次扫描密不透风。

上线前要配一件事：SkillSpector 自己也暴露一台 MCP 服务器，带一个 scan_skill 工具，好让智能体替自己扫描；而它的 HTTP 传输没有认证，只限回环地址。这是正确的默认值，同时也是一个提醒——一台你暴露给智能体的扫描器，也是目录里多出来的一台需要有人去审的服务器。

Snyk Agent Scan——换了东家的那个

从 mcp-scan 到一款厂商产品

2025 年 4 月 7 日创建、当时叫 Invariant Labs mcp-scan 的那个仓库——2025 年大半年里"我该怎么检查一台 MCP 服务器"的默认答案——如今解析到 snyk/agent-scan，工具也叫 Snyk Agent Scan 了。范围随着改名一起长大：它会自动发现机器上的 Claude、Cursor、VS Code、Windsurf、Gemini CLI 等智能体；从 v0.6 起，它为 MCP 服务器报出打过分的风险（提示注入、不可信内容、私密数据、破坏性能力），也为 skill 报出风险（可疑下载、恶意代码、凭据处理、密钥检测）。skill 扫描可用 --no-skills 关掉。

你在做的那笔交换

分析是一项服务。你导出一个 SNYK_TOKEN，工具便把智能体应用详情、MCP 服务器配置与签名、工具名称与描述，以及 skill 内容发出去做分析，配置值与文本中的密钥先行脱敏。它声明不存储也不记录使用数据，指的是 MCP 工具调用的内容与结果。README 正文里没有写出许可证名称，只链向一份 TERMS.md，并说明项目不接受外部贡献——尽管仓库自身的许可证字段仍写着 Apache-2.0，这种不一致该交给你自己的法务去解决，而不是交给一篇博客。

如果你智能体的工具描述本身就是机密——内部服务名、未公开的端点、一份私有 schema 的形状——那就是要掂量的地方。任何做语义推理的扫描器都必须读到那些文字；而这一个把它读到了别处。还要留意扫描本身为了检查工具做了什么：它会启动 stdio MCP 服务器、连上你配置的远端 URL，所以跑它就等于执行命令、发出外联请求。交互式运行默认开启确认提示，而 CI 路径被明明白白地拼成 --ci --dangerously-run-mcp-servers。这个 flag 的名字干的是诚实的活。

Cisco MCP Scanner——旋钮最多的那个

九个分析器，其中三个不花钱

就"愿意看什么"而言，Cisco 的扫描器是三个扫描器里最宽的：在线服务器上的工具、提示、资源与服务器指令；对 MCP 服务器源码做行为分析；PyPI 与 npm 包，默认在 Docker 沙箱里；Python 依赖经由 pip-audit；二进制文件经由 VirusTotal 哈希查询。分析器包括 YARA（支持自定义规则）、一个 LLM 分析器、Cisco AI Defense inspect API、带 20 条启发式规则的 readiness 分析器、检查是否缺少针对 12 类攻击向量防御的 prompt_defense 分析器，外加 vulnerable-package、virustotal、behavioral，以及一个需显式开启的 schema 分析器。readiness 与 prompt_defense 不需要任何 API key。

它也是最诚实地适配气隙流水线的那一个。static 子命令在不连在线服务器的情况下扫描预先生成的 JSON，这正是你在 CI 里想要的形状；把它与 YARA、readiness 组合，整次扫描不需要走出你的网络。LLM 与 API 分析器确实会外联——README 提到 LLM 这条路在 GPT-4o、GPT-4.1 与 AWS Bedrock 上的 Claude 4.5 Sonnet 上测过——所以离线配置是你逐个分析器做的选择，而不是一个一键打开的模式。

它会在哪里让你意外

大规模跑之前要知道两个默认值。VirusTotal 免费层允许每分钟 4 次、每天 500 次请求，而扫描器默认每个目录最多取 10 个文件，所以一次二进制偏多的扫描远在跑完之前就被限了速。另外 stdio 启动超时默认 60 秒——对一台健康的服务器足够宽裕，但也足够长，长到一台卡住的服务器会安静地吃掉你流水线的大半挂钟时间。

Trail of Bits mcp-context-protector——问出第二个问题的那个

首次使用即信任，并且在路径上强制

mcp-context-protector 不是扫描器。它是一个你放在宿主应用与服务器之间的包装器——stdio 用 --command、streamable HTTP 用 --url、旧式 SSE 用 --sse-url——因此它对任何 MCP 客户端都有效，而不要求宿主内部提供支持。连接建立时，以及每一次收到 notifications/tools/list_changed 时，它都会把服务器的配置与一份已批准的副本做比对。比对是语义层面的，覆盖服务器指令、工具描述与工具输入 schema，并忽略工具与参数的顺序，所以一次纯粹的重排不会虚报。批准结果存在 ~/.mcp-context-protector/servers.json；你用 --review-server 授予一次，它会连上去、把配置摊给你看，你接受它就存下来。

关键的那句话是：任何与已批准配置的偏离，都会拦住后续的工具调用，直到你显式批准新的那一份。这是一道闸，不是一条告警。而且服务器的身份由传输方式加上 URL 或精确的启动命令共同确定——在客户端配置里给服务器改个名没关系，但改动命令字符串会让它成为一台需要重新批准的新服务器，这个方向上的保守是对的。

它还会读回来的东西

设置了 --guardrail-provider（比如 LlamaFirewall）之后，每一个工具响应都会被扫一遍提示注入。检出之后，响应既不会被改写也不会被丢弃：它被写入 ~/.mcp-context-protector/quarantine.json，宿主应用收到的是提供商的输出，你用 --review-quarantine 去复核；如果你批准，模型可以通过一个 quarantine_release 工具取回原文。它还会清理 ANSI 控制字符，并提供 --visualize-ansi-codes 让转义序列在排查时可读。本文的四个工具里，只有它会看到工具返回的结果。

而它已经归档了

228 颗星，最后一次提交 2026 年 4 月 14 日，仓库已归档。代码本身没什么问题——钉住配置的数据库格式很朴素，比对逻辑也属于那种经得起时间的东西——但在每一次工具调用的路径上放一个已归档的安全包装器，是一个决定，而不是一个默认值。它不会再跟进协议修订，而 2026-07-28 版的 MCP 改动不小（没有握手、没有 session id、每请求携带元数据），"它对我的服务器还管不管用"如今是一个你得自己回答的经验问题。

两个问题，以及为什么只有一个有人维护

一次判定是关于某个时刻的事实

拿检测质量去比这四个，会错过结构性的那个差别。SkillSpector、Snyk Agent Scan 与 Cisco MCP Scanner 读的都是声明出来的文字——指令、工具描述、schema、源码、依赖——对它推理，然后给出一个判断。这个判断对它们读到的那些字节成立，在它们读的那一天成立。三者都不坐在调用路径上，所以谁都无法发觉那些字节后来变了。mcp-context-protector 读得更少、记得更多：它对"一条工具描述是否危险"没有意见，只对"它是否还是你当初接受的那条描述"有意见。

哪个问题更要紧，取决于威胁。对一次从公开注册表来的一次性安装，风险集中在最初的内容上，扫描器才是对的工具——那个 5.2% 就是论据。对一台你已经调用了半年的服务器，最初的内容早有人审过，风险已经挪了位置：它现在在那次你没审的更新里。一次工具投毒式的改动，装在一条描述里发出来，在下一次调用时生效，而且不会出现在任何你正盯着的 diff 里。SkillSpector 的 skillspector baseline 加 --baseline 是这里的扫描器最接近抓住它的做法，但那是一次你得记得去触发的运行上的发现差异，不是一道会拦人的钉子。

数据会去的三个地方

把这些架构写成数据流，它们就干净地分开了。SkillSpector 把文件内容留在本地，除非你启用它的 LLM 阶段；而无论如何都会带着依赖名去问 OSV.dev。Snyk Agent Scan 把配置、工具名称与描述、skill 内容发给 Snyk 做分析，密钥先脱敏。Cisco MCP Scanner 可以只跑不需要 key 的分析器、全程不出你的网络，也可以带上 LLM 与 AI Defense 分析器、每次扫描都出去一趟。mcp-context-protector 默认什么都不往外发；配了 guardrail 提供商之后，提供商会看到工具响应。

它们都不做的那件事

四者都不判断某个工具一开始是否就该被允许调用。对一个既能读你的仓库、又能往互联网发帖的工具给出干净判定，是对一组致命三要素式能力组合的真实陈述，而那组合照样会伤到你。扫描是一项供应链控制；它不是受限凭据或出口管控的替代品，而把这些工具当成提示注入的防线来读，是买错东西最常见的那条路。

实操建议并不华丽：在安装时跑一个扫描器，而那把钉子自己拿着。给你批准的那份配置做哈希——服务器指令、每一个工具的名称、描述与输入 schema，顺序先归一化——把它和部署配置放在一起，并在每次启动与每一次 tools/list_changed 时比对。这是一百行代码，它永远不会被归档，而且当厂商格局再次挪位时，它是这套栈里仍然管用的那一部分。

常见问题

靠一个扫描器能挡住 MCP 工具投毒吗？

不能。扫描器判定的是它运行那天读到的文字，而以"批准之后改描述"形式到来的工具投毒对它是隐形的，除非你重跑扫描并比对结果。真正挡住它的控制，是一份被钉住的配置加一道重新批准的闸。

mcp-scan 后来怎么了？

2025 年 4 月创建、当时叫 Invariant Labs mcp-scan 的那个仓库，如今是 snyk/agent-scan，工具叫 Snyk Agent Scan。它需要一个 SNYK_TOKEN，并把配置、工具描述与 skill 内容发给 Snyk 做分析，密钥先行脱敏。

这些工具里有能完全离网运行的吗？

Cisco MCP Scanner 最接近：它的 static 子命令在没有在线服务器的情况下扫描预先生成的 JSON，而 YARA 与 readiness 分析器不需要任何 API key。SkillSpector 在 --no-llm 下把文件内容留在本地，但仍会带着依赖名去查 OSV.dev，并备有离线退回清单。Snyk Agent Scan 的分析是一项托管服务。

该在调用路径上用一个已归档的安全工具吗？

只在睁着眼的情况下。mcp-context-protector 的设计是扎实的，批准数据库也只是一个普通 JSON 文件，但它从 2026 年 4 月起就不再跟进协议，而 2026-07-28 那版 MCP 改动很大。要么拿你自己的服务器验一遍并把版本钉死，要么在你自己的网关里实现同一套"首次使用即信任"的比对。

公开的 skill 里究竟有多少真带恶意？

SkillSpector 的 README 引 Liu et al.（2026）：一个 31,132 个 skill 的子集中 26.1% 含有漏洞、5.2% 表现出可能的恶意意图，带脚本的 skill 出现漏洞的可能性高 2.12 倍。把第二个数字当作分类器对一个公开语料的判断，而不是对你自己注册表的测量。
