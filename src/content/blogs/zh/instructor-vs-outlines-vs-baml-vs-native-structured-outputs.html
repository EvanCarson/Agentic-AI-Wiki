如果你选这四个中的某一个，理由是它"能给你可靠的 JSON"，那你会在某个周二发现那条昂贵的真相：它们每一个都保证输出可解析，没有一个保证输出正确，而一个模型压根没有答案的必填字段，它照样会填。真正把它们分开的那根轴，是 schema 在哪里被强制——生成之后靠重试、生成之中靠掩蔽令牌、生成周围靠一个编译器，还是上游在厂商的 API 内部——而仅这一个选择，就定下了你的重试账单、你的厂商可移植性，以及模型还能不能告诉你"我不知道"。

速览

四个都能从一次模型调用中产出类型化对象的工具，位于技术栈的四个不同位置。

方案强制位置前置要求schema 未命中的代价
Instructor 生成之后 任意厂商客户端 再来一次完整计费调用
Outlines 生成之中 能访问 logits——本地或 vLLM 按构造不可能发生
BAML 生成周围 一个 DSL 文件与一个构建步骤 常被它自带的解析器修复
厂商原生 上游，服务端 一个支持你 schema 的厂商 在受支持子集内不可能发生

问题之前的那个问题

受约束解码保证的是语法有效。那是一份真实且有用的保证，而它比人们以为自己买到的那份要小。一个形状完美的对象里，值仍然可以是错的、是编出来的，或者比模型本会用散文写出来的更糟——而由于对象能解析，下游每一个系统都会把它当作干净数据。schema 是一次类型检查，不是一次事实核查。

这一点最锋利的版本是必填字段。一个把每个字段都标为必填的 schema，等于在指示模型无论输入里有没有值都要产出一个值，而模型会照办：当一个必填字段没有好答案时，你得到的是一个包在有效语法里的自信杜撰，而不是一句承认不确定。一个没有"我不知道"这一格的 schema，会把弃答变成编造，而且是无形地这么做的，因为失败是以一个类型良好的字符串的形式抵达的。修法不是换一个更好的库——而是 Optional、一个 confidence 字段，或一个显式的 not_found 变体，好让"不知道"成为一个可表达的状态（见幻觉与接地）。

选之前值得知道的第二件事：约束生成在质量上并不免费。掩蔽掉模型想输出的令牌，会在剩下的令牌上重新归一化分布，并可能把生成推上一条它在训练中很少见到的非规范分词路径。已发表的评测报告称，在受约束生成下，复杂任务上的表现相比自由生成会退化约 10–15%，而 schema 的字段顺序是这一落差的重要驱动因素。最后这条细节的可操作性强过多数质量结论：把推理类字段放在结论类字段之前，因为一个必须先输出 answer 再输出 rationale 的模型，是在思考之前就已经表态了。

Instructor——深入

它拿下的是什么

平淡无奇——这是最好意义上的平淡。你定义一个 Pydantic 模型、包住你已有的客户端，它就能用了——跨 15 家以上厂商，Python 之外还有一份原生的 TypeScript 实现，月下载量约三百万。几乎没有新词汇要学，这正是它至今仍是多数今天起步的团队正确默认选项的原因。

你拿回来的是什么

一个类型化对象，或者在 max_retries 用尽后的一个异常。有意思的部分发生在两者之间：校验错误会作为下一次尝试的上下文回喂给模型，而这确实用对了 LLM 的强项——它修正一个被点名的错误，远胜于避开一个没被点名的错误。

它让什么变难

搞清楚你在花多少钱。每次重试都是另一次完整的计费调用，而上面那张图不过是算术：首轮有效率 95% 时，你每个对象付 1.05 次调用，你永远不会注意到；60% 时付 1.67 次；40% 时，你为每一个产出的对象付两次半调用，外加两个额外往返的延迟。在一个每步都重发对话记录的智能体循环里，这个乘数会落在一份本已超线性的账单上（智能体成本控制）。按 schema 埋点统计重试率，并把上升的数字当作 schema 设计问题而不是预算问题——会重试的那些 schema，通常是被过度约束的那些。

Outlines——深入

它拿下的是什么

可得的最强保证。Outlines 把你的 schema——或正则、或语法——编译成一个覆盖令牌词表的状态机，并在每一步掩蔽掉一切会让输出无法解析的令牌。没有重试逻辑，因为没有可重试的失败模式：采样器无法输出无效内容。对一条每次重试都是真金白银的高吞吐抽取流水线，这是结构上正确的答案，而不是方便的答案。

你拿回来的是什么

符合语法的输出，第一次就符合，每次都符合。它还能处理 JSON Schema 压根表达不了的约束——一个正则、一个固定选项集、一门领域专用语法——而这是那些托管选项干脆没有的能力。

它让什么变难

它需要 logits，也就需要采样器，也就意味着本地权重或一个你自己掌控的服务器（如 vLLM）。仅这一条要求，就把它从任何搭在托管前沿 API 上的技术栈里排除了，而这不是谁能打补丁的局限——掩蔽你从未收到的 logits 是不可能的。这片邻域里值得知道的：xgrammar 已成为 vLLM 中默认的结构化输出后端，凭 JIT 编译的语法在多数 schema 上更快；而当一个复杂 schema 被成千上万次请求复用、其编译成本被摊薄时，Outlines 仍有竞争力。开销本身则大体不再是反对理由了——vLLM 的 V1 引擎报告的每输出令牌时间只略高于无约束解码，而在 V0 里，一个受约束的请求就可能拖垮整台服务器。

BAML——深入

它拿下的是什么

那个主张：一门专门设计的语言才是正确的抽象层——正是让 SQL 胜过字符串拼接查询的那个论点。一个 .baml 文件把函数、schema 与提示词放在一处；一个 Rust 编译器为 Python、TypeScript、Go、Ruby 等生成原生类型化客户端。约 8400 颗 GitHub star，社区比 Instructor 小，而它每周发版。

你拿回来的是什么

每种语言里的一个类型化函数调用，都由同一份定义生成。如果你有一个 Python 服务和一个 TypeScript 前端在调用同一次抽取，那么这是本文中唯一能让它们的类型"可证同一"而非"约定同一"的选项——而后者的漂移，正是六个月后引发一个生产 bug 的东西。BAML 还自带解析器，能修复一些会让严格 JSON 加载失败的畸形输出，所以它实际的失败率低于"生成之后强制"那一栏所暗示的水平。

它让什么变难

一门 DSL 加一个构建步骤。这是真实的成本：仓库里多一种文件类型、CI 里多一个代码生成阶段、每个新工程师都得学的一样东西，以及错误浮现在编译期而不是模型调用所在之处。这笔交换是"更早发现错误与更好的自动补全"换"更慢的迭代"——当 schema 跨服务共享且长期存活时值得，而为一个脚本里的一次抽取则难以自辩。

厂商原生结构化输出——深入

它拿下的是什么

它本来就在那儿。把一个 JSON Schema 随请求发出，厂商就会在服务端跑受约束解码——没有依赖、没有重试循环、没有编译步骤。对于"给我这个对象"这种朴素情形，厂商已经把这个问题商品化了，而这重新定义了那些库的用途：它们的战场是 schema 周围的一切，而不是 schema 本身。

你拿回来的是什么

符合你 schema 的有效 JSON，在厂商所支持的那个子集之内被保证——而那个限定语就是全部故事。

它让什么变难

可移植性，而且是以一种悄悄咬人的方式。每家厂商遵守的是 JSON Schema 的不同切片，而被丢掉的那些恰恰是表达力强的部分——递归、联合类型、条件子 schema、某些字符串格式（各厂商的 JSON Schema 子集）。一个在某家厂商上能用的 schema，可能被下一家拒绝，或者更糟：被静默接受、而某条约束被忽略，于是模型可以自由违反你正指望的那一条规则。如果你有一个会跨厂商故障转移的网关，那这就是一次藏在可用性功能里的行为变更。

横向对比

强制位置就是整套分类法

每一个要紧的差别，都位于强制位置的下游。在之后强制处处可用、按次失败付费，这让 Instructor 可移植性最强，也对糟糕的首轮有效率暴露最深。在之中强制让失败不可能发生、且需要采样器，这正是 Outlines 在你自己硬件上是正确答案、而在托管前沿模型上不可用的原因。在周围强制买到的是跨语言类型同一性，代价是一条工具链。在上游强制的采纳成本为零，买到的是一家厂商的方言。问一句"约束跑在哪里"，短名单就自己写出来了。

JSON 已被解决之后，还剩什么可选

这些库不再围绕"我能不能拿到 JSON"竞争了。它们竞争的是周边工程：把错误作为上下文回喂的重试、流式吐出部分对象好让界面在生成结束前就能渲染（流式输出与中间结果）、跨多种语言的同一份 schema、给提示词用的测试运行器，以及在 schema 方言彼此不一致的厂商之间的可移植性。按你真正需要哪一项来选，并且注意：对于一个只调用一家厂商的单个 Python 服务，诚实的答案往往是一个都不需要。

schema 就是提示词，所以要像写提示词那样写它

"字段顺序会可测量地改变输出质量"这个发现，就是那个破绽：schema 不是一份被动的契约，它是指令的一部分。有三条值得付诸行动的推论。给字段排序，让推理先于结论，因为生成是从左到右的，而模型无法修改一个它已经输出过的字段。把任何可能合法缺席的字段都设为可选，好让模型有办法诚实。并且保持 schema 扁平——深度嵌套的必填结构，正是重试率与质量退化共同聚集的地方。然后把语义校验与形状校验分开做，因为本文提到的任何工具都不会替你做：一个带着幻觉发票号的可解析对象，能通过这里描述的每一道检查。

常见问题

如果厂商已经支持结构化输出，我还需要库吗？

对于一个只调用一家厂商、处理简单对象的服务，不需要——而说出这一点才诚实。库挣得自己位置的场合是：你需要跨厂商可移植性、带错误回喂的重试、流式的部分对象、跨语言类型，或者厂商受支持子集之外的约束。

受约束解码会让模型不那么准确吗？

有时会，而且是可测量的：已发表的评测报告称，相比自由生成，复杂任务上会退化约 10–15%，部分源于非规范分词、部分源于 schema 的字段顺序。缓解手段是 schema 设计——推理字段在前、结构扁平、可以缺席的就设为可选——而不是放弃结构。

结构化输出与工具调用有什么区别？

机制上它们是近亲；两者都把模型约束到一个 schema 上。区别在意图：工具调用是请你的代码去做某件事，结构化输出本身就是答案。有些厂商用其中一个来实现另一个，这也是它们的可靠性特征常常一致的原因。

xgrammar 是 Outlines 的替代品吗？

它们占据同一个位置，你通常只选一个。xgrammar 已成为 vLLM 的默认后端，凭 JIT 编译的语法在多数 schema 上更快；而当一个复杂 schema 被成千上万次请求复用、编译成本被摊薄时，Outlines 仍有竞争力。在你自己的 schema 上把两个都测一遍，而不要相信任何一个默认值。

为什么我的抽取返回看似合理但错误的值，而不是 null？

几乎总是因为那个字段是必填的。一个输入中没有答案的必填字段，是一条"去编一个"的指令，而受约束解码保证这个编造的东西类型良好。把它设为可选，或加一个显式的"未找到"变体。

这些能组合起来用吗？

能，而且有一种组合很常见：用厂商原生约束管形状，加上你自己的校验层管语义——单位、取值范围、引用完整性、跨字段一致性。抓到真错误的是第二层，而这四者一个都不提供它。
