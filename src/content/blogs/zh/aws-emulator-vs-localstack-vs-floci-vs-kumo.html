按服务数量来挑本地 AWS 模拟器，你优化的恰好是那条帮不上你的轴。智能体调用一个模拟器没实现的 API，拿到的是一个桩或一个错误的错误码，于是它断定自己的代码有问题，接着不断修改本来能跑的代码，直到那个桩肯接受——而测试变绿了。唯一能保护你的那条轴，是这个项目是否告诉你它做错了什么；而截至 2026 年 11 月，这四个里恰好只有一个公开按服务的保真度分数和一份被追踪的自身缺口清单。

为什么服务数量是错的那个数字

每一篇比较这些工具的文章都以「各自覆盖多少个 AWS 服务」开场。这个数字几乎没用，理由有两个，而且彼此独立。

第一个理由是：它不是一个可比较的量。「支持 S3」可以指「你的代码会调用的那十二个操作，且错误语义正确」，也可以指「PutObject 与 GetObject 返回 200」。每个项目都按自己的标准定义「某服务已支持」，而那些标准彼此都不是同一个。把不可通约的单位加总，只会得到一个带着虚假精度的数字。

第二个理由专属于智能体，也正是该驱动这个决定的那一个。一个撞上未实现 API 的人类开发者通常能自己想明白——他有上下文去想「这个模拟器大概不做那个」。智能体并不可靠地持有那个先验，而它强烈倾向于假定故障出在自己身上。于是循环就这么跑起来：

损失不是那次浪费的迭代。损失在于，智能体那次修改是看起来合理的——它加了一次重试、放宽了一个断言、捕获了一个真实 AWS 从不抛出的异常——而那次修改落进了你的仓库，因为「看起来很防御性」而通过了评审，并且在代码遇上真实 AWS 时依然躺在那里。模拟器里一处缺失的功能不是一处「缺席」；在有智能体参与的循环里，它是一个主动产出「对能跑的代码的修改」的源头。这与智能体的预发布环境里论证的是同一种危害：给工具打 mock，删掉的恰恰是你本该看见的那些错误形状。

所以真正要紧的那条轴是缺口的可见性：在智能体开始编造理论之前，它或你的框架能否查出「这个行为未经验证」？这件事的讨论会很短，因为目前只有一个项目回答了它。

AWS Emulator——唯一公开自己做错了什么的那个

AWS 的这款是一个 Rust 工作区，每个服务一个 crate；截至 2026 年 11 月 13 日，main 上的清单列出 436 个服务成员。每个 crate 都带着该服务的 Smithy 模型——仓库把它描述为「驱动线上协议的那份东西」——以及一个据此生成服务声明的 build.rs，所以请求与响应的形状是从 AWS 自己发布的规范生成出来的，而不是推断出来的。

不过它的区别性特征并不是广度，而是保真度被测量并公开了。保真度分数随每个版本发布，缺口住在一个 issues/things-that-do-not-work/ 目录里，修好的条目会移到 issues/things-that-now-work/。支撑这些分数的测试位于一个单独的 CC0 仓库，其 README 声明每一条保真度测试都在至少两个 AWS 沙箱账号上验证过，并且没有任何保真度测试覆盖的行为就是未经验证的行为。那句话就是产品本身。AWS 是怎么走到那一步的——以及为什么这套流程在没有裁判的情况下搬不过来——我们在难的那部分是裁判里拆开讲了。

代价是真实的，而且大多在运维层面。从源码构建需要 target/ 至少 100 GB 空闲磁盘，因为 debug 构建会编译每一个服务 crate；预编译的 Linux 包可以避开这一点，而 Windows 与 macOS 走容器路径。它在 127.0.0.1:9297 上以自签名证书提供 HTTPS，所以你的 SDK 配置需要用它写出的那个 CA，而不是一个普通的 HTTP 端点——这与另外三个共有的 :4566 HTTP 惯例相比，是一处虽小但真实的差别。遥测默认开启。而且它只有几天大：没有积累下来的 Terraform 配方，没有多年的 Stack Overflow 答案。

有一个官方的智能体技能——aws agent-toolkit add-skill --skill-name aws-emulator，需要 AWS CLI 2.35.0 或更高。很方便；而它同时也是一个来自「不接受 pull request 的仓库」的、由智能体撰写的产物，所以请按你对待任何第三方技能的方式来对待它：装之前先读它。参见审查第三方技能。

LocalStack——既有霸主，以及那道功能闸门

LocalStack 是这个品类存在的原因：一个功能完备的本地 AWS 栈，以单个容器运行，Python 写成，约 65,000 星。如果你已经有一套本地 AWS 工作流，那它大概就是这个；而生态优势差距悬殊——Terraform 与 CDK 集成、Testcontainers 支持，以及十年里积累下来的、针对「刚刚坏掉的那个具体东西」的答案。

在把智能体指向它之前要弄清楚的是分层。社区版是 Apache-2.0 外加一份最终用户许可协议，而 LocalStack 自己的 README 声明 Pro 版支持额外的 API。这是一个正当的商业模式，而它对智能体工作流有一个具体后果：一个被闸住的 API 与一个缺失的 API，对智能体来说无法区分。它打到端点，没拿到真实行为，于是上面那张图里的循环就开始了。如果你跑社区版，请把你那些服务里哪些是 Pro 独占的逐条列出来、写进智能体的指令里，因为它不会去发现这条边界——它会围着它编理论。

当「生态集成的广度」比「知道自己的缺口」更要紧时选 LocalStack：一个已有 Terraform 固件的成熟仓库、一支已经熟练使用它的团队，或者你依赖它那许多非 AWS 的便利之一。

Floci——没有闸门的直接替换

Floci 是那个有意思的中间选项：MIT，Java，约 31,600 星，并且明确地站在分层模式的对面——「不需账号。不需 auth token。没有功能闸门。只要 docker compose up。」它在 http://localhost:4566 上服务，与 LocalStack 同端口同协议，而 README 把它作为直接替换提供：换掉镜像，继续走。任何已发布的 AWS region 都能用，在每个 partition 里都能用；而凭据可以是任何非空值，除非你显式启用更严格的按服务鉴权检查。

有一处设计说明值得比它得到的更多关注：README 说 Floci 在「进程内模拟会降低保真度」的地方使用真实 Docker 容器——点名了有状态数据库、连接密集型协议与运行时。这在「保真度最要紧」的那些情形下是正确的取舍，而它也意味着你的 CI 占用不是一个容器，而是一个会启动容器的容器。在受限的 runner 上请为此留预算。

Floci 还是一个家族而非单一工具：floci-az 对应 Azure，在 4577；floci-gcp 在 4588；floci-oci 在 4599。如果你智能体的集成测试跨多个云，那份一致性是选它而不选任何「仅限 AWS」方案的真实理由。

当你想要 LocalStack 的接口与生态假设、却不要那条付费边界时选 Floci；或者当你需要用同一种方式伪造不止一个云时。

Kumo——真正塞得进 CI 的那个

Kumo 是最小的，也是对自身范围最诚实的：一个用 Go 写的轻量 AWS 模拟器，MIT，约 1,500 星，83 个服务。它的 README 公开了一张在「arm64 Docker 宿主、4 CPU、8 GiB」上实测的占用表——容器镜像约 17 MB 压缩（磁盘上约 72 MB）、单个二进制约 44 MB、从 docker run 到首个 API 响应的冷启动约 0.12 秒、空闲内存约 9 MiB，而在一千个 S3 对象、一千条 SQS 消息与一千个 DynamoDB 条目之后约 20 MiB。

这些数字正是「每个测试用例一个模拟器」的样子，而这解锁了一种更重的选项支撑不起的模式：为每个测试起一个全新的空模拟器，没有跨测试状态需要推理。对智能体工作来说，这比听起来更要紧，因为共享的可变固件状态是让智能体的调试循环变得不自洽的可靠办法——它修好了这个测试，上一个测试留下的残渣变了，于是它又从头开始。通过 KUMO_DATA_DIR 提供的可选持久化，覆盖了「本地开发时你确实想让状态活过重启」的情形。

它的局限是广度。八十三个服务是一个真实的覆盖面——S3、DynamoDB 与 Streams、SQS、SNS、Lambda、ECS、EKS、RDS、Redshift 等等——而它远不是整个 AWS。当你的服务依赖落在那个集合里，并且你在意 CI 分钟数、测试隔离，或者想在开发者笔记本上跑一个模拟器而察觉不到时，选 Kumo。

何时选哪个

情形选因为
智能体无监督地写代码并自行验证 AWS Emulator 唯一会按服务、按版本声明「什么未经验证」的来源
已有 Terraform / CDK 本地工作流 LocalStack 生态深度；那些固件已经存在
撞上 Pro 边界，或需要多云伪造 Floci 同一接口、没有功能闸门、每个云都有同族模拟器
需要按测试隔离、CI 预算紧 Kumo 约 17 MB 与约 0.12 秒让「每个测试一个新实例」可行

无论你选哪个，请做两件事。把已知缺口写进你智能体的指令里，这样第一次未实现的调用产出的是一次停止，而不是一套理论。并且在任何东西合并之前保留一次真实 AWS 的集成运行，因为本页上的每一个选项都是「在那次运行上少花一点」的办法，而不是「把它删掉」的办法。

常见问题

AWS Emulator 会杀死 LocalStack 吗？

就现有证据而言不会。它带着一套公开的保真度叙事和一个广阔的生成覆盖面登场；LocalStack 带着十年的集成、配方与机构知识。压力最可能落在 Pro 分层的价值主张上——而那也正是 Floci 本来就在推的地方。

我能并排跑两个模拟器吗？

技术上可以——它们都是按端点配置的，而 Kumo 的占用让「再加一个」很便宜。但这很少值得：两个伪造意味着两套缺口，而你的智能体现在有两种自信地出错的方式。更推荐「一个模拟器 + 一次真实 AWS 运行」。

有了模拟器就不需要针对真实 AWS 测试了吗？

不是，而把它当成那样是主要的失败模式。模拟器放宽授权、跳过跨 region 行为、并近似错误语义。它们服务于快速的内层循环；一次真实集成运行仍然留在合并的关键路径上。

该不该告诉智能体它在跟哪个模拟器说话？

该，而且要明确说，并连同你那些服务的已知缺口清单一起给它。一个知道自己在模拟器上的智能体，能正确归因一个奇怪的错误；一个以为自己在 AWS 上的，会把它归因到你的代码。

为什么星标数和服务数量差别这么大？

因为星标衡量的是采用度与年龄，不是覆盖度。Kumo 星标最少，却公开了一张别人都没提供的占用表；AWS Emulator 的星标只有 LocalStack 的一小部分，而生成覆盖面比它们任何一个都大。这两个数字都不该替你定夺这件事。
