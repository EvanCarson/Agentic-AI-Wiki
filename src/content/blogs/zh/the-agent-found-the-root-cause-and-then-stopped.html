一个叫 ZeroOps 的产品在 2026 年 11 月 19 日发布，而它没有任何改动权限：Databricks 这个新智能体盯着作业、流水线与表，推断出某一个为什么坏了，然后在一个分支上提出修复方案，等人来处理。这份克制本身并不出奇——如今每一个严肃的生产运维智能体都是这么发的。真正值得为之去读这份公告的，是关于「它如何得出根因」的那一句，因为那一步跑在 Unity Catalog 的血缘之上，而这意味着被出售的能力，是你早就建好的那张依赖图。

Databricks 表示这次公测承接自一轮私有预览，而那轮预览是由对 80,000 多起客户流水线问题的观察塑形的——这是一个关于外部无法检视的语料的厂商数字，所以请把它读作「这些启发式从哪里来」的断言，而不是一项质量度量。该功能标为 Beta，由管理员按工作区启用，作用在工作区而非账户层级，并且文档中写明不符合 HIPAA。

诊断跑在一项资产上，而不是跑在模型上

数据平台上的根因分析，是一个穿着文本问题外衣的图问题。你看到的那个报错几乎从来不在故障所在之处：一个作业因为一个 null 挂了，而这个 null 之所以出现，是因为上游四跳处有个团队把一列改了名，而他们并不知道你在读他们的表。一个只拿到堆栈和 notebook 的模型，对此可以给出一个自信、合理而错误的答案——它没有任何办法知道第四跳存在。

把依赖图给它，问题的性质就变了。现在搜索空间是可枚举的：往上游走，把每张表的 schema 与新鲜度跟上一次成功运行做差异比较，候选集就塌缩成少数几个带时间戳的变更。Databricks 的表述对此很明确——血缘给了智能体完整的依赖图，正是它让智能体能把一次失败归因到一个代码 bug、上游三张表之外的一次 schema 变更，或另一条流水线写入的数据。

所以对这次发布的诚实读法不是「现在有智能体能修你的流水线了」。而是：如果你的资产都登记在册、如果血缘是完整的、如果你的新鲜度期望是声明过的，那么一个智能体就能替你做那次你本来凌晨三点手工做的上游遍历。这三个条件合起来是一次编目迁移，而大多数组织都在这件事的半途上。智能体是便宜的那一半。

在评测任何运维智能体之前，先把它一般化——无论是哪家厂商的产品，还是你自己做的：找到智能体对世界作出断言的那一步，然后问这一步读的是什么结构化资产。如果答案是「日志加模型的先验」，那么无论用什么模型，天花板都很低。本站对应的模式在工具错误恢复里；而它检索形态的版本在Graph RAG里。

批准闸门搬走了什么，而不是移除了什么

一个只提议的智能体，并不会减少人对生产所做的决定的数量。它改变的是这些决定是什么，而在你仔细看之前，这个改变并不显然是有利的。

之前：一个工程师被呼叫，花四十分钟查明上游有一列被改了名，用两分钟写出一个三行的修复，然后以很高的信心把它合并了——因为他刚刚花了四十分钟建立起对这次失败的心智模型。排查是成本所在，同时也正是合并的正当性所在。

之后：一个 pull request 已经在等着，还附了一份诊断。那个三行修复已经写好了。这位工程师现在的工作，是判断一个他并未亲自得出的结论是否正确——这是一件不同而且更难的认知任务，而且是在没有当年排查所建立的那份上下文的情况下做的。这正是每一个产出工件的智能体都会撞上的评审容量问题，也是为什么人员配置的结论是「不同的工作」，而不是「更少的工作」。本站的论述在智能体产出的评审队列，而人力成本的算式在人工评审的成本。

有两项缓解措施值得向任何厂商、以及向你自己做的任何东西坚持要求。第一，提议必须带着它的证据，而不只是它的结论：它归咎的那次上游变更，连同链接与时间戳，这样评审者可以在三十秒内核对这个断言，而不必重做一遍排查。第二，必须有一次试运行，而且其输出要让评审者看到。对这次公测的报道描述了在提议之前先在数据的浅克隆上做沙箱化试修；这个细节正是「一个可评审的工件」与「一条建议」之间的区别，也是你该在自己工作区的文档里第一个去确认的事。

文档里决定能否落地的那三行

发布博文是市场材料；启用页面才是合同。其中三句话会决定这件事能不能过你自己的审查，而这三句话都能推广到任何一个被要求你批准的常开智能体上。

  • 启用监控是一项长期有效的处理决定。文档说得很清楚：选定要监控的资产，意味着它们会被一个大语言模型持续、自主地处理，直到你关闭该功能为止。这不是一次按事件给出的同意，而是一次开放式的同意，它该进你的处理活动记录，而不是停留在某人拨过的一个工作区开关里。智能体的数据治理是那份记录的形状。
  • 智能体继承了一个人的触及范围。它遵循既有的 Unity Catalog 权限——这是正确的设计——而文档还补了一句：在排查过程中，它也可能查询你有权访问的那些表。请仔细读这句：排查的爆炸半径是「启用它的那个身份能看到的一切」的并集，而不是正在被修的那条流水线。这是一项作用域很宽的长期授权，恰恰就是环境权限所命名、而给智能体的受限凭据所反对的那个东西。
  • 合规边界是明说的，而且比平台本身更窄。文档写明不符合 HIPAA。就这么一行，就能决定一个受监管的团队究竟能不能启用这个功能，而它比一整页保证都有用得多。请预期、并且主动索要每一家厂商给出同样这一行——该模式在第三方模型与厂商风险里。

该给的信用要给到：通知离开平台之前先脱敏、权限继承、按工作区的开关、以及一条明说的合规限制，这套默认设置比多数智能体发布都更诚实。批评不在于这个边界小，而在于——决定就住在这个边界里，而盒子上的名字指向了相反的方向。

如果你要自己做这件事

这套架构能推广到数据流水线之外，适用于任何「故障沿着一张图传播」的运维领域——服务依赖、CI、基础设施、功能开关。有四件事要做对，按它们咬人的顺序排。

  • 先建图，再建智能体。无论你那边与血缘对应的是什么——一份服务目录、一份依赖清单、一张构建图——它的完整度就设定了智能体准确率的天花板。一个跑在完整度 70% 的图上的智能体，会对那 70% 给出自信的归因，而对其余部分从不提起，这比没有归因更糟。
  • 把检测与裁决分开。「这张表旧了」是一个监控谓词，有没有模型它都该触发。把模型留在「为什么」上，把「是否」留给一个你能讲清道理的阈值——论证在决策模型的阈值里。
  • 让提议能在一分钟内评审完。证据在前，diff 在后，置信度最后。如果评审者必须重做一遍排查，那你搬动了这份工作，而不是移除了它。
  • 决定「没人评审时会怎样」。这是所有人都跳过的那一条。一堆没人评审的提议，堆在一条仍然坏着的流水线上，是一个比「页面还敞着」更糟的状态，因为它看起来像已经处理了。让提议过期、在第二次出现时升级，并把「未评审时长」算进 SLO——见失败分类与分诊。

常见问题

Genie ZeroOps 会自己改动生产数据或代码吗？

不会。按公开测试时的文档，它排查并提议——把你链接到源头，或把修复推到一个新分支上发起 pull request——而在任何东西到达生产之前，由人批准。

那么「ZeroOps」是个名不副实的名字吗？

就「施加」这一步而言，是的。就检测与根因定位而言，它更接近准确，而那两件正是时间真正花掉的地方。有用的心理校正是把它读成零排查，而不是零运维。

我必须用 Unity Catalog 吗？

实践上是的，而这正是这次发布的结构性要点，而不是一条授权许可的脚注：血缘追溯与权限模型都依赖它，而根因那一步的质量，取决于你的血缘有多完整。

启用之前最该评审的风险是什么？

那项长期授权。启用监控意味着对选定资产持续进行 LLM 处理，直到关闭为止；而智能体的排查触及范围，是启用它的那个身份能看到的一切，而不是正在被修的那条流水线。请有意识地收窄那个启用身份，并把这个决定记录下来。

一道批准闸门能让运维智能体变安全吗？

它限住了一个错误修复的损害，而那是风险的大部分；同时它把一项新风险转移给了评审者：批准一个你并未亲自得出的诊断。一道闸门若挡在一堆没人有余力去核的提议前面，那它是形式，不是控制手段。
