一个把修复做成 pull request 交出来的智能体，几乎是顺手解决了智能体治理里最难的那个问题：PR 是大多数团队本来就拥有的唯一一处审批面，而且自带 diff、具名审阅者、CI 和一条审计记录。2026 年 11 月 19 日，Databricks 把 Genie ZeroOps 开放到公开测试，并把它的产出正好接到了那里。值得注意的是什么没有一起过来。审阅者看到的是那次改动；他看不到产出这次改动的那一堆读取；而「未经批准不会动生产」这条保证，悬在一个 Databricks 管不着的仓库设置上。

为什么 pull request 是对的答案

智能体审批界面这两年一直在重新发明一个对话框。那个对话框拿到的是一个布尔值，通常在一秒之内，来自当时正好坐在键盘前的那个人，留下的是一行「某人点了是」的日志。再看 pull request 免费提供了什么：一份可逐行评论的 diff、一个你的目录服务早就认识的审阅者身份、必需的状态检查、一条分支保护策略，以及一份会活得比这次会话更久的记录。如果你要从零设计一道面向「智能体所作改动」的审批闸，你会试着把这些造出来，而且会造错。

它也是你的组织已经配了人的那道闸。那里有审阅轮值；有合并队列；有一个人的职责里包含「注意到对数据摄取作业的改动是周五落下的」。把智能体的产出接进那根管子，就把这一切都继承了下来——这比一个只有一个用户、没有审计要求的定制审批面，是好得多的起点。这跟智能体产出的审核队列是同一个结构性论证：你已经在清的那条队列，胜过你还得发明的那条。

Databricks 并不孤单。GitHub 的 Copilot coding agent 被约束为每个任务一个分支、一个 pull request。Claude Code 的后台会话会提交到自己隔离的分支，并在完成时开一个草稿 pull request，而不是先来问你。三家厂商、三个领域，同一个结论：pull request 就是智能体工作该落的地方，因为审阅是一条人按自己节奏去清的队列，而不是智能体强加给人的一次打断。

但 diff 是修复，不是推理过程

这里就是 PR 装不下的那部分。等到分支存在的时候，这个智能体已经读过你的作业定义、你的表结构、你的血缘图，以及——对 Git 托管的作业——你仓库的内容。它已经把一份生产数据的浅克隆拉进了沙箱。它已经形成了一个根因假设。这些统统不在 diff 里。

于是审阅者在做的事，跟审阅同事的补丁有一处微妙的不同。面对同事，diff 和 PR 描述是对某段推理的压缩，而审阅者可以靠追问去盘查它。面对智能体，描述是由产出这次改动的同一套流程生成的——这意味着一个自信而错误的假设，会给出一段自信而错误的描述，挂在一个看着挺像样的三行修复上。审阅者唯一独立的核验手段，是把调查重做一遍，而那正是部署这个智能体所要省掉的工作。

已经有调查证据表明这件事在咬人了。《Who Pays the Review Cost?》（arXiv:2610.11179）调查了 31 个国家的 239 位从业者，给这个现象起了个名字：可审阅性债务（reviewability debt）——当一个由 AI 撰写的 pull request 到来时，若它没有范围限制、没有针对本项目的理由说明、没有超出 CI 的验证，也没有一个具名的合并后负责人，审阅者就要吸收掉这些工作。审阅者最常提到的推迟理由，是一段含糊的、由 AI 生成的描述。受访者形容自己像是在给一个机器人善后的人类调试器。

ZeroOps 在这一点上比多数产品做得好——它会展示受影响资产的可视化图，以及它所做的基于血缘的根因分析，还会标明某个修复经过了沙箱验证。这正是对的直觉；而需要说准确的是它买到了什么：是这个修复在一份克隆上能跑的证据，不是这个诊断判对了的证据。一个把某列悄悄转成字符串的「模式漂移修复」，对着真实数据验证会通过，而它仍然是错的改动。

对任何做这种形状产品的厂商，实际的要求是：把调查产物放进 pull request 正文里，而不是放在一个需要审阅者自己去翻的控制台里。一条会过期的 trace 链接不是审计记录；而一个必须离开 diff 才能核验推理的审阅者，最终只会照着 diff 批准。

这条保证悬在一个归你管的设置上

「未经你直接批准，绝不更改你的代码或数据」是一句关于生产的话。推分支是另一个动作，而且是你主动要求的那一个：在你要求时，智能体会推送到一个新分支或你指定的分支。指定一个特性分支，PR 这道闸就成立，因为合并仍然需要审阅。指定默认分支，这次推送就直接落地了——除非你的仓库保护拒绝它。

这与其说是 ZeroOps 的缺陷，不如说是整个模式的一项属性；而值得明说出来，是因为它把你的智能体策略搬了家。一旦智能体的审批闸是 pull request，你的分支保护配置就是你的智能体授权策略。一个能推送的智能体，其影响半径由这些决定：默认分支是否受保护、智能体所用的那个身份是否被强制要求审阅、那个身份能否绕过保护、以及是否允许强制推送。这是仓库设置页上的四个勾选框，由另一个团队管理（不是打开这个智能体的那个团队），而且没有谁在特别审计它。

两条推论。第一，智能体的触达范围也就是那位开启者的触达范围：ZeroOps 在 Unity Catalog 之下以你的权限运行，只监控你能看到的东西——这是不错的最小权限卫生，也意味着「这个智能体能碰到什么？」这个问题，离开「是谁把它打开的？」就没有答案。一位工作区管理员替团队打开它，和一位分析师替自己打开它，是两套不同的系统。第二，身份和策略一样重要——一个以某个人的账号在推送的智能体，会继承那个人的绕过权限，这正是要给智能体自己的目录账号、并单独界定其权限范围的理由。

Databricks 公布的那个数字，和它没公布的那个

这次发布建立在私有预览期间对超过 80,000 个客户流水线问题的观察之上。请照它本来的意思读：这是一句关于这套系统见过多少的话，值得自豪，但不是一个准确率声明。Databricks 没有公布「提议的修复有多经常是对的」这个数字，也不存在第三方评测。

对一个产出是 pull request 的智能体来说，两个数字几乎能告诉你一切，而且一旦跑起来都不难采集：

  • 采纳率——被原样合并的提议修复占比。高只有在第二个数字低的时候才算好。
  • 「采纳了但是错的」比率——已合并修复中后来被回滚、被热修，或在某次事故中被牵连的占比。这个数字才给审阅定价，也是唯一能把「有用的智能体」和「有说服力的智能体」区分开的那一个。

按故障类别分别统计，而不是看总数。「上游模式变更」和「数据质量异常」是 Databricks 点出的两个例子，它们的难度并不相同：模式变更有一个可机械核验的正确答案，而质量异常通常编码着「这份数据本该意味着什么」的某种判断。一个在前者上出色、在后者上平庸的智能体，混合采纳率会很好看，同时悄悄花掉你一个季度攒下的对某块看板的信任。故障分类与分诊是你拿到分类别分母的办法；CI 修复智能体是最近的同类模式，并且有同一个度量问题。

如果你要上一个会开 pull request 的智能体，先做这四件事。保护默认分支，并核实该智能体的身份无法绕过保护——那才是你真正的授权策略，不是厂商那页安全说明。要求调查产物出现在 PR 正文里，并把「没有解释的 diff」当成审阅阻塞项，而不是一个风格意见。决定谁有权开启这个智能体，因为智能体的读取范围就是那个人的读取范围。并且从第一天起就按故障类别统计「采纳了但是错的」，因为没有人会替你公布这个数字。

常见问题

Genie ZeroOps 是什么？

Databricks 里的一个后台智能体，监控数据与 AI 资产——流水线、作业、表、ML 模型——然后去调查诸如上游模式变更或数据质量异常这类故障，并提议修复。它于 2026 年 11 月 19 日开放公开测试；Databricks 称其私有预览覆盖了超过 80,000 个客户流水线问题；需要工作区管理员从 Previews 页面开启。

它能自己改动生产吗？

Databricks 的文档写明，未经你直接批准它绝不更改你的代码或数据，并且调查在一个隔离沙箱里、对着一份生产数据的浅克隆运行，带权限护栏与网络隔离。要盯住的写入路径是 Git 推送：它在你明确要求时发生，并且由你仓库的保护规则治理，而不是由 Databricks 治理。

为什么让智能体的审批走 pull request，比走一个审批对话框更好？

因为 pull request 已经带着审批所需的一切，而对话框没有：逐行 diff、审阅者身份、必需的状态检查、分支保护策略，以及一份持久记录。它也是一条人按自己节奏去清的队列，而不是一次打断——这正是几家互不相关的厂商都收敛到它的原因。

什么是可审阅性债务？

这是 2026 年一项针对 31 个国家 239 位从业者的调查（arXiv:2610.11179）提出的说法，指的是：当一个由 AI 撰写的 pull request 没有范围限制、没有针对本项目的理由说明、没有超出 CI 的验证、也没有具名的合并后负责人时，审阅者所要吸收的那部分工作。实用信号是：含糊的 AI 生成描述，是审阅者推迟一次改动最常提到的理由。

沙箱验证通过，是否意味着修复是正确的？

不。它意味着这个修复对着真实数据跑通了，而且没有碰到生产。验证检验的是这次改动能不能跑，不是诊断判得对不对；而昂贵的错误就住在这两者之间的空隙里——一个让模式错误消失的类型转换，会干干净净地通过验证。
