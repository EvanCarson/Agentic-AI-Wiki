这四个工具，每一个都能把 PDF 变成看起来没问题的 Markdown，而问题恰恰在这里：少掉一行的表格、被横向读串的双栏页面，出来的都是干净的散文；到了下游，它们会变成一个自信的错答案，还带着一条能正确指回原文档的引用。所以别照榜单选——四者之间唯一公开的正面对比，就躺在其中一个项目自己的 README 里，而榜首是该项目的付费托管产品。请照「输出会不会告诉你每一段文字来自哪一页、哪一个框」来选，因为那是你唯一能用来设闸的信号。

概览

于 2026 年 11 月 1 日读自各项目自己的仓库。星数只是一个流行度指标，别无他意；它出现在这里，是因为这个排序出人意料。

项目许可证星数自述定位

MinerU（OpenDataLab）MinerU Open Source License——基于 Apache 2.0 并附加条件82.9k把复杂文档转成适合 LLM 的 Markdown 与 JSON

唯一那块记分牌，以及它由谁掌管

Marker 的 README 公布了一组 olmocr-bench 的宏平均结果，里面包含了它的竞争对手。在那张表上，Marker balanced 总体得 76.0%、在原生数字文档上 83.5%；Marker fast 为 66.6% 与 71.6%；关掉 OCR 的 Marker fast 为 43.6% 与 55.8%；MinerU pipeline 总体 72.7%；Docling 总体 50.3%。而表格的榜首，总体 85.8%，是 Chandra 2——一个来自 Datalab 的托管模型，而 Datalab 正是发布 Marker 的那家公司。

请从两个方向认真对待这件事。这个基准本身是第三方的，而那些测量原则上是可复现的——这已经比另外三家提供的更多了，而且这里没有任何迹象说明那些数字是错的。但这张表是由一个竞争者组装、由该竞争者运行、并由该竞争者的商业产品夺冠的；而那个只拿 43.6% 的版本，也同样是 Marker。这三件事里的任何一件单独成立，就已经足以让人把这个排序当作一份候选名单、而不是一个决定。三件叠在一起，则意味着这张表诚实的用法是：「在扫描页面上，Docling 大概比 Marker 和 MinerU 弱，我应该拿自己的文档去验一验」——这是一件实打实有用的认知，而它离「一份排名」还隔着很远。

请注意哪些东西不在任何表上：MarkItDown、MinerU 与 Docling 都不公布自己的准确率数字。在这个类别的四个工具里，有三个压根不存在「需要怀疑的厂商声明」，因为根本没有厂商声明。

MarkItDown——那个主动告诉你「我没在争这个」的

MarkItDown 是这个领域星数最多的文档工具，比 Marker 多出 4.7 倍，而它的 README 对这份流行度究竟服务于什么，坦白得不寻常。它把自己描述成面向 LLM 与文本分析流水线的轻量工具，说自己的输出「本意是交给文本分析工具去消费」，并提醒说它可能不适合那种供人阅读的高保真转换。

你拿到的是什么

广度，以及一条通往字符串的极短路径。它能吃下 PDF、Word、PowerPoint、Excel、HTML、CSV、JSON、XML、EPub、ZIP 压缩包、带 EXIF 与 OCR 的图片、带 EXIF 与转写的音频，以及 YouTube 链接。对于一个必须接下用户随手附上的任何东西的智能体，这份清单就是产品本身，而这里没有别的工具能以这么低的代价覆盖办公文档的长尾。

它到哪里为止

版面理解不在盒子里。更重的 OCR 与版面分析被转交给 Azure Document Intelligence 或 Azure Content Understanding——云服务、按量计费，而且这是一场与本地库完全不同的信任与数据驻留对话。Content Understanding 这条路会输出 <!-- page 1 --> 这样的注释标记，所以你在那儿能把页码找回来；而任何地方都没有边界框，仓库也没有给出任何准确率数字。

解读它星数的正确方式是：大多数做文档转换的人并没有保真度问题——他们有的是「把十四种文件格式里的文字弄出来」这个问题，而 MarkItDown 解决得比这里任何东西都好。但对于一个表格很重要的 PDF 语料，它是个错误的默认选项。

MinerU——分档，以及一份真的得去读的许可证

MinerU 把自己描述为把复杂文档转成适合 LLM 的 Markdown 与 JSON、用于智能体工作流，而它是四者中最可配置的一个。4.x 版本给出四个质量档——flash、basic、standard、advanced——并把工作拆给跑在 ONNX 或 Torch 上的小模型，以及由 llama.cpp、vLLM 或 LMDeploy 承载的 VLM。仓库列出九种渲染目标：Markdown、HTML、LaTeX、DOCX、EPUB、PDF、Structured Content，以及 Content List V1 与 V2，每套 CLI 与 API 各暴露其中一个子集。

溯源

这是 MinerU 挣得自己位置的地方。它的结果契约用形如 doc:{short_id}/tier:{tier}/page:{page_no}/block:{block_no} 的定位符来寻址内容，页号与块号从 1 开始计，而块级图片要求一个有效的边界框。一个把「档位」也写进去的定位符，是个值得注意的细节：它意味着一段被存下来的文字记录的不只是「它来自哪里」，还有「流水线当时下了多大功夫」——而当你重跑一遍语料、想知道该重新核查哪些答案时，这恰恰是你需要的东西。

那份许可证

「MinerU Open Source License」，仓库里的描述是基于 Apache 2.0 并附加条件。这句话是在干实事的，而它不是 Apache 2.0。如果你要把它装进产品里出货，这句话就是你该在做任何基准测试之前，摆到那个为依赖项签字的人面前的那一句。

Docling——治理层面的那个答案

Docling 的代码是 MIT 许可，作为一个项目托管在 LF AI & Data Foundation 之下，由 IBM Research Zurich 的 AI for knowledge 团队发起。对于那些采购流程会在意「一个依赖项归谁所有、以及赞助方哪天没兴趣了会怎样」的人，这个组合不是什么软性因素——它是四者中唯一具备中立基金会治理的那一个，也正是 Docling 为何总能赢下那些 Marker 靠分数赢的评估。

它产出什么

一个 DoclingDocument，项目称之为一种统一而富有表达力的表示，可序列化为 Markdown、HTML、WebVTT、DocLang、DocTags 与无损 JSON。它的 PDF 理解覆盖页面版面与阅读顺序——后者是这里没有别家宣传自己处理过的那个失效模式，也是会悄悄毁掉一篇双栏论文的那一个。它为 LangChain、LlamaIndex、CrewAI 与 Haystack 提供了集成，所以把它塞进一条既有的检索流水线，工作量是最小的。

那两点保留

确实是两点。在那份唯一公开的对比里，Docling 得 50.3%，明显落在 Marker 与 MinerU 之后；而那张表由一个竞争者掌管——但它是目前唯一存在的数字，而它指向的是：扫描件与图像密集的文档，是你该下最重手去测的地方。另外，仓库首页并没有说明 DoclingDocument 是否记录逐元素的边界框；「无损 JSON」与明确处理阅读顺序都是好兆头，而如果框级溯源是一项硬要求，你应该去 schema 里确认它，而不是从「无损」这个词里推断出来。

Marker——公开分数最高，以及许可证里的一道门槛

Marker 把 PDF 转成 Markdown、JSON、HTML 以及现成的分块，而每一种格式都还会返回一个元数据字典，里面带目录与逐页统计。它的 JSON 是四者中溯源信息最丰富的输出：每个块都带一个把页码编码进去的 id（例如 /page/10/Page/366）、一个 block_type、一个给出四角坐标的 polygon，子块上还有 section_hierarchy。这些足以在原始页面上渲染出一块高亮，而这正是「用户能自己核对的引用」与「用户只能选择相信的引用」之间的差别。

它还有一个混合模式：--use_llm 把难处理的区域送给一个视觉模型，支持 Gemini、Google Vertex、Ollama、Claude、兼容 OpenAI 的端点、Azure OpenAI 与 OpenRouter，而文档里写明的默认模型是 gemini-3.5-flash。那个 76.0% 是 balanced 配置的成绩；不走 OCR 的 fast 路径只有 43.6%——所以你选的配置，对结果的影响比你在工具之间做的选择还要大。

Marker 的代码是 Apache-2.0。它的模型权重不是：权重依一份改写版 AI Pubs Open Rail-M 许可发布，对研究、个人使用，以及融资或营收低于 500 万美元的初创公司免费，其他商业用途需要向 Datalab 购买许可。营收跨过 500 万美元那一天，你不会希望同时发现一个依赖项把自己换了许可证。这是本文中最有可能改变一个决定的那一句话。

真正能预测下游质量的那个维度

下面是这些工具在生产里真正会产出的那种失效，以及为什么准确率百分比抓不住它。一张表格因为分页丢掉了一行。一页双栏被横着读过去，把两句互不相干的话编织在一起。一个脚注标记落在句子中间。这三种情况里，Markdown 在语法上都完美无瑕、读起来也通顺，所以这次解析「成功」了；分块嵌入正常，检索会在正确的查询下把它返回来，而模型就据此作答。你的检索指标是绿的，因为检索确实是对的。答案是错的，因为那段文字是错的。

转换器下游的流水线里，没有任何东西能侦测到这件事，因为每一个下游组件的输入都是转换器的输出，而它手上没有任何可比对的东西。唯一能让它变得可侦测的，是溯源：如果每一段文字都带着页码和边界框，你就能把被引用的区域渲染在原始页面上，而一个人一秒之内就能看出一次双栏横读。如果它只带页码，你至少能把核查范围缩小。如果它什么都不带，那么找到这个错误的唯一方式，就是有人注意到答案不对、然后回头去翻。

所以真正重要的排序是：Marker 与 MinerU 今天就给你元素级定位符，Docling 大概可以、而你应该去核实，MarkItDown 在一条代码路径上给你一个页码注释。这个排序与那张准确率表几乎无关，而它决定的是：一个解析 bug 抵达用户时，是以一个看得见的瑕疵出现，还是以一句听着在理的话出现。面向 RAG 的文档解析讲的是它所处的那条流水线，而引用与来源标注讲的是拿到坐标之后该做什么。

常见问题

哪个「文档转 Markdown」工具最准？

在那份唯一公开的正面对比里——Marker 自己 README 中的 olmocr-bench 宏平均结果——Marker balanced 以总体 76.0% 领先开源阵营，MinerU pipeline 为 72.7%，Docling 为 50.3%。那张表由 Marker 的厂商公布、并由该厂商的付费托管产品夺冠，所以请把它当作一份候选名单，并拿自己的文档去验。

MarkItDown 一个分数都不公布，为什么还这么流行？

因为大多数人解决的是另一个问题。MarkItDown 以一份 MIT 许可、无需自托管模型，覆盖了十四种以上的输入格式，而当你需要把用户随手附上的东西里的文字弄出来时，这恰恰正确。它的 README 写明自己可能不适合高保真转换，而它不公布任何准确率数字。

哪几个会给我边界框？

Marker 的 JSON 给每个块一个把页码编码进去的 id、一个 block_type 和一个四角 polygon。MinerU 用 doc/tier/page/block 定位符寻址块，并要求块级图片带一个有效边界框。MarkItDown 只在它的 Content Understanding 路径上给页码注释标记。Docling 的首页没有说明逐元素边界框——如果你需要，请去查 DoclingDocument 的 schema。

这四个真的都能免费商用吗？

不是。MarkItDown 与 Docling 的代码是 MIT。Marker 的代码是 Apache-2.0，但它的模型权重依一份改写版 AI Pubs Open Rail-M 许可发布，只对研究、个人使用，以及融资或营收低于 500 万美元的初创公司免费。MinerU 用的是自己的许可证，描述为「Apache 2.0 并附加条件」。出货之前请把后两份读完。

我需要 GPU 吗？

对 MinerU 的较高档位与 Marker 的模型路径来说，GPU 会改变经济账——MinerU 的仓库称核心推理在受支持的加速器上大约是 CPU 速度的两到三倍。MarkItDown 的内置转换器完全不需要 GPU，它把重活的 OCR 推给 Azure 服务。

我能同时用两个吗？

能，而这往往就是正确答案：办公文档与图片走 MarkItDown 求广度，PDF 走 Marker、MinerU 或 Docling 求结构。两边保持同一份输出 schema，下游代码就不必知道是哪个转换器跑的。
