这份名单上能力最强的那把代码搜索工具，恰恰是你最没有自由去发布的那一把。这个倒置就是全部的决策所在：既然前沿编码智能体已经丢掉了嵌入索引、改为直接搜索工作区，那么智能体搜索工具背后的那个二进制程序就成了一项产品选择——而四个主要候选者各自精确回答四个不同的问题：一个字符串、一种代码形状、数千个仓库里按相关度排序的命中，以及不可信输入是否到达了某个危险汇点。按「智能体能验证什么」和「你的许可证允许什么」来选，顺序就是这个。

一览

这四者都是你今天就能作为工具交给智能体的东西。它们并不是通常意义上的竞争者：其中三者回答的问题，另外几者根本表达不出来。

为什么这件事在 2026 年成了一项决策

有两年时间，关于代码检索的有意思的问题是「该用哪个嵌入模型」。而当前沿的 harness 放弃了索引，它就不再有意思了：Cursor 在 2026 年期间移除了语义代码库索引——重新同步与删除索引的控件从界面上消失了，检索改为一个在本地构建的精确匹配索引，它称之为 instant grep——而 Claude Code 压根就没有过索引，它用 glob、正则搜索和读文件，对着磁盘上此刻的代码树做导航。

Cursor 发在自家社区论坛上的理由，其实质值得引述：模型使用 grep 和索引搜索的能力已经好到让那条专门的语义通路不再带来有意义的帮助。Cursor 自己早前的研究曾测得语义搜索相对纯 grep 平均约 12.5% 的准确率提升，所以那份收益是真实的；它是被更好的工具使用吃掉了，而不是被推翻了。

而 2026 年 5 月的一项研究发现，决定胜负的根本不是检索器。《Is Grep All You Need? How Agent Harnesses Reshape Agentic Search》（arXiv:2605.15184）固定检索器不变、只改变投递方式：当结果内联在工具响应里返回时，grep 在受测的全部十组 harness 与模型组合上都胜过向量检索；而当结果被写进文件、需要智能体自己去打开时，向量检索赢了十组中的五组。精确搜索取胜，是因为它的失败是可读的——零命中意味着名字不对，四百个命中意味着这个词太泛——而这恰恰是一个正在反复收敛的模型所需要的。

于是嵌入那个问题坍缩成了一个更朴素的问题：用哪一个精确搜索工具、它的查询语言是什么、返回什么形状的结果。本文余下的部分讲的就是这件事，而它的运营版本在仓库导航与代码上下文里。

ripgrep——默认项，而且通常是对的

ripgrep 是用 Rust 写的按行正则搜索，没有索引、没有状态，以单个二进制程序分发，采用宽松许可（有资料列为 Unlicense，也有列为 MIT）。它是多数智能体 harness 实际调用的那一个，而原因不是速度：原因是 path:line:match 对模型来说是理想的结果形状。每条命中都可以独立核验、返回成本低，并且带着智能体打开一个 40 行窗口（而不是整份文件）所需要的坐标。

它的局限在于：正则表达不了结构。except:\s*pass 能找到那样写的裸 except，却会漏掉中间夹了一行注释的；而「这个函数被调用、且第二个参数是字面量」这样的模式根本写不出来。在命名良好的代码库里，这个局限很少真的卡住你——这正是 ripgrep 仍然是正确默认项的原因，而另外几个是补充、不是替代。

ast-grep——最便宜的一次真正升级

ast-grep 把模式匹配到 tree-sitter 的语法树上，于是模式是用被搜索的那门语言写的，而不是用正则写的。foo($$$ARGS) 能匹配这个调用，不论它如何排版、是否跨行，并且忽略注释与空白。它是 MIT 许可、单个 Rust 二进制程序、不需要索引——所以它与 ripgrep 有着同样的运营特征，而在任何有 tree-sitter 语法的东西上，表达力严格更强。

对智能体而言，这个区别在一个具体的地方要紧：ast-grep 回答的是「这个构造在哪里」，而不是「这段文本出现在哪里」，所以它正是那一类「答案存在、但名字不存在」的查询所需要的工具。它同时也是一个改写器，这让它成为一次大规模迁移中机械那一半的天然器械——智能体提出一个模式和一个替换，工具确定性地把它应用到 400 个位置，而不是让模型逐个编辑、然后漂移。

Zoekt——关乎规模，而不关乎匹配

Zoekt 是一个采用 Apache-2.0 的、基于三元组索引的排序式代码搜索引擎，为同时搜索许多仓库而建。它的轴与另外三者不同：它并不能匹配那三者匹配不了的东西，它能回答的是那三者无法在合理时间内走完的那个语料范围。

这就让它的取舍成了索引新鲜度与失效里的那个取舍，而不是检索质量上的取舍。有索引就意味着有同步任务，而过期的代码索引比没有索引更糟，因为它会满怀自信地返回一个已经不存在的行号——这正是自信的错误定位所命名的那种失败。当你智能体的问题确实横跨一个组织的多个仓库、而不是一个检出目录时，就把它跑起来，并在旁边保留一个不依赖索引的工具来对付当前工作区。

Semgrep——最强大，也最受约束

Semgrep 的社区版是一个采用 LGPL-2.1 的开源引擎，用来求值语义规则，其中包括单文件内的污点追踪：它能回答「一个来自不可信来源的值是否到达了某个危险汇点」，而这是另外三者都表达不出来的。跨文件的污点分析不在 CE 里，它需要付费平台。

约束在规则上，而这也是团队往往发现得太晚的那一部分。Semgrep 自家规则仓库里的规则——社区规则与 pro 规则一样——按 Semgrep Rules License v1.0 发布，该许可把它们的可用范围定为内部商业使用。这是一个完全寻常的安排，而它只在一种用例上是严重问题：发布或转售一个「其价值来自替别人跑这些规则」的产品。如果你的智能体是一个内部安全评审者，这不成问题。如果你的智能体是一个产品，请在动手做这个功能之前读许可证，而不是之后。

这是一般性的教训，而不是对 Semgrep 的抱怨：搜索后端是一项带许可证的依赖，而对智能体产品来说，这个许可证是承重的，程度与它对一位开发者自己终端里的情形不同。开放权重许可证把同一个论点用在了模型上。

智能体拿回什么，比谁产出的它更重要

在这四者之上，结果形状是对智能体行为影响最大的那个变量，而且它在你的掌控里、不在厂商手里。2026 年 5 月那项 harness 结果说，投递方式在不同检索器之间翻转了胜负；同一机制也适用于这四者之间。

由此得出三条规则，不论你挂载哪个后端都适用。把命中内联返回，带路径、行号和周围几行上下文，好让模型在不打开任何文件的前提下决定下一步打开什么。给结果集设上限，并且明说——一个在第 50 条命中处静默截断的工具，教给模型的是「50 就是答案」；而「412 条匹配，显示 50 条，请收窄你的模式」教给它的是去改进模式。还有，即便你无法返回命中，也要返回计数，因为计数正是区分「名字写错了」与「这个词太泛」的那个信号。这三条的一般形式在塑形工具结果与工具错误信息里。

常见问题

语义代码搜索死了吗？

没有——测得的收益是真实的，而前沿 harness 仍然丢掉了它，因为更好的工具使用用更低的成本到达了同样的答案。对于「目标有个没人写下来的名字」的那类查询，以及面对超大代码树的延迟，它依然值得留着——这也正是以索引为基础的产品把索引保留下来的原因。

我该给智能体挂载多个搜索工具吗？

通常最多两个，而且只在它们回答不同问题的时候。挂上四个彼此重叠的搜索工具，会在每个回合都花掉描述 token，并把「选哪个」从你的问题变成模型的问题；ripgrep 加一个结构化工具几乎覆盖一切。

Semgrep 的许可证是否完全阻止我把它和智能体一起用？

对内部工作并不阻止——那恰恰是规则许可所允许的。约束咬人的时候，是「跑这些规则」成了你收费提供的服务。LGPL-2.1 的引擎与规则是分别授权的，所以两份都要读。

为什么返回匹配计数这么要紧？

它是回路里最便宜的一条信息，而且它决定下一步。零命中意味着标识符写错了；四百个意味着模式太泛。没有计数，两者看上去都像「这没成」，于是模型只能猜。

ast-grep 是 ripgrep 的替代品吗？

不是，是补充。对一个字面字符串、一行日志或一个配置键，正则仍然是正确的器械，而且它在任何语法都覆盖不到的文件上照样能用。结构化搜索挣到它那份价值的地方，是排版或命名挫败了模式的那些场合。
