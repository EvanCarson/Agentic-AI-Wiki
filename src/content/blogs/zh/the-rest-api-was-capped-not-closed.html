读了那些标题，你会惊慌地搬迁自己的 Workspace 集成：「AI 智能体的 REST API 访问将于 2027 年 2 月 1 日终止。」它不会终止。REST API 还会继续应答——它们只是不再有资格使用你花钱能买到的配额；这意味着 Google 对智能体流量的这项新控制根本不是一次访问检查。它是一份价目表，而一份价目表需要知道你是谁。

实际宣布的是什么

2026 年 11 月 24 日，Google 让两样东西正式可用：一套由 Google 托管的 Workspace MCP 服务器，覆盖 Gmail、Drive、Docs、Sheets、Slides、Calendar、Chat 与 Tasks，Keep 尚待推出；以及一个官方的 Workspace CLI（gwscli），面向那些活在终端、虚拟机或沙箱里、而不是嵌在某个应用里的智能体。面向 Rapid Release 与 Scheduled Release 域的推送要花大约两周，所以管理控制项不会在同一天全部出现。

与它们一同到来的是一份 Workspace AI Tools Addendum（AI 工具附加条款）与一套标准化的两层用量模型。真正要紧的日期：

日期变化是什么约束谁
2026-11-24MCP 服务器与 gwscli 正式可用；Standard 与 Scaled 两层发布；附加条款生效每一个持有 Workspace API 项目的人
2027-02-01直接调用 Workspace REST API 的智能体被限制在 Standard 层配额，无论所选的是哪一层任何被 Google 归类为 AI 智能体或同类访问工具的东西
2027-04-01超出每日免费额度的用量开始计费；超过 Standard 上限却未转入 Scaled 的项目会回落到 StandardScaled 层项目，以及当前已超出 Standard 的任何人

Standard 层是免费的，而据正式可用时的报道，它把每一台已正式可用的 MCP 服务器限制在每天 5,000 次请求。请注意各家报道并不一致的那一处细节：这个上限是按项目计，还是按项目再按产品计。在你据此做任何容量规划之前，Google 自己的配额文档才是定夺之处；而就八台已正式可用的服务器而言，这个差别是八倍。Scaled 层的按次价目表在正式可用时未获确认；有一个数字从单一家媒体流传开来，而只出现在一个地方的数字，不是你拿来做预算的数字。

「终止」是个错误的动词，而正确的动词会改变你的计划

一次下线和一道配额上限，失败的方式不同、时间线不同、修法也不同，所以这个区分不是吹毛求疵。如果 REST 访问真的终止了，你的智能体会在 2 月 1 日坏掉，而你会把迁移排成一个硬期限。它不会坏掉。它会继续跑，跑在 Standard 层配额上，直到你的流量长过每天 5,000 次请求的那一天——然后它会以这个行业里最平淡无奇的那种错误失败：一个限流响应；你的重试逻辑会把它吸收掉，而你的仪表盘会把它读成延迟。

这是一种比宕机更糟的失败形状，因为它正是你的监控被设计出来去掩盖的那一种。宕机会把人叫起来。一道你花钱也抬不起来的配额上限，会产生一场缓慢、不均匀的退化，而病因是四个月前的一条合同条款。在这里受伤的团队不是那些漏看了公告的人；而是那些读到「终止」、便断定「二月份还能跑的东西想必就是合规的」的人。

执行机制是计费资格，所以真正的要求是「可识别」

看看 2 月 1 日那条规则要生效，必须先做到什么。它适用于「AI 智能体或同类访问工具」——不适用于某个协议，不适用于某个 IP 段，也不适用于某个 scope。总得有谁来判定某一股 REST 调用流属于一个智能体，而 Google 伸手去拿的机制，正是它本来就拥有的那个：项目、它的 OAuth 客户端，以及那个项目被允许持有的层级。

这把通常的迁移问题倒了过来。你被要求的首先不是采纳一个协议；你被要求的是申报自己哪一部分流量是智能体流量，因为正是那次申报让这股流量有资格使用付费配额。在新模型下，智能体需要专属的 OAuth 客户端 ID 与最小权限 scope，而这恰恰就是让计量成为可能的那一步注册。一个没贴标签的智能体不是一个漏洞——它是一个买不到余量的项目。

这也正是 MCP 拿下这个位置的原因，而这主要不是一个关于协议质量的故事。REST API 是一个厂商能限流、却不容易刻画的表面：一次 GET 就是一次 GET，不管它是人点出来的还是规划器吐出来的。而一台托管的 MCP 服务器是厂商自己运营的咽喉要道，每一次调用抵达时就已经归属于一个有名字的客户端、一件被声明的工具、一场会话。能在企业里胜出的协议，是让数据所有者数得清的那一个。我们在身份这一侧论证过它的镜像——机器人验证与智能体访问就是同一个问题从请求另一侧看过去的样子——而商业版本先到了。

二阶效应现在就值得点名，因为它会塑形未来一年的采购：一旦数据所有者能数清智能体，定价就会停止跟着席位走，开始跟着按量计费的智能体调用走。一份席位许可不在乎你的规划器发出多少次工具调用。一份按次额度则在乎得要命，而它会把你工具的粒度变成一个账目行项：五个各自发出一次调用的收紧工具，花的是一次设计良好的调用的五倍，而你的智能体框架不会有任何东西来告诉你这件事。

那条会比配额更贵的条款

配额是算术，你会解决它。附加条款才是触及架构的那部分。从正式可用时的报道里有两条格外醒目：一条是对你可以把衍生于 Workspace API 使用的数据保留多久的限制——据报道，对嵌入向量这类材料是 30 天；另一条是禁止使用 AI 智能体去抓取 Workspace API。

如果那条保留期限制的含义正如报道所述，它会直直落在当前生产环境中最常见的 Workspace 智能体设计上：把用户的邮件与云盘索引进一个向量库，让索引保持热，然后从它上面作答。对衍生数据的 30 天上限，会让那个索引从一项耐久资产变成一个带强制过期的缓存；而运维后果是一次周期性的你现在必须为之做预算的重建索引——既要算成本，也要算你刚开始付钱的那份配额，因为重建索引本身就是 API 流量。在你重做设计之前，请对着附加条款核实确切措辞；但如果你正在跑一个长期存活的 Workspace 索引，那么该先读的是这条条款，而不是价目表。

抓取禁令是更安静的那一条。「抓取」不是单凭请求量来定义的；而一个为了构建语料库、对 Drive 目录树做广度优先遍历的研究型智能体，从服务端看过去，正好长得就是那个被禁止的东西。站得住脚的姿态，也正是那个一向属于好工程的姿态：为一个任务按需取数，保留一个你指得出来的任务作用域，而不要因为方便就给别人的语料库造一份镜像。

二月之前、以及四月之前该做什么

四件事，按「它们能把其余几件缩小多少」排序。

给你的 Workspace 流量归属。在任何别的事情之前，先查清今天是哪些项目与 OAuth 客户端在发出智能体调用，并把它们与人类驱动的调用分开。你没法评估一个你测不出来的层级，而后面每一个决定都依赖这次切分。如果同一个客户端 ID 同时服务你产品的界面和它的后台智能体，那这就是第一件要修的事——它也是那件会让 2 月 1 日那条规则对你变得含混、而对干净切分过的团队并不含混的事。

按任务数请求，不要按用户数。取你最常见的十个智能体任务，把每一个从头到尾真正发出的 Workspace 调用数清，重试与重读都算上。那个数对着每天 5,000，就是你的余量；而它通常比团队预期的糟得多，因为一个智能体循环重读上下文的方式是人类从来不会有的。如果单次工单分诊运行要碰邮箱十一次，那你的免费层是每天 454 次运行，不是 5,000。

把热路径搬到 MCP 服务器或 gwscli 上，其余的留着。这是一次你可以按流量占比、而不必整体一把搬的迁移。会撞上上限的那些路径就是智能体路径；一个并非智能体的夜间批处理作业，不是二月那条规则在说的事。把托管服务器当作被计量的那条车道，把 REST 留给那些确实不是智能体流量的东西——但请把哪个是哪个写下来，因为那份写下来的分类正是你将被要求出示的东西。

在给层级定价之前先读附加条款。一条保留期条款能让一个设计作废；一道配额只会让它更贵。各个团队很可靠地会把这两件事做反顺序，因为价目表更短。

还有那件不该做的事：把 2 月 1 日当成期限。真正咬人的期限是 4 月 1 日——那天，未转入 Scaled 的项目会回落到 Standard 上限，而那两周的推送意味着你的管理控制项可能连出现都还没出现。二月改变的是你被允许买什么。四月才是「没买」显形的时候。

常见问题

我现有的 Workspace REST 集成会在 2027 年 2 月 1 日停止工作吗？

不会。直连 REST 调用会继续工作。变化的是：被 Google 归类为来自 AI 智能体的流量将被限制在 Standard 层配额，无论你的项目选了哪一层——所以你再也不能为那条路径买余量。

Google 现在对 Workspace MCP 服务器收费吗？

不收。Standard 层是免费的，而据正式可用时的报道，它把每台已正式可用的 MCP 服务器限制在每天 5,000 次请求。对 Scaled 层项目，超出每日免费额度的用量将自 2027 年 4 月 1 日起计费。按次价目表在正式可用时未获确认。

每天 5,000 次这个上限是按项目算还是按产品算？

正式可用时的各家报道在这一点上不一致，而就八台已正式可用的服务器而言，这个差别是八倍。在拿它做任何容量规划之前，请查 Google 自己关于 Workspace API 与 MCP 服务器的用量层级与配额文档。

对一个终端或沙箱里的智能体，MCP 服务器和 CLI 哪个更好？

CLI 的存在正是为了这种情形——终端、虚拟机或沙箱里的智能体——它避免了在一个可能没有 MCP 客户端的环境里再去跑一个。嵌在应用里的智能体才是 MCP 服务器的情形。两者都在被允许的那条路径之内，所以这是一次人机工效的选择，不是一次合规的选择。

这是否意味着 MCP 已经赢下了企业智能体协议之争？

它意味着一位重要的数据所有者把 MCP 变成了智能体流量唯一能买到容量的那条车道，而这是一种比技术偏好更强的采纳形式。机制是商业性的、而非架构性的：托管的 MCP 服务器是厂商能够归属并计量调用的地方，而一个 REST 端点不是。
