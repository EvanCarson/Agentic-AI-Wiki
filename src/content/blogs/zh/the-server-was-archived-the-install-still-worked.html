那些漏洞不是故事本身。故事是：没有人添加过这个依赖——一个包名从模型的权重里出来，智能体把它写进了一份 MCP 客户端配置，npx 从注册表里把它解析出来，于是一个能读你文件系统、能花你令牌的进程就跑起来了；而它在任何锁文件里都没有条目，没有任何东西供依赖扫描器去扫，上游仓库则早在 2025 年就已归档、不会再被修补。Glow Labs 在 2026 年 11 月 2 日发布了这项研究，把这个现象称作 MCPhantom。而最让人不舒服的那个说法来自云安全联盟关于它的研究简报：模型知识如今已是一条软件供应链，而且是一条无法打补丁的供应链。

速览

研究里的四项主张，以及每一项各自立在什么之上。细节是 Glow Labs 对自己工作的陈述、经由业内报道转述；而其结构，在任何智能体、任何注册表上都可自行核验。

主张它说了什么出处你怎么自己验
智能体凭记忆说出服务端名字 安装命令来自回忆出来的包名，而非一次实时的注册表查询 Glow Labs，2026 年 11 月 2 日 让智能体给某个服务加一个 MCP 服务端，看它是否先去搜
目标大多已归档 受影响的包大多是最初那批 MCP 参考服务端；其中若干在 2025 年间归档 Glow Labs；仓库自己的归档提示 打开你的智能体刚加上的那个包背后的 GitHub 仓库
不会有补丁了 四项高危发现，包括一个可由提示词注入触达的 Puppeteer 服务端缺陷，在已归档仓库上被按"不在范围内"关闭 Glow Labs；它引用的维护者回复 去读一个已归档参考服务端的 issue 列表
标记弃用并不能阻止它 一个被标记弃用的 npm 包，依然能通过 npx 装上并运行 Glow Labs；npm 自己记录的行为 对任意一个已弃用的包跑一次 npx

为什么锁文件对此无话可说

供应链工具链建立在一个单一假设之上：有人声明过一个意图，而工具链的职责是约束这个意图如何被满足。package.json 记录意图，锁文件钉住解析结果，扫描器读锁文件，评审读 diff。这四道控制，每一道都把那份声明当作自己的输入。

而一次由智能体发起的 MCP 服务端安装，不产生任何声明。那个包不是你项目的依赖；它是一份客户端配置文件里的一条命令——通常是一对 command 与 args，在启动时去跑一个包运行器。没有版本范围可钉，因为配置通常根本不带版本。没有锁文件条目，因为 npx 并不是在往你的项目里安装。如果配置是智能体自己写的，就没有 diff 供人评审。而仓库里也没有任何东西供扫描器发现，因为这件产物住在一个按用户划分的配置目录里，不在代码树里。

弃用那一行最值得多坐一会儿，因为那正是"显而易见的修法"失效的地方。npm 的 deprecate 命令会给包打上标记并打印一条警告；它不会撤包，也不会让安装失败。在交互式终端里，人或许会读那条警告。在一次智能体运行里，那条警告只是几千行标准输出中的一行，而智能体自己的成功判据——服务端起来了、工具列表回来了——已被完全满足。Glow Labs 报告说维护者会考虑把这些包标记为弃用，并直白地指出了这个局限：被弃用的包依然能通过 npx 装上。打标记是给读者的信号。而这里没有读者。

这也是为什么"把版本钉住"在这里是错误的指令——给出它只会让团队感觉更安全，而不是真的更安全。钉版本解决的是漂移：你选定的那个东西在你脚底下变了。而这里的缺陷完全位于版本选择的上游——缺陷在于那个名字是由一个无法访问当下时态的过程挑出来的。你没法靠钉版本摆脱一条推荐。

"已归档"是个比"没人维护"更重的词

一个没人维护的包是你还能推理的风险：也许有人会回来，也许会出现一个分叉，也许报告终究会被受理。而一个已归档的仓库是一扇关上的门，门上贴了通知。Glow Labs 针对 Puppeteer 参考服务端的那项发现就是说明性的案例——一个可经提示词注入触达的缺陷，已上报，然后以"仓库已于 2025 年 5 月归档、因此不在范围内"为由被关闭。那个回复是对的。它同时也是终点：公告不会发布，版本不会发版，而智能体写下的那条 npx 命令，只要注册表还在供应，就会一直解析到同样那串字节。

不过范围要说准，因为那个标题很容易引出过度概括。并非每一个最初的参考服务端都已归档——比如文件系统服务端仍在维护，并在 2026 年间发布过带有修复版本的安全公告，而这恰恰是一个活项目该有的样子。真正有问题的总体是那个已归档的子集；而它之所以格外要紧，是因为那些名字正是训练数据里被最充分呈现的名字：在生态转向由服务方自己维护的第一方服务端之前，它们曾有一整年是每篇教程、每份 README 里的标准范例。

这就是那个机制，一句话，而它远不止适用于 MCP。模型的回忆，按互联网谈论某事的多少来加权，而互联网谈得最多的，是十八个月前的那个标准答案。训练数据是一份带滞后的流行度索引。任何让模型的回忆去挑选一件要执行的产物的系统，都把这份滞后作为默认继承了下来，而那个默认指向的，正是此后已被取代的东西。同样的形状也出现在知识截止与时间里；而它那个"幻觉包名"的变体——回忆出来的名字根本不存在，而攻击者去把它注册了——则是这个问题更早、也更出名的那一半。

那个 98% 的数字，要读仔细

二手文章都把一个数字放在开头：智能体在 98% 的被追踪会话里选择了已弃用的 MCP 服务端。请把它当作一个关于条件总体的数字，因为它描述的正是那个。报道所支持的读法是：在那些确实装上了一个已弃用服务端的会话中，有 98% 的用户并没有点名要那个服务端。这是一个关于归因的陈述——这个选择是智能体做的，不是人做的——而它才是有意思的那个主张，因为正是它让这件事成为系统问题，而不是用户教育问题。

它不是什么：它不是"智能体整体上多久会选错"的度量。研究的一位评论者正是指出了这一点：这项工作完全没说智能体正确挑到在维护的服务端的比率是多少。如果你想要那个分母，就得在你自己的环境里把它量出来，而这个测量很便宜——扫二十台开发机上的 MCP 配置，数一数。

在决定该多在意之前，先把那次扫描跑起来。~/.cursor/mcp.json、~/.codex/config.toml、项目根目录下的 .mcp.json，以及你团队所用客户端的各自对应位置——grep 一下 @modelcontextprotocol/，把每个包解析到它的仓库，然后看那个仓库是否已归档。这个结果是唯一对你有意义的流行度数字，它只要一个下午；而如果你不想自己写脚本，针对这项检查的开源离线检测器已经有了。

真正有用的那些做法，按收益排序

有用的控制都共享一个性质：它们作用在解析之前、作用在名字上，而不是作用在解析之后、作用在产物上。

  • 一份获准 MCP 服务端的允许名单，在客户端处强制执行。这是上面那张矩阵里唯一既看得见也能阻止的控制。它同时也不时髦，因为它意味着得有人维护一份名单。请维护那份名单。一个团队真正需要的服务端集合很小，而且变得很慢；而替代方案是：这个集合由一个"以服务端能起来为优化目标"的过程，在每次会话里临时挑定。
  • 一个拒绝已弃用或已归档包的预安装钩子。如果你的客户端支持生命周期钩子——而那些钩子自身的风险面是另一个主题，见生命周期钩子与运行壳配置——那么这项检查就是一次注册表元数据查询加一次仓库状态查询，并且失败时关闭。这正是研究发布后几天内多人公开的那套做法，而它的形状是对的。
  • 优先用服务方自己的服务端。凡是厂商如今已提供第一方 MCP 服务端的地方，模型记住的那个参考实现就是错误答案，无论它的安全状况如何——因为那是个演示，而第一方那个是产品。
  • 把注册表与仓库状态加进你的准入标准。弃用状态、最近一次发版日期、仓库归档标记，以及发布账号是否与它声称要对接的那个服务相符。这是四次 API 调用，而它们比 star 数是更好的信号。
  • 无论如何先假定这个服务端是敌对的，并把它围住。上面每一项都是过滤器，而过滤器都有孔。真正值得工程化的性质是：一个被攻陷的 MCP 服务端读不到它不该读的东西——而这是个沙箱与出网问题，不是个包的问题。见端点上的本地 MCP 服务端与面向智能体的出网控制。

而没用的、也是多数团队第一个伸手去抓的那个：告诉智能体优先选在维护的包。这条指令要和那个最初产出名字的回忆去竞争，智能体又无法在不做它本来就不打算做的查询的情况下核实它，并且它不留下任何产物。提示词不是一道控制。

常见问题

这是 MCP 的漏洞吗？

不是。协议里没有任何东西坏掉。缺陷在于服务端"被挑中并被启动"的那条路径：一个模型回忆出的名字，由一个包运行器解析，中间没有闸门。任何从模型输出里取包名的扩展机制，都会有同样的现象。

把版本钉住能解决吗？

不能，而这是最常见的错误答案。钉版本约束的是"你选定的那个包用哪个版本"；对一个没人选过的包，它什么也没说。相关的控制作用在名字上，在解析之前。

这些包真的被利用过吗？

Glow Labs 报告在发布时未观察到攻击。暴露在于结构——带已知高危发现、无法打补丁的产物，以开发者权限运行，且安装时不留记录——而不在于一场正在进行的行动。

我该把配置里每一个 @modelcontextprotocol/ 服务端都删掉吗？

不要一刀切：其中有些包仍在积极维护，并在 2026 年间发布过修复。请把每一个解析到它的仓库，看那个仓库是否已归档。已归档的该走；仍在维护的，则需要与任何其他依赖同等的版本卫生。

把 MCP 服务端跑在容器里能解决吗？

它能限住损害范围，这很有价值；但它不解决选择问题。一个被容器化的、已归档的、带可由提示词注入触达缺陷的服务端，依然会读你挂进去的任何东西，依然能触达你允许的任何网络。

智能体为什么会去装一个用户没要的服务端？

因为任务是"接上这个服务"，而通向一份可用工具列表的最快路径，就是一个模型已经知道的名字。智能体的成功判据是"服务端起来了"，而一个已归档的服务端起得完美无缺。
