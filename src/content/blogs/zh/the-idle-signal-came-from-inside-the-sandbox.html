三十年来，平台判断你的负载是否空闲，靠的都是从外面看——CPU 低于某个阈值、N 秒没有请求、调度器的一个超时。Google 在 2026 年 10 月 22 日宣布的 Agent Compute Engine 把这件事反转了："当一个智能体执行完一次工具调用、进入智能体循环的'思考'阶段时，该 microVM 会发信号表示自己空闲，宿主随即把它从活跃状态挪到空闲状态。"这是正确的设计，同时它也悄悄把你的空闲账单变成了你智能体代码的一个属性——也就是说，挂起的边界从此是你必须自己挑选、评测并为之辩护的东西，而不是平台替你做对的东西。

这次到底宣布了什么

Agent Compute Engine 的定位是"一项专门打造的计算服务，它已经在支撑 Gemini 作为处理工作任务的智能体运行"，并让"每一个 Gemini 智能体都拥有属于自己的、高性能且安全的计算机去动手"。它尚未正式可用："它将在未来数月内以预览形式提供"，而且"你很快就能用这项服务来驱动你自己的自定义智能体"。所以该这样读它：这是一份来自某个已经在内部大规模跑它的平台的公开设计，而不是你本季度能买到的产品。

整篇文章由三套机制承担。隔离是"一道硬件隔离的 Cloud Hypervisor 边界，拥有自己的客体内核与 root 权限"，跑在 Google 的卸载型 IPU Titanium 之上，文中称之为"为不可信 AI 智能体打造的、根植于硅的纵深防御"。密度来自"用写时复制的内存共享，在单一操作系统模板上跑多个智能体"。而生命周期是"通过快速检查点与恢复暂停空闲的 microVM"，文中还说它可以"在智能体等待人类或外部系统时暂停一台正在运行的 microVM，并迅速从快照恢复"。

那些数字属于它的兄弟，不属于它

Agent Compute Engine 自己那一节没有任何性能数字——只说 microVM"启动迅速"，仅此而已。公告里的量化指标都挂在与它同场发布的开源 GKE 运行时 Agent Substrate 上："相比传统计算，计算密度最高可达 10 倍"，以及"在运行 200,000 个智能体的基准验证中，Agent Substrate 维持了每秒 500 次激活，且挂起与恢复延迟低于 500 毫秒"，而 Filestore 集成被标注为"亚秒级恢复延迟"。

这些才是值得拿来做规划的数字；而它们是厂商为同一家族里另一个产品给出的基准数字，所以请把它们当作数量级，而不是 SLO。数量级本身就是重点：挂起与恢复是一次亚秒级的操作，而不是一次免费的操作。

为什么把判断挪进盒子里是对的

就"按利用率判断空闲"而言，智能体是最糟糕的那种负载。一次长周期运行在两种状态间来回切换：一阵真实的工作——一次工具调用在编译什么、一个浏览器在渲染页面——以及一段段沙箱攥着已检出的仓库、热的解释器与一个打开的会话、而实际上什么都没在执行的时间，因为模型正在别的地方生成 token。从外面看，那些时段跟"随时可能下一毫秒就恢复的进程"一模一样，这正是为什么调度器最安全的选择一直是让它保持温热。而这也正是一个沙箱如何在四小时的审批等待里为纯粹的无所事事计掉大约 66 美分。

盒子里的软件对答案知道得一清二楚。harness 刚刚投出一个工具结果，正在等下一次模型响应；没什么要调度，也没什么会丢。任何从外向内的启发式都拿不回这个事实，而任何为了安全而调的超时也都不可能激进。给客体一条说出这件事的通道，是这个问题上第一次真正的改进，也是不管你以后会不会碰 Google Cloud 都该照抄的设计：唯一能宣布循环处在哪个阶段的，是知道那个阶段的那个运行时。

你顺手接下了什么

另一面是：一个空闲信号是代码，而代码这种东西可以缺失、可以出错、可以迟到。由此有三个后果，公告里一个都没写。

  • 一个从不发信号的智能体，会被永远按活跃计费。你最贵的那次运行，会变成 harness 在某个罕见位置崩掉的那次，或者自定义工具包装器把调用后钩子吞掉的那次。这种失效在你拥有的每一块仪表盘上都无声无息，因为沙箱看起来是健康的——它确实健康，它只是醒着。
  • 一个在错误边界上发信号的智能体，会在每一步都付一次恢复。在每次工具调用结束时挂起，一个二十步的任务就要吃掉二十轮挂起与恢复。按 Agent Substrate 那个数量级，这是在一个思考阶段加起来可能还不到这么久的任务上，额外添了几秒挂钟时间。
  • 这个信号如今是你评测面的一部分。"这次运行有没有在每一个静默点发出空闲信号？"是一条轨迹属性，可以像你衡量一次运行是否调了对的工具那样去衡量——而如果你不衡量它，那次让它不再发信号的回归，会先以一张云账单的形式现身。

挂起边界是一个穿着成本外衣的延迟决定

别算架构，算算术。在步骤之间挂起，省下的是思考阶段里被攥住的资源成本，付出的是一次挂起加一次恢复。这笔交换是正还是负，完全由你的思考阶段有多长决定——而那是你的模型与努力预算的属性，不是平台的属性。

一个思考预算很小、工具调用很快的循环落在第一行：等待很短，省下的是几分之一个 vCPU 秒，而代价是在每一步上都加一笔用户可见的延迟。一个努力预算很大的推理模型可以落在中间：几十秒的思考长到足以把一次亚秒级恢复吞掉。而最后一行——等人、等批处理任务、等一个也许几小时都不会来的 webhook——是这件事不再是优化、而是另一种成本结构的场景，也正是公告里明确点名的那个场景。

于是落下来的规则，比"空闲就挂起"要窄得多：在你叫得出名字的等待上挂起，而不是在你探测得到的空隙上挂起。等人或等外部系统是你的 harness 本来就知道、也能安全宣布的语义事件。而步骤之间的空隙是机械的，把检查点绑在它上面，会把一个成本收益换成一笔延迟税，而你的 p95 会比你的财务同事更早发现它。

两个该马上抄走的设计细节

凭据从不进入盒子

"每台 microVM 以其智能体自己的身份运行，使用短生命周期凭据。每台 microVM 还会拿到自己的、经过密码学校验的 ID，而服务凭据是在 microVM 之外的出口处注入的。"把最后那半句慢慢读一遍，因为它是全文最有力的一句。关于沙箱，人们通常问的是代码能不能跑出去；而真正决定你爆炸半径的那个问题，是平台在智能体开始之前往盒子里放了什么，而这里的答案是：没有什么值得偷的东西。出口流量走 Agent Gateway，也就是文中那位"客户端到智能体、以及智能体到任何地方的流量的空中交通管制员"，由网关来挂上凭据。

要精确地讲清这买到了什么。一个被提示注入的智能体在盒子里照样能发出请求，而网关照样会给那些请求挂上凭据——这仍然是被混淆的代理，一点没变。被消掉的是密钥自身的外泄：那枚 token 没法被读取、记录、拷进文件或带进下一个会话，因为它从来就不在那里。这是对最坏情况的一次实打实的削减，而且它与用哪种虚拟化无关——这正是为什么它值得在你运行的任何沙箱上实现。

快照是一份没人给它定留存策略的状态

快速检查点与恢复意味着客体内存如今是一份持久化的产物，而任务进行中的客体内存就是智能体的工作集：它刚读到的工具结果、它刚取回的文档、它正在推理的那条客户记录。对话记录之所以有留存规则与脱敏流水线，是因为有人把它们归类成了会话数据。而快照拿到的生命周期规则，出自那些把它们归类成机器镜像的基础设施团队。

上面那套凭据设计在这里能帮你一半——一份从未装过 token 的快照，是个无趣得多的东西——但它救不了你内容那一半。如果你对"这位用户的数据在哪里"必须给出完整回答，那就在清单上加一条"以及任何曾在处理它的沙箱的检查点里"，趁还没有别人替你加。这与持久状态给其他每一个可恢复系统带来的义务是同一件事，只是这次它来的形态不像一个数据库。

这个季度该做什么

Agent Compute Engine 要"在未来数月内"进入预览，所以这里没有一条是迁移计划。它是一份如今已被两个 Google 运行时实现的设计规格，而其中大部分可以搬到你今天正在跑的东西上。

  • 找出你最长的那个等待，并给它上仪表。不是沙箱的平均寿命——而是那些具体叫得出名字的等待：人工审批、外部任务、计划重试。把被攥住的资源成本乘以那段时长、再乘以运行量。如果这个数不大，那这一切目前跟你无关。
  • 让 harness 显式宣布静默。就算没有检查点机制，一个明确的"这次运行停在 X 上"事件，也正是让你能释放一个沙箱、退掉一个池位，或者把这台温热的沙箱交给别人的东西。这个信号在挂起机制存在之前就已经有用。
  • 不要因为厂商能做就在步骤之间打检查点。先量一下你思考阶段的分布。如果中位空隙短于一次恢复，那么逐步挂起是一次你以成本优化的名义发布出去的延迟回归。
  • 无论如何都把凭据挪出沙箱。这一条不需要新平台：一个在出口处挂上 token 的代理是一个下午的活，而它会改变"一次被攻破"究竟值多少钱。
  • 把你的快照归类为内容。谁负责对话记录的留存，谁就该负责检查点的留存，而且该知道这事归自己管。

常见问题

现在就能用上 Agent Compute Engine 吗？

不能。2026 年 10 月 22 日的公告说它已经在支撑 Gemini 作为处理工作任务的智能体运行，并说它"将在未来数月内以预览形式提供"，对自定义智能体的支持还要再往后。请把它当作一份公开的设计，而不是一款可用的产品。

挂起与恢复有多快？

Google 没有为 Agent Compute Engine 本身公布任何数字。同一份公告里的数字属于它的开源 GKE 兄弟 Agent Substrate：在一个 200,000 个智能体的基准里，每秒 500 次激活、挂起与恢复延迟低于 500 毫秒，经由 Filestore 则是亚秒级恢复。那是厂商为另一个运行时给出的基准，所以请按数量级规划，而不是按具体数位。

在工具调用之间给 microVM 打检查点能省钱吗？

只有当它覆盖的那段空隙足够长时才能。省下的是思考阶段期间被攥住的资源成本；付出的是一次挂起加一次恢复，而且在关键路径上。对一个工具调用很快的循环，空隙常常短于一次恢复，这会让逐步挂起成为一笔披着成本节约外衣的延迟开销。而对等人或等外部任务的场景，它显然是正的。

凭据在出口处注入，是不是就解决了提示注入？

没有。被注入的智能体照样能发出请求，网关也照样会给那些请求挂上凭据——代理依然是被混淆的。这套设计消掉的是密钥本身被偷，因为它从来就不在沙箱里可供读取。

空闲信号对我的评测意味着什么？

它变成了一条轨迹属性。一次运行是否在每个静默点发出了空闲信号，可以像工具选择那样在 trace 里衡量，而且值得写成断言，因为那次让它不再发信号的回归不会让任何测试失败——它只会开出一张账单。
