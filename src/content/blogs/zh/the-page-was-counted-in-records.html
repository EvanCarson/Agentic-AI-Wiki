GitHub 官方的 MCP 服务器从一开始就做了分页——perPage 最多 100，较新的工具还带 after 游标——可它的 issue 列表里照样堆满了单次调用就撑爆上下文窗口的报告：30 个提交超过 64k token，30 个拉取请求 508KB，50 个项目条目约 100K token。分页限制的是返回多少条记录。上下文窗口却是一笔 token 预算，而一条记录多重都有可能。按 token 来数你的分页，先裁字段再分页，并且要假定：你的用户实际在用的宿主，处理溢出的方式和你测试时用的那个不一样。

一台服务器留下的一串记录

大多数撑爆上下文窗口的 MCP 服务器都没留下任何记录。GitHub 的留下了十八个月的记录，因为它的用户会提 issue，维护者也会公开回复。按时间顺序读下来，这些 issue 每一次讲的都是同一个故事。

第一份是 2025 年 4 月的 #142，一次针对 zalando/skipper 的 list_commits 调用。三十个提交在下一次模型调用时产生了超过 64k token，每个提交约 5–6KB。报告者是 OpenAI 的 tier-1 用户，收到了一个 429：这次请求需要 68,490 token，而限额是每分钟 30,000 token。这是整个故事里唯一一个硬性的成本数字。这次调用完全在页大小范围之内，却还是发不出去。

这个模式一直延续下去。2025 年 5 月，get_pull_request_comments 给一位上限为 25,000 的 Claude Code 用户返回了 26,688 token（#425）。6 月，一份报告指出完整的作业日志「很容易超出 LLM 的上下文上限」，由此催生了 tail_lines 参数（#608）。2026 年 2 月，list_pull_requests 为 30 个 PR 返回了 508KB——每个约 17KB，另一次查询中每个 36KB——报告者希望加上 search_repositories 早已具备的 minimal_output 选项（#1934，仍未关闭）。4 月，50 个项目条目合计约 400KB，大约 100K token，报告者称这「大约是一个典型 LLM 上下文窗口的一半」；两页 50 条就能把一个窗口填满（#2383）。

问题出在记录本身，而不是条数

GitHub 的 REST 对象是为那些会忽略无用字段的程序设计的：一个用户对象就带着十五个以上的 URL 模板，外加模型永远用不上的 reactions 和元数据。原样透传的话，每条记录五到十七 KB，乘以 perPage 上限 100，就是一页任何模型都装不下的数据。这台服务器的页大小对 HTTP 客户端来说很合理，对上下文窗口来说却大得离谱。

每一次真正奏效的修复都是投影。2026 年 5 月 28 日合并的 PR #2563 为项目条目加上了精简类型。维护者对五个线上条目做了测量：修改前约 12,875 token，修改后 901——削减 93.0%，每个条目从约 2,575 token 降到 180。按一页 50 条换算，就是从 128,750 token 降到 9,010。页大小没变，每条记录都变小了。同样的修复如今正在一个端点一个端点地铺开：issue 和拉取请求的列表与搜索工具新增了 fields 参数，其 README 写道「省略 body 就去掉了每条结果中最大的那部分数据」；PR #2675 让 search_pull_requests 默认返回紧凑结果，需要原始对象时传 minimal_output: false；精简类型则集中放在 pkg/github/minimal_types.go 里。截至 2026 年 10 月，下一个排队的是 pull_request_read，它的 get_files 仍然返回完整补丁（#3236）。

够不着的分页不算分页

2026 年 3 月的 issue #2122 展示了按记录分页失效的另一种方式。pull_request_read 的 get_review_comments 方法宣称支持游标分页，但工具的 schema 里根本没有 after 参数，而且有三个方法会悄无声息地忽略 page 和 perPage。模型没法请求第二页，因为 schema 里没有任何东西允许它这么做。超过约 50–100KB 的结果会让 Cursor 和 VS Code 的 CPU 飙到 100%，只能强制重启。PR #2489 补上了 after，这个 issue 在 5 月关闭。游标只有在模型能从 schema 里看到它时才管用，也只有在每一页都装得下时才有帮助。

为什么记录条数框不住窗口

Datadog 从截然相反的一类数据出发，得出了同样的结论。他们的工程师发现智能体耗尽上下文，是因为「有几条日志特别大」——「一条 Datadog 日志消息可能只有 100 个字符，也可能有 1 MB」。没有哪个条数能框住这种情况。于是他们改变了一页的含义：「服务器在达到一定 token 数后截断响应，并返回一个用于获取更多内容的游标。」页由 token 来定义，剩下的交给游标。

接着他们着手压低每条记录的成本。每条记录用 CSV 只需 JSON「大约一半的 token」；嵌套数据用 YAML 能省「约 20%」；格式更换再加上去掉不常用的字段，让某些工具「在同样的 token 数里多装大约 5 倍的记录」。最大的收益来自让智能体聚合而不是翻页。有了 SQL，智能体可以 SELECT 字段、LIMIT 行数或者 COUNT，评测成本「便宜了约 40%」。

另外两台服务器展示了一个感知大小的分页写成代码是什么样子。MotherDuck 的 DuckDB 服务器默认把行数上限设为 1,024、字符上限设为 50,000。它会比上限多取一行来判断是否还有更多数据，设置 truncated: true 并附上一条警告（「结果限制为 N 行。查询返回了更多数据。」），如果 JSON 仍超过字符上限，就每次丢掉约 10% 的行，直到装得下为止。Grafana 的 query_loki_logs 默认返回 10 行、最多 100 行，并在数据旁边返回 resultsTruncated 和 maxLinesAllowed；服务器还设有响应体字节上限，遇到超大响应会直接报错拒绝，而不是原样传下去。

两种预防措施都没做的服务器，则展示了默认情况。ClickHouse 的服务器在文档里写了查询超时，却没有行数上限；crystaldba/postgres-mcp 调用 fetchall() 时不加任何限制。通过其中任何一个对大表执行 SELECT *，唯一的约束就是宿主决定怎么处理它——这正是下一节的主题。

协议分页的是目录，不是调用

MCP 有分页。它恰好覆盖四个方法——tools/list、resources/list、resources/templates/list 和 prompts/list——在 2025-11-25 和 2026-07-28 两个修订版中都是如此。规范自己的措辞是「list 操作」。在这两个修订版里，tools/call 都没有游标、没有大小上限、也没有分块。每一台对工具结果做分页的服务器，都得像 GitHub 那样自己发明 page、perPage、after 或 cursor 参数。

这并不是没人提过。issue #229「Pagination for tool/call」从 2025 年 3 月 26 日起一直开着。issue #798 提议加一个 paginationHint 注解，并在工具结果里加一个 pagination: {hasMore, nextCursor} 块，提交当天就被关闭了。今年有两份关于流式返回部分结果的提案被关闭：7 月 2 日的 SEP-2664 和 9 月 22 日的 SEP-2998，一位维护者指出「每一份新的 SEP 都应在工作组的协助下推进」。路线图最后一次更新是 2026 年 8 月 22 日，列出了 tools/call 结果形态的重新设计、「渐进式发现」以及工具调用结果的 ETag。三项都在计划中。没有一项已经发布，也没有一项给出日期。

两种膨胀，只解决了一种

过去一年那些广为人知的上下文节省，大多落在这条线的另一边。Anthropic 的 Tool Search 把工具定义的 token 削减了约 85%；Cloudflare 的 Code Mode 服务器用约 1,000 token 的定义描述了 2,500 多个端点，而不是 117 万；Cursor 把工具描述同步到一个文件夹里，在调用了 MCP 工具的运行中把智能体的总 token 削减了 46.9%。这三者缩小的都是模型在调用任何东西之前要读的目录。没有一个能让单次 list_pull_requests 的响应变小。协议分页的是目录，业界大部分优化工作针对的也是目录。

于是由宿主说了算，而宿主们各执一词

协议里什么都没规定，每个宿主就各自设定上限，以及越过上限之后的行为。截至 2026 年 10 月：

落盘不是分页

落盘看起来像是宿主把问题解决了。结果保住了，窗口省下了，模型可以按需读取。Datadog 的文章提到 Cursor 和 Claude Code 现在都这么做，这可能让格式效率变得不那么重要——同时也指出这「还没有写进 MCP 规范」。实际上，只有当模型能读取文件的一部分、并根据读到的内容采取行动时，这个文件才有用。有三份报告展示了它在哪里失灵。

  • Notion，#206（2026 年 2 月）。notion-fetch 返回了一个 2,376 行、41,207 token 的页面，JSON 被压缩成大约 5 行。Claude Code 把它存进了文件，但它的 Read 工具按行偏移分页，五行巨长的内容无法部分读取，而读取整个文件则报错「exceeds maximum allowed tokens (25000)」。数据就在磁盘上，却够不着。
  • Atlassian，#106（2026 年 3 月）。一个 Confluence 页面的 ADF 正文有 50–70KB。报告者说 Claude Code 会把超过约 20KB 的输出持久化到磁盘，所以模型从没看到过正文——而要调用 updateConfluencePage，它又得把大约 15K token 的正文内联输出一遍。读是能读的；改读到的内容却不行。落盘打断了这次往返。
  • VS Code，#311068。一个 50KB 到 999KB 的 get_file_contents 结果在到达模型之前就被截断，并提示通过一个 vscode-chat-response-resource:// URI 读取其余部分。读取这个 URI 时会以「outside the workspace」失败。在 VS Code 1.116.0 上用 120KB 和 233KB 的文件测试，智能体就这么卡住了。

宿主们在调整。Claude Code 2.1.105 开始为超大输出给模型提供按格式区分的处理方法——JSON 用 jq，文本给出分块大小——2.1.287 则不再让 Claude 用 Read 的 offset 和 limit 去分页读取大 JSON。第二项修复针对的正是 Notion 那份报告掉进去的同一个坑。但每个宿主都按自己的节奏修自己的落盘逻辑。服务器不能指望其中任何一个。

服务端该怎么做

服务器是唯一知道一条记录里装了什么、哪些字段重要的地方。下面四条做法来自那些不再溢出的服务器。

按 token 来数一页

设一个预算，而不只是一个条数：不断加入记录，直到下一条会越过预算，然后返回一个游标。条数上限也要保留——它能防止一页小记录变成一张超长的列表——但让预算来决定一页在哪里结束。按宿主的方式来衡量预算；既然宿主有的数 token、有的数字符，那就两者都设上限。Block 团队的 MCP 服务器设计手册把第一步说得很直白：在返回之前先测量输出。

先投影，再分页

默认只返回智能体会据以行动的字段，完整对象则让它主动去要。GitHub 的 −93% 全部来自这一点，页大小一点没动。不过，标识符要留着。Anthropic 的 Slack 示例用一种简洁格式把一次响应从 206 token 压到 72，而这个简洁格式恰恰丢掉了后续调用需要的 ID——所以「精简」必须是对下一次调用而言的精简，而不是对展示而言的。如果智能体要的是一个数字而不是一堆行，就给它聚合的手段，就像 Datadog 的 SQL 工具那样。

把截断标记和补救办法放进结果

模型永远不该去猜自己是否拿到了全部。多取一条来判断，在一个字段里明说，再加一句下一步该怎么做。Anthropic 的工具编写指南要求截断提示文字引导智能体去做「许多小而有针对性的搜索」。下面是一个信封的草图，字段名由你自己定：

{
  "items": [ { "number": 4182, "title": "Fix cursor reset", "state": "open" } ],
  "returned": 40,
  "truncated": true,
  "reason": "token_budget",
  "nextCursor": "eyJvIjo0MH0",
  "hint": "More PRs match. Pass nextCursor for the next page, or narrow with state or author."
}

为最小的宿主而设计

按你的用户在用的最严格的宿主来定默认页大小，而不是按你桌上那一个。这意味着低于 Claude Code 的 25,000 token 默认值——最好低于它 10,000 token 的警告线——并且低于 Gemini CLI 的 40,000 字符。Claude Code 允许服务器通过 _meta["anthropic/maxResultSizeChars"] 提高单个工具的上限，最多 500,000 字符。那只是一个宿主的逃生口，不是解决方案。如果结果非得写进文件，就让文件按行组织，好让按行分页的读取器能用上它；也不要设计那种需要模型把一段它读不到的正文重新输出一遍的编辑流程。

常见问题

MCP 支持对工具结果分页吗？

不支持。截至 2026-07-28 修订版，MCP 分页只覆盖 tools/list、resources/list、resources/templates/list 和 prompts/list。tools/call 的结果没有游标、没有大小上限、也没有分块，所以要对工具结果分页的服务器只能自己定义游标参数。

GitHub 的 MCP 服务器明明做了分页，为什么还会撑爆上下文窗口？

它的页是按记录数计算的，而它的记录很大——在已报告的案例中，每个提交 5–6KB，每个拉取请求 17–36KB。一页 30 条就可能超过 64k token。解决问题的是精简响应类型，而不是更小的页：PR #2563 把项目条目削减了 93%。

在 Claude Code 中，MCP 工具结果太大会怎样？

Claude Code 在 10,000 token 时发出警告，默认上限为 25,000 token，可通过 MAX_MCP_OUTPUT_TOKENS 设置。成功的文本结果超过上限或超过 50,000 字符时，会被保存到文件，模型收到一条带文件路径的消息。超过约 11,000 字符的错误结果只保留开头和结尾各 5,000 字符。

一个 MCP 工具的页应该多大？

用 token 或字符来设定，而不是记录数，并按用户在用的最严格的宿主来定大小——低于 Claude Code 的 25,000 token 默认值和 Gemini CLI 的 40,000 字符截断线。同时返回截断标记、游标，以及一句如何缩小查询范围的说明。

MCP 规范会加入工具结果分页吗？

短期内不会。2026 年 8 月更新的路线图计划重新设计 tools/call 的结果形态，并为工具调用结果引入 ETag，但没有给出日期。关于流式返回和部分工具结果的提案已在 2026 年 7 月和 9 月被关闭，维护者现在希望新提案通过工作组来推进。
