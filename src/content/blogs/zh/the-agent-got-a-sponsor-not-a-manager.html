Ignite 2026 看上去像是微软给智能体安排了一份工作——一个身份、一个邮箱、一本日历、组织架构上的一格——各家转述也顺理成章地写成「每一个都配了一位负责的经理」。并没有。Entra Agent ID 真正不肯缺省的那层关系是 sponsor（担保人），而 sponsor 恰恰是它定义的三种关系里最弱的那一个：sponsor 能把智能体关掉，却改不动它。微软把「负责」的那个字段设成必填，把「有权限」的那个字段留成选填，这跟服务账号三十年来的做法正好相反；而无论你会不会用上 Entra，这一点都值得照搬。

速览

Entra Agent ID 在一个智能体上定义了三种管理关系。只有一种是必填的，而且不是权力最大的那一种。先读最后一列——每个角色被禁止做什么，才是设计的落点。

关系是否必填能做不能做
Sponsor 是——创建智能体身份与 blueprint 时都要有 停用该身份、更改它的 sponsor、软删除它 更改应用或认证设置；重新启用；恢复
Owner 否（blueprint 那一页写的是「建议设置」） 搭建、配置、凭据；重新启用、恢复、硬删除 在它被指派的那个对象里，没有不能做的
Manager 否 组织层面的监督；申请访问包；看到向自己汇报的智能体 根本改不动、也删不掉这个智能体

在进入论证之前先交代两点。第一，Ignite 2026 的会期是 2026 年 11 月 17 日至 20 日；给智能体发邮箱的那个功能叫 Microsoft 365 Resources for Agents，其服务说明列出的公开预览日期是 Autopilot 智能体 2026 年 11 月 17 日，Sales Development Agent、Service Agent 与 Copilot Studio 为 2026 年 12 月 1 日。不少聚合媒体把这条新闻记成 11 月 19 日，还加了一句「负责的经理」；这两处细节在微软自家页面上都站不住。第二，「manager」不是凭空捏造——它确实是那三种关系之一——但在 Microsoft Graph 里，manager 这层关系挂在智能体那个选配的配对用户账号上，而不是挂在治理真正瞄准的那个智能体身份上。

设成必填的那个字段，恰恰没有「配置」按钮

文档把 sponsor 描述为：对该智能体的用途与生命周期决策负责的业务代表，且不具备技术管理访问权。请把后半句当成一项特性来读。sponsor 被允许的动作是一张短的、封闭的非破坏性生命周期操作清单：停用该身份、更改谁来做它的 sponsor、软删除它。他们碰不到身份或 blueprint 上的应用设置，改不了认证属性，也无法重新启用或恢复任何被自己移除的东西——那是留给 owner 和管理员的。

拿这个去对照你接手过的每一个服务账号。唯一被可靠记录在册的人，是当时握着凭据的那个人，而真正起作用的字段是一句选填的描述，写着 迁移脚本，勿删。责任是一个 wiki 页面，权限才是 schema。Entra Agent ID 把这一对颠倒了过来：负责的那个人成了对象创建时就会被校验的必填属性，而能改动智能体认证方式的那个人是选填的。

这是把职责分离写进了目录服务的 schema，而不是写进一份policy 文档；而且这道不对称的方向是对的。为智能体行为负责的人拿到一个停止按钮，没有配置按钮。能重新配置它的人，是另一项独立的、选填的指派。如果某一个人两者都需要，那他就显式地同时持有两个角色——这是有人做出的一个决定，而不是「谁跑了部署脚本」带来的副作用。

这项约束连边角都在发力：微软把每个对象的 sponsor 上限设为 100 个，其中最多 5 个可以是组，并且排除了可指派角色的组与「指派成员」类型的安全组。一个能用 全体员工 来满足的字段，就是一个在技术上永远被填上、在实际上永远无人负责的字段。

sponsor 的权力集，恰好就是一个急停开关

把 sponsor 可做的事排开来看——停用、换 sponsor、软删除——你描述的就是一个急停开关加一次移交，别无其他。负责的那个人永远能把智能体停下来，永远能把这份责任交出去。他没法让智能体做任何新的事，也没法悄悄把这次停止撤销掉。

最后这条限制看着像摩擦，其实不是。正因为 sponsor 无法重新启用一个已停用的身份，「这个智能体被关掉了」就成了一种只有 owner 或管理员才能解除的状态——于是它是一件持久、可归属的事件，而不是某人在站会前又拨回去的一个开关。默认不活跃策略用它自己的话说了同一件事：一旦某个智能体身份被停用或删除，只有 owner 或管理员能把它找回来，而 sponsor 被明确写为无此授权。一个「只能单向叫停」的负责人，比一个「叫停可逆」的负责人是更强的控制——道理和「你自己按不掉的火警才是好火警」是一样的。

它同时也让「叫停」变得便宜，而这正是所有人都会跳过的前提。一个必须开工单才能暂停失控智能体的审核者，实际会选择再多观察一小时。把直接停用交给负责的那一方，同时把恢复权留在他之外，这个形状能让你压低「停下来」的代价，而不抬高「弄错了」的代价——这跟可逆性那篇对产品动作所做的权衡是同一笔账，只是换到了一个身份上。

微软把衰减曲线也一起发了，这是诚实的那部分

必填的 sponsor 阻止了智能体一出生就无人负责。它阻止不了智能体变成无人负责，因为人会换团队、会离职——而微软显然看到了这一点。默认不活跃策略在不活跃满 60 天时通知 sponsor 与 owner，90 天停用该身份，455 天删除；而在默认策略下，这些动作与时限是不可自定义的。当没有 sponsor 也没有 owner 时，通知会发给管理员提供的兜底收件人——这是一句安静的承认：那个必填字段最终可能指向没有人。

管理中心那一侧说得更直白。Agent Registry 会显示一个无 owner 的智能体计数，配一个一键筛选把它们挑出来，并随用户被删除而更新；微软明确写道，当你把创建者用户删掉时，共享智能体就会变成无 owner。而重新指派的范围比仪表盘看起来要窄：你可以重新指派 Agent Builder 与 Copilot Studio 共享智能体的归属，但不能重新指派第一方智能体；一条重新指派无主智能体的规则可以按 Entra 层级把归属批量转给前任 owner 的经理，但只支持用 Copilot Agent Builder 做出来的智能体；而微软自己的文档写着，管理员目前必须手动识别并转移归属，这会造成生命周期治理缺口。

专门针对 sponsor 的离职路径，是一个 Lifecycle Workflows 任务：找到离职用户的经理，把他加为这位离职者所 sponsor 的每个智能体身份的 sponsor，再把离职者移除——而这要求离职者自己的 manager 属性是填好的。这正是没人去审计的那个依赖。一个 manager 属性填得零零散散的组织，手上那套 sponsor 转移机制会悄悄地无处可发，而他们会在最糟的时刻发现这件事，也就是一次组织调整。

没有人会为一个自己认为很罕见的问题，专门做一个计数、一个筛选器、一条最低 sponsor 数策略和一个 455 天的计时器。微软没有公布真实租户里无 owner 智能体到底有多普遍——专门用来找它们的工具本身就是那个结论。

如果你不在 Entra 上，该照搬什么

2026 年 11 月还在跑智能体的团队，大多不会为了这件事去上一套身份平台，也不需要。可迁移的部分是三个决定加一道不对称，代价是一次数据迁移和一个下午。

把「负责的人」做成必填列，并在创建时校验。你的智能体清册里大概有一个可为空的 owner，并且只在有人上心的那些智能体上填了。一个在写入行时就被校验的必填字段是另一种东西：它让「谁为这个智能体负责？」变成一次查询而不是一次调查，也让这个答案的缺失变成一次构建失败，而不是一个考古项目。

把「负责」和「管理」拆开，并让负责的那个角色是更弱的那个。负责的人需要能叫停智能体、能把责任交出去，仅此而已。请抵住那股「给他编辑权让他能去修」的本能——他一旦能重新配置这个智能体，那次停止就不再是任何事情的证据了，因为他也能把它解除。

在需要之前先把离职路径建好，并去测它依赖的那个属性。不管你那套「转给离职者的经理」等价物是什么，它都要读 HR 或目录系统里的某个字段。今天就去查这个字段的空值率。然后决定那些空值怎么办——因为「通知一个兜底收件人」是微软给出的答案，它好过另一种选择，也就是什么都不发生。

还有一道值得保留的不对称：责任在创建时绑定，却是持续衰减的。上面写的全是后半段的事。一个按固定节奏重新追问「这个人还是对的人吗？」的访问审查——微软自己的最佳实践建议每季度扫一遍缺失的 sponsor 与过期元数据，并让 sponsor 每六到十二个月做一次确认——才是让那个必填字段在被填上的那天之后仍然诚实的东西。下线一个智能体是同一根管子的另一端。

如果只带走一件事：可治理的单位不是智能体，而是「智能体 + 一个能叫停它的、有名有姓的人」这一对。Entra 在创建时强制这一对成立，然后用四项独立的功能去维持它仍然成立。你的清册这周就能强制同一对：一条 NOT NULL 约束，加一个每周跑一次、列出「人已经走了」的那些行的作业。

常见问题

Microsoft Entra Agent ID 已经正式可用了吗？

Entra 的发布说明把 Agent ID 平台列在一个 2026 年 4 月的标题之下，标为正式可用。围绕它的一些东西并没有：blueprint 实例模式、Agent ID 生命周期策略、默认不活跃策略，以及面向「数字同事」的访问包，截至 2026 年 11 月在文档中都标为预览。所以「Agent ID 已 GA」不该被读成「治理面已 GA」。

智能体到底能不能有一位 manager？

能，但这位 manager 挂在智能体那个选配的配对用户账号上，而不是挂在智能体身份上；Microsoft Graph 把 manager 列为 agent-user 资源上的一层关系。manager 获得组织层面的监督，并可以为自己名下的智能体申请访问包；微软写明 manager 没有修改或删除智能体的授权，那些动作需要 owner、sponsor 或管理员来做。

每个 Microsoft Foundry 智能体都会拿到自己的 Entra Agent ID 吗？

并不一致，而这正是值得盯住的那个责任缺口。已发布与托管的 Foundry 智能体会拿到自己的 Entra 智能体身份，新创建的智能体在文档中写为默认获得唯一的 blueprint 与身份，已连接的智能体现在也会自动获得 Agent ID——但同一项目中未发布或处于开发中的智能体，曾被记录为共用一个公共的项目身份，而 Foundry Agent Applications 被记录为并未注册进 Entra 智能体注册表。草稿态智能体是你该追问的那一类。

还有别家要求智能体必须有一个负责的人吗？

Okta 最接近。Okta for AI Agents 会把智能体注册进 Universal Directory，并带一位有名有姓的人类 owner，用来为访问申请与认证复核确立责任归属；Okta 与 Gemini Enterprise 的集成也描述为智能体绑定到一位人类 owner。我们无法从 Okta 的开发者文档确认这个字段在注册时是像 Entra 的 sponsor 那样强制必填，也没有找到 Google 或 AWS 定义了某个必填的「负责人」属性的文档——最接近的是一条架构原则，不是一个被强制的 schema 字段。

这里面收益最大的那一个改动是什么？

把那个「负责人」字段在你已有的智能体清单里改成非空。本页其他每一项控制——停止按钮、离职路径、衰减计时器、复核节奏——都假定这个字段里有一个真人，而当它没有的时候，没有一项会优雅降级。
