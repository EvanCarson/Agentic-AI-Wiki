Concepts · Agentic AI Explained

Multi-Agent Systems

A single agent with tools is the right starting point for almost every agentic task. Multi-agent systems — where several models orchestrate or collaborate to complete work — are a deliberate architectural escalation. They exist for three reasons: parallelism that a single context window cannot support, specialisation that a single generalist model handles poorly, and fault isolation that a single failure point cannot provide. Understanding when those reasons apply, and what they cost, is the entry-point to the Deep-Dives on multi-agent coordination and the Field Guide chapter on advanced orchestration.

STEP 1

The default position: one agent with tools.

A single agent backed by a good general model and a well-designed toolset handles the majority of agentic workloads. It is cheaper to build, easier to debug, and simpler to reason about than a multi-agent system. Before splitting into multiple agents, confirm the single-agent design has actually hit a ceiling it cannot clear.

The typical ceilings are: a context window too small to hold all the work-in-progress at once, a task decomposing cleanly into independent subtasks that could run in parallel, or a quality requirement that one model cannot meet on a specialised subtask — a coding-specialist for code generation, an analysis-specialist for structured extraction.

STEP 2

Three honest justifications for splitting.

  • Parallelism. A single agent is sequential — it chooses one action, observes, then chooses the next. When a task branches into independent subtasks (crawl ten URLs simultaneously; run five test suites in parallel), a supervisor dispatching to concurrent worker agents shrinks wall-clock time. The gain is real only when the subtasks are genuinely independent; dependencies between workers re-introduce sequencing and eliminate much of the benefit.
  • Specialisation. A subtask may benefit from a model or system-prompt that would be counterproductive for the rest of the pipeline. A code-generation agent tuned for tight, tested functions may write worse prose than a generalist. Separating concerns into purpose-built agents produces better outputs where quality on a specific subtask dimension is the bottleneck.
  • Context isolation. Long, noisy intermediate results from one stage pollute the context for the next. Running each stage in a fresh context prevents prompt-confusion and keeps costs bounded. This is the weakest justification — aggressive summarisation and structured hand-offs often achieve the same effect within one agent.

STEP 3

The coordination tax — why multi-agent is not free.

Every agent boundary is a serialisation point: results must be formatted, transmitted, parsed, and validated before the next stage can act. That overhead is latency, cost, and failure surface. A worker that produces malformed output breaks the pipeline in a way a sub-step within one agent would not. Debugging a multi-agent failure requires reconstructing the trace across several independent loops — harder than reading a single agent's transcript.

Coordination also introduces new failure modes absent in single-agent designs: a supervisor that misattributes a worker's error, a worker that interprets its task differently than the supervisor intended, a downstream worker that silently proceeds on bad input. Every additional agent is an additional source of compounding uncertainty.

The coordination tax is permanent. It does not shrink as models improve. Budget for it explicitly before choosing multi-agent over a more capable single-model upgrade.

STEP 4

A one-liner decision and where to go next.

Use multiple agents when — and only when — parallelism, specialisation, or context isolation produces a measurable benefit that outweighs the coordination tax and the debugging cost. If you cannot articulate which of those three you are buying, the single-agent design is the right call.

Deep dive: read the Multi-Agent Coordination group for protocols, patterns (handoff, supervisor, hierarchical, consensus), and failure modes. Field Guide chapter x4 covers production multi-agent orchestration end-to-end.
